# 5. Правила

[Курс](README.md) · [English](../05-rules.md) · **Українською**

Правила — написана вручну половина архітектури. Вони живуть у `keylang/rules.md` (або в будь-якому файлі із заголовком `# rules`). Вони називають ID зі знімка. Модулів вони не оголошують; це робить карта.

Цей репозиторій перевіряє сам себе. Жолоб зелений, бо кожен звітований критерій на цих рядках виконався, а дерево навігації — список шарів з `keylang.json`:

![keylang/rules.md в інтерфейсі](../images/tui-rules.png)

Проза зверху — опис для читача. Маркери — твердження. У цьому файлі вони кажуть: конвеєр шарів — `base < extract < lang < check < map < features < tui < cli`; ядро мови не залежить від карти, екстрактора і `web-tree-sitter`; перевірка — теж; TUI також не залежить від екстрактора; фіксований набір модулів є точками входу (CLI, репортер тестів, trace-hooks, worker аналізу); у графі імпортів немає циклів.

## `layers`

```markdown
- layers domain < application < presentation
  - infrastructure
```

Ліворуч — нижче. Залежність може йти вниз: presentation може імпортувати application, application — domain, presentation — domain. Імпорт application з domain — це K101, підтверджена розбіжність.

Шари, вкладені під маркер `layers`, плюс `external` і `unassigned`, без порядку. Ребро в невпорядкований шар вільне, доки `deny` його не заборонить. Ребро з невпорядкованого шару в упорядкований потребує `allow`, інакше це K101.

Кілька рядків `layers` утворюють один частковий порядок. `a < b` і `b < c` разом забороняють `a` → `c`. `a < b` і `c < d` нічого не кажуть про `a` і `d`. Рядок, що суперечить попередньому, повторює шар або містить ID з крапкою, — це K005, і він не оцінюється.

Кожен рядок `layers` має власний вердикт. `ok`, коли жодна залежність не ламає порядок і в області немає дірки рівня залежностей. `unverified`, коли дірка є (нерозв'язаний імпорт, файл, що не розібрався, виключений файл, `eval`). `fail` (K101), коли розв'язане ребро дивиться не в той бік. Діагностика вказує на рядок джерела ребра і називає правило.

## `allow` і `deny`

```markdown
- allow infrastructure presentation
- deny domain infrastructure
- deny lang external.web-tree-sitter
```

Обидва беруть джерело і одну чи кілька цілей. ID — шари, модулі (клас рахується модулем свого файла) або їхні префікси. ID функції, типу, події чи аліаса залежності — K005: ребра правил ідуть між модулями, і таке правило нічого б не перевіряло.

Перемагає найконкретніше правило, що підійшло. Специфічність — сума глибин двох ID у сегментах, не довжина рядка. `deny app.x domain` (2 + 1) і `allow app domain.storefront` (1 + 2) рівні, і за рівності перемагає `deny`. `allow app.x.y domain` (3 + 1) перемагає `deny app domain.storefront`. `allow` також знімає K101 для своєї пари: так `infrastructure → presentation` у прикладі shop лишається законним, хоча порядок шарів інакше його відхилив би.

Одна залежність модуля від модуля дає одну K102, скільки б ребер її не показували (import, call, type, re-export). Повідомлення називає ребро і рядок `deny`.

`deny` — це `fail`, коли заборонене ребро розв'язане; `unverified`, коли в області є дірка рівня залежностей і забороненого ребра немає; `ok`, коли область прочитана повністю і ребра немає. Область ще без модуля — `ok` («no module … yet»), якщо тільки єдине оголошення не є `planned`: тоді `unverified`. Дірка всередині однієї функції (невідомий декоратор) змінює те, що виконує ця функція. Вона не змінює того, що імпортує модуль, тож сама по собі не робить `deny` непровіреним.

Коментар у shop читається правильно: «домен не залежить від infrastructure» — це твердження про ребра, які keylang записав. Це не доказ, що жодна функція не робить I/O каналом, якого frontend не бачить.

## `entry`, `exports`, `no-cycles`

```markdown
- entry
  - infrastructure.server
  - presentation.terminal
- module application.purchase
  - exports buy, cancel
  - no-cycles
```

`entry` перелічує стартові модулі. Досяжність іде ребрами import, call, type і re-export, зокрема реекспортом через `index.ts` і `new URL("./worker.ts", import.meta.url)` або `module.register`, коли специфікатор — рядок, який резолвер бачить. Модуль упорядкованого шару, якого не досягає жоден entry, — попередження K103 на файлі модуля. Дірка рівня залежностей у досяжному модулі перетворює цю «недосяжність» на `unverified` замість K103, бо відсутнє ребро могло бути шляхом. Модулі невпорядкованих шарів не перевіряються. Entry, що називає відсутній модуль, — K001, тож видалений worker, якого ви записали, лишається видимим. `entry` із шаром або префіксом стартує з кожного модуля під ним.

K103 не валить процес. Це попередження. JSON-формат звітує його як `warning`, не як `fail`.

`exports` порівнює перелічені імена з таблицею публічних експортів цього модуля у знімку, не з його підмодулями. `export { a as b }` порівнюється як `b`. `export default` — це `default`. `export *` розкривається в імена іншого модуля, і якщо той модуль непрозорий, правило `unverified`, а не «ви забули ім'я». Зайвий публічний експорт — K104 (розбіжність). Заявлене ім'я, якого модуль не експортує, — відсутність, теж K104. Імена в списку — імена експорту, не ID карти, тож K001 вони не дають.

`no-cycles` дивиться на компоненти сильної зв'язності графа import / re-export. На верхньому рівні, як у цьому репозиторії, область — увесь граф. Під `module <id>` область — цей модуль і його підмодулі. Цикл в області — K105, і повідомлення містить шлях. Файл, що імпортує сам себе, — цикл. Одна K105 на компонент. Дірка в області без відомого циклу — `unverified`, не `ok`.

## Як читати результат

Результат правила — один із:

| Вердикт | Значення |
|---|---|
| `ok` | Твердження виконалось, і область покрита. У людському форматі це називається convergence |
| `fail` | Порушення показано (розбіжність або відсутність, яку знімок достатньо повний, щоб ствердити) |
| `unverified` | Порушення не показано, і знімок недостатньо повний, щоб закрити твердження |
| warning | K006, K103, K202. Записано, це не провальний вердикт |

`check` вказує на код для знахідки ребра і на специфікацію для структурної. `--explain-edge <a> <b>` друкує ребра знімка між двома ID або нерозв'язані конструкції, які могли б таке ребро утворити, і нічого не пише.

`✓` в інтерфейсі на рядку правила означає, що кожен критерій, звітований на цьому рядку, — `ok`. Рядок, який структурно `ok`, а за покриттям `unverified`, показує `◌`, не `✓`. Підсумки в рядку стану рахують рядки, не окремі рядки доказів. Тому інтерфейс цього репозиторію може показати 11 пройдених рядків, тоді як `check` друкує 43 результати `ok`: багато рядків потоку несуть кілька результатів, а застарілий trace знижує весь рядок.

## Практичний порядок

1. `keylang init` або напишіть `layers` у `keylang.json`, щоб групи збігалися з тим, як ви вже говорите про код.
2. `keylang draft rules` пропонує рядок `layers` з ребер, які є сьогодні, плюс `no-cycles`, коли циклів немає. Він пише пропозицію, не специфікацію. Прочитайте її. Пропозиція, що лише переказує сьогоднішні випадковості коду, — слабке правило.
3. Додайте ті `deny`, які ви справді маєте на увазі. Краще кілька заборон на рівні шарів, ніж заборона на кожну пару файлів.
4. Перелічіть справжні процеси як `entry`: CLI, сервер, worker-и, тестові hooks, які ви хочете зберегти.
5. Поставте `keylang check` і `keylang map --check` у CI. `--strict` додавайте, лише коли рядки unverified або виправлені, або прийняті як поза обсягом.

`draft rules --mode llm` просить у налаштованої моделі правила і потім перевіряє кожне запропоноване правило окремо. Коментар на рядку — `agree`, `conflict` або `llm-only`. `hybrid` дописує алгоритмічні правила, які модель пропустила. Конфлікт друкується разом із K101 чи K102, які він створив би. Останнє слово не за моделлю: після злиття його має `check`.
