# 7. Wiring, інтерфейс і агенти

[Курс](README.md) · [English](../07-tools.md) · **Українською**

Правила й потоки перевіряють код, який згенерував агент: ви написали специфікацію, а не функції, і сам keylang агента ніколи не запускає. На тому самому аналізі працюють ще три інструменти: генератор wiring, інтерфейс у терміналі та браузері й інструменти для агентів. Жоден із них не виносить власного, другого вердикту, тож хоч би що вони показували, остаточне слово лишається за `check`.

## Wiring

Секція `# wiring` перелічує фабрики. З неї `keylang wire` пише `keylang.gen.ts` — типовану функцію `async function wire(env)`, яка будує кожну фабрику один раз, починаючи із залежностей. Контейнера й пошуку за рядком немає, тож результат — звичайний код, який можна прочитати. Контракт описано в [ADR 0003](../../adr/0003-wiring-lifecycle.md).

```markdown
# wiring

- wire app.purchase.createPurchase
  - store domain.store.Store
- wire domain.store.Store
  - db infra.db.createDb
    - when env.DB = memory → infra.memory-db.createMemoryDb
    - compose infra.logged.logged
```

`wire <id>` називає або функцію, яку викликають з об'єктом іменованих залежностей, або клас, який створюють із цим об'єктом. Кожен вкладений рядок `<псевдонім> <id>` — одна залежність. Id, що не має власного рядка `wire`, — це лист: його створюють без аргументів. Рядок `when env.NAME = value → <id>` обирає іншу реалізацію, коли змінна має саме це значення; перемагає перший збіг, а якщо жоден не підійшов, береться сам рядок залежності. `compose <id>` обгортає значення. Коли рядків `compose` кілька, вони застосовуються в порядку запису, і перший опиняється найближче до значення.

Помилки в секції стають діагностиками. Невідомий id — це K001, повторений id у `wire` — K002, цикл між фабриками — K301. K302 означає, що згенерований файл не може зібрати ціль, бо це модуль, тип, код Python чи Rust, метод екземпляра або ім'я, якого модуль не експортує; статичний метод при цьому дозволений. Правило `deny` між фабрикою та її залежністю дає K102.

`keylang wire` не перезапише файл без маркера `// keylang:generated`, а натомість завершиться з кодом 1. Якщо в секції є хоч одна діагностика, нічого не записується. `--check` лише порівнює й теж нічого не пише. Згенерований файл — звичайний модуль у тому шарі, куди потрапляє його шлях, тому на нього діють ті самі правила `deny`. Типи в ньому перевіряє `tsc`, а не keylang.

Wiring не ізолює модулі: імпорт, написаний вручну, просто обходить `wire()`, і такі імпорти ловлять саме правила. Генерацію для Rust і час життя в межах запиту вже спроєктовано, але в інструменті їх поки немає.

## Термінал і браузер

Якщо запустити `keylang` без команди, він відкриває інтерфейс, коли stdin і stdout під'єднано до термінала; інакше друкує довідку й завершується з кодом 2. `keylang web` віддає той самий інтерфейс за адресою `http://127.0.0.1:7070/#t=<token>`. Токен міститься у фрагменті URL, а фрагмент браузер на сервер не надсилає. Типово сервер слухає localhost. Якщо вказати інший `--host`, інтерфейс захищатиме лише токен, тому для віддаленої роботи безпечніше прокинути SSH-тунель на localhost.

На екрані — специфікація, жолоб із позначкою біля кожного рядка, рядок стану й дерево. `?` відкриває список клавіш:

`?` відкриває цей список, а Esc закриває його:

`Enter` на id відкриває переглядач лише для читання, коли `$EDITOR` не задано, а в `keylang web` — завжди. У терміналі із заданим `$VISUAL` або `$EDITOR` відкривається цей редактор. `Esc` повертає назад:

![cli.cli.main, відкритий з тригера](../images/tui-code.png)

Під час редагування `Ctrl+S` записує файл, а `Ctrl+Space` доповнює ключові слова й id. `Ctrl+G` перетворює виділений текст на рядки `step`, `when` / `then`, `invariant` або `emits`. Модель при цьому не викликається: розпізнаються лише id, які вже є в знімку, і кілька слів-підказок (`when`, `if`, `коли`, `якщо`).

`keylang web <url>` спершу клонує репозиторій так само, як `keylang clone` (див. [першу годину](../existing/uk/01-the-first-hour.md)), а потім віддає інтерфейс над клоном.

У репозиторії є `Dockerfile`, щоб запускати keylang разом із git у контейнері. Клони лягають у том `/cache`, а `/work` — тека, яку ви монтуєте:

```sh
docker build -t keylang .
docker run --rm -v keylang-cache:/cache keylang clone https://github.com/owner/repo
docker run --rm -p 127.0.0.1:7070:7070 -v keylang-cache:/cache keylang web https://github.com/owner/repo --host 0.0.0.0
docker run --rm -v "$PWD":/work keylang check
```

У контейнері сервер мусить слухати `0.0.0.0`, тож стереже лише токен; `127.0.0.1:` у `-p` лишає порт на вашій машині. У надрукованому URL замініть `0.0.0.0` на `localhost`.

## Сторінка діаграм

`keylang web` віддає ще й сторінку діаграм. Посилання «Діаграми» у правому верхньому куті сторінки терміналу відкриває її в новій вкладці з тим самим токеном.

![Потік checkout на сторінці діаграм, вибрано крок](../images/diagrams-flow.png)

У списку ліворуч — потоки, знайдені потоки, точки входу й вид шарів. Полотно малює вибраний вид фігурами в стилі BPMN, по доріжці на шар, і фарбує їх тими самими вердиктами, що й жолоб. Панель праворуч показує id вибраної фігури, її місце в коді й у специфікації та результати `check`. Над списком — чотири режими: «Діаграми»; «Дослідник» — дерево викликів точки входу, з якого можна зберегти потік як пропозицію; «Сліпі зони» — звіт `keylang coverage`; і «Редактор».

![Редактор: до потоку checkout додано запланований крок](../images/diagrams-editor.png)

У редакторі вид «з коду» дозволяє змінювати лише розкладку, а «чернетка» редагується повністю. З палітри перетягують шар, крок, тригер, `when`, `parallel`, подію чи таймер, а фігури з'єднують зі змістом: послідовність, виклик, залежність, `allow`, `deny`, `emits` або `continues`. Нова фігура отримує id `planned:`. `Ctrl+Z` і `Ctrl+Y` скасовують і повторюють, SVG і PNG експортують малюнок у браузері, а `Ctrl+C` / `Ctrl+V` копіюють фігури між вкладками і навіть між двома серверами `keylang web` як пакет `flow export`. Розкладка йде в `keylang/diagrams/<view>.layout.json`, і її комітять, щоб команда бачила той самий малюнок. «Запропонувати зміни» перетворює малюнок на пропозиції для специфікацій, які він змінює, так само як `keylang diagram propose`. Жодна дія на сторінці не пише специфікацію напряму.

`keylang web --new <dir>` починає проєкт із малюнка. Він відкриває редактор на порожньому полотні з шаблоном доріжок, а кнопка «Створити специфікацію» записує `keylang.json`, `rules.md`, фічі й розкладку, але лише ті файли, яких ще немає. Його крок за кроком проходить [маршрут «Проєкт з нуля»](../from-scratch/uk/README.md).

Ті самі види виходять з браузера й файлами. `keylang export bpmn <flow>` пише BPMN 2.0, `keylang export drawio <view>` — файл draw.io, а `keylang export c4` — діаграму C4 для PlantUML чи Mermaid. `keylang import drawio <file>` читає малюнок, який хтось змінив у draw.io, назад як одну пропозицію для специфікації потоку. `keylang flow export <name>` пакує потоки в один переносний Markdown-пакет; в іншому репозиторії `keylang flow import` пропонує їх як фічу на `planned`-вузлах разом із рядками `keylang/migration.md`, а `keylang migration status` потім звітує, потік за потоком, чи є в новому стеку відповідник і чи проходять ті самі тести в обох.

`keylang lsp` передає ті самі діагностики через stdio. Клієнт у `editors/vscode/` — лише тонка обгортка над ним; у Marketplace його не опубліковано, і до пакета npm він не входить.

## Агенти

keylang агента не запускає. Натомість `init` і `keylang agents` записують короткий блок інструкцій, а там, де знаходять Claude, Codex, Cursor чи opencode, ще й ставлять сервер MCP і skill. Які саме теки вони шукають, сказано в [уроці 2](02-install-and-check.md). Розподіл роботи не змінюється: ви пишете специфікацію, агент генерує з неї програму, а функції самі ви не пишете. Хоч би що згенерував агент, вирішальне слово й далі за `check`.

Файл фічі — звичайна специфікація. `keylang feature <slug>` вважає фічу готовою, коли кожен `planned` реалізовано, кожен крок має static `ok` і не лишилося жодного `fail` правил. Тести й trace показуються, але не блокують.

Для Claude і Codex keylang також ставить хук Stop, який спрацьовує, коли агент збирається завершити роботу. `keylang hook stop` запускає перевірку змінених файлів. Якщо з'явився новий `fail` або специфікацію послаблено відносно `HEAD` (K108), відповідь — `decision: block`, і агентові доводиться працювати далі. Якщо нового `fail` немає або та сама подія приходить повторно з `stop_hook_active: true`, відповідь — `{}`. В обох випадках це JSON і код виходу 0. Коли перевірити хід неможливо взагалі (немає git, зламаний `keylang.json`), відповідь містить `systemMessage`, який харнес показує вам, не блокуючи агента. Рядок unverified не блокує. Cursor користується хуками Claude, а opencode хука Stop не отримує взагалі.

Рукописні правила змінюються лише через пропозицію. `apply_diff` зберігає новий текст, але сам файл не чіпає, доки ви не зіллєте зміни, а згенерований файл відхиляє зовсім.

| Команда | Що пропонує | Чого не зробить |
|---|---|---|
| `draft flow <trigger>` | Потік у `.keylang/proposals/` | Специфікацію не редагує. `--mode algo` іде за розв'язаними викликами на глибину 4 |
| `draft rules` | Правила, які код уже виконує, або правила моделі з мітками `agree`, `conflict`, `llm-only` | Не послабить ваш `deny`, доки ви не зіллєте відповідний шматок |
| `draft map` | Нічого; лише друкує розкладку | Файл змінюється, лише коли ви його редагуєте |
| `code-to-spec <file:line>` | Потоки для функції або для кожної експортованої функції | `--since <git-ref>` обмежує чернетку функціями, яких торкається diff |
| `spec-to-code <id>` | Заготовку й тести, що падають, для `planned fn` | Файли записує лише з `--apply`, типово — ні |
| `draft flow --from-trace <file>` | Потік із того, що спостеріг один запуск trace | Кроки, яких не бачить static, позначено як спостережені, а не доведені |
| `flows adopt <name>` | Знайдений потік як специфікацію | Сам `flows discover` пише лише згенероване представлення |
| `diagram propose`, `import drawio` | Зміни малюнка, по одній пропозиції на специфікацію | Нові шари для `keylang.json` лише друкує |
| `explain <id> --llm` | `keylang/explain/<id>.md` | Вердикту ніколи не змінює |

`keylang mcp` надає search, node, code, flows, check, explain, context, `validate_spec`, `scaffold`, `feature_status`, `list_entries`, `discover_flows`, `coverage_report`, `list_integrations`, `project_tour`, `migration_status` і `apply_diff`. Із них щось записує лише `apply_diff`, і записує він тільки пропозицію.

В інтерфейсі `m` відкриває diff. `a` приймає шматок, `r` відхиляє його, а `w` записує прийняті шматки. Шматок, щодо якого ви не ухвалили рішення, не застосовується. Поза інтерфейсом `keylang proposals` перелічує, що чекає, `proposals show <target>` друкує diff, а `proposals accept` чи `proposals reject` вирішують справу. Приймає пропозицію людина, ніколи не агент.

У режимі перегляду `Ctrl+Space` на потоці з тригером просить у моделі чернетку й відкриває злиття. Для цього потрібна модель: `agent` у `keylang.json` або `KEYLANG_AGENT`, як в [уроці 2](02-install-and-check.md). Після злиття `check` оцінює нові кроки так само, як будь-які інші, тож рядок, якого знімок не підтверджує, стане `unverified` або `fail`, але ніколи не `ok`.

Текст-привид — це один запропонований рядок у кінці щойно створеного пункту `- `, і `Tab` його вставляє. Голосове введення (`Ctrl+R` під час редагування) необов'язкове, а `keylang doctor` підкаже, який рушій налаштовано. Жоден із них не записує файл самостійно.

Отже, дайте інструментові пропонувати, читайте кожен шматок і приймайте ті, що кажуть саме те, що ви мали на увазі. А якщо сумніваєтеся, вірте `check`, а не коментарю про те, що рядок написала модель.
