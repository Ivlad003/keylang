# 2. Встановлення, check, explain

[Курс](README.md) · [English](../02-install-and-check.md) · **Українською**

Як і раніше, специфікацію пишете ви, а функції генерує агент, тож самі ви їх не пишете. keylang агента не запускає, а результат перевіряють команди з цього уроку.

Потрібен Node.js ≥ 22.18. Під час встановлення пакет не компілює жодного нативного коду. Необов'язкові голосові модулі (`@fugood/whisper.node`, `decibri`) ставляться лише тоді, коли для вашої платформи є готовий бінарник, і keylang працює й без них.

```sh
npx keylang init .     # шари, keylang.json, карта, baseline, файли харнеса
npx keylang check      # розв'язати id і перевірити правила в keylang/
npm i -g keylang       # далі: keylang check
```

У копії цього репозиторію точка входу — `node bin/keylang.js`, і вона виконує TypeScript напряму. Пакет, встановлений з npm, натомість завантажує скомпільований `dist/`.

`init` записує `keylang.json`, карту і `keylang/rules.baseline.md`. Baseline забороняє кожному шару ті шари, від яких він досі не залежить. Шар, який уже імпортує пакети, отримує дозвіл на ці пакети і заборону на решту `external`. Оскільки baseline описує граф, який `init` щойно побачив, одразу після `init` він не додає жодного нового `fail`. Але якщо пізніше з'явиться імпорт через одну з цих прогалин, він дасть K102, доки ви не зміните правило або не запустите `keylang baseline` знову.

Якщо не передати `--agents=none`, `init` також записує керований блок в `AGENTS.md` між `<!-- keylang:begin -->` і `<!-- keylang:end -->`, а текст поза цими маркерами лишає як був. Якщо вже є `.claude/`, `.codex/`, `.cursor/` або `opencode.json`, той самий запуск реєструє MCP-сервер `keylang`, копіює skill `keylang-feature`, а для Claude і Codex ще й додає хук Stop. Тека skill, яку створив сам keylang, не вважається ознакою того, що Claude встановлено, тому повторний `init` не додає нових адаптерів. `keylang agents` повторює це встановлення в репозиторії, де `keylang.json` уже є. З `--check` команди `init`, `agents` і `baseline` нічого не записують і завершуються з кодом 1, коли згенерований текст застарів.

Ім'я шару має бути одним сегментом id. Зарезервовані імена (`external`, `unassigned` і ключові слова карти `layer`, `allow`, `deny`, `entry`, `module`, `no-cycles`) отримують `_` у кінці, і `init` повідомляє про це в stderr. Якщо `keylang.json` немає, наступні команди вгадують шари за структурою тек.

## Команди, з яких починають

| Команда | Пише файли? | Що читати |
|---|---|---|
| `keylang check [paths…]` | Ні | Знахідки в stdout, `N fail, M unverified, K ok` у stderr. `--changed` лишає тільки знахідки, що стосуються файлів, змінених від `HEAD` (або `--since`), плюс невідстежувані файли, зокрема видалений файл, який ще згадує потік |
| `keylang baseline` | `keylang/rules.baseline.md` | Згенерована рамка deny/allow. `--check` завершується з 1 і називає `keylang baseline`, коли файл більше не збігається |
| `keylang feature <slug>` | Ні | Чи готовий `keylang/features/<slug>.md`. Код 0 — готово, 1 — є прогалини, 2 — файла немає |
| `keylang agents` | Файли харнеса поза `keylang/` | Ті самі адаптери, що й `init`. `--agents=none` прибирає це встановлення і лишає baseline |
| `keylang map [dir]` | `keylang/map/*.md`, `.keylang/index.json` і `keylang/map-explained/`, коли ввімкнено `explain.map` | Відмовляється перезаписувати файл карти без маркера `keylang:generated` |
| `keylang map --check` | Ні | Код 1, коли закомічена карта відрізняється від свіжої або у файлі карти немає маркера |
| `keylang explain K001` | Ні | Навіщо існує цей код діагностики, короткий приклад і виправлення |
| `keylang explain <id>` | Ні | Вид, сигнатура, файл, виклики, хто викликає, потоки й правила, а також `fresh` або `stale` для збереженого пояснення |
| `keylang explain <id> --llm` | `keylang/explain/<id>.md` | Текст від налаштованого агента. Вердикту він не змінює |
| `keylang fmt <file>` | Сам файл | Код 1 при структурній помилці або, з `--check`, коли файл не був у канонічному вигляді |
| `keylang parse <file>` | Ні | Текстовий дамп. З `--json` у stdout іде лише JSON, а діагностики — у stderr |
| `keylang doctor` | Ні | Мови, чи задано ключ агента, підтримка голосу. Завершується з 0, навіть коли знаходить проблему |

Типово `check` бере каталог специфікацій, вказаний у `keylang.json`, зазвичай `keylang/`. Якщо передати шлях, наприклад `examples/shop`, він перевірить саме це дерево.

| Код | Значення |
|---|---|
| 0 | Немає знахідок, що блокують |
| 1 | Порушення; застаріла карта, baseline чи файли харнеса під `--check`; або будь-який `unverified`, якщо передано `--strict` |
| 2 | Хибні аргументи або помилка I/O. Повідомлення називає файл, а для конфігурації — ще й поле |

`--format` на код виходу не впливає. Типовий формат — `human`, а `json`, `sarif` і `github` призначені для CI.

## Хибне ім'я, потім чисте

У `examples/shop` є одна навмисна помилка: модуль purchase залежить від `domain.aggregate`, хоча насправді існує модуль `domain.orderAggregate`.

![K001 на examples/shop, вихід 1](../images/cli-shop-k001.png)

З цього виводу можна прочитати три окремі факти:

1. `K001` — це помилка: ім'я не розв'язується. Підказка пропонує найближчий наявний id, а код виходу — 1.
2. Другий рядок — `unverified`, а не ще одна помилка. У цьому прикладі немає вихідних файлів, тож потік нема на чому довести. `no snapshot` означає «не доведено», а не «зламано».
3. Однієї поломки досить, щоб увесь процес завершився невдачею. Рядок unverified сам по собі до цього не призвів би, хіба що ви передасте `--strict`.

![explain K001](../images/cli-explain-k001.png)

У `examples/shop-fixed` ім'я написано правильно: `domain.orderAggregate`. Коду, як і раніше, немає, тож потік лишається unverified, але нічого не зламано, і процес завершується з 0:

![shop-fixed виходить з 0](../images/cli-shop-fixed.png)

«Немає порушень» і «кожне твердження доведено» — різні речі. Вмикайте `--strict`, коли прогалина в доказах має валити пайплайн. Типовий режим підходить, наприклад, коли у свіжому клоні ще немає звітів тестів і червоними мають бути лише структурні поломки.

Якщо ім'я відображає справжній намір, а коду просто ще не написали, оголосіть його як заплановане:

```markdown
- planned fn domain.orderAggregate.create (items: Item[]) → Order
```

Посилання на `planned` id не дає K001. Натомість його доказ `ID` має статус `unverified` з причиною `planned`. Коли символ згодом з'являється в коді з тим самим видом і сигнатурою, оголошення перетворюється на попередження K202 — нагадування, що рядок `planned` тепер можна прибрати. Якщо ж вид або сигнатура відрізняються, буде помилка K201.

## Цей репозиторій

`keylang check` у корені цього репозиторію перебудовує знімок і перевіряє `keylang/rules.md`, але карту не записує. Запуск на знімку екрана не показав жодної поломки:

![check цього репозиторію, середину пропущено](../images/cli-check-repo.png)

`ID ok` означає, що символ є у свіжому знімку. `static ok` означає, що знайдено шлях викликів від батьківського кроку, тут — «called from `cli.cli.main`». `trace unverified` означає, що файл trace записано для іншого знімка. Запустіть `npm test`, щоб перегенерувати `.keylang/reports/` і `.keylang/trace/`. Доти `--strict` завершуватиметься з 1, а звичайний `check` — з 0.

![explain cli.cli.cmdCheck](../images/cli-explain-id.png)

`internal` означає, що функція не входить до публічних експортів модуля. `closure … (incomplete)` означає, що щось досяжне з цієї функції динамічне або нерозв'язане, тож відбиток не є повним доказом її поведінки.

## Форматування

`keylang fmt` переписує файл за деревом розбору. Маркери списку стають `-`, між токенами лишається один пробіл, а файл закінчується рівно одним переводом рядка. Повторний запуск нічого не змінює. Файл зі структурною помилкою (непарний відступ, табуляція, порожній пункт) лишається без змін, а помилка звітується як K003, бо форматер, який вгадував би дерево, міг би змінити зміст.

`keylang parse --json file.md` видає IR для інших інструментів. Діагностики йдуть у stderr, тож stdout, переданий іншій програмі через конвеєр, лишається валідним JSON.

## Конфіг, який ви відкриєте

`keylang.json` у корені репозиторію водночас позначає, де цей корінь.

| Поле | Роль |
|---|---|
| `format` | Редакція мови. Якщо поле пропущено, діє редакція 1. Якщо `keylang.json` немає зовсім, використовується поточна редакція, 2. У редакції 2 непорівнюваний `deny` перемагає |
| `languages` | Підмножина з `javascript`, `php`, `python`, `rust`, `typescript`. Якщо пропущено — визначається за розширеннями файлів |
| `module` | `file` (типово, коли мови не згодні) або `dir` |
| `layers` | Ім'я шару → список глобів. Порядок ключів задає порядок кольорів і дерева |
| `exclude` | Глоби, які лишаються у знімку як непрозорі модулі |
| `dir` | Каталог специфікацій, типово `keylang` |
| `check.tests` | JSON-звіт keylang або JUnit XML |
| `check.trace` | Trace у форматі JSONL |
| `check.static` | `behavior` (типово) або `shape`. Прапорець у командному рядку важить більше за файл |
| `agent` | Необов'язкове. `anthropic:<model>` або `openrouter:<model>` для `explain --llm` і чернеток |
| `explain.map` | Необов'язкове. `true` додатково записує `keylang/map-explained/`. `check` це поле не читає |

Без `check.tests` і `check.trace` ці види доказів не друкуються і на `--strict` не впливають. У цьому репозиторії обидва поля вказують на `.keylang/`, який внесено в gitignore, тож CI, якому потрібні докази trace, має сам створити ці файли під час завдання.
