# 2. Встановлення, check, explain

[Курс](README.md) · [English](../02-install-and-check.md) · **Українською**

Ви пишете специфікацію. Агент генерує функції. Ви — ні. keylang агента не запускає. Команди нижче перевіряють результат.

Потрібен Node.js ≥ 22.18. Пакет не компілює нативний код. Необов'язкові голосові модулі (`@fugood/whisper.node`, `decibri`) ставляться, коли для платформи є готовий бінарник. Їх можна не ставити.

```sh
npx keylang init .     # шари, keylang.json, карта, baseline, файли харнеса
npx keylang check      # розв'язати id і перевірити правила в keylang/
npm i -g keylang       # далі: keylang check
```

У цьому клоні точка входу — `node bin/keylang.js`. Він виконує TypeScript напряму. Встановлення з npm вантажить `dist/`.

`init` пише `keylang.json`, карту і `keylang/rules.baseline.md`. Baseline забороняє кожному шару шари, від яких він ще не залежить. Шар, який уже імпортує пакети, отримує дозвіл на ці пакети і заборону на решту `external`. Одразу після `init` baseline не додає нового `fail`: він описує граф, який щойно побачив. Пізніший імпорт через прогалину — K102, доки ви не зміните правило або не запустите `keylang baseline` знову.

Без `--agents=none` `init` також пише керований блок у `AGENTS.md` між `<!-- keylang:begin -->` і `<!-- keylang:end -->`. Текст поза маркерами лишається як був. Якщо вже є `.claude/`, `.codex/`, `.cursor/` або `opencode.json`, той самий запуск реєструє MCP-сервер `keylang`, копіює skill `keylang-feature` і, для Claude і Codex, хук Stop. Тека skill, яку створив сам keylang, не означає «Claude встановлено», тож другий `init` нових адаптерів не нарощує. `keylang agents` повторює встановлення на репозиторії, де `keylang.json` уже є. `--check` на `init`, `agents` або `baseline` нічого не пише і виходить з 1, коли згенерований текст застарів.

Ім'я шару — один сегмент id. Зарезервовані імена (`external`, `unassigned` і ключові слова карти `layer`, `allow`, `deny`, `entry`, `module`, `no-cycles`) перейменовуються з `_` у кінці. `init` каже про це в stderr. Без `keylang.json` пізніші команди вгадують шари з тек.

## Команди, з яких починають

| Команда | Пише файли? | Що читати |
|---|---|---|
| `keylang check [paths…]` | Ні | Знахідки в stdout, `N fail, M unverified, K ok` у stderr. `--changed` лишає знахідки, що торкаються файлів, змінених від `HEAD` (або `--since`), плюс невідстежувані, включно з видаленим файлом, який потік іще називає |
| `keylang baseline` | `keylang/rules.baseline.md` | Згенерована рамка deny/allow. `--check` виходить з 1 і називає `keylang baseline`, коли файл більше не збігається |
| `keylang feature <slug>` | Ні | Чи готовий `keylang/features/<slug>.md`. Вихід 0 готово, 1 прогалини, 2 немає файла |
| `keylang agents` | Файли харнеса поза `keylang/` | Ті самі адаптери, що й `init`. `--agents=none` знімає встановлення і лишає baseline |
| `keylang map [dir]` | `keylang/map/*.md`, `.keylang/index.json` і `keylang/map-explained/`, коли ввімкнено `explain.map` | Відмовляється перезаписати файл карти без маркера `keylang:generated` |
| `keylang map --check` | Ні | Вихід 1, коли закомічена карта не збігається зі свіжим рендером або у файла немає маркера |
| `keylang explain K001` | Ні | Чому код існує, короткий приклад і виправлення |
| `keylang explain <id>` | Ні | Вид, сигнатура, файл, виклики, хто кличе, потоки і правила, і `fresh` або `stale` для збереженого пояснення |
| `keylang explain <id> --llm` | `keylang/explain/<id>.md` | Проза від налаштованого агента. Вердикт не змінює |
| `keylang fmt <file>` | Файл | Вихід 1 на структурній помилці або, з `--check`, коли файл не канонічний |
| `keylang parse <file>` | Ні | Текстовий дамп. `--json` — єдине в stdout. Діагностики йдуть у stderr |
| `keylang doctor` | Ні | Мови, чи заданий ключ агента, голос. Вихід 0 навіть коли повідомляє проблему |

`check` типово бере каталог специфікацій з `keylang.json`, зазвичай `keylang/`. Шлях `examples/shop` перевіряє те дерево.

| Код | Значення |
|---|---|
| 0 | Немає блокувальної знахідки |
| 1 | Порушення, застаріла карта, baseline або харнес під `--check`, або будь-який `unverified`, якщо передали `--strict` |
| 2 | Погані аргументи або помилка I/O. Повідомлення називає файл і, для конфігу, поле |

`--format` код виходу не змінює. Типово `human`. `json`, `sarif` і `github` — для CI.

## Хибне ім'я, потім чисте

У `examples/shop` одна навмисна помилка. Модуль purchase залежить від `domain.aggregate`. Модуль, який є, — `domain.orderAggregate`.

![K001 на examples/shop, вихід 1](../images/cli-shop-k001.png)

Прочитайте три окремі факти:

1. `K001` — помилка. Ім'я не розв'язується. Підказка — найближчий id. Код виходу 1.
2. Другий рядок — `unverified`, не ще одна помилка. У прикладі немає вихідних файлів, тож потік довести не можна. `no snapshot` означає «не доведено».
3. Однієї поломки досить, щоб процес упав. Рядок unverified сам не вронив би, хіба що ви передасте `--strict`.

![explain K001](../images/cli-explain-k001.png)

`examples/shop-fixed` пише `domain.orderAggregate`. Коду все одно немає, тож потік лишається unverified, і процес виходить з 0:

![shop-fixed виходить з 0](../images/cli-shop-fixed.png)

«Немає порушення» і «кожне твердження доведене» — різні речі. `--strict` ставте, коли прогалина має валити пайплайн. Типовий режим — коли свіжий клон ще без звітів тестів і червоними мають бути лише структурні поломки.

Якщо ім'я — справжній намір, а коду ще немає, оголосіть його:

```markdown
- planned fn domain.orderAggregate.create (items: Item[]) → Order
```

Посилання на `planned` id — не K001. Доказ `ID` — `unverified` з причиною `planned`. Коли символ пізніше з'являється з тим самим видом і сигнатурою, оголошення стає попередженням K202. Інший вид або сигнатура — помилка K201.

## Цей репозиторій

`keylang check` у корені перебудовує знімок і оцінює `keylang/rules.md`. Карту не пише. Запуск на знімку не надрукував поломок:

![check цього репозиторію, середину пропущено](../images/cli-check-repo.png)

`ID ok` означає, що символ є у свіжому знімку. `static ok` — шлях викликів від батька, тут «called from `cli.cli.main`». `trace unverified` означає, що файл trace зібрано для іншого знімка. Запустіть `npm test`, щоб перегенерувати `.keylang/reports/` і `.keylang/trace/`. Доти `--strict` виходить з 1, а звичайний `check` — з 0.

![explain cli.cli.cmdCheck](../images/cli-explain-id.png)

`internal` означає, що функції немає серед публічних експортів модуля. `closure … (incomplete)` означає, що щось досяжне динамічне або нерозв'язане, тож відбиток — не закритий доказ поведінки.

## Форматування

`keylang fmt` переписує файл із розбору. Кулі стають `-`. Між токенами один пробіл. Файл закінчується одним переводом рядка. Другий запуск нічого не змінює. Структурна помилка (непарний відступ, таб, порожній пункт) лишається як є і звітується як K003. Форматер, який вгадав би дерево, змінив би сенс.

`keylang parse --json file.md` — IR для інструментів. Діагностики йдуть у stderr, тож канал stdout лишається валідним JSON.

## Конфіг, який ви відкриєте

`keylang.json` у корені репозиторію — позначка кореня.

| Поле | Роль |
|---|---|
| `format` | Редакція мови. Пропущене поле — редакція 1. Немає `keylang.json` взагалі — читається поточна редакція, 2. Редакція 2 віддає перемогу непорівнюваному `deny` |
| `languages` | Підмножина `javascript`, `typescript`, `python`, `rust`. Пропущено: за розширеннями |
| `module` | `file` (типово, коли мови не згодні) або `dir` |
| `layers` | Ім'я шару → список глобів. Порядок ключів — порядок кольорів і дерева |
| `exclude` | Глоби, які лишаються у знімку непрозорими модулями |
| `dir` | Каталог специфікацій, типово `keylang` |
| `check.tests` | JSON-звіт keylang або JUnit XML |
| `check.trace` | Trace JSONL |
| `check.static` | `behavior` (типово) або `shape`. Прапорець сильніший за файл |
| `agent` | Необов'язково. `anthropic:<model>` або `openrouter:<model>` для `explain --llm` і чернеток |
| `explain.map` | Необов'язково. `true` також пише `keylang/map-explained/`. `check` це не читає |

Без `check.tests` і `check.trace` ці види доказів не друкуються і на `--strict` не впливають. Цей репозиторій вказує обидва на `.keylang/`, а це в gitignore. CI, якому потрібен доказ trace, має створити файли в джобі.
