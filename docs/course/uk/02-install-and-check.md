# 2. Встановлення, check, explain

[Курс](README.md) · [English](../02-install-and-check.md) · **Українською**

Потрібен Node.js ≥ 22.18. Пакет не компілює native-додатки. Опційні голосові модулі (`@fugood/whisper.node`, `decibri`) ставляться, коли для платформи є готовий бінарник, і їх можна не ставити.

```sh
npx keylang init .     # вгадати шари, записати keylang.json, згенерувати карту
npx keylang check      # резолвити ID і перевірити правила в keylang/
npm i -g keylang       # далі: keylang check
```

У цьому чекауті точка входу — `node bin/keylang.js`: вона вантажить TypeScript напряму. Встановлення з npm вантажить `dist/`. `npm link` дає команду `keylang`, поки ви працюєте над інструментом.

`init` пише `keylang.json` і карту. Ім'я шару — один сегмент ID. Імена, які інструмент резервує (`external`, `unassigned` і ключові слова карти `layer`, `allow`, `deny`, `entry`, `module`, `no-cycles`), перейменовуються з суфіксом `_`, і `init` пише про це в stderr. Без `keylang.json` подальші команди вгадують шари з дерева каталогів.

## Команди, з яких починають

| Команда | Пише файли? | Що читати |
|---|---|---|
| `keylang check [шляхи…]` | Ні | Знахідки в stdout, `N fail, M unverified, K ok` у stderr |
| `keylang map [тека]` | `keylang/map/*.md` і `.keylang/index.json` | Згенерована карта. Відмовляється перезаписати файл карти без маркера `keylang:generated` |
| `keylang map --check` | Ні | Код 1, коли закомічена карта не збігається зі свіжим рендером або у файла карти немає маркера |
| `keylang explain K001` | Ні | Чому код існує, короткий приклад і виправлення |
| `keylang explain <id>` | Ні | Вид, сигнатура, файл, виклики, хто викликає, потоки й правила, що називають ID |
| `keylang explain <id> --llm` | `keylang/explain/<id>.md` (у git; `--brief`: `keylang/explain/brief/<id>.md`) | Прозове пояснення від налаштованого агента. Жодного вердикту не змінює |
| `keylang fmt <файл>` | Файл у канонічній формі | Код 1, якщо були діагностики або, з `--check`, файл не був канонічним |
| `keylang parse <файл>` | Ні | Текстовий дамп IR. `--json` придатний для машини і є єдиним, що лежить у stdout |
| `keylang doctor` | Ні | Мови, чи налаштований ключ агента, рушій голосу. Код 0 навіть коли знаходить проблему |

`check` типово бере каталог специфікацій з `keylang.json`, зазвичай `keylang/`. Можна передати файли чи теки. `examples/shop` перевіряється, хоч це не каталог специфікацій проєкту.

Коди виходу:

| Код | Значення |
|---|---|
| 0 | Немає блокувальної знахідки |
| 1 | Порушення, застаріла карта з `--check`, або будь-який `unverified`, якщо передано `--strict` |
| 2 | Хибні аргументи, невідома команда або помилка I/O. Повідомлення називає файл і, для конфігурації, поле |

`--format` не змінює код виходу. `human` — типово. `json`, `sarif` і `github` — для CI. `json` — один об'єкт у stdout (`snapshotId`, `results`, `coverage`).

## Порушення, потім чистий ID

`examples/shop` — текст слайдів з однією навмисною помилкою: модуль purchase залежить від `domain.aggregate`, а модуль, який існує, — `domain.orderAggregate`.

![K001 на examples/shop, код виходу 1](../images/cli-shop-k001.png)

Читайте це як три окремі факти:

1. `K001` — помилка. Посилання не резолвиться в повністю проіндексованому модулі. Підказка — найближчий оголошений ID. Код виходу 1.
2. Другий рядок — `unverified`, не ще одна помилка. Правилам і крокам потоку потрібен знімок коду, а в прикладі немає джерел. `no snapshot` означає «не доведено».
3. Підсумок рахує обидва. Однієї помилки досить, щоб процес упав. Рядок unverified сам по собі не валить процес, доки ви не передасте `--strict`.

`keylang explain K001` — той самий текст, який інтерфейс показує для цього коду:

![explain K001](../images/cli-explain-k001.png)

Виправлення в прикладі — написання. `examples/shop-fixed` використовує `domain.orderAggregate`. Коду все ще немає, тож потік лишається unverified, і процес завершується кодом 0:

![shop-fixed завершується кодом 0](../images/cli-shop-fixed.png)

Цей код виходу — сенс тризначного результату. «Немає порушення» і «кожне твердження доведене» — різні речі. `--strict` ставте в конвеєр, який мусить відхиляти прогалину. Типовий режим — коли свіжий клон ще не створив звітів тестів і червоними мають бути лише структурні порушення.

Якщо ID — справжній намір, а коду ще немає, оголосіть його замість посилання на друкарську помилку:

```markdown
- planned fn domain.orderAggregate.create (items: Item[]) → Order
```

Посилання на `planned` ID не є K001. Його доказ `ID` — `unverified` з причиною `planned`. Коли символ з'являється з тим самим видом і сигнатурою, декларація стає попередженням K202 (її можна прибрати). Інший вид або сигнатура — помилка K201.

## Цей репозиторій

`keylang check` у корені перебудовує знімок, резолвить кожен ID потоку за ним і оцінює `keylang/rules.md`. Карту він не пише. Запуск, з якого знято знімки екрана, не мав порушень. Середину звіту на картинці пропущено; рядок підсумку — справжній рядок stderr:

![check цього репозиторію, середину пропущено](../images/cli-check-repo.png)

`ID ok` означає, що символ є у свіжому знімку. `static ok` означає розв'язаний шлях викликів від батька, тут «called from `cli.cli.main`». `trace unverified` називає файл і id знімка, для якого зібрано trace. Id різні, тож trace не зараховується. `npm test` перегенерує `.keylang/reports/` і `.keylang/trace/` для поточного дерева. Доти `--strict` дає код 1, а звичайний `check` — код 0.

`explain` для ID працює офлайн і не потребує агента:

![explain cli.cli.cmdCheck](../images/cli-explain-id.png)

`internal` у другому рядку означає, що функція не входить до публічного списку експортів модуля. `not resolved` рахує конструкції, які frontend бачив і не перетворив на ребро. `closure … (incomplete)` означає, що транзитивний відбиток викликів не є замкненим доказом поведінки, бо щось досяжне динамічне або нерозв'язане.

## Форматування і розбір

`keylang fmt` рендерить файл з IR. Маркери стають `-`, токени розділені одним пробілом, коми канонічні (`a, b`), опис сидить одразу під вузлом, файл закінчується одним переводом рядка. Другий запуск нічого не змінює. Файл зі структурною помилкою (непарний відступ, таб у відступі списку, порожній елемент) лишається як є і звітується як K003: форматер, що вгадав би дерево, змінив би зміст.

`keylang parse --json file.md` — IR для інструментів. Діагностики йдуть у stderr, тож пайп stdout лишається коректним JSON.

## Конфігурація, яку справді відкривають

`keylang.json` у корені репозиторію — маркер кореня. Поля, які задають руками:

| Поле | Роль |
|---|---|
| `languages` | Підмножина `javascript`, `typescript`, `python`, `rust`. Якщо пропущено — за розширеннями |
| `module` | `file` (типово, коли мови не згодні) або `dir` |
| `layers` | Ім'я шару → список глобів. Порядок ключів — порядок кольорів шарів і дерева навігації |
| `exclude` | Глоби, які лишаються у знімку непрозорими модулями |
| `dir` | Каталог специфікацій, типово `keylang` |
| `check.tests` | Шлях або глоб звіту JSON keylang чи JUnit XML |
| `check.trace` | Шлях або глоб trace JSONL |
| `agent` | Необов'язково. `anthropic:<model>` або `openrouter:<model>`, для `explain --llm` і чернеток |

`check.tests` і `check.trace` — те, як потік дізнається про запуск. Без них ці види доказів не друкуються і не впливають на `--strict`. Цей репозиторій ставить обидва на глоби в `.keylang/`, і цей каталог у gitignore. CI, якому потрібен доказ trace, має створити файли в джобі.
