# 6. Потоки

[Курс](README.md) · [English](../06-flows.md) · **Українською**

Потік — один сценарій. Правила кажуть, які модулі можуть знати одне одного. Потік каже один шлях крізь них: тригер, кроки під ним і докази, які ви доклали.

`keylang/flows/check.md` описує сам `keylang check`:

![Потік check, курсор на тригері](../images/tui-flow.png)

`/` знаходить `cli.cli.main`. На рядок нижче, `K` відкриває функцію. Ролик знято пізніше, після `npm test`, тож trace — `ok`. Знімок вище — старіший запуск, де trace був застарілий:

![Пошук, потім K на наступному кроці](../images/tui-flow.gif)

## Форма

```markdown
# flow checkout

- kind business
- trigger presentation.terminal.checkout
- step application.purchase.buy
  - reads infrastructure.products.find
  - step domain.orderAggregate.create
  - step infrastructure.orderStore.save
  - emits event order.created
- invariant total equals the sum of price times quantity
  - test tests/purchase.test.ts "computes total"
- when the item is out of stock
  - then application.purchase.OutOfStock
  - test tests/purchase.test.ts "rejects out of stock"
```

`kind` — `business` або `technical`. Це мітка, не перевірка. Тригер — де сценарій починається. Крок під кроком — виклик усередині батька. Сусідні кроки — «спочатку це, потім те». Крок поруч із тригером вкладений під тригер.

`reads` і `emits` — твердження на кроці. `emits` з картою не звіряється. `invariant` і `when` — проза. `then` — посилання, коли це один id з крапкою, інакше проза. `test` прив'язує файл і ім'я тесту в лапках до твердження, під яким стоїть.

## Чотири рядки доказів

Кожен вид — окремий результат. Один успіх не зафарбовує інші.

| Доказ | `ok` | `unverified` | `fail` |
|---|---|---|---|
| `ID` | Символ є у свіжому знімку | id — `planned`, або член сидить у непрозорому модулі | K001. Модуль прочитано повністю, і члена немає |
| `static` | Шлях розв'язаних викликів від батька | Шлях може не виконатись, або шляху немає, а щось, за чим keylang не йде, могло його створити | `absence`: ніщо досяжне не може назвати цей виклик |
| `tests` | Названий тест пройшов у звіті для цього знімка | Немає звіту, тест не знайдено, пропущено, або звіт для іншого знімка | Тест упав |
| `trace` | Крок бачили в завершеному запуску, вкладеним і по порядку | Trace для іншого знімка, запуск неповний, або гілка `when` не виконувалась | Обов'язкового кроку немає в завершеному інструментованому запуску, або крок почався раніше за попереднього сусіда |

На тригері зі знімка смужка читається `ID ✓`, `static —`, `tests —`, `trace ◌`. Рисочка означає «не звітувалось». У тригера немає батька, тож статичний шлях доводити нічим. Файл trace зібрано для старішого знімка. Позначка рядка — `◌`, найгірший із звітованих видів. Це не `✓`, навіть коли id точний.

`K` відкриває ті самі факти плюс кілька рядків оголошення:

![Наведення на cli.cli.main](../images/tui-hover.png)

Позначки, від найгіршої: `✗` поломка, `◌` будь-який обов'язковий вид `unverified`, `!` лише попередження, `✓` кожен звітований вид `ok`, `◇` оголошення `planned`.

`--static=behavior` (типово) іде ще й за хуком: типове значення `g` у `const g = p.x ?? f` і функція, яку передав викликач. Повідомлення каже `through the default of the hook` або `injected at file:line:col`. `--static=shape` іде лише за викликами, написаними в джерелі. `check.static` у конфігу — той самий перемикач. Прапорець перемагає.

Статичний `fail` навмисно важко дістати. Якщо будь-який нерозв'язаний виклик іще міг виконати крок, відповідь лишається `unverified`. Поломка означає, що keylang упевнений: виклику немає.

## Тести і trace

`check` ваших тестів не запускає і нічого не трасує. Ви вказуєте `keylang.json` на файли:

```json
"check": {
  "tests": ".keylang/reports/*.json",
  "trace": ".keylang/trace/*.jsonl"
}
```

Якщо ключів немає, ці види не друкуються і `--strict` їх ігнорує. Якщо файли старі або відсутні, ви отримуєте `unverified`, як на знімку.

Звіт тестів — власний JSON keylang (схема 1, від репортера `node:test` у цьому пакеті) або JUnit XML із `keylang.snapshotId`. JUnit без цієї властивості поточний код не підтверджує. Збіг — шлях файла плюс ім'я в лапках.

Trace — JSONL, одна подія на рядок. `start` і `end` вкладаються за `parentSpanId`. Порядок сусідів — `end` попереднього перед `start` наступного на тому самому `clockId`. Сортування за часом не досить. Rust і Python тримають один годинник на процес.

| Мова | Як записувати |
|---|---|
| TypeScript / JavaScript | `node --import keylang/trace script`. Тест, чиє ім'я містить `@flow <name>`, — тутешня домовленість |
| Python | `python3 adapters/python/keylang_trace.py script`, з `KEYLANG_TRACE_PLAN` на вивід `keylang trace-plan <flow>` |
| Rust | `mod keylang_trace` з `adapters/rust/keylang_trace.rs`, `span("<id>")` у функції і `finish()` у кінці `main`. Неінструментований крок лишається `unverified` |

`keylang trace-plan checkout` друкує функції для інструментування, з хешами файлів. Файл, що змінився після плану, не інструментується. Наступний `check` зве trace застарілим, бо зрушив `snapshotId`.

## `planned`

Крок, що називає `planned fn`, — не K001. `ID` і `static` — `unverified` з причиною `planned`. Коли символ з'являється з тим самим видом і сигнатурою (пробіли не рахуються, `->` і `→` одне й те саме), оголошення попереджає K202. Розбіжність — K201.

Те саме оголошення може жити в `keylang/features/<slug>.md`. `keylang feature <slug>` готовий, коли кожен `planned` там реалізовано, кожен крок — static `ok` і не лишилось жодного `fail` правил, включно з baseline. Тести й trace друкуються. Цю відповідь вони не вирішують.

Пакет, якого ще ніхто не імпортує, — `planned module external.<pkg>`, із кроком від модуля, який його імпортуватиме. Доки той модуль не імпортує, крок лишається `unverified`. Коли імпортує, оголошення — K202, а крок — static `ok`.

`spec-to-code <id>` пропонує заготовку, що кидає `not implemented`, і падаючий тест для кожного відсутнього тестового файла, який називають потоки. Після того як ви їх приймете, перевірка id може пройти, і K202 пропонує прибрати `planned`. Тести лишаються `fail`, доки їх хтось не напише. Згенерована заготовка — не пройдений сценарій.

## Позначка на рядку

Перемагає найгірший звітований вид: `fail`, потім `unverified`, потім попередження, потім `ok`. Гілка `when`, якої trace не взяв, не вимагає вкладених кроків у тому запуску.

`check --strict` виходить з 1, коли будь-який обов'язковий результат — `unverified`. На свіжому клоні це кожен застарілий trace. Пайплайн, якому треба «id справжні і правила шарів тримаються», запускає `check` без `--strict`. Пайплайн, якому потрібні свіжі trace, запускає тести в тому самому джобі, потім `check --strict`.
