# 8. Сценарії

[Курс](README.md) · [English](../08-use-cases.md) · **Українською**

Чотири сесії на знімках цього репозиторію і `examples/shop`. Кожна каже, що запустити, що показує картинка і яке рішення вона підтримує. Останній розділ — коли не варто братися.

Знімки інтерфейсу — `keylang web` 2026-09-28. Артефакти trace і тестів у `.keylang/` були застарілі. Підсумок CLI того самого дерева: `0 fail, 22 unverified, 43 ok`.

## 1. Перейменований модуль

Хтось копіює слайд і пише `order domain.aggregate` під `application.purchase`. Модуль у карті — `orderAggregate`.

```sh
node bin/keylang.js check examples/shop
```

![K001, висяче посилання domain.aggregate](../images/cli-shop-k001.png)

Перший рядок — рішення: це друкарська помилка або застаріле ім'я, і процес падає. У дужках — найближчий ID. Другий рядок — інший факт. Приклад не містить TypeScript, тож потік покупки довести не можна. Ви виправляєте ID (див. `examples/shop-fixed`) або, якщо модуля справді ще немає, оголошуєте `planned` і приймаєте `unverified`, доки не з'явиться код.

```sh
node bin/keylang.js explain K001
```

![Що означає K001](../images/cli-explain-k001.png)

Так робіть, коли код новий. Інтерфейс показує той самий абзац для діагностики під курсором, коли ви тиснете `?`.

Після виправлення процес завершується кодом 0, а потік усе ще не доведений:

![Код 0, один unverified, бо знімка немає](../images/cli-shop-fixed.png)

Не читайте це як «архітектуру крамниці перевірено». Читайте як «ID, які можна резолвити, резолвляться, а коду, проти якого перевіряти правила, немає».

## 2. Правило шару, яке має тримати CI

Правило цього репозиторію: парсер і перевірка не імпортують екстрактор tree-sitter і не імпортують `web-tree-sitter` напряму. TUI в тому самому становищі: він просить у аналізу факти і сам джерело не розбирає.

![Файл правил із зеленим жолобом](../images/tui-rules.png)

На що дивитися:

- Жолоб на рядках 14–31 — `✓`. Кожен критерій на цих рядках для цього знімка виконався.
- Кольори йдуть за порядком шарів у `keylang.json`. `base` і `lang` не того кольору, що `extract` чи `external`.
- Дерево навігації праворуч — знімок, не намальований вручну конспект. `cli` розкритий досить, щоб показати `keylang`, `index`, точки входу LSP і MCP, репортер тестів і trace-hooks.
- Рядок стану — `✗ 0  ◌ 22  ✓ 11`. Жодного проваленого рядка. Двадцять два рядки, чия найгірша позначка — unverified (застарілі trace і тести в потоках). Одинадцять рядків повністю ok — це ці правила.

У CI запускають обидві команди:

```sh
node bin/keylang.js check
node bin/keylang.js map --check
```

`check` падає, якщо новий імпорт перетинає `deny`. `map --check` падає, якщо хтось змінив код і не перегенерував `keylang/map/`. Жодна команда файлів не пише. Pull request, що додає `import web-tree-sitter` з `src/parser.ts`, валить `check` із K102 на цьому імпорті, а файл правил лишається поясненням.

`draft rules` може запропонувати стартовий рядок `layers` з того, що код робить сьогодні. Трактуйте пропозицію як опис теперішнього і відредагуйте її в правило, яке вам потрібне, перш ніж зливати. Правило, що лише переказує сьогоднішні імпорти, завтрашнього не зловить.

## 3. Потік, доведений частково

Відкрийте `keylang/flows/check.md` і поставте курсор на тригер.

![Рядок тригера: ID ok, trace unverified](../images/tui-flow.png)

Розгорнута смужка під рядком 16 — увесь сенс потоку:

| Позначка | Як читати |
|---|---|
| `ID ✓` | `cli.cli.main` є у свіжому знімку |
| `static —` | Не звітовано. У тригера немає батьківського виклику, який треба довести |
| `tests —` | На цьому рядку не звітовано. Тести причеплені до invariant нижче |
| `trace ◌` | Звітовано, і файл trace належить іншому знімку |

Жовтий рядок унизу називає файл `.keylang/trace/check.jsonl` і старий id знімка. `✓` на весь сценарій утримано, бо trace, який цей проєкт налаштував, не поточний. Це корисний результат. Єдиний зелений значок його сховав би.

`K` показує той самий розкол, і смужку читати не треба:

![Hover: id ok, trace unverified, два посилання в специфікаціях](../images/tui-hover.png)

Рамка — сигнатура, `src/cli.ts:114`, два рядки доказів, ім'я потоку і початок функції. «referenced 2 time(s) in specs» — інші рядки потоків або правил, що називають цей ID.

`Enter` відкриває функцію. У браузері і в терміналі без `$EDITOR` переглядач усередині keylang:

![main у src/cli.ts:114](../images/tui-code.png)

Заголовок лишається на специфікації, з якої ви прийшли. У куті — `read-only`, `Esc` повертає. Це навігація. TypeScript вона не редагує.

Щоб trace став `ok`, запустіть набір тестів, щоб репортер і адаптер trace переписали `.keylang/` для поточного `snapshotId`, і знову `check`. Доки хеші не збігаються, чесна позначка — `◌`. Якщо конвеєр мусить цей стан відхиляти, передайте `--strict`. Якщо trace ви не завели, приберіть `check.trace` з `keylang.json`, і цей вид перестане звітуватися.

Та сама форма в CLI, середину звіту обрізано:

![CLI: ID ok, static ok, trace unverified, потім підсумок](../images/cli-check-repo.png)

`static ok` на `cli.cli.run` — виклик з `main`. Нижче `generateMap` досягається через типове значення хука `generate`: `--static=behavior` це рахує, `--static=shape` — ні. Підсумок `0 fail, 22 unverified, 43 ok` збігається з інтерфейсом, якщо пам'ятати, що інтерфейс рахує рядки, а CLI — результати.

`explain` — офлайн-версія hover для оболонки або коментаря в рев'ю:

![explain cli.cli.cmdCheck](../images/cli-explain-id.png)

## 4. Прочитати репозиторій, перш ніж його правити

Перша сесія на незнайомому чекауті:

1. `keylang web` і відкрийте надрукований URL або запустіть `keylang` у терміналі.
2. `:` і частина шляху. Палітра нечітко збігає `open <файл>`:

   ![Палітра, відфільтрована словом rules](../images/tui-palette.png)

3. `F2`, коли потрібен список, а не палітра. Специфікації над згенерованою картою:

   ![Список файлів: правила й потоки над картою](../images/tui-files.png)

4. На згенерованій карті йдіть за посиланням або натисніть `Enter` на функції. Файл позначений `generated, read-only`. Змініть джерело, потім `keylang map`. Не редагуйте Markdown руками: наступний `map` його перезапише, а файл, що загубив маркер, блокує весь запис.

   ![Карта шару lang](../images/tui-map.png)

5. `v`, коли хочете читати прозу як документ. Жолоб лишається, тож правило, яке ви читаєте, все ще перевірене:

   ![Режим читання](../images/tui-read.png)

6. `?`, коли забули клавішу. Накладання своє для кожного режиму. На рядку з помилкою воно містить і текст `explain`:

   ![Довідка](../images/tui-help.png)

Далі правки звичайні. `i`, щоб змінити правило, `Ctrl+S`, щоб записати, `F5`, якщо аналіз потрібен одразу, а не після паузи. Агент, який має допомагати, кладе чернетки в `.keylang/proposals/` через `draft`, `code-to-spec` або MCP `apply_diff`. Ви зливаєте через `m`. Від запису агента специфікація не змінюється.

## Коли лишити це

keylang виправдовує себе, коли в репозиторії є шари, про які люди вже сперечаються, і ви хочете, щоб ця суперечка валила pull request. Він погано пасує, коли:

- Код — один шар, або межі рухаються щотижня і ніхто не оновлюватиме ID.
- Баги, які вас цікавлять, поведінкові, числові або з безпеки і ніколи не виглядають як імпорт чи виклик між модулями.
- Потрібна мова, яку frontend-и не розбирають. Неіндексований файл — дірка, і проєкт із самих дірок вічно звітуватиме `unverified`.
- Ви хочете, щоб прозу специфікації звірили з кодом. Цієї перевірки немає. `check` читає маркери списку.
- Потрібен runtime-інжектор залежностей для Rust або час життя на запит. `keylang wire` випускає один корінь композиції TypeScript.

Мале впровадження, яке все ще окуповується: `keylang.json` плюс короткий `rules.md` із `layers` і двома-трьома рядками `deny`, `check` і `map --check` у CI, і жодних потоків, доки сценарій не вартий trace. Потоки варті того, коли наскрізний тест уже є і ви хочете прив'язати його назву до функцій, яких він має досягати.
