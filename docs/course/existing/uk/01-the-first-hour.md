# 1. Перша година

[Додавання до кодової бази](README.md) · [English](../01-the-first-hour.md) · **Українською**

У перший день не беріться перебудовувати репозиторій. Наведіть на нього інструмент, подивіться, що він бачить, і запишіть кілька правил, яких ви справді готові дотримуватися. Ці правила й стануть специфікацією. Функції, що з'являться пізніше, напише агент, а не ви. keylang агента не запускає, він лише перевіряє те, що вийшло.

```sh
npx keylang init .
npx keylang map
npx keylang check
```

`init` робить шар із кожної теки, де є код. Якщо в репозиторії є `src/` або `lib/`, шарами стають теки всередині неї. Потім `init` створює `keylang.json`, згенеровану карту і `keylang/rules.baseline.md`. Baseline забороняє ті залежності між шарами, яких у коді ще немає, тож якщо така залежність з'явиться пізніше, ви про неї дізнаєтеся. Прочитайте baseline, перш ніж іти далі. Коли `deny` забороняє виклик, який вам ще потрібен, це привід поговорити з командою, а не баг інструмента.

Відкрийте `keylang/map`. Під кожною функцією стоїть її id. Саме його ви потім набиратимете, тож копіюйте id з карти й не вигадуйте коротших.

Перш ніж писати правило, подивіться, що бачить знімок коду. Ці команди не пишуть специфікацію, а `check` їхнього виводу не читає:

```sh
npx keylang flows discover
npx keylang tour
npx keylang entries
npx keylang coverage
```

`flows discover` запускайте першою. Вона пише чернетку флоу для кожної точки входу в `keylang/flows-discovered/`. Це згенероване представлення, і завдяки йому кожен флоу в огляді має свій файл і посилання на діаграму. `tour` друкує одну сторінку для новачка й обходиться без моделі. На ній є те, що система каже про себе, шари з їхнім розміром і зв'язністю, бізнес-процеси та їхні флоу, точки входу, інтеграції, сліпі зони й десять функцій, з яких варто почати читання. `tour --out keylang/tour.md` зберігає її як згенерований файл, а вкладка «Огляд» у `keylang web` показує ту саму сторінку. `entries` показує, звідки починається виконання. Це `bin` у `package.json`, `main`, маршрут із літеральним шляхом, а також маршрути, cron-задачі, споживачі й спостерігачі фреймворку, для якого в keylang є адаптер (Magento, Laravel, Symfony, NestJS, PWA Kit, SFCC, Django, FastAPI, Flask, Celery, Express, Fastify, Next.js). Адаптер вмикається сам, щойно в репозиторії видно його фреймворк: маніфест, імпорт чи файл конфігурації. Поле `frameworks` у `keylang.json` має перевагу над цим здогадом. `coverage` показує, де keylang нічого не бачить: функції, до яких не доходить жодна точка входу, модулі з найбільшою кількістю дірок, точки входу без флоу й налаштування, які задають поведінку через дані.

Буває, що один зі знайдених флоу — саме той сценарій, про який питає новачок. Тоді `npx keylang flows adopt <назва>` пропонує його як `keylang/flows/<назва>.md`, а ви приймаєте пропозицію командою `npx keylang proposals accept keylang/flows/<назва>.md`. Відтоді `check` перевіряє його так само, як флоу, написаний вами.

Правте `keylang.json` лише там, де `init` не вгадав. Одна деталь: теку з назвою `external` буде перейменовано на `external_`, бо це слово зарезервоване. Нову назву init покаже під час запуску.

Тепер запишіть у `keylang/rules.md` правила, які ви справді маєте на увазі. Baseline лишається окремим файлом. Для початку вистачить двох-трьох рядків:

```markdown
# rules

- layers domain < application < presentation
  - infrastructure
- deny domain infrastructure
- deny domain external
```

`infrastructure` стоїть поруч із ланцюгом, а не під `domain`. У ланцюгу внутрішній шар стоїть ліворуч від `<`. Два рядки `deny` кажуть, що domain не може імпортувати ні базу, ні пакет. Залежність із бічного шару в ланцюг дає K101, доки ви її не запишете. Якщо сховище зберігає об'єкти домену, додайте `- allow infrastructure domain` і одним реченням поясніть чому.

`keylang check` нічого не записує. Код виходу 0 означає, що блокувальних знахідок немає; рядки, які ще мають статус `unverified`, при цьому проходять. Код 1 означає справжній злам, а для `map --check` — застарілу карту.

У CI запускайте обидві команди: перша ловить порушені правила, друга — застарілу карту.

```sh
npx keylang check
npx keylang map --check
```

## Чужий репозиторій

Щоб познайомитися з репозиторієм до роботи в ньому, не треба самому його клонувати чи щось у нього записувати. `keylang clone` робить неглибокий клон у кеші keylang (`~/.cache/keylang/repos/<host>/<шлях>`), запускає там `init` без файлів для агентів і будує карту:

```sh
npx keylang clone https://github.com/owner/repo
npx keylang clone https://github.com/owner/repo --explain map-and-ai --dry-run
npx keylang clone https://github.com/owner/repo --explain map-and-ai
npx keylang web https://github.com/owner/repo
```

Перший рядок виводу каже, де лежить клон. Його `keylang/map` відкривайте так само, як свою. Щоб забрати нові коміти, запустіть ту саму команду ще раз. З `--explain map-and-ai` keylang ще й просить модель коротко описати кожен вузол і пише `keylang/map-explained/`, а `--explain all` додає докладне пояснення кожного шару. Обом варіантам потрібна модель, задана в середовищі, наприклад `KEYLANG_AGENT=cli:claude`, бо `keylang.json` клону належить keylang. `--dry-run` лише друкує оцінку токенів і нічого не питає. `web` з URL робить клон і відкриває для нього інтерфейс у браузері.

У клоні `keylang flows discover` і `keylang tour` працюють так само, як описано вище, і це найшвидший спосіб розібратися в коді.

Якщо вам була потрібна лише огорожа навколо коду, на цьому можна зупинитися. Наступна частина про зміну, якої в коді ще немає.
