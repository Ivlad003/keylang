# 2. Нова фіча

[Додавання до кодової бази](README.md) · [English](../02-a-feature.md) · **Українською**

Крамниця вже вміє оформлювати покупку, а повертати замовлення ще не вміє. Специфікацію повернення ви пишете раніше, ніж з'явиться хоч одна функція. Саму функцію ви й тут не пишете: її згенерує агент із цього файла.

Створіть `keylang/features/refund.md`. Ім'я файла — це slug фічі, тож тут slug — `refund`.

```markdown
# flow refund

Покупець повертає замовлення. Правила замовлення збирають повернення. Екран не говорить з базою.

- planned fn application.purchase.refund (order: Order) → Refund
- trigger presentation.terminal.refund
  - step application.purchase.refund
    - test tests/refund.test.ts "refunds a paid order"
    - step domain.orderAggregate.refund
```

Беріть id зі своєї карти. У карті крамниці вже є `application.purchase`, `presentation.terminal` і `domain.orderAggregate`, і вони посилаються на `src/app/purchase.ts`, `src/ui/terminal.ts` і `src/domain/order.ts`. Самих файлів коду в прикладі немає. Зверніть увагу, що `order.ts` не називається `orderAggregate`: з імені файла id не завжди вгадаєш. У справжньому репозиторії копіюйте id точно так, як його друкує карта.

`planned fn` фіксує намір: функцію чекають, але її ще не написано. Тому посилання на неї не вважається помилкою, а крок, який її використовує, лишається `unverified`, доки функція не з'явиться. Рядок `test` називає тест, що підтвердить крок: файл і назву тесту.

```sh
npx keylang feature refund
```

Коли команда завершується з кодом 0 і друкує `done` у stderr, справджуються три речі. По-перше, кожен рядок `planned` у цьому файлі збігається з кодом, і keylang повідомляє про це попередженням K202. По-друге, кожен крок має статичний шлях виклику (`ok`). По-третє, від цієї зміни не лишилося жодного fail: ні на файлі, зміненому в цій гілці, ні на id, який називає фіча. Без git не має бути жодного fail узагалі, включно з baseline. Fail, що існував ще до гілки, keylang натомість називає в рядку `hint:`. Тести і trace теж друкуються, але на готовність фічі не впливають.

Доти stdout перелічує прогалини, а код виходу дорівнює 1. Відсутня функція показується як `planned`. Функція, що існує, але має інший вид або іншу сигнатуру, дає K201. Пробіли в сигнатурі значення не мають, а `->` означає те саме, що `→`.

Заготовку можна отримати командою. Перша команда нижче друкує заготовку запланованої функції та падаючий тест для кожного рядка `test`, чийого файла ще немає. Усе це вона лишає пропозиціями в `.keylang/proposals/`, а зливаєте їх ви. Друга, з `--apply`, записує файли одразу (`--print` нічого не записує):

```sh
npx keylang spec-to-code application.purchase.refund
npx keylang spec-to-code application.purchase.refund --apply
```

Команда будує заготовку лише з `planned fn`. Запланований модуль — це файл, який створює агент, і ця команда його не створить. Заготовка може бути на TypeScript, JavaScript, Python, Rust або PHP. Для TypeScript і JavaScript тест виходить файлом `node:test`, для PHP — класом PHPUnit. Для Python і Rust команда тесту не пише: його напише агент із тієї самої специфікації. Id, який уже існує, команда відхиляє.

Щойно з'являється K202, `feature` вже може сказати done. Тоді видаліть рядок `planned`, і попередження зникне.

Агентові ви віддаєте саме файл специфікації. Функції генерує агент, а keylang його не запускає. Поки агент працює, `check --changed` зупиняє його хід лише у двох випадках: з'явився новий fail або специфікацію послаблено від останнього коміту. Послаблення — це K108: прибраний `deny` чи крок, новий `allow`, ширший `exclude` у `keylang.json`. Пропустити послаблення може лише людина, з `--accept-weakening`. Рядок `unverified` хід не зупиняє, тож такі рядки переглядайте самі. Якщо треба змінити `rules.md`, зміна має прийти пропозицією в `.keylang/proposals/`, а ви вирішуєте, зливати її чи ні.

Буває, що фіча вже є в старому стеку: в іншому репозиторії, можливо, іншою мовою. Тоді перенесіть її потоки, а не набирайте їх заново. У старому репозиторії `npx keylang flow export checkout --out checkout.bundle.md` пише один Markdown-файл. У ньому є потоки, кожен id з видом, сигнатурою, документацією й `файл:рядок`, тести, події, інтеграції та походження: репозиторій, коміт, знімок. У цьому репозиторії `npx keylang flow import checkout.bundle.md --layer-map app=application` пропонує два файли. Перший — `keylang/features/checkout.md` з тими самими кроками на `planned`-id у ваших шарах, з оригінальними сигнатурами й тестами. Другий — рядки `keylang/migration.md`, які зіставляють кожен старий id з новим. Прийміть обидві пропозиції через `keylang proposals accept`, і `feature checkout` та `spec-to-code` працюватимуть із файлом так само, як із написаним вручну. Після цього `npx keylang migration status --from ../old-repo` показує паритет: кожен старий потік поруч із його відповідником тут зі статусом `ok`, `fail` чи `unverified`, а також те, що ще не перенесено.

Те саме можна зробити з діаграм, просто скопіювавши флоу. Відкрийте `keylang web` старого репозиторію, знайдіть флоу на карті й натисніть «Копіювати як пакет» (або `Ctrl+C` на виділенні в редакторі). У буфері обміну опиниться той самий пакет звичайним текстом, а фігури та їхні місця будуть у блоці `keylang-layout`. Вставте його через `Ctrl+V` у редакторі `keylang web` цього репозиторію, тобто на іншому порту, в іншій вкладці. Відкриється діалог, що зіставляє старі шари з вашими. Він заповнений за назвами, кнопка «запитати модель» звертається до налаштованої моделі, а остаточне рішення за вами. «Імпортувати» запише ті самі дві пропозиції, що й `flow import`, і намалює флоу на полотні `planned`-фігурами у ваших доріжках. Злийте пропозиції, і в агентів буде фіча для реалізації. Вставлений текст keylang вважає лише даними: нічого з нього не виконується, а модель бачить його з позначкою «недовірений».
