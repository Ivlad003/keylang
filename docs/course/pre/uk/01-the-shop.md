# 1. Крамниця

[Підготовчий курс](README.md) · [English](../01-the-shop.md) · **Українською**

Уявіть маленьку програму, яка продає речі. Людина набирає кошик. Програма збирає замовлення, рахує гроші, зберігає замовлення і друкує чек.

Першого дня це один файл. Він працює. Потім файл росте. Міняєте чек — ламається сума. Міняєте, як зберігається замовлення — ламається чек. Нова людина питає: «де правило ціни?» Чесна відповідь: «десь посередині того файла».

Ліки — не новий фреймворк. Розділіть програму за **роботою**. Кожну роботу скажіть одним реченням.

## Чотири роботи

Крамниця має чотири групи. Назви — звичайні слова. keylang цих назв не вимагає. Цей репозиторій, сам інструмент, має інші назви (`base`, `lang`, `check`, …), бо його роботи інші.

| Група | Одне речення | У прикладі |
|---|---|---|
| `presentation` | Те, чого торкається людина або інша програма | Екран термінала і HTTP API |
| `application` | Завдання, яке виконує крамниця | `purchase`: купити кошик, скасувати замовлення |
| `domain` | Правила замовлення, правдиві навіть на папері | `orderAggregate`: створити замовлення, порахувати суму |
| `infrastructure` | Зовнішній світ: диск, мережа, процес, лог | Товари, сховище замовлень, конфіг, логер, сервер |

Тримайте ці чотири речення. Решта мови — спосіб їх записати і перевірити, що код їх досі слухає.

Fowler зупиняється на трьох шарах. Причина розрізу в Cockburn: програма має працювати без екрана і без бази. Четверта назва крамниці, `application`, — завдання між ними. Посилання — у [частині 4](04-reading.md).

> One of the most common ways to modularize an information-rich program is to separate it into three broad layers: presentation (UI), domain logic (aka business logic), and data access. […] It's biggest advantage (for me) is that it allows me to reduce the scope of my attention by allowing me to think about the three topics relatively independently.
>
> — Martin Fowler, [Presentation Domain Data Layering](https://martinfowler.com/bliki/PresentationDomainDataLayering.html), 26 серпня 2015

Переклад: один із найзвичніших способів поділити програму з багатьма даними — три широкі шари: подання (інтерфейс), логіка предметної області і доступ до даних. Для мене найбільша вигода — думати про ці три теми майже окремо.

> Create your application to work without either a UI or a database so you can run automated regression-tests against the application, work when the database becomes unavailable, and link applications together without any user involvement.
>
> — Alistair Cockburn, [Hexagonal architecture](https://alistair.cockburn.us/hexagonal-architecture/), стаття 2005 року

Переклад: зробіть застосунок так, щоб він працював без інтерфейсу і без бази. Тоді можна ганяти регресійні тести, пережити недоступну базу і з'єднувати застосунки без участі людини.

Така група — це **шар**. Шар — названа купа коду з однією роботою. Тека стає шаром, лише коли роботу можна сказати. «Утиліти» зазвичай не робота. «Правила замовлення, правдиві навіть на папері» — робота.

Усередині шару те, на що можна показати пальцем, — **модуль**. У крамниці `purchase` — модуль у `application`. Усередині модуля названа дія — **функція**. `buy` — функція. Названа форма даних, як помилка `OutOfStock`, — **тип**. Тут це слово означає «названий вид значення, який оголошує цей модуль».

## Потреба має напрям

`purchase.buy` сам замовлення не збере. Він просить `orderAggregate` створити його, список товарів — знайти позицію, сховище — зберегти результат.

Скажіть це з напрямом:

> `application.purchase` **потребує** `domain.orderAggregate`.

Протилежне речення — інше рішення:

> `domain.orderAggregate` **потребує** `application.purchase`.

Друге речення болить. Правила замовлення тоді знали б про завдання, яке ними користується. Правило ціни не прочитати без «купити». Екран і база можуть знати про замовлення. Замовлення не знає про екран і базу.

Ця спрямована потреба — **залежність**. Архітектура, яку вміє виразити ця мова, — список таких речень плюс сценарії, які ви не хочете лишати безіменними.

## Перша поломка — хибне ім'я

У прикладі крамниці помилка навмисна. Під `purchase` залежність записана як `domain.aggregate`. Модуль, який є, — `domain.orderAggregate`. `aggregate` немає.

Документ, який називає код, стверджує, що ім'я існує. Хибне ім'я — зламане твердження. keylang називає ім'я **id**: шлях через крапки, шар, потім модуль, потім функція.

```text
application . purchase . buy
шар           модуль      функція
```

`domain.aggregate` ні на що не вказує. `domain.orderAggregate` вказує на модуль. Урок 2 основного курсу показує команду, яка це друкує. Команда поки не потрібна. Коли пишете ім'я цією мовою, ви вказуєте, а не прикрашаєте. Ім'я ваше. Функцію за ним пише агент. Ви — ні.
