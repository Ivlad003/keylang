# keylang — глибоке рев'ю 2026-10-05: код, рішення, DX для coding agents

Дата: 2026-10-05. Охоплення: увесь код на коміті `2f01c9a` (0.5.0), дизайн і ADR 0001–0015, `docs/format.md`, `docs/tools.md`, `llm.txt`, skill і блок `AGENTS.md`, пакування. Метод: ведучий (ядро мови, правила й потоки, CLI, MCP, харнес, продуктивність, наскрізні сценарії агента) плюс чотири рецензенти по зонах (TUI і web; операції та модель; екстрактор, граф і карта; LSP, докази й адаптери). Кожну знахідку відтворено на копії у тимчасовому каталозі або скриптом: **✔** — відтворив ведучий, **✔р** — відтворив рецензент зони скриптом, **гіпотеза** — лише за кодом. Репозиторій не змінювався, крім цього файла.

Базовий стан: `npm run typecheck` — 0. `npm test` — 738 тестів, 733 pass, 1 fail, 4 skip, ~15 хв під навантаженням. Єдиний fail (`generated maps of the repo and the fixture parse`) не є дефектом коду: паралельна сесія переписувала `README.md` і `docs/course/*` під час прогону, карта з поясненнями бере brief репозиторію з README, тож `map --check` став `stale`. `keylang check` на самому keylang — `0 fail, 0 unverified, 71 ok`.

Рівні як у рев'ю 2026-09-28: **P1** — хибний `ok`/`fail` основної перевірки, запис поза дозволеними цілями, падіння на валідному вводі; **P2** — хибний результат окремого правила чи команди, розбіжність із контрактом або документацією; **P3** — якість, шум, продуктивність, документація.

Наскрізні сценарії, на яких перевірено DX (усі в тимчасових копіях): свіжий TS-репозиторій з чотирма шарами (`init` → `feature` → `spec-to-code --print` → реалізація → `done` → заборонений імпорт → `check --changed` → `hook stop`); NestJS-подібний код з декораторами; Python-пакет із підпакетами; `bench/repos/health-tracker` (74 файли, Python + TS); MCP-сервер, яким керував скрипт-клієнт з усіма 11 інструментами; `node:test`-репортер і trace-адаптер; граматичні крайні випадки для `parse` і `fmt`.

## Головне

1. **P1. Хибні ребра графа дають хибний `ok` у `deny` і хибний `static ok`.** П'ять незалежних причин, усі відтворені фікстурами (розділ «Аналізатор»): у `module: "dir"` і при злитті `x.ts` + `x/index.ts` локальні імена одного файла протікають в інший (однойменні приватні fn зливаються, неімпортований глобал резолвиться в сусідній файл); `import * as ns` при виклику `ns()` рахується `default`-експортом; затінення не бачить `for`/`if let`/`match` у Rust, `match … case` і `:=` у Python, `const` у гілці `switch` у TS. Контракт §4.2 («`fail` надійний, за сумніву — `unverified`») тут порушено у бік хибного `ok`.
2. **P1. `fmt` — єдиний writer поза спільним протоколом запису:** пише через symlink за межі репозиторію і переписує файли з маркером `keylang:generated`. ✔
3. **P1. `apply_diff` приймає `keylang/explain/<id>.md` і `keylang/explain/brief/<id>.md`** — збережені пояснення моделі, які `tools.md` називає «не специфікаціями». Харнес може підкинути пропозицію з довільним заголовком `closure=`, і після merge brief стане «свіжим» на карті з поясненнями. ✔
4. **P2. `hook stop` без git або з не-JSON на stdin завершується кодом 2 без JSON.** `llm.txt` обіцяє «prints JSON and exits 0 either way», `tools.md` каже «без git — код 2». Для Claude Code код 2 хука Stop — блокувальна помилка: хід блокується один раз із повідомленням про git. ✔
5. **P2. `init` не додає `.keylang/` у `.gitignore`**, хоч `llm.txt` стверджує, що індекс, пропозиції й trace «gitignored». Агент, що робить `git add -A`, комітить `index.json`, `cache/facts.json` (мегабайти) і пропозиції. ✔
6. **P2. `dir` у `keylang.json` налаштовується, а харнес цього не знає:** із `"dir": "spec"` baseline і `new flow` ідуть у `spec/`, але `.claude/settings.json` забороняє `Edit(keylang/rules.md)`, а блок `AGENTS.md` і skill велять писати `keylang/features/<slug>.md`. ✔
7. **P2. Кеш фактів пишуть лише `map` та `init`**; `check`, `feature`, `hook stop` і MCP лише читають. Після будь-якої зміни коду хук Stop парсить усе tree-sitter-ом щоходу: на keylang `check` без кешу 5.5 с проти 1.4 с із кешем. ✔
8. **P2 (DX). Пропозиції зливаються лише клавішею `m` у TUI.** Немає `keylang proposals list|accept|reject`, тож у headless-сценаріях (Claude Code web, CI, SSH без TTY, суто агентний цикл) зміну правил неможливо прийняти. ✔
9. **P2 (DX). `feature` блокує готовність будь-яким `fail` правила в репозиторії**, навіть не пов'язаним із фічею. На brownfield-репозиторії з одним успадкованим порушенням жодна фіча не стає `done`. ✔
10. **P2. TUI: режим Browse пише `.keylang/stats.json`** всупереч обіцянці «нічого не пише»; `track()` перетворює відхилений проміс на unhandled rejection — термінальна сесія завершується кодом 2, а `keylang web` падає цілком; дві різні клавіші в одному чанку поза редагуванням відкидаються як «paste». ✔р
11. **P2. Порядок модулів у карті — `localeCompare("en")`** (ICU), тоді як індекс сортує за code units: байтовий порядок карти залежить від ICU збірки Node, і `map --check` у CI на іншому Node може впасти. ✔р
12. **P2. Канал trace працює надійно лише в однопроцесному запуску самого keylang.** Завантаження квадратичне (80 К spans — 64 с), `fail` будь-якого запуску перекриває `ok` іншого (юніт-тест, що дійшов до одного кроку, ламає тригер e2e), `.cjs` на Node 24 не інструментується, а перетин `instrumented` між процесами знищує докази відсутності. ✔р
13. **P2. Звіти JUnit від pytest, jest і PHPUnit ніколи не зіставляються:** `file` має дослівно збігатися з `test <file>`, а ці раннери пишуть абсолютний шлях або не пишуть його взагалі. ✔р
14. **P3. Пакет тягне голос за замовчуванням:** `optionalDependencies` ставлять `@fugood/whisper.node` з CUDA- і Vulkan-збірками — 266 МБ на диску після `npm i keylang` на Linux x64; `@anthropic-ai/sdk` — ще 14 МБ; `@vscode/tree-sitter-wasm` (22 МБ) лишається прод-залежністю, хоч `treesitter.ts` читає граматики з `dist/wasm`. ✔

Решта знахідок — у розділах нижче; план дій — у «Що покращити для агентів» і «Що спростити».

## Правила, потоки, докази, готовність фічі

| # | Рівень | Знахідка |
|---|---|---|
| 1 | P2 | `feature` рахує готовність за всіма `fail` правил у репозиторії: заборонений імпорт `domain → infra`, не пов'язаний із фічею `refund`, дає прогалину `rule` і `1 gap(s) · stage ready`. Механізм `--changed` уже вміє звужувати звіт до зачеплених модулів, але `feature` його не використовує. ✔ |
| 2 | P2 | `llm.txt` (рядок 177) каже, що крок «під декоратором, якого keylang не знає (`@app.post`, `@Controller`, `@Get`, `@Injectable`)» лишається `unverified`. Для TS це неправда: екстрактор не записує декораторів як дірок (`extract/ts.ts` згадує їх лише для doc-коментарів), NestJS-контролер із `@Get()` дає `static ok` з нульовим покриттям дірок. Для Python декорована fn як **тригер** теж дає `static ok` (`@router.post` у health-tracker); `unverified` «may not run its own body» вона дає лише як **ціль кроку**. У `format.md` §11 немає підрозділу **TypeScript**, тож політика щодо декораторів TS ніде не записана. ✔ |
| 3 | P3 | Одна дірка роздуває `unverified`: нерозв'язаний імпорт у `health-tracker` дає два рядки `unverified` (на кожен `deny` baseline, чия область містить файл); у NestJS-копії з проби 2 імпорти дали 8 рядків. Підсумок `N fail, M unverified` не каже, скільки різних причин. ✔ |
| 4 | P3 | Немає способу заявити «цей імпорт свідомо відсутній»: gitignored `src/config.ts` → `unresolved import` → `unverified` у baseline; `outside` на присутній файл → K107 у кожного імпортера; `exclude` → файл в `unassigned` → K102 від baseline. У CI (файла немає) і локально (файл є) вердикти різні. ✔ |
| 5 | P3 | Повідомлення `static fail` після `spec-to-code`: «absence: no call path from ui.cli.main; `app.purchase.refund` and its callers are called only by name, and no call from ui.cli.main's reachable code can reach them» — правильне, але не каже агенту, що робити (додати виклик із тригера або з того, кого тригер досягає). ✔ |
| 6 | P3 | `dependencyHoleIn` (`rules.ts:~201`) — лінійний `coverage.find` на кожен модуль кожного правила: O(правил × модулів × записів покриття); у профілі `check` — 89 мс `rules.ts` на 71 вердикт. ✔ |
| 7 | P3 | `check` будує індекс ID через рендер знімка в Markdown і повторний розбір цього Markdown (`analyze.ts`: `map.files → parse`): `parser.ts` 236 мс + `emit.ts` 90 мс з 1 470 мс теплого `check`. Індекс можна будувати зі знімка напряму. ✔ |

Перевірено й без зауважень: K102 і K107 дають код 1; `check --changed` лишає лише зачеплене; прогноз `deny`-прогалини у `feature` з точною підказкою (`a person adds - allow domain infra …`); `planned module external.stripe` відомий з `package.json` ще до імпорту; K202 після реалізації й `done` після видалення `planned`; `check --format json|github` чистий; `feature --format json` лише JSON у stdout.

## DX для coding agents: що працює, що заважає

Сильні сторони циклу, підтверджені наскрізними сценаріями: детермінований знімок і три значення вердикту; `init` за 2–3 с дає карту, baseline, MCP, skill, deny і хук; `feature` зі стадіями `idea → behavior → structure → ready → done` і прогалинами з позиціями; прогноз `deny` до реалізації з готовим рядком `allow`; `validate_spec` і `scaffold` без запису; `planned module external.<pkg>` з `package.json`; `check --changed` і хук, що блокує лише нові порушення; MCP-відповіді за мілісекунди; NestJS DI через параметр-властивості резолвиться без налаштувань; FastAPI-маршрут як тригер дає `static ok`.

Що заважає агенту (і людині поруч), у порядку ваги:

1. **Цикл не замикається без TTY.** Правила змінюються лише пропозицією, а пропозицію приймає лише людина в TUI (`m`). Claude Code web, CI-агент, pair-сесія по SSH без TTY — усі впираються. Потрібна команда `keylang proposals list|show|diff|accept|reject <path>` з тим самим протоколом запису (atomic + `expect`), і згадка про неї у skill.
2. **Хід агента платить за повний аналіз.** Хук Stop = `npx` + повний парсинг без кешу після кожної правки коду. Персистити кеш фактів з усіх команд, що будують знімок (це кеш, запис безпечний), і додати швидкий шлях за mtime+size у `currentAnalysis`/хуку. У `.claude/settings.json` можна віддавати перевагу локальному `node_modules/.bin/keylang`, якщо він є, а `npx` лишати запасним.
3. **`done` недосяжний без причини.** `feature` має звужувати `rule`-прогалини до правил, чия область містить ID фічі або змінені файли (як `--changed`), або принаймні показувати їх окремо як `inherited`. K201 має трактувати план без типу результату як префікс контракту. Повідомлення `static fail` має називати дію («add a call from `ui.cli.main`, or from a function it reaches, to `app.purchase.refund`»).
4. **Інструкції без граматики.** У блок `AGENTS.md` (є ще 2.8 КіБ бюджету) треба додати: 6–8 рядків прикладу фічі (`# flow`, `planned fn … (sig) → T`, `trigger`, `step`), звідки брати ID (`keylang/map/*.md`, MCP `search`), що після перейменування файла ID змінюється і треба `keylang map`. Паралельно — англійська сторінка-шпаргалка граматики (EBNF із Додатку А вже є, бракує таблиці позицій і 10 прикладів), на яку посилається `llm.txt` замість 187 КБ українського `format.md`.
5. **Шум `unverified`.** Групувати підсумок за причинами («2 holes → 4 unverified lines»), друкувати дірку один раз із переліком зачеплених правил; дати конфігу спосіб заявити відомо відсутній або gitignored імпорт (`"assume": ["src/config.ts"]`), щоб він не був ні діркою, ні K107.
6. **Довіра до дрібниць.** `.gitignore`, `dir`, коди виходу хука, узгодженість трьох документів — усе це те, на чому агент «обпікається» на першій хвилині і далі ігнорує інструмент.
7. **Recall викликів для TS.** На самому keylang 7 014 `dynamic` проти 4 026 `resolved` викликів: кожен метод через значення — дірка. Для TypeScript є дешевий шлях підняти recall у рази — опційний backend на `typescript` (вже в devDependencies; як peer/optional, завантажується лише коли встановлений): типи отримувачів для `x.m()`, `import type` як не-runtime ребро, `export type *`. Це єдиний спосіб зняти «втому від `◌`» (design §10.7) без переписування коду під аналізатор.
8. **Докази тестів і trace важко підключити поза keylang.** Репортер `node:test` працює з однієї команди, але JUnit від pytest/jest/PHPUnit не зіставляється (п. 13 «Головного»), trace-адаптер TS/JS потребує трьох змінних середовища на тест і валить файл без них, а між запусками `fail` перекриває `ok`. Поки це так, `feature` правильно не рахує тести й trace; але README показує саме trace як головну демонстрацію (`✗ 0 ◌ 0 ✓ 34`). Варто або довести канал до «одна команда — один звіт» для трьох популярних раннерів, або чесно позначити trace експериментальним.

## Що спростити

Варіанти з наслідками, не рішення:

1. **Відокремити голос і вбудовану модель від ядра.** Варіант A: `keylang-voice` як окремий пакет (whisper + decibri), `keylang` без `optionalDependencies` — встановлення легшає на ~270 МБ, `doctor` підказує пакет. Варіант B: лишити, але перенести в `peerDependenciesMeta` optional і ставити за запитом. `@anthropic-ai/sdk` замінити на `fetch` (OpenRouter уже так працює) — мінус 14 МБ і одна залежність ланцюга постачання.
2. **Переглянути, що з «агента всередині keylang» справді потрібне поряд із харнесом.** ADR 0005 каже: код пише харнес, keylang — специфікація й перевірка; ADR 0012 додає харнес як текстову модель. Ghost-текст, `Ctrl+Space`, `Ctrl+G`, голос, `draft --mode llm`, `explain --llm`, `spec-to-code --mode llm` — це другий агентний контур, який дублює харнес і тягне `operations.ts` (4 439 рядків, 27 видів), `tui/app.ts` (5 929), 21 форму TUI і 10 472 рядки `tests/tui.test.ts`. Варіант: заморозити цей контур (не розвивати, не описувати в курсі), лишивши детерміновані `draft --mode algo`, `scaffold`, `explain` офлайн і brief-и як опційну команду. Виграш — менша площа коду й документації для людини, що супроводжує проєкт сама; ризик — втрата сценарію «людина в TUI без харнеса», який заявлено в design §7.3.
3. **Розбити god-модулі за наявними швами.** `operations.ts` → `operations/{types,generate,explain,draft,code,doctor}.ts` з `runOperation` як фасадом (26 фабрик `emptyX()` і `resultWithout` на 26 гілок замінюються одним generic); `tui/app.ts` → редактор, контролер зуму, панель F6, сесія операцій, форми як дані (один `Form`-дескриптор замість 21 × `open/refresh/change/submit`, мінус ~1 500 рядків); `buildGraph` (650 рядків, 8 замикань `scopeOf`) → `FileScope` + `CallResolver`, що водночас закриває знахідки «Аналізатор» 1 і 5.
4. **Документація.** `format.md` розрізати на `grammar.md` (Додаток А + таблиці позицій), `semantics.md` (правила, потоки, докази) і `snapshot.md` (§11 за мовами з підрозділом TypeScript); розділ TUI винести з `tools.md`; старі рев'ю й дослідження — в `docs/archive/`; один англійський довідник для агентів. Кожне твердження `llm.txt` має мати тест (три з них уже розійшлися з кодом).
5. **Тести.** 15 хвилин на прогін — ціна `--test-concurrency=1` і одного файла на 10 К рядків. Варіант: паралельність за файлами з ізольованими тимчасовими каталогами й портом 0 для web, `tui.test.ts` розрізати за екранами, важкі e2e позначити `--test-name-pattern` для швидкого циклу.
6. **Один обхід дерева й одна компіляція глобів.** `loadConfig` компілює матчери один раз; `sourceTree`/`excludedSourceFiles`/`outsideSourceFiles` стають однією класифікацією; індекс ID будується зі знімка без Markdown-roundtrip; `coverage` індексується за файлом і модулем. Разом це ~400 мс із 1 470 мс теплого `check` і кратне прискорення на монорепозиторіях.

## Що зроблено добре

- Семантика перевірки чесна: кожен виклик — ребро або дірка з причиною й позицією; `unverified` ніколи не стає `ok`; `fail` правил вимагає підтвердженого ребра. Хибні ребра з розділу «Аналізатор» знайшлися лише на свідомо незвичних фікстурах.
- Один протокол запису (`safe-write.ts`: тимчасовий файл + rename, межа symlink-переходів, `expect`, маркер generated) і одна форма операцій (обчислити → `beforeCommit` → перевірити входи → атомарні кроки) — через них проходять карта, baseline, харнес, wire, пояснення, пропозиції. Винятки (`fmt`, `init` для конфігу) тепер відомі.
- Знімок детермінований: `snapshotId` від вмісту джерел, конфігу й версій, без часу; кеш фактів ключується хешем власного коду екстрактора.
- `rules.md` keylang справді тримає ядро мови й перевірку без tree-sitter (`deny lang extract`, `deny check external.web-tree-sitter` — `ok`), і це видно в коді: `spec-ir.ts`, `rules.ts`, `flows.ts` працюють з даними.
- Агентний контур добре продуманий там, де він є: baseline як нижчий шар правил (ADR 0013), прогноз `deny` до коду, стадії фічі, `validate_spec`/`scaffold` без запису, пінована версія в MCP і хуку, перевірка `agents --check`.
- TUI тестується без TTY через чистий `render(State) → Grid`; воркери операцій settle-ять рівно раз; термінал відновлюється на кожному шляху виходу; `web` тримає токен поза URL і перевіряє Host/Origin.
- Повідомлення діагностик і прогалин майже всюди називають дію: `did you mean`, `declare planned`, `run keylang baseline`, `a person adds - allow …`.

### Що зробити після злиття

- `npm install`: прибирає голосові пакети зі старих `optionalDependencies`.
- `npm test` ще раз: `snapshotId` змінився один раз (справжня версія `web-tree-sitter`, `assume`, `m1.11`), тож старі звіти тестів і trace — `stale`.
- `README.md` і `README.uk.md` (рядок про тести TUI) досі називають `tests/tui.test.ts`, а його вже розрізано на `tests/tui-*.test.ts`. README у робочому дереві `master` переписує інша сесія, тож у гілці його не змінено.
- `docs/course/02-install-and-check.md` (en, uk) змінено в гілці на одне речення про голос. Курс у робочому дереві `master` переписує інша сесія, тож при злитті там можливий конфлікт на цьому реченні.
