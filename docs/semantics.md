# Семантика keylang

Частина специфікації формату keylang v0.2 (покажчик — [format.md](format.md)): ID і резолвінг, діагностики, семантика правил, потоків і доказів (тести, trace, стейлнес прози), wiring і версії формату. Синтаксис — у [grammar.md](grammar.md), семантичний знімок коду — у [snapshot.md](snapshot.md). Розділи пронумеровано наскрізно для всіх трьох файлів.

## 6. ID та резолвінг

- ID оголошення — крапковий шлях від кореня: шар → модуль(і) → `fn`/`type`/`event`/аліас залежності. Приклад: `application.purchase.buy`, `presentation.terminal.checkout` (аліас).

```keylang Р12 path=keylang/flows/pay.md
# flow pay
- trigger presentation.terminal.checkout
```

```keylang path=keylang/map.md
  - module terminal

- layer order
  - module place
```

- Посилання всередині файлів завжди абсолютні, крім `exports` (відносно модуля).
- Резолвінг глобальний: `keylang check <dir>` збирає всі `*.md` під директорією (рекурсивно, крім прихованих директорій, `node_modules` і `target`), будує один індекс і перевіряє всі посилання. Символічне посилання на файл чи теку читається як його ціль (цикл посилань обходиться раз), а файл, до якого ведуть два шляхи, — один документ під шляхом без посилання.
- Шари оголошує `keylang.json`, а карта друкує шар, лише коли в ньому є модуль. Тому шар конфігурації без модулів (наприклад, `wiring` до першого `keylang wire`) і синтетичні `external` та `unassigned` — відомі ID: правило може їх назвати без K001 і до того, як у них щось з'явиться.
- Пакет, записаний у `package.json` (`dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`), у `Cargo.toml` крейта (`dependencies`, `dev-dependencies`, `build-dependencies` і ті самі таблиці під `target`) чи в `composer.json` (`require`, `require-dev`; PHP, його розширення `ext-*`, бібліотеки `lib-*` і API composer пакетами не є) у корені або в теці між проаналізованим файлом коду й коренем, відомий як `external.<сегмент>` навіть без імпорту і коли єдиний імпортер виключено: посилання на нього не дає K001, а знімок нового вузла не додає. Маніфести шукаються лише на цих шляхах, жодна тека не обходиться: маніфест у теці без проаналізованого коду або такий, що його збігає `exclude` (як `bench/**`), пакетів не оголошує. `package.json` читається як JSONC (коментарі й кінцеві коми, як у `tsconfig.json`); `Cargo.toml` без `[package]` (кореневий воркспейс) маніфестом крейта не є. `@types/x` рахується як `x`, а `@types/scope__pkg` — як `@scope/pkg`. Діапазон `workspace:`, `file:`, `link:` чи `portal:`, ім'я пакета з тек кореневого `workspaces` чи `packages` файла `pnpm-workspace.yaml` і пакет із `path`-репозиторію кореневого `composer.json` — код цього репозиторію, не external. Пакет composer має ID за повним іменем: `monolog/monolog` — `external.monolog-monolog`. Пакет, який є лише в `node_modules`, відомим не є. Маніфести Python не читаються: назва дистрибутива не збігається з іменем імпорту (`Pillow` імпортується як `PIL`), тож Python-пакет відомий лише з імпорту. Стандартна бібліотека Python (`typing`, `asyncio`, `email`) пакетом не є і вузла `external.*` не має ([snapshot.md](snapshot.md) §11, «Python»); вбудовані модулі Node — навпаки, один вузол `external.node`. Без мов у `keylang.json` (немає коду для аналізу) читаються лише кореневі маніфести, а `check` специфікацій без коду маніфестів не читає. Тексти прочитаних маніфестів входять у `snapshotId`. `planned module external.<pkg>` дає K202 лише коли імпорт уже створив вузол.

Правило пошуку ID:

1. Точний збіг з оголошенням — ok.
2. Інакше береться найдовший оголошений префікс (Р13).

Сусід — ім'я, що містить відсутнє (або навпаки; коротше з двох — від 3 символів), чи близьке за відстанню редагування: до 1 для імен до 5 символів, до 2 для довших, 0 для одно- і двосимвольних. Тож `zz` не підказує `ab`, а `banana` — шар `a`.

**Р13. Без знімка модуль без членів непрозорий** (слайди: `infrastructure.config.log`). Член — це `fn`, `type`, `event`, `module` або аліас залежності: модуль, під яким є лише `- log infra.logger`, має члени, тож `infra.config.anything` — K001, а `infra.config.log` — його аліас. Зі знімком вирішує він: `members: complete` дає K001 на невідомого члена, а `members: opaque` (зовнішній модуль, помилка розбору, файл із `exclude`) — `unverified`, не K001, навіть коли карта перелічує члени, які вдалося прочитати з частково розібраного файла. K001 має підказку `did you mean` і `declare `planned``.

## 7. Діагностики

Формат виводу `keylang check`: `file:line:col: CODE message`, рядок і колонка з 1, колонка в символах Unicode.

| Код | Рівень | Значення |
|---|---|---|
| K001 | error | висяче посилання; у згенерованому файлі підказка — команда генератора з маркера |
| K002 | error | дубльований ID (або ім'я потоку) |
| K003 | error | структура: відступ, таб, порожній елемент |
| K004 | error | ключове слово невідоме або недозволене в цій позиції |
| K005 | error | неправильні аргументи відомого ключового слова, невалідне ID/посилання/лапки |
| K006 | warning | невідомий заголовок секції |
| K008 | warning | `then` з одного слова без крапки збігається з останнім сегментом оголошеного ID і лишається текстом |
| K101 | error | divergence: залежність проти порядку `layers` (вгору або з шару поза порядком) |
| K102 | error | divergence: залежність, заборонена `deny` |
| K103 | warning | absence: модуль недосяжний з жодного `entry` |
| K104 | error | divergence: зайвий публічний експорт або absence — заявлене ім'я, якого модуль не експортує |
| K105 | error | divergence: цикл залежностей там, де оголошено `no-cycles` |
| K106 | warning | непорівнювані `allow` і `deny`: сума глибин `allow` більша, правила на перетині немає |
| K107 | error | divergence: код архітектури (модуль шару чи `unassigned`) залежить від файла, який `outside` у `keylang.json` виводить поза архітектуру |
| K201 | error | `planned` розходиться з реалізованим символом: інший вид або сигнатура |
| K202 | warning | `planned` реалізовано з тим самим видом і сигнатурою — декларацію можна прибрати |
| K203 | warning | `test` у потоці називає файл, якого немає в репозиторії (з `check.tests` чи без нього) |
| K301 | error | цикл між фабриками `wire`: одна з них отримала б ще не побудовану залежність |
| K302 | error | ціль `wire`, залежність чи `compose`, яку згенерований файл не збудує: не fn, не статичний метод і не клас (модуль, шар, тип; для `compose` — не fn чи статичний метод), метод екземпляра, неекспортоване ім'я, код не TS/JS |

K005 у `check --format json` і в `diagnostics` `parse --json` має поле `reason`. Інші коди цього поля не мають. Human-вивід і `--format github` його не друкують.

| `reason` | Коли |
|---|---|
| `arguments` | бракує аргументів, зайві чи не ті; форма рядка; умова wiring не `env.NAME = value` |
| `id` | токен не є ID чи ім'ям, зокрема ім'я секції |
| `link` | зламаний лінк |
| `quote` | незакрита лапка |
| `layer` | не шар, шар двічі, суперечність порядків, шар і в порядку, і вкладений |
| `scope` | fn, type, event чи аліас залежності в `allow` / `deny` |

**Вердикти.** Кожен результат перевірки — `ok` (критерій підтверджено в заявленій області), `fail` (підтверджене порушення; діагностика рівня error або вердикт `fail`) або `unverified` (порушення немає, але доказів бракує; причина друкується). Діагностика рівня warning (K006, K008, K103, K106, K202, K203) у `--format json` має вердикт `warning` і не валить перевірку. Вердиктом `fail` вона не буває, тож CLI, JSON, LSP і TUI рахують її однаково; критерій і область такої діагностики правила вона несе сама (K103 — `entry` і модуль, K106 — текст `allow` і перетин областей). У повідомленнях: **divergence** — підтверджена невідповідність, **absence** — відсутність обов'язкової сутності за достатніх доказів, **convergence** — підтверджений збіг (повідомлення `ok`-вердикту правила, наприклад `convergence: no edge from …`); невизначеність ніколи не перейменовується на `ok`. Менше інформації (`exclude`, нерозв'язаний імпорт, режим `shape` — прапорець `--static` або поле `check.static`) переводить `ok` або `fail` лише в `unverified`, ніколи між `ok` і `fail` (предикати `hole` і `area` в «Семантика правил»). K103 остаточний нарівні з `ok` і `fail`: він не стає іншим вердиктом. Задокументований виняток один: маніфест Python не читається, тож пакет, відомий лише з імпорту, після `exclude` цього імпорту може дати K001. `warning` у JSON — не четвертий вердикт, а рівень діагностики: результат не валить перевірку. Кожен вердикт має `specHash` — SHA-256 канонічного тексту рядка правила чи потоку: усі результати одного рядка (`ok`, `unverified`, K102, K104, K105) ділять цей хеш. Результат із кількох рядків хешує їхні тексти в порядку (файл, рядок), з'єднані `\n`: K101 — рядки `layers` зв'язного порядку; K103 і `unverified` досяжності — усі рядки `entry`; «no snapshot» — усі рядки правил. Один рядок дає той самий хеш, що й текст цього рядка. Посилання, записане лінком, хеш не змінює. Діагностика без вердикту (K001, K003, K201…) і далі хешує код і повідомлення. K102 називає і ребро в коді, і правило `deny` з його файлом і рядком.

Команди CLI, MCP, LSP, TUI і web описано в [cli.md](cli.md#commands).

**Правила (K101–K105, K107)** рахуються на ребрах актуального знімка. `keylang check` перебудовує аналіз у пам'яті і не записує карту чи `.keylang/index.json`. Згенеровані файли `map/` замінюються картою, відрендереною з цього знімка, тож ID у flows і rules резолвляться за поточним кодом, навіть якщо закомічена карта застаріла. Корінь репозиторію — найближчий вгору каталог із `keylang.json`; шлях до специфікацій можна записати як завгодно (`keylang`, `./keylang`, абсолютний, `.` зсередини). Діагностика вказує на файл і рядок коду, де є ребро. Якщо в каталозі немає коду (examples, слайд), правила дають `unverified` з причиною `no snapshot`, а резолвінг ID лишається. Цей вердикт один на всі рядки правил і стоїть на першому з них у порядку (файл, рядок, колонка), а не на першому файлі; `specHash` — хеш усіх рядків правил (див. «Вердикти»). Підсумок у stderr: `N fail, M unverified, K ok`. `unverified` правила через дірку покриття несе в `--format json` поле `hole` — `file:line:col` цього запису `coverage` ([cli.md](cli.md#formats)). Одна дірка лишає `unverified` кожне правило, в області якого вона є, тож коли дві чи більше `unverified` мають ту саму дірку, підсумок каже, зі скількох дірок вони: `0 fail, 8 unverified (from 2 holes), 71 ok`, а коли частина `unverified` дірки не має (потоки, `planned`) — скільки з дірок: `9 unverified (8 from 2 holes)`. Інакше підсумок той самий. Коди виходу: `0` — блокувальних знахідок немає; `1` — порушення, а з `--strict` також будь-який `unverified`; `2` — некоректний виклик або I/O.

Формати виводу `check` і `--explain-edge` описано в [cli.md](cli.md#formats).

Уточнення:

- **Вгадані шари.** Без `keylang.json` (`init`, `draft map`, а також `check` і `map` з вгаданим конфігом) корінь джерел — `src/` або `lib/`, якщо є. Інакше — єдина тека, на яку кореневий `composer.json` відображає всі простори імен `autoload.psr-4` (у Laravel — `app/`). Інакше — єдина тека кореня репозиторію, що дала б шар, коли вона Python-пакет (має `__init__.py`) і її підтеки містять код: типовий застосунок `app/` з `api/`, `db/`, `core/`. Інакше корінь джерел — сам корінь репозиторію. Кожна тека кореня джерел із кодом стає шаром (теки тестів — ні), файли самого кореня джерел — шаром `main`. Коли корінь джерел окремий, файли кореня репозиторію стають шаром `app`, а `bin/` — шаром `bin`. Тож пакет `app/` з підпакетами дає шари `api`, `core`, `db` і `main: ["app/*"]`, і baseline забороняє залежності між ними, а не лише `app external`. Несумісна зміна: у такому репо без `keylang.json` ID втрачають сегмент пакета (`app.api.routes.get_user` → `api.routes.get_user`).
- **Імена шарів.** Ім'я шару в `keylang.json` — один сегмент ID. `external`, `unassigned`, `outside` (синтетичні шари keylang) і ключові слова верху карти (`layer`, `layers`, `allow`, `deny`, `entry`, `module`, `no-cycles`: карта пише шар рядком `- <name>`) зарезервовано — такий шар є помилкою конфігурації з кодом 2, що називає файл і поле `layers.<name>`. `init` таких імен не вгадує: тека `src/external/` стає шаром `external_`, а друга тека, що санітизується в уже зайняте ім'я (`src/2fa/` і `src/_2fa/` — обидві `_2fa`), — `_2fa_2`; про кожне перейменування — примітка в stderr. `dir` нормалізується: `./keylang/` — це `keylang`. ID — у Unicode NFC: ім'я шару з `keylang.json` і сегмент ID з імені файла чи теки нормалізуються, тож тека `café`, яку macOS зберігає в NFD, і `café`, набране в специфікації, — один ID, а шлях у знімку лишається таким, як на диску. Так само ім'я функції, класу чи члена, написане в коді в NFD: ID — NFC, а `name` у знімку — як у коді. Ім'я в коді знаходить оголошення й імпорт свого файла в NFC, а `exports` порівнює імена з таблицею експортів (вона зберігає їх, як у коді) теж у NFC. Два ключі `layers`, однакові після NFC, — помилка конфігурації з кодом 2, що називає обидва.
- **Глоби шарів.** Глоб — POSIX-шлях від кореня з `**`, `*`, `?` і `{a,b}`; `[` — літерал, тож `app/[id]/**` — тека маршруту Next.js. Файл належить першому шару з `keylang.json`, чий глоб його збігає. `map` і `map --check` попереджають у stderr, коли розкладка, мабуть, каже не те, що задумано: файли, які збігають глоби двох шарів (`` warning: keylang.json: 2 file(s) match the globs of both `layers.app` and `layers.core` (e.g. `src/a.ts`); the layer listed first takes them: `app` by `src/**` `` — рядок на пару шарів і глоб, що переміг), і глоб шару, що не збігає жодного файла джерел, прочитаного чи виключеного (``warning: keylang.json: `layers.ghost`: `lib/**` matches no source file``). Це попередження, не помилка: коди виходу ті самі, а вгадана розкладка їх не дає.
- `layers a < b < c`: `a` найнижчий; залежність може йти лише вниз (`c` → `a` можна, `a` → `c` — K101). Вкладені під `layers` шари, а також `external`, `unassigned` і `outside`, — без порядку: залежність *у* них вільна, якщо не заборонена `deny`. Усі рядки `layers` разом — один частковий порядок: `a < b` і `b < c` ставлять `c` над `a` (`a` → `c` — K101), а `a < b` і `c < d` нічого не кажуть про `a` і `d`. K005 (і рядок не перевіряється): шар двічі в одному рядку, ID з крапкою замість шару, рядок, що суперечить попереднім (`b < a` після `a < b`), шар, водночас впорядкований і вкладений. Кожен рядок `layers` має вердикт: `ok`, коли жодна залежність не порушує порядку його шарів і в області немає прогалини рівня залежностей; з прогалиною — `unverified` з її назвою; порушення — K101. Область — модулі шарів усієї зв'язної компоненти цього рядка (рядки `layers`, з'єднані спільними шарами) і модулі шарів поза будь-яким порядком (вкладені, `external`, `unassigned`, `outside`). Прогалина `unassigned-file` сама область не робить `unverified`: ребра того файла відомі; інша прогалина в ньому — робить. Залежність угору, яку вирішив `deny`, не дає рядку ні `ok`, ні другої K101 (лишається одна K102). Залежність угору, яку дозволив `allow`, лишає `ok`, і доказ називає цей `allow`. Залежність униз, заборонена `deny`, лишає `ok` із доказом «points down». Предикати `above` і `k101` — у «Семантика правил».
- `allow`/`deny` приймають шари, модулі й їхні префікси; клас — модуль свого файла, тож його ID теж область: ребро до класу чи з його методу — доказ. ID fn, типу, події чи аліаса залежності (зокрема `planned fn`) — K005 з назвою модуля, бо ребра правил — між модулями, і таке правило нічого б не перевіряло. Правила впорядковані частково. Правило конкретніше за інше, коли жодна його область не ширша за відповідну область того й хоча б одна вужча (`app.purchase` — глибина 2 у сегментах, не довжина рядка). Рівні області вирішує `deny`: два `deny` з тією самою сумою глибин дають кожен свою K102. Непорівнювані — ті, де одне вужче за джерелом, а інше за ціллю. У форматі 1 таку пару вирішує лише сума глибин, і за рівності перемагає `deny`. Тож `deny app.x domain` (2 + 1) і `allow app domain.storefront` (1 + 2) непорівнювані з рівною сумою: перемагає `deny`, K106 немає. `allow app.x.y domain` (3 + 1) і `deny app domain.storefront` (1 + 2) теж непорівнювані: у форматі 1 перемагає `allow`, і K106 стоїть на рядку `allow`, доки немає правила на перетині `app.x.y domain.storefront`. У форматі 2 серед правил, яких ніхто не домінує, будь-який `deny` перемагає (deny-overrides): та сама пара лишає K106, але ребро забороняє `deny`. «more specific rules» пишеться лише коли ребро вирішило порівнюване вужче правило; непорівнюваний `allow` у доказі називається сам. `allow` знімає K101 для своєї пари. Одна залежність модуля від модуля — одна K102 на правило, скільки б ребер її не показували (імпорт, виклик, тип-клас). Кожне `deny` має власний вердикт: підтверджене заборонене ребро — `fail`; інакше `unverified`, якщо в області є прогалина рівня залежностей (нерозв'язаний чи обчислюваний імпорт, синтаксична помилка, виключений файл, тека, яку не вдалося прочитати, `eval`), і `ok` без неї. Область `deny` — модулі джерела разом із модулями, з яких вони імпортують (розв'язане ребро `import`/`re-export`, далі ланцюжком реекспортів): непрозорий barrel (виключений, із синтаксичною помилкою) міг би реекспортувати заборонену ціль, тож його прогалина лишає `deny` `unverified`, а не `ok`; `exclude` такого barrel переводить `fail` лише в `unverified`. Прогалина `unassigned-file` в імпортованому модулі прогалиною не є: його ребра відомі. Дірка всередині однієї декларації (`unsupported` із `source` — ID fn чи класу, як Python-декоратор, що може підмінити fn) змінює, який код виконує виклик, а не що імпортує модуль, тож прогалиною рівня залежностей не є. Область без жодного модуля — `unverified` «planned», коли вона існує лише як `planned`, і `ok` «no module … yet» інакше (шар без модулів). Виклик через локальне значення залежності між модулями не створює: без імпорту код іншого модуля недосяжний. Предикати `within`, `score`, `dominates`, `winner`, `k102`, `k106` — у «Семантика правил».
- `entry`: досяжність іде лише ребрами `import` / `call` / `type` / `re-export` знімка, зокрема через `index.ts`, що реекспортує сусідів, і через модуль, названий відносно модуля: `new URL("./worker.ts", import.meta.url)` (як у `new Worker(…)`) та `register(spec, import.meta.url | { parentURL: import.meta.url })` — ребро `import`, коли специфікатор — рядок, тернарник рядків або `const`, прив'язаний до такого (`URL` — лише відносний шлях із розширенням JS/TS). Пункт `entry` з ID модуля, якого немає у знімку, — K001, тож видалений worker, записаний в `entry`, помітний; його нерозв'язаний `new URL(…)` — ще й прогалина `unresolved import` у модулі, що його завантажує. Ієрархія ID не робить сусідів досяжними, а тека-модуль без власного коду не звітується. Клас — частина модуля свого файла: досяжний файл робить досяжними його класи, і невикористаний експортований клас K103 не отримує. K103 вказує на файл модуля. Коли досяжні всі модулі, кожен рядок `entry` має вердикт `ok`. Прогалина рівня залежностей у досяжному модулі (нерозв'язаний імпорт тощо) перетворює недосяжність на `unverified` із назвою цієї прогалини, а не на K103. Модулі шарів без порядку не перевіряються. `entry` із шаром чи префіксом (`- domain`) — точки старту всі модулі під ним. Предикати `reach` і `k103` — у «Семантика правил».
- `exports` порівнюється з таблицею публічних експортів самого модуля знімка, не з fn без `<!-- internal -->` і не з таблицями його підмодулів: `purchase/buy.ts` поруч із `purchase.ts` — окремий модуль зі своїми експортами. Модуль правила, що існує лише як `planned`, — `unverified` «planned»; відомий ID, що не є модулем знімка (шар, fn), — `unverified`; невідомий — лише K001. Імена в `exports` — публічні імена модуля, а не ID карти, тож K001 вони не дають. `export { a as b }` порівнюється за `b`, `export default …` (включно з `export default function main`, `export default 3`), TypeScript `export = x` і CommonJS `module.exports = x` — за `default`, `export namespace N {}` і `export * as N from` — за `N`, `export * from "./x"` розкривається до імен `x` без `default` (транзитивно й через цикли `export *`; ім'я, яке два джерела `export *` дають різними оголошеннями, ESM не експортує). Зайве ім'я — K104 із видом і формою (`alias`, `default`, `namespace`, звідки re-export; публічне ім'я, яке Python-модуль без `__all__` імпортує, — «imported from `m`»); заявлене відсутнє ім'я — absence. `export *` із модуля з невідомим вмістом (зовнішній пакет, нерозв'язаний або виключений файл, файл із синтаксичною помилкою) робить правило `unverified`, а не absence; так само непрозорий модуль правила (файл з `exclude`, помилка розбору) — заявлене відсутнє ім'я там `unverified`.
- Цикли — це SCC графа `import` / `re-export` без ребер `typeOnly`. Залежність лише від типів (TypeScript `import type`, `export type … from`, `export type * from`, а також `import { type A }` чи `export { type A } from`, де кожне ім'я — `type`, коли tsconfig файла не задає `verbatimModuleSyntax`; [snapshot.md](snapshot.md) §11, «TypeScript») — ребро `import` чи `re-export` з `typeOnly: true`: під час виконання модуль її не завантажує, тож циклу вона не утворює, а для `allow`, `deny`, `layers` і `entry` це звичайна залежність. `no-cycles` під модулем спрацьовує, якщо модуль або його підмодуль входить у SCC; маршрут проходить через нього. Файл, що імпортує сам себе, — self-loop і теж цикл. Одна K105 на кожну SCC. Без циклу серед відомих імпортів, але з прогалиною залежностей в області — `unverified`, не `ok`. Для `no-cycles` під модулем область — цей модуль, його підмодулі й модулі, досяжні з них імпортом або реекспортом; `unassigned-file` там прогалиною не є. Глобальний `no-cycles` і далі рахує `unassigned-file`. Предикати `scc`, `k105`, `hole` і `area` — у «Семантика правил».
- `planned fn|module|type|event <id> [signature]` — намір (кандидат до v1): рядок верхнього рівня секції flow, сигнатура — довільний текст до кінця рядка. Посилання на нього не є K001: `ID` і `static` — `unverified` «planned», trace його не вимагає, ребер у знімок він не додає. Повторна декларація того самого ID — K002 (і в каталозі без коду). Коли в коді з'являється символ із цим ID, крок перевіряється як звичайний код, а декларація дає K202 (вид і сигнатура збігаються; сигнатури порівнюються без пробілів, `->` = `→`; у файлі `.py` перший параметр коду `self` чи `cls` можна не писати в плані: `(self, to: str)` збігається з `(to: str)`; план без частини результату — лише список параметрів, без `→` чи `->` після нього — обіцяє тільки параметри: `(order: Order)` збігається з кодом `(order: Order) → Refund`, а план із частиною результату порівнюється повністю) або K201 (інший вид чи сигнатура). Виду `event` у знімку немає, тож fn, тип чи модуль з ID запланованої події — K201.

`keylang lsp` віддає ті самі коди, позиції й вердикти, що й `check`.

### Семантика правил

Нормативна модель поточної перевірки графа. Факти знімка: `module(M)` — модуль, клас включно; `unit(U)` — файл-модуль (не клас і не тека без власного коду); `edge(From, To)` — розв'язане ребро `import`, `call`, `type` або `re-export` між модулями різних файлів. Немає ребер `via: injected` і ребер усередині одного файла. Для `allow`/`deny` кінець ребра — найближчий модуль. Self-import файла — self-loop лише для циклів.

```text
within(M, A) :- M = A; M починається з A + ".".
score(R, From, To) = max (depth(A) + depth(B))
  для правила R «effect A B…», де within(From, A) і within(To, B).
depth(Id) = кількість сегментів.
dominates(R1, R2) :- джерело R1 у within джерела R2, збігла ціль R1 у within цілі R2,
  і хоча б одна область вужча.
incomparable(R1, R2) :- одне вужче за джерелом, інше — за ціллю.
generated(R) :- R у файлі з маркером keylang:generated (baseline, rules.baseline.md).
hits(E) = правила, що покривають ребро E, без кожного generated R, для якого є
  не-generated правило з тим самим джерелом і тією самою найглибшою ціллю на E
  (baseline — нижчий шар правил: ручне правило за рівної точності його заміщає).
  winner нижче обирається серед hits(E), в обох форматах.
winner(E) у форматі 1 = правила з найбільшим score на ребрі E;
  за рівності — кожен deny, а allow лише коли deny з тим самим score немає.
winner(E) у форматі 2 = правила, яких ніхто не dominates;
  якщо серед них є deny — лише ці deny (deny-overrides), інакше ці allow.
beaten(R, E) :- R — deny і R не входить у winner(E).
k102(R, U1, U2) :- R входить у winner, R — deny, ребро між файлами-модулями U1 і U2.
  Одна K102 на правило і пару файлів. Вердикт deny: fail, якщо є k102;
  інакше unverified, коли hole в area; інакше ok. «more specific rules» — лише коли
  переможець порівнюваний і вужчий. Непорівнюваний allow, що вирішив ребро сумою
  глибин, називається в доказі сам.
k106(Allow, Deny) :- пара incomparable хоча б на одній парі цілей, score(Allow) > score(Deny),
  і жодне правило не має областей рівно на перетині (вужче джерело і вужча ціль).
  Одна на пару рядків, на рядку allow, незалежно від знімка. Формат 1 каже, що переміг allow;
  формат 2 — що переміг deny. Правило на перетині прибирає K106.

above(L, H) — транзитивне замикання сусідніх пар усіх рядків layers (один порядок).
k101(U1, U2) :- ребро не вирішив winner, і або above(шар U1, шар U2),
  або шар U1 поза порядком, а шар U2 впорядкований і не unordered.
  Рядок layers без ok, якщо його шар — кінець такого ребра або ребра вгору, яке виграв deny.
  Інакше ok, а з hole в area — unverified. Дозвіл allow лишає ok і називає цей allow.

reach(U) — файли-модулі, досяжні з точок entry ребрами edge
  (шар або префікс, який сам не модуль, сіє кожен unit під ним).
k103(U) :- unit U має власний код, не reach, шар не unordered.
  hole серед reach перетворює такий U на unverified, не на K103.
  Рядок entry має ok, коли кожного такого unit досягнуто.

scc — сильні компоненти графа import / re-export без typeOnly плюс self-loop.
  Циклічна компонента має більше одного модуля або self-loop.
k105(R, C) :- одна на кожну таку C, що містить модуль правила чи його підмодуль
  (глобальне no-cycles — кожну C). ok, коли таких C немає.

hole(U) :- запис покриття unresolved-import, parse-error, unsupported,
  unassigned-file або skipped-file у U чи під ним, крім
  «unsupported construct `computed call`» і unsupported всередині однієї декларації.
  unassigned-file не є hole для layers і для no-cycles під модулем.
  Кілька hole — перша за відсортованим id модуля.
area(deny, U) :- U в області джерела, або модуль області джерела має розв'язане ребро
  import / re-export до U, або area(deny, V) і V має ребро re-export до U
  (unassigned-file у такому імпортованому U не є hole).
area(layers, U) :- шар U в зв'язній компоненті рядка або поза будь-яким порядком.
area(no-cycles під M, U) :- U є M, підмодуль M, або досяжний з них import / re-export без typeOnly.
area(no-cycles глобальне, U) :- кожен unit.
area(entry, U) :- reach(U).
unverified(R) :- not fail(R), area(R, U), hole(U).

outside(U) :- шар U — outside (файл U збігає глоб `outside` з keylang.json).
k107(U1, U2) :- edge між U1 і U2, outside(U2), not outside(U1).
  Одна на пару файлів, на першому ребрі; allow її не знімає, рядка правил не потребує.
  Запис покриття outside-file не є hole.
```

**Baseline — нижчий шар правил** ([ADR 0013](adr/0013-baseline-lower-rule-layer.md)). Ручний `- allow article mail` у `rules.md` дозволяє ребро `article → mail`, хоча baseline має `- deny article app, mail, …`: області однакові, тож ручне правило заміщає згенероване, і K102 немає. Без цього `allow` ребро дає K102 з рядком `rules.baseline.md`. Вужче правило baseline (`allow app external.stripe`) і далі перемагає ширше ручне (`deny app external`). Між ручними правилами deny-overrides діє як завжди. Рядок `deny` з baseline, чиї ребра вирішили ручні правила, має `ok` з доказом «manual rules over the baseline».

Приклад K106. Файла `keylang.json` немає, тож редакція 2: пара непорівнювана, перемагає `deny`, попередження стоїть на рядку `allow`.

```keylang path=keylang/map.md
- layer app
  - module x
    - module y
- layer domain
  - module storefront
```

```keylang path=keylang/rules.md
# rules

- allow app.x.y domain
- deny app domain.storefront
```

```diagnostics
keylang/rules.md:3:1: K106 `allow app.x.y domain` and `deny app domain.storefront` (keylang/rules.md:4) are incomparable; deny wins (deny-overrides); add `allow app.x.y domain.storefront` or `deny app.x.y domain.storefront`
```

`external.<pkg>`, оголошений у `package.json` або `Cargo.toml`, не дає K001 і не додає вузол у знімок, доки якийсь файл його не імпортує. `exports` ця модель не описує. Сегмент ID береться з імені пакета: `@scope/pkg` → `scope-pkg`, `lodash.get` → `lodash_get`. Коли два імені дають один сегмент (`@scope/pkg` і `scope-pkg`), суфікси `-2`, `-3`… рахуються над оголошеними й імпортованими іменами разом: ім'я, що дорівнює сегменту, лишається без суфікса, інші отримують суфікс у порядку імен, і про кожне `map` попереджає. Тож ID пакета не залежить від того, який із двох пакетів код імпортує (ADR 0010).

### Flows: докази кроку

`step` задає **вкладеність** щодо батьківського кроку; сусідні кроки — **послідовність**. Для кроку верхнього рівня (поруч із `trigger` чи під ним) батьком є `trigger`. Кожен вид доказу друкується окремим рядком `file:line:col: <доказ> <verdict> <id>: <причина>`, а в `--format json` — окремим результатом із `criterion` (`ID` / `static` / `tests` / `trace`), `area` (ID кроку або текст твердження), `verdict`, `evidence` і `provenance` (`syntactic`, `test-report`, `trace`; для trace також `runId`, `testId`).

| Доказ | ok | unverified | fail |
|---|---|---|---|
| `ID` | символ є у свіжому знімку | `planned`, член `opaque`-модуля | K001 — відсутній у `complete`-модулі (`static` тоді не друкується) |
| `static` | шлях resolved-викликів від батька, жоден з яких не сидить у closure (сусідні кроки шляху не потребують; рекурсія — шлях); з `--static=behavior` (типово) — також через хук: «through the default of the hook `g`», «`g` injected at file:line:col»; крок через ребро з `provenance: docblock` (PHP: властивість, яку типізує лише `@var`/`@param`) — доказ у будь-якому режимі, і вердикт це називає: «called from X, typed by a docblock at file:line:col»; крок на модуль `external.<pkg>` — resolved-імпорт цього пакета з модуля fn-батька, що завантажує пакет («imported by»): type-only імпорт (`import type`, `export type … from`) компілятор стирає, тож він не доказ | шлях є, але проходить через тіло, що може не виконатися: fn під декоратором чи атрибутом, якого keylang не знає (`@replace` може повернути іншу функцію; у coverage — `@…` чи `#[…]` з `source` цієї fn або перед нею), або код модуля, що не розбирається («may not run its own body», «is in a module that does not parse» з позицією); шляху немає, але його могла б дати конструкція, яку keylang не відстежує (нижче): з нею та позицією; шляху немає, а досяжний код є в модулі, що не розбирається; батько чи крок — не функція (крім `external.<pkg>`, де з модуля батька немає імпорту, що завантажує пакет: «no import of», а за type-only імпорту ще й «the type-only import at … is erased from the code that runs»); `planned`; прямий нащадок нереалізованого `planned`-кроку — «parent `<id>` is planned, not implemented» (глибші кроки рахуються від реалізованого батька) | `absence: no call path …` — крок і його виклики досяжні лише за назвою, і жоден виклик із досяжного коду не може їх назвати; повідомлення закінчується дією `` add a call to `<крок>` in `<батько>` or in a function it reaches `` |
| `tests` | однозначний тест пройшов у звіті поточного знімка | звіту немає, тест не знайдено, неоднозначний (перелік кандидатів), пропущений, звіт іншого знімка або без `snapshotId`; твердження без `test` («no test evidence»; для кількісних чи заперечних — «needs a separate predicate or test») | тест провалився |
| `trace` | крок спостережено в завершеному запуску тесту з вкладенням і підтвердженим порядком | trace іншого знімка чи без нього; жоден запуск не спостеріг тригер («trigger not observed in <testId>»); неповний запуск, навіть коли крок спостережено (`complete: false` у будь-якій події `run` чи її немає, `dropped > 0` або не вказано, відкриті spans; для відсутнього кроку — ще й символ не інструментовано); різні годинники без `links` (зокрема `end` попереднього на іншому годиннику); паралельні sibling-и; асинхронний крок без `link`; гілка `when` не виконувалась; span кроку є лише коренем іншого дерева викликів і не почався раніше за образ батька на тому самому годиннику («observed outside … in another call tree»); другий і наступні `trigger` і вузли під ними («a flow is matched from its first trigger only»); крок під `planned`-кроком («parent step … is planned») | обов'язковий крок відсутній у завершеному й інструментованому запуску, що спостеріг тригер: символу немає в жодному span, усі його spans у тому самому дереві викликів поза образом батька, або span в іншому дереві почався раніше за образ батька на тому самому годиннику; крок почався раніше за попереднього сусіда; образ кроку лежить у піддереві образу попереднього сусіда («nested in …, not after it»), синхронно і з `links` |

**Знайдені потоки — представлення, не твердження.** `<dir>/flows-discovered/<шар>.md` пише `keylang flows discover` ([cli.md](cli.md#flows-discover)): чернетку потоку для кожної точки входу з ребер знімка, з маркером `keylang:generated`. `check` цієї теки не читає, як і `map-explained/` та `explain/` ([ADR 0014](adr/0014-one-model-many-views.md) п. 4): знайдений потік не дає вердиктів, не додається до «N ok», а застарілий ID у ньому — не K001, лише застаріле представлення (`flows discover --check` → 1). Твердженням потік стає, коли людина зливає пропозицію `keylang flows adopt <name>` у `<dir>/flows/`.

**Звіт покриття — представлення.** `keylang coverage` ([cli.md](cli.md#coverage)) обчислюється зі знімка, специфікацій і `resources/data-logic.json` і нічого не стверджує: сирота — не K-код, «логіка в даних» — місце для ручної перевірки, а не дірка знімка; `check` звіту не читає і вердиктів від нього не змінює.

#### Семантика

Trace-доказ — впорядковане ін'єктивне включення дерева кроків потоку в дерево spans одного запуску `(runId, testId)`. Kilpeläinen і Mannila (1995) розв'язують булеве включення дерев; keylang бере максимальне часткове включення і дає вердикт кожному кроку. Тригер — корінь, батько кроку верхнього рівня — тригер. Образ кроку — нащадок образу батька на будь-якій глибині, тож зайві виклики дозволені. Ін'єктивність: один span є образом не більше одного вузла. Рекурсивний крок потребує власного вкладеного span (один span — `trace fail` «missing step», вкладений — `trace ok`; два рівні специфікації і два spans — `ok` першому кроку і `fail` найглибшому). Два однакові сусідні кроки потребують двох викликів: один span дає одному `trace ok`, другому `missing step`, а `static ok` — обом, бо static не рахує кратність.

Порядок сусідів причинний: `end` попереднього раніше за `start` наступного на тому самому `clockId`, або `links` на попереднього, коли span не лежить у його піддереві. Сортування `ts` порядок не доводить. Образ наступного сусіда в піддереві попереднього — `fail` «nested in `<попередній>`, not after it», і для синхронного вкладення, і для async-продовження з `links`. У неповному запуску цей `fail` стає `unverified`. Перекриття без відношення предок — нащадок лишається `unverified` «parallel». Різні годинники без `links` — `unverified`; `links` між ними — `ok`.

`when` прозорий: кроки гілки вкладаються під батька `when`, порядок усередині гілки зберігається, а відносно сусідів `when` — ні. Гілка, чий перший крок спостережено, має «branch exercised», навіть якщо цей крок стався перед сусіднім кроком поза гілкою.

Серед максимальних часткових включень перемагає те, де більше `ok`, потім менше `fail`, потім раніші spans. Trace `save, create, save` під `buy` дає `trace ok` обом крокам `create` і `save` (обрано другий `save`). Trace, де `save` лежить під `buy`, а `create` — під `later`, дає обом «missing step». Trace `buy`, `later`, `buy{create}`, `later{save}` дає всім крокам `trace ok` і `static ok`.

`fail` «missing step» лишається лише в трьох випадках завершеного інструментованого запуску: символу немає в жодному span; усі його spans у тому самому дереві викликів, що й образ батька, але поза ним; spans в іншому дереві почалися раніше за образ батька на тому самому годиннику. Span лише як корінь іншого дерева, що не почався раніше, — `unverified` «observed outside `<батько>` in another call tree (root `<корінь>`): nesting unknown». Інший `clockId` цього не вирішує: Rust і Python мають один годинник на процес, тож span іншого потоку — корінь, а не інший годинник. `links` такого кореня на батька вкладення не доводять.

Static-доказ — існування шляху у графі викликів знімка від батька, без порядку й кратності.

На рядку з K003 і в його піддереві `ok` будь-якого доказу стає `unverified` «structure recovered after K003 at L:C» ([grammar.md](grammar.md) §3).

**`calls` у потоці** — static-доказ без порядку, що батько (найближчий `step` чи `trigger`; для рядка верхнього рівня — тригер) викликає ціль **сам**, а не через інші виклики. Кожне ID рядка `calls a, b` має власні `ID` і `static` на колонці цього ID. `static ok` — resolved-виклик у тілі fn батька, який доводить поточний режим `--static` (не в closure; ребро хука — лише в `behavior`). `static fail` `` absence: `<батько>` does not call `<ціль>` `` — за тими ж правилами надійності, що absence кроку: жоден виклик батька не може бути ціллю (нерозв'язаний чи неоднозначний виклик її назви, перевизначення методу, виклик у closure чи через хук у `shape`), тіло батька розібрано, і ціль не «тікає» (див. «Static без шляху»: прочитана як значення, викликана з closure, `eval` у тілі батька тощо). Якщо батько доходить до цілі через інші виклики, повідомлення додає `` (it reaches it via …; `step` proves a path) ``. Закінчується воно дією `` ; add a direct call in `<батько>` ``. Інакше — `static unverified` із причиною. `planned`-ціль чи батько, ціль `external.<pkg>` (імпорт з модуля батька) і ціль, що не є fn, — як у `step`. `reads <id>` поки дає лише `ID` для кожного ID: читання знімок від виклику не відрізняє. `trace` для `calls` не друкується. Текст специфікації, `fmt`, `parse --json` і `specHash` інших рядків від цього не змінюються.

Перевірюваний сценарій має один `trigger`: trace зіставляє потік від першого. Другий і наступні `trigger` і вузли під ними — `trace unverified` «a flow is matched from its first trigger only». Кожен крок під нереалізованим `planned`-кроком, на будь-якій глибині, — `trace unverified` «parent step `<id>` is planned», де `<id>` — найближчий такий предок. Static прямої дитини — «parent `<id>` is planned, not implemented»; глибші кроки рахуються від реалізованого батька. Без `check.trace` цих рядків немає. `check --strict` рахує такий `unverified`.

**Виклик методу через значення з відомим класом.** Виклик `x.m()` — resolved-ребро до `X.m`, коли синтаксис називає клас `x`, а `X` — клас, прочитаний keylang (свій чи імпортований). Член шукається в `X`, далі вгору базовими класами, які keylang прочитав; без такого члена виклик лишається діркою. TypeScript: параметр `x: X`, локальна `const x: X` чи `const x = new X()`, поле `this.x` з типом `X` чи `= new X()`. Python: параметр з анотацією класу — `x: X`, `x: "X"`, `x: X = Depends(…)` (типове значення не важить), `Optional[X]`, `X | None`, `Annotated[X, …]` — або локальна, чиє єдине присвоєння у функції `x = X(…)` чи `x: X = …`. Друге присвоєння імені будь-де у функції (зокрема у вкладеній), інша анотація (`list[X]`, `Callable[…]`, псевдонім-значення) чи `X`, перевизначене у функції, лишають виклик діркою «call through a local value `x.m`». Анотація — доказ у обох режимах `--static`: keylang не виконує код і не перевіряє, що значення справді має цей клас.

**Static без шляху.** Коли resolved-шляху немає, пошук триває через виклики з кількома можливими цілями: виклик із невідомим отримувачем (`x.feed()`, `cb()`) може бути будь-якою fn тієї ж назви, розв'язаний виклик методу — перевизначенням тієї ж назви, неоднозначний — будь-яким кандидатом, ребро хука в режимі `shape` — своєю ціллю, а виклик у closure (`return () => hit()`, колбек `items.forEach(() => …)`) — своєю ціллю лише тоді, коли цю функцію-значення хтось викличе: маршрут, що доходить до кроку тільки так, — `unverified` «reached only through a closure of X». Знайдений так маршрут дає `unverified` із першим таким викликом на ньому (найближчим до батька; виклики з назвою кроку перевіряються раніше) і лічильником `(and N more unresolved calls in reachable code)`. Інакше `unverified` лишається, якщо fn на якомусь маршруті до кроку «тікає»: прочитана як значення (`later(save)`, `{ save }`, `obj.save` без виклику, `extends A` для конструктора `A`; за назвою, в усьому репозиторії), accessor, неявний метод (`then`, `next`, `return`, `throw`, `toString`, `valueOf`, `toJSON`), викликана з closure; викликана з коду поза оголошеннями — верхнього рівня модуля (він виконується під час завантаження, зокрема через `import()` чи `new Worker(new URL(…))`), методу об'єктного літерала, функції-значення, обгорнутої викликом (`export const load = cache(() => step())`), — «is called from module-level code» / «from a function value outside declarations» (виклик із невідомим отримувачем там робить такою кожну fn тієї ж назви); метод класу, чий базовий клас keylang не прочитав (пакет, глобальний, нерозв'язаний: `extends Readable`, `extends React.Component`, і їхні нащадки), — «may be called by the base class»; синтезований `Class.static` (виконується під час завантаження). Так само `eval`, `new Function`, `obj[k]()` чи `import(expr)` у коді, до якого веде доведений або можливий маршрут, обчислюваний член класу, `namespace` чи інша непрочитана конструкція, що згадує таку fn (ім'я — цілим ідентифікатором, зокрема з `$` чи не-ASCII літерами), і непрочитаний (`opaque`) модуль при будь-якій дірці. Назву тут порівнюють так, як її порівнює мова цілі: fn PHP — без регістру латинських літер A–Z (`$x->RUN()` може бути `run`, `[$o, 'SAVE']` читає `save`, `$k->HANDLE()` у коді модуля викликає `handle`, `call_user_func('HELPER')` згадує `helper`). Повідомлення називає причину з позицією; нерозв'язаний виклик із досяжного коду воно називає лише тоді, коли той виклик є в fn, що передала значення далі, або в коді, який вона викликає. Лише коли нічого з цього немає — `fail`: він має бути надійним, тож за сумніву вердикт — `unverified`.

**Хуки (`--static`).** Хук — виклик через локальне значення, параметр чи поле з типовим значенням поруч: `const g = p.x ?? f` (або `||`), `const { x: g = f } = p`, параметр `g = f` чи `{ g = f }`, поле `this.g = options.g ?? f` у конструкторі (або параметр-властивість `private readonly g = f`). Виклик `g()` лишається діркою в `coverage` («call through the hook `g` (default `f`)») і дає ребро `call` з `via: "default"` до `f`. Якщо `p` — параметр самої функції (для поля — параметр конструктора), розв'язаний виклик, що передає за тим самим аргументом і властивістю функцію-значення (`analyze({ generate: worker.generate })`, `new App({ analyzer })`, `run(save)`), дає ребро `via: "injected"` з `site` — позицією того виклику; контекст виклику не розрізняється. `--static=behavior` (типово) доводить шлях і цими ребрами, `--static=shape` — лише записаними викликами; `--static` з іншим значенням — код 2. Ребро `default` карта друкує в `calls` і правила бачать (модуль і так імпортує `f`); `injected` — ні: це залежність того, хто передає значення. Режим хука типового значення задає `check.static` у `keylang.json` (`"behavior"` або `"shape"`). Пріоритет: прапорець `--static`, потім це поле, потім `behavior`. У режимі `shape` доказ називає джерело: `set by --static` або `set by keylang.json check.static`. Невалідне значення дає код 2 і називає файл і поле `check.static` для кожної команди, що читає конфіг. Те саме значення читають `check` (зокрема `--changed`), `feature`, `hook stop`, LSP, MCP, TUI і `keylang web`. `init` і `draft map` поле не пишуть. Типове `behavior` можна змінити лише з новою версією формату.

`tests` друкується на твердженні (`invariant`, `when`, `then`, `reads`, `emits`), до якого прив'язаний `test`. `trace` для `when` — «branch exercised» або «branch not exercised»; кроки невиконаної гілки в цьому тесті не обов'язкові. Вердикт кроку за кількома запусками trace: запуск, у якому тригер потоку не спостережено (жодного span тригера), — не запуск цього потоку, а, скажімо, юніт-тест одного кроку (у PHPUnit кожен тест, що дійшов до функції плану, — окремий запуск). Усі його вузли — `unverified` «trigger not observed in <testId>», і до вердикту він не входить, коли тригер спостережено в іншому запуску. Серед запусків поточного знімка, що спостерегли тригер (у потоку без тригера — серед усіх): `fail`, якщо хоч один запуск крок порушив; інакше `ok`, якщо хоч один підтвердив; інакше причина першого запуску в порядку читання. Запуски іншого знімка чи без знімка, як і запуски без тригера, дають причину `unverified` лише тоді, коли тригер не спостеріг жоден запуск. Без `check.tests` / `check.trace` відповідні докази не друкуються (зокрема «no test evidence» для твердження без `test`): непотрібний вид доказу не входить до агрегації й до `--strict`. Файл тесту перевіряється завжди, з `check.tests` чи без нього: `test` з файлом, якого немає в репозиторії (шлях — від кореня з `keylang.json`), дає K203 `` `tests/nope.test.ts` does not exist `` на шляху. Це попередження: вердиктів і `--strict` воно не змінює. Специфікації, перевірені без коду репозиторію, K203 не дають.

### Звіт тестів (`check.tests`)

`check.tests` у `keylang.json` — шлях (має існувати, інакше код 2) або глоб (може ще нічого не знаходити: тоді «no report»). Формат визначається за вмістом:

- **JSON keylang, схема 1** — `{"schemaVersion": 1, "snapshotId", "runId", "tests": [{"file", "suite"?, "name", "status": "pass"|"fail"|"skip"}]}`. Пише репортер `node:test` з пакета: `node --test --test-reporter=spec --test-reporter-destination=stdout --test-reporter=keylang/node-test-reporter --test-reporter-destination=stdout` (у цьому репозиторії — `./src/adapters/node-test.ts`, див. `npm test`). Він рахує `snapshotId` поточного коду і пише `.keylang/reports/node-test.json` (або `KEYLANG_TEST_REPORT`); suite — вкладені `describe`/`test`, через ` > `. Той самий формат пише розширення PHPUnit з `adapters/php/keylang_phpunit.php` (`.keylang/reports/phpunit.json`): suite — коротке ім'я класу тесту, назва — метод; знімок воно бере з `KEYLANG_SNAPSHOT_ID`, плану trace або `.keylang/index.json` ([cli.md](cli.md#trace)).
- **JUnit XML** — `<testcase file classname name>` з `<failure>` / `<error>` / `<skipped>` у `<testsuite>` (вкладених чи під `<testsuites>`); читається як XML: лапки обох видів, сутності, коментарі, CDATA. Зв'язок зі знімком — `<property name="keylang.snapshotId" value="…"/>` у `<properties>` самого testcase або найближчого suite навколо нього (так само `keylang.runId`): кожен suite злитого звіту має власний знімок. Без нього testcase не підтверджує поточний код. Некоректний XML — код 2 з `file:line`. `file` — шлях від кореня репозиторію; абсолютний шлях під коренем (так пишуть PHPUnit і jest-junit) стає відносним, шлях поза коренем лишається як є. Без `file` файлом testcase вважається `classname`; коли це не шлях тесту (pytest за замовчуванням пише `tests.test_buy`), `test` лишається `unverified` «no report: `<звіт>` has the test without a `file` attribute». `file` пишуть: pytest з `-o junit_family=xunit1` (`--junitxml=…`), jest-junit з `addFileAttribute: "true"`, PHPUnit (`--log-junit`) — завжди.

`snapshotId` і `runId` звіту (і `snapshotId` рядка JSON) — рядок; відсутнє поле чи `null` — звіт без знімка, інший тип — код 2 з назвою файла й поля (`` <звіт>: `snapshotId` must be a string or null, got 123 ``). Позначка порядку байтів (BOM) на початку звіту пропускається, JSON це чи XML.

`test <file> "<name>"` зіставляється за файлом і назвою; `"Suite > name"` уточнює suite. Неоднозначні лише кілька результатів поточного знімка («ambiguous: …»); результати інших знімків чи без знімка — історія, і без поточного вердикт називає перший із них («stale report …», «… is not bound to a snapshot»). Некоректний звіт — код 2 з назвою файла й поля.

### Trace (`check.trace`), JSONL схеми 1

`check.trace` — шлях або глоб до файлів JSONL. Кожен рядок — подія одного запуску тесту `(runId, testId)` для потоку `flow`. Файл запуск не розділяє: події процесів одного тесту можуть лежати в різних файлах у будь-якому порядку, і це той самий запуск (`end` закриває свій `start`, навіть коли його файл прочитано раніше):

```jsonl
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli-repository.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s1","parentSpanId":null,"symbolId":"cli.cli.main","clockId":"pid-7","seq":1,"ts":12.5}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli-repository.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s2","parentSpanId":"s1","symbolId":"cli.cli.run","clockId":"pid-7","seq":2,"ts":12.6}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli-repository.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s2","outcome":"ok","clockId":"pid-7","seq":3,"ts":40.1}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli-repository.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s1","outcome":"ok","clockId":"pid-7","seq":4,"ts":40.2}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli-repository.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"run","clockId":"pid-7","complete":true,"dropped":0,"instrumented":["cli.cli.main","cli.cli.run"],"open":[]}
```

- `start`: `spanId` (унікальний на виклик — повтори й рекурсія мають різні), `parentSpanId`, `symbolId` (ID знімка), `clockId` + `seq` (порядок подій одного годинника), `ts`, необов'язкові `links` (каузальні зв'язки з іншими spans); `end`: `spanId`, `outcome`; `run` — метадані завершення: `clockId` (годинник процесу, що пише запис; необов'язковий), `complete` (boolean), `dropped` (невід'ємне ціле), `instrumented` (ID символів), `open` (ID spans). Кожен процес пише власну подію `run`: запуск завершений, лише коли завершені всі, `dropped` сумується, `open` об'єднується, а інструментованим вважається символ, який назвали всі. Годинник, що має `start` чи `end`, але жодної події `run` зі своїм `clockId`, — процес, який не дійшов до кінця (воркер, зупинений `terminate()`, дочірній процес, убитий сигналом, воркер `multiprocessing`): запуск неповний, і кроки в ньому `unverified` «incomplete trace (N process ended without its run record)», а не `missing step`. Подія `run` без `clockId` (адаптер до цього поля) не каже, чий процес завершився, тож із нею годинники не судяться. Адаптери дописують події у файл у міру виконання (на кожному `end` і обмеженими пачками), а не лише при виході, щоб span-и такого процесу не губилися разом із ним. Процес називає інструментованим кожен символ плану, який він записав би, якби той виконався: файл має вміст, який бачив знімок, і функцію можна обгорнути (не генератор), — завантажив процес цей файл чи ні, бо код, якого процес не завантажив, у ньому не виконувався. Не називає — символ файла, що завантажився з іншим вмістом чи повз обгортку. Тож воркер, що завантажив лише свій файл, не робить кроки головного процесу неінструментованими. Без `dropped` кількість втрачених подій невідома — запуск неповний.
- Кроки зіставляються впорядкованим ін'єктивним включенням (підрозділ «Семантика» вище) у межах одного тесту: зайві виклики дозволені, одна подія задовольняє один крок. Кожен span тригера чи кроку — кандидат: тест може викликати його кілька разів (спершу з раннім `return`), і перемагає вибір spans, що спостерігає найбільше кроків (за рівності — з меншою кількістю `fail`, потім раніший). `missing step` означає, що символу немає ніде, усі його spans у тому самому дереві поза батьком, або span іншого дерева почався раніше на тому самому годиннику. Порядок сусідів підтверджує `end` попереднього раніше за `start` наступного на тому самому `clockId` або `links` на попереднього, якщо span не в його піддереві; вкладений у попереднього сусіда span — `fail` «nested in …, not after it». Сортування `ts` порядок не доводить. Дочірній span, що почався після завершення батька, підтверджує вкладення лише з `link` на батька.
- Невідома версія, некоректний рядок чи поле — код 2 з `file:line` і назвою поля. `snapshotId` — рядок; відсутній чи `null` — запуск без знімка, інший тип — код 2. Позначка порядку байтів (BOM) на початку файла пропускається.

Адаптери trace і `trace-plan` описано в [cli.md](cli.md#trace).

### Стейлнес прози (`check --stale`, `<dir>/baseline.json`)

Проза специфікацій не перевіряється за змістом, але прив'язана до коду fingerprint-ом (design.md §4.4). Твердження — це:

- опис вузла (текст під елементом) у секціях map і flow рукописних файлів; згенеровані файли (з маркером `keylang:generated`), rules і wiring не входять. Предмет — ID оголошення, інакше посилання елемента (`step`, `trigger`, `calls`…);
- кожен `when`, `then` і `invariant` секції flow. Предмет — посилання найближчого `step`/`trigger` над ним і всі посилання під ним (`then <id>`, кроки гілки `when`); текстовий `invariant` чи `when` верхнього рівня без посилань стосується всіх посилань потоку.

Fingerprint твердження — SHA-256 від fingerprint-ів предметів у свіжому знімку ([snapshot.md](snapshot.md) §11): для fn і типу — `closure` (нормалізований синтаксис тіла й сигнатури без коментарів і розкладки разом з усім, що він транзитивно викликає; цикл хешується як одне ціле), для модуля, класу чи шару — хеш залежностей і closure-ів усього під ним, як для пояснень. Зміна `total > 0` на `total >= 0` змінює fingerprint опису цієї fn, `invariant` під її кроком і опису кожного, хто її викликає; переформатування й коментарі — ні. Предмет, якого немає у знімку, хешується як `?`, тож його поява теж зміна.

**Неповнота.** Твердження `incomplete`, коли предмета немає у знімку або з нього досяжний виклик, якого keylang не розв'язав (`closure.complete: false`): зміна за таким викликом може лишитися непоміченою. Це позначка, а не вердикт.

**Baseline** — `<dir>/baseline.json` (типово `keylang/baseline.json`), під версійним контролем поряд зі специфікаціями. Об'єкт: шлях файла специфікації (відносно кореня, POSIX) → ключ твердження → fingerprint (64 hex). Ключ — ID вузла для опису, `invariant:<текст>`, `when:<текст>`, `then:<текст або id>` для тверджень потоку (текст канонічний, як його пише `fmt`); друге й наступні твердження з тим самим ключем у файлі — ` #2`, ` #3` за порядком у файлі. Файли й ключі відсортовано за code units, JSON з відступом 2 і кінцевим переносом. Інша форма чи значення — код 2 з назвою файла й поля.

```json
{
  "keylang/flows/order.md": {
    "invariant:total is positive": "…64 hex…",
    "main.order.valid": "…64 hex…"
  }
}
```

**`keylang check --stale [paths…]`** будує знімок у пам'яті й порівнює твердження з baseline. У stdout — рядок на твердження до перегляду: `file:line:col: stale <що>` (код під ним змінився з часу прийняття), `new <що>` (прийнятого fingerprint ще немає), `incomplete <що>` (без змін, наскільки видно); причина неповноти додається після `; incomplete:`. Запис baseline перевірених файлів без твердження — `obsolete` (текст змінено чи твердження видалено); без `paths` — і запис файла, якого вже немає. У stderr — підсумок `N stale, N new, N fresh, N incomplete[, N obsolete]`. `stale` — попередження для перегляду, не `fail`: код 0, хай що знайдено. З `--strict` (для CI) код 1, якщо в stdout є хоч один рядок: `stale`, `new`, `incomplete` чи `obsolete` — усе це чекає перегляду й `--accept` (obsolete-запис теж розходження baseline зі специфікаціями). Код 2 — помилка виклику, конфігурації, невалідний baseline, шлях поза `<dir>/` чи репозиторій без мов. Нічого не пише. Звичайний `check` baseline не читає; `--stale` не поєднується з `--format`, `--static`, `--changed` і `--explain-edge`.

**`check --stale --accept`** — явне прийняття після перегляду: записує поточні fingerprint-и тверджень перевірених файлів і прибирає obsolete. З `paths` замінюються записи лише цих файлів, решта лишається; без них baseline перебудовується цілком. `map`, `map --check`, `fmt` і звичайний `check` baseline не змінюють. `--accept` без `--stale` — код 2; `--accept` з `--strict` теж код 2: прийняття пише baseline, а `--strict` перевіряє його, і разом вони не мають сенсу.

### Wiring (`# wiring`, `keylang wire`)

Контракт — [ADR 0003](adr/0003-wiring-lifecycle.md) (прийнято). `- wire <id>` — фабрика: fn (виклик з об'єктом іменованих залежностей) або клас (`new` з тим самим об'єктом). Дочірні `- <name> <id>` — залежність `name`, яку будує фабрика `<id>`. ID без власного `wire` — лист, він створюється без аргументів. Під залежністю `- when env.NAME = value → <id>` обирає іншу реалізацію, коли змінна середовища має саме це значення: `value` — одне слово, як його записано до `→` (кома — частина значення: `env.DB = a,b` порівнюється з `a,b`). Кілька `when` перевіряються в порядку запису, без збігу діє рядок залежності. `- compose <id>` обгортає значення fn одного аргументу; кілька `compose` застосовуються в порядку запису, перший найближчий до значення.

`check` перевіряє розділ разом з іншими специфікаціями. Невідомий ID — K001, повторний `wire` того самого ID — K002, як і дві залежності з одним ім'ям під одним `wire` (об'єкт аргументів мав би ключ двічі). Умова не у формі `env.NAME = value` — K005. Цикл між фабриками (через залежності та гілки `when`) — K301 з повним шляхом. K302 — те, що згенерований файл не може імпортувати чи викликати: модуль, шар чи тип як фабрика або залежність; `compose` не з fn (модуль, тип, клас); метод екземпляра класу (його нема на чому викликати). Статичний метод (`static` у знімку) — фабрика чи `compose`, що викликається на імпортованому класі: `Pool.open(deps)`; клас імпортується за своїм рядком експорту, default-клас удруге — як `default as`; ім'я, якого модуль не експортує; fn Python чи Rust (`wire` генерує TypeScript). Клас у знімку — вузол-модуль, оголошений у файлі свого батьківського модуля. Залежність (зокрема `when` і `compose`), яку забороняє `deny` між ID фабрики й залежності, — K102 з текстом правила та його `файл:рядок`.

Команда `keylang wire` описана в [cli.md](cli.md#wire).

`feature`, `baseline`, `agents`, `check --changed` і `hook stop` описано в [cli.md](cli.md#agents).

Інтеграція, якої ще немає в коді, — `planned module external.<pkg>` і крок потоку до цього модуля. Нового виду вузла немає. Доки пакет ніхто не імпортує, ID і static лишаються `unverified` «planned». Коли модуль кроку-батька імпортує пакет, `planned` дає K202, а static — `ok` («imported by»). Власного файла пакет не має, тож місце в K202 — перший (за шляхом і рядком) імпорт: `is implemented (imported by src/mail/mail.service.ts:2)`. Імпорт з іншого модуля чи лише type-only імпорт (`import type`) K202 може дати (вузол пакета вже є), але static цього кроку лишається не `ok`, і `feature` має прогалину `static`.

### Версії формату

Поле `format` у `keylang.json` — редакція мови, за якою keylang читає специфікації. Назва збігається з прапорцем `check --format`, але той задає вигляд звіту (`human`, `json`, `sarif`, `github`), а не редакцію мови.

| Версія | Значення |
|---|---|
| 1 | Мова цього документа, v0.2. До заморожування v1 (design.md, етап M3, тікет 40 у `.scratch/design-v0.2/`) текст ще змінний. Непорівнювані `allow` і `deny` вирішує сума глибин; за рівності — `deny`. |
| 2 | Поточна редакція. Серед правил, яких ніхто не домінує, перемагає `deny` (deny-overrides). Щоб лишити переможцем `allow` із більшою сумою глибин, додайте правило на перетині: `allow` або `deny` з вужчим джерелом і вужчою ціллю. |

Поле відсутнє — редакція 1, тож уже написаний `keylang.json` не змінює значення після оновлення пакета. Файла `keylang.json` немає — поточна редакція (зараз 2): так читаються `examples/`, `validate_spec` у теці без конфігу і вгаданий конфіг. Ціле, більше за відому редакцію, — код 2 з назвою файла й поля `format` і порадою оновити keylang. Рядок, `null`, нуль, від'ємне чи дробове число — теж код 2: поле має бути додатним цілим. Відмовляє кожна команда, що читає конфіг, включно з `fmt` і `parse` (вони читають лише це поле).

Несумісна зміна значення вже написаних текстів потребує нової редакції. Редакція 1 підтримується до наступної мажорної версії пакета: прибрати її можна лише мажорним релізом. `fmt` мовчки не мігрує: не змінює поле `format` і не переписує тексти під іншу редакцію. Команди міграції немає; автор змінює текст сам. `init` на новому репозиторії і `draft map` без файла пишуть поточну редакцію першим ключем. Наявний `keylang.json` `init` не переписує.
