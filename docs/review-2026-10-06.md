# keylang — рев'ю 2026-10-06: state machine, баги, ризики в продакшні

Дата: 2026-10-06. Охоплення: коміт `45cc74d` (0.6.0), тобто 159 комітів після `2f01c9a`, де закінчилося [рев'ю 2026-10-05](review-2026-10-05.md). Рев'ю складається з трьох частин:

1. Чи будувати в keylang state machine.
2. Пошук багів, кожну знахідку перевіряли на відтворення.
3. Які проблеми виникнуть, коли keylang використовуватимуть на продакшн-проєкті.

Базовий стан: `npm run typecheck` дає 0 помилок (41 с). Повний `npm test` (≈15 хв) не запускали. Верифікатори запускали окремі тест-файли й сам CLI на фікстурах у тимчасовій теці. Репозиторій не змінювали.

Рівні такі самі, як у рев'ю 2026-09-28 і 2026-10-05:
- **P1:** хибний `ok`/`fail` основної перевірки, запис поза дозволеними цілями, падіння на валідному вводі;
- **P2:** хибний результат окремого правила чи команди, порушений задокументований контракт;
- **P3:** граничний випадок.

## Головне

1. **State machine.** Окрему секцію `# machine` зараз не будувати. keylang не бачить значень полів: у знімку немає ребер запису, а в trace span немає даних. Тому для головної властивості автомата, «нелегального переходу немає», чесного `ok` keylang дати не може. Робити поетапно:
   - **Зараз.** Задокументувати рецепт з наявного синтаксису: по fn на перехід, `deny`/`allow`/`exports`, табличний тест. Виправити trace, який уже сьогодні дає хибний зелений результат на сценаріях життєвого циклу.
   - **Після v1.** Тікети pl-theory 45–47 (`never`, `at-most`, `never … before`).
   - **Лише якщо проба зручності Р-14 покаже попит.** Контекстні слова `states`/`on`/`initial`/`final` всередині `# flow` і необов'язкове поле `state:{before,after}` у trace.

   Інше прочитання питання — явний FSM у самому TUI. Тут відповідь «так, частково»: неявні режими вже дали три відтворені баги MERGE (§1.5).
2. **Баги.** Підтверджено 68 знахідок: P1 — 17, P2 — 31, P3 — 20. Ще 3 кандидати відкинуто як задокументовану поведінку. 67 знахідок відтворено фікстурами. Головні класи P1: Виправлення: ✔ наприкінці заголовка пункту — злито в master (стан оновлюється в міру злиття тікетів з `.scratch/review-2026-10-06/`).
   - зріз `--changed`, від якого залежать `hook stop` і `feature`, губить K104 (`exports`), K105 (`no-cycles`) і перейменування лише регістром, тож агент проходить хід з порушенням;
   - резолвер дає хибний `ok` у `deny` через pnpm-workspace, `paths` вкладеного tsconfig, Rust-workspace не в корені, виключений barrel і регістр на APFS/NTFS;
   - `clone` чужого репозиторію через закомічені symlink видаляє й пише файли поза клоном, а `--agents=none` переписує чужі конфіги харнесів;
   - брама пропозицій перевіряє зарезервовані теки за текстом шляху, і виправлення ✔ п. 3 з минулого рев'ю неповне;
   - trace-адаптери (TS, Python, PHP) губляться при fork, `worker.terminate()` і SIGTERM, а результат — хибний `fail missing step` або код 2.
3. **Продакшн.** Найімовірніші проблеми:
   - агент послаблює специфікацію замість того, щоб виправити код (`allow`, `baseline`, `exclude`);
   - `hook stop` і `check --changed` не працюють як gate;
   - монорепо дають мовчазний `ok`;
   - звіти tests/trace можна підробити;
   - «N ok» читають як «сценарій коректний»;
   - на 5000 файлах хук займає 15–50 с.

   Чекліст для команди і пріоритети виправлень наведено в §3.

Як проводили рев'ю, описано в кінці файла (§4).

## 1. Чи будувати в keylang state machine


### 1.1. Рішення

**Окрему конструкцію state machine зараз не будувати. Будувати по частинах і по етапах.** keylang бачить імпорти, виклики й типи (`EdgeKind`, `src/snapshot.ts:24`) і spans, у яких немає даних (`TraceSpan`, `src/trace-evidence.ts:19-26`). Головна властивість автомата, «нелегального переходу немає», стосується значення поля конкретної сутності, тому чесного `ok` для неї keylang не дасть. Спершу треба виправити trace, який уже зараз дає хибний зелений результат. Ключові слова автомата всередині `# flow` варто додавати лише після v1, після тікетів 45–47 і коли проба Р-14 покаже попит.

### 1.2. Що можна вже зараз

Рецепт без нової граматики (позиції ключових слів: `src/parser.ts:136-155`):

```markdown
# rules
- deny infrastructure domain.order.transitions
- allow application.order domain.order.transitions
- module domain.order.transitions
  - exports pay, ship, refund, IllegalTransition

# flow order-refund
- trigger application.order.service.refundOrder
  - step domain.order.transitions.refund
  - when the order is delivered
    - then domain.order.transitions.IllegalTransition
      - test tests/order.test.ts "refund rejects delivered"
- invariant переходи відповідають таблиці draft→paid→{shipped,refunded}
  - test tests/order.test.ts "transition table"
```

Як це працює: на кожне ребро є окрема fn. `deny`/`allow` і `exports` ловлять обхід через імпорт (K102) і новий публічний сетер (K104). Таблицю переходів перевіряє табличний тест. Тест треба класти під `then`, а не під `when`.

Чого цей рецепт не ловить:
- **Нелегальний перехід у trace.** Кроки зіставляються як підпослідовність, тому `pay, refund, ship` дає `trace ok`.
- **Прямий запис `o.status = "shipped"`.** Ребра запису в знімку немає.
- **Спробу переходу, яка впала.** Крок з `outcome:"error"` рахується як `ok`: поле читається (`src/trace-evidence.ts:152`), але Matcher його не використовує.
- **Неспрацьований guard.** `branch()` вважає гілку виконаною, якщо її перший крок, наприклад спільний хелпер, видно будь-де під батьком (`src/trace-evidence.ts:489-500`).
- **`when` без `step`.** Він ніколи не отримує `trace ok`.
- **Потік без тригера.** Він завжди має `static unverified: no trigger to reach it from` (`src/flows.ts:424`), тому під `--strict` не стає зеленим.
- **Правило на рівні fn.** Правила не беруть fn (K005).
- **Проза в `when` і `invariant` без `check.tests`.** Вона просто мовчить.

### 1.3. Рекомендований шлях

**Фаза 0, зараз, незалежно від автоматів.** Це виправлення помилок, знайдених під час ревю:
1. Якщо всі spans кроку завершились з `outcome:error`, вердикт має бути `unverified (ended with error)`, крім кроків під `when`. Це треба вирішити до 45–47, інакше `at-most` рахуватиме і відхилені спроби, і ретраї.
2. `src/adapters/trace.ts:124` пише події лише в `process.on("exit")`. Дочірній процес, убитий SIGTERM, не пише нічого, а `run` при цьому з `complete:true`. У результаті хибний `trace fail: missing step` замість `unverified`. Події треба скидати по ходу або писати маркер старту процесу, а буфер обмежити.
3. `branch()`: вимагати span, унікальний для гілки. Для `when` без `step` доказ брати з `test`.
4. Для потоку без тригера static не потрібен.
5. `normalizeSignature` (`src/flows.ts:821`) прибирає лише пробіли. Через це той самий union у іншому порядку дає хибну K201. Union треба порівнювати як множину.
6. У `quantitative()` (`src/flows.ts:238-240`) немає меж слова для кирилиці: «рівно» спрацьовує на «рівномірно». Також треба однаково обробляти «every» і «only».
7. У підсумку `check` показувати підказку, що є твердження без каналу доказів.
8. Описати рецепт і таблицю його меж у документації.

**Фаза 1, коли заморожено v1.** Реалізувати тікети 45–47. У semantics.md прямо записати, що властивості рахуються на кожен виклик тригера, а не на сутність: два замовлення в одному тесті дають хибні `ok`/`fail`. Додати в `docs/usability-probe.md` завдання з життєвим циклом. Четвертий шаблон, `never <b> after <a>` (Dwyer «absence after», для поглинальних станів), додавати лише якщо проба його вимагатиме.

**Фаза 2. Тригер:** у пробі Р-14 щонайменше 2 з 5 учасників самі пишуть правила життєвого циклу, які 45–47 не виражають, або трапився інцидент, який тест пропустив. Ескіз синтаксису, контекстні слова всередині `# flow`:

```markdown
# flow order-lifecycle
- states domain.order.Order status
  - initial draft
  - on domain.order.pay draft → paid
    - test tests/order.test.ts "pays a draft"
  - on domain.order.refund paid, shipped → refunded
  - final refunded
```

Що перевіряється і чим:
- **Сама специфікація** (діагностики, не вердикти): невідомий стан, немає `initial`, стан недосяжний з `initial`, тупик у стані без `final`, вихід із `final`. Усе це розв'язне на скінченному графі.
- **ID.** Fn із `on` є у свіжому знімку → `ok`. Висячий ID → K001. `planned` чи opaque → `unverified`.
- **static.** Лише одне: чи збігається множина станів зі знімком, як множина літерального union. Для enum, `string` чи значень із БД → `unverified`. Твердження «інших переходів немає» статично не звітується взагалі.
- **tests.** Тест під `on` перевіряється як у потоках.
- **trace.** Необов'язкове поле `state:{before,after}` у події `end`. Схема 1 ігнорує невідомі поля, тож розширення сумісне. Кожен виклик перевіряється окремо, як трійка Хоара: `ok`, якщо `before ∈ from` і `after = to`; `fail`, якщо такої пари в жодному `on` цієї fn немає. `fail` тут — позитивне спостереження, тому він надійний і в неповному запуску. `before = after` не відкидати мовчки, бо інакше подвійний refund не видно: або петля оголошена явно, або `unverified`. Для імутабельного стилю `before` береться з аргументу, `after` — з результату. Ідентичності сутності й PII цей підхід не потребує. Першим робити адаптер для TS.
- **unverified у trace,** коли немає `state` (старий адаптер, Python/PHP/Rust, `pay(orderId)` з читанням із БД), значення не є оголошеним станом, є лише error-spans або знімок застарів. `ok` на рівні всієї машини немає ніколи.

### 1.4. Чого не робити

- **Не робити окрему секцію `# machine`.** Сьогодні це валідний текст: K006 є лише warning (`src/diag.ts:54`), а `- draft` оголошує шар. Нова секція змінила б значення валідного тексту, тож за ADR 0007 потрібна редакція 3. Слова всередині `# flow` зараз дають K004, тому там зміна додавальна.
- **Не додавати guards над даними, лічильники («retry ≤ 3»), statecharts, wildcard.** Лічильник — це вже автомат зі змінними. Такі речі лишаються прозою з тестом або `at-most`.
- **Не витягувати автомат із коду так, що з'являються вигадані ребра.** Прототип прочитав Prisma `where:{status:"paid"}` як запис стану, а ORM, SQL і `Object.assign` невидимі. Максимум — представлення за ADR 0014, яке `check` не читає.
- **Не прирівнювати шаблони ADR 0009 до автомата.** LTLf покриває лише star-free частину регулярних мов.
- **Не додавати `subject` у trace першим кроком:** це PII і чотири адаптери.

**Що зламається на продакшн-проєкті:**
- Стан пишуть ORM, SQL, міграції, вебхуки: немає ні ребра, ні span.
- Життєвий цикл розтягнутий на кілька запитів, черг і cron. Це різні дерева викликів, а `never ship before pay` на тесті із засіяним станом дасть `fail`.
- Кілька сутностей в одному тесті дають хибні `ok`/`fail`.
- Ретраї та ідемпотентні повтори ламають `at-most`. Конкурентні refund trace не відтворить.
- У prod-trace є sampling і `dropped > 0`. `snapshotId` деплою не збігається з робочою копією, а новий файл у корені робить застарілими всі trace і звіти тестів.
- Команда звикає до `unverified` і перестає його читати. Зелений потік читають як «автомат коректний».

### 1.5. State machine всередині keylang (TUI)

**Так, явний FSM варто зробити, але частково і без бібліотеки.** Неявний стан уже дав три відтворені баги:

- **C, фантомний MERGE.** `open()` кладе в стек повернення `mode:"merge"` (`src/tui/app.ts:785`), а тип `Place.mode: Mode` це дозволяє (`src/tui/state.ts:349-353`). `goBack` відновлює `mode` при `merge=null` (`app.ts:1266`), після чого `merge-session.ts:235` ковтає Esc, `q` та `i`.
- **A, рішення MERGE тихо губляться.** Enter на записі F6 відкриває MERGE без перевірки, чи не триває вже інший (`src/tui/results-panel.ts:109-112`). `open()` перемикає `merge` на `view`, але `state.merge` не очищає (`app.ts:792`).
- **B, клік проходить крізь палітру й help.** `app.ts:1280` враховує лише `barrier` і `quit`. Загалом «що зараз модальне» обчислюється в семи місцях, і набори різні.

Порядок робіт:
1. Локальні виправлення (S).
2. Оракул інваріантів у `send()` у `tests/tui-helpers.ts`: `mode==="merge"` ⇔ `merge!==null`, у стеку повернення немає `merge`/`code`.
3. Тип `Screen` як discriminated union, одна функція `inputLayer()`, тип `OpPhase` для cancel/commit/quit.

XState не потрібен (ADR 0002).

### 1.6. Відкриті питання до автора

1. Яка мета автомата: вхід для агента, перевірка в CI чи візуалізація? Від цього залежить, що будувати: рецепт, фазу 2 чи Mermaid.
2. Цільові життєві цикли живуть у межах процесу (retry, з'єднання) чи зберігаються в БД (замовлення, платіж)? Чи входять цикли між запитами в обсяг keylang?
3. Який вердикт давати кроку з `outcome:error`? Чи дозволена помилка під `when`?
4. Тікет 47: `<b>` без `<a>` давати `fail`, як зараз, лише задокументувавши, або `unverified` для тестів із засіяним станом?
5. Чи прийнятно, що keylang читає значення стану (`state:{before,after}`) у trace? Це зміна принципу, а не просто фіча.

## 2. Рев'ю реалізації: баги

Знахідки не повторюють пунктів рев'ю 2026-10-05, крім випадків, де виправлення з ✔ виявилося неповним (п. 14). У колонці «Місце» вказано місце дефекту, яке уточнили верифікатори. Воно може відрізнятися від рядка, де дефект проявляється. Дублікат (обрізання пропозиції скрепки на вкладеній огорожі коду) злито в один пункт P2.

### 2.1. P1 (17)

#### Хибний `ok` у зрізі `--changed` / `hook stop` / `feature`

**1. `check --changed`, `hook stop` і `feature` гублять K104 правил `exports`** — `src/changed.ts:113` ✔

- **Що:** `ruleHits` у `filterChanged` збирає лише `dependency`, `layers`, `entry` і `no-cycles`. Правила `module X / exports …` там немає взагалі. K104 стоїть на рядку `rules.md`, а не в зміненому файлі коду, тож зріз `--changed` його завжди відкидає. Через `thisChange` (`feature-status.ts:337`) той самий K104 у `feature` стає успадкованою підказкою. Причина: `fail.id` — це модуль, а `isNamed` перевіряє лише, чи лежить кінець під ID фічі, і не перевіряє зворотне.
- **Сценарій:** `rules.md`: `- module domain.b` / `  - exports b`. Агент дописує в `src/domain/b.ts` `export function leaked()`. Повний `check` дає K104 і код 1. `check --changed` дає «0 fail» і код 0, `hook stop` повертає `{}` і агента не зупиняє. На гілці з фічею `planned fn domain.b.leaked ()`, що реалізує цей експорт, `keylang feature leak` друкує `hint … inherited (no file changed since merge-base …, no id of this feature)` і `done`, код 0. Насправді `src/domain/b.ts` змінено, а `domain.b.leaked` — ID фічі. Це суперечить cli.md: «правила, чия область містить змінений модуль».
- **Виправлення:** Додати в `ruleHits` гілку `rule.kind === "exports"` з `scope: [rule.module.target]` і `criterion: \`exports ${rule.module.target}\``. В `isNamed` у `thisChange` рахувати fail своїм і тоді, коли ID фічі лежить під `fail.id`. Додати тест: `check --changed`, `hook stop` і `feature` з K104.

**2. `--changed` бере для `no-cycles` під модулем лише сам модуль, а не його область** — `src/changed.ts:120` ✔

- **Що:** Для `module M / no-cycles` зріз `--changed` має scope `[M]`. За semantics.md область такого правила — M, його підмодулі і все, що вони досягають import/re-export. Цикл, який створила зміна файла поза M, дає K105 у повному `check`, а `check --changed` і `hook stop` його відкидають.
- **Сценарій:** `src/app/a.ts` імпортує `../domain/b.ts`, у `rules.md` стоїть `- module app` / `  - no-cycles`. Агент змінює лише `src/domain/b.ts` і додає `import { a } from "../app/a.ts"`. Повний `check` дає `K105 divergence: dependency cycle app.a → domain.b → app.a` (exit 1). `check --changed` дає `0 fail, 0 unverified, 0 ok` (exit 0), `hook stop` повертає `{}`, тож хід з новим циклом проходить. `feature` теж вважає цей K105 успадкованим: `fail.id` = `app`, а ID фічі лежать під ним.
- **Виправлення:** Передати в filterChanged ребра import/re-export (без typeOnly) і для `no-cycles` під M брати область як M, його підмодулі й усе, що з них досяжне (як area() у semantics.md), або просто лишати K105 цього правила, коли SCC містить змінений модуль.

**3. Перейменування файла лише регістром (core.ignorecase) ховає зміни від `check --changed` і `hook stop`** — `src/git-changes.ts:83` ✔

#### Trace-адаптери: хибний `fail` і падіння `check`

**15. Python trace-адаптер не обробляє fork: кроки в процесі-воркері губляться або check падає з кодом 2** — `adapters/python/keylang_trace.py:235` ✔

- **Що:** Адаптер не реєструє `os.register_at_fork`. Дочірній процес після fork успадковує колбеки `sys.monitoring`, `clock`, лічильник span-ів і вже накопичені `lines`. Воркер `multiprocessing` (fork, типово на Linux для Python 3.12) виходить через `os._exit`, тож `atexit` не спрацьовує і його span-и мовчки зникають. Батьківський процес при цьому пише `instrumented` з цим кроком і `complete: true`. Дочірній процес після `os.fork()`, що завершується звичайно, дописує копію подій батька з тими самими `spanId`.
- **Сценарій:** (1) `main()` викликає `Pool(1).map(crunch, …)`, потік `trigger app.main.main / step app.work.crunch`. Після запуску під адаптером `keylang check` дає `trace fail app.work.crunch: missing step in run.py > @flow crunch`, exit 1, хоча `crunch` виконався (вивід `[2, 4]`). (2) `main()` робить `os.fork()`, і обидва процеси викликають `crunch`. `keylang check` завершується кодом 2: `.keylang/trace/crunch.jsonl:6: span py-…:s1 started twice in run …`. Падає вся перевірка, не лише цей потік.
- **Виправлення:** Зареєструвати os.register_at_fork(after_in_child=…): у дочірньому процесі брати новий clockId і очищати lines, open, spans і стеки потоків. Скидати JSONL дочірнього процесу не лише через atexit, а й через multiprocessing.util.Finalize або обгортку os._exit. Інакше задокументувати, що fork-процеси не трасуються, і давати unverified замість missing step.

**16. Spans, що буферизуються до виходу, губляться при worker.terminate() чи kill дочірнього процесу, а крок стає хибним `fail missing step`** — `src/adapters/trace.ts:124` ✔

- **Що:** TS-адаптер тримає всі події в пам'яті (`lines`) і пише їх лише в `process.on("exit")`. Цей обробник не викликається, коли воркер зупиняють через `worker.terminate()`, коли головний процес робить `process.exit()` при живих воркерах, і коли дочірній процес вбито сигналом SIGTERM/SIGINT. Головний процес за ADR 0018 усе одно вносить у `instrumented` увесь план, «завантажив чи ні». Тому крок, що виконався у втраченому процесі, отримує `trace fail … missing step`, хоча документація (cli.md, «Воркер пише власні корені…») обіцяє `trace unverified`. У Rust і PHP та сама схема: Rust пише лише у `finish()`, PHP — у shutdown-функції, і SIGTERM без обробника pcntl їх пропускає.
- **Сценарій:** Тригер `app.main.main` викликає крок `app.w.inWorker` у worker_threads, як це роблять пули piscina, tinypool чи workerpool, і в кінці викликає `worker.terminate()`. Або e2e-тест запускає `fork()` сервера під адаптером і в кінці робить `server.kill()`. Подій воркера чи дочірнього процесу в trace немає. Run головного процесу має `instrumented` з цим кроком, і `check` дає `fail app.w.inWorker: missing step in t` з кодом виходу 1. Коли той самий воркер чи процес завершується сам, результат правильний: `unverified … observed outside app.main.main in another call tree`.
- **Виправлення:** Писати події в файл одразу (appendFileSync на кожну подію чи на кожен end) замість буфера до exit, а в trace-evidence вважати clockId без власної події `run` неповним запуском (unverified, не missing step); для дочірніх процесів ще й обробити SIGTERM/SIGINT: скинути буфер і повторно надіслати сигнал.

**17. PHP: pcntl_fork дублює буфер подій і лічильник span, тож check падає з кодом 2** _(статус: plausible — код-шлях очевидний, відтворення без PHP-середовища не робили)_ — `adapters/php/keylang_trace.php:109`

- **Що:** Події лежать у `$this->lines` до кінця процесу. `clock` (`php-<pid>-<rand>`) і лічильник `spans` створюються один раз в `install()`. Після `pcntl_fork()` дочірній процес отримує копію буфера, того самого годинника й того самого лічильника. Його `exit()` запускає `register_shutdown_function([$trace,'finish'])` і дописує скопійовані події ще раз. До того ж наступні span дочірнього й батьківського процесів отримують однакові `spanId`. `loadTraces` у такому разі кидає «span … started twice», і `check` завершується з кодом 2. Це той самий клас, що й підтверджений P1 у Python-адаптері.
- **Сценарій:** PHPUnit з `-d auto_prepend_file=keylang_trace.php` і розширенням keylang. Тест викликає тригер, а код усередині форкає процес: spatie/fork, Laravel `Concurrency::driver('fork')` або ручний `pcntl_fork(); … exit(0);`. Дочірній процес на `exit` пише всі буферизовані з початку процесу `start`/`end` (зокрема з попередніх тестів) і свої span `php-<pid>-<rand>:sN`. Батьківський процес наприкінці пише ті самі рядки. Будь-яка наступна `keylang check` чи `feature` падає: `keylang: .keylang/trace/f.jsonl:N: span \`php-…:s1\` started twice in run …`, код 2. Перевірка потоків у CI зламана, доки файл trace не видалено.
- **Виправлення:** Зберігати pid з install() і в start()/event()/finish() при зміні getmypid() скидати успадкований $lines, створювати новий clock з новим pid і обнуляти spans/seq/open/stack; або скидати буфер у файл після кожного тесту.

### 3.2. Решта

- **Точність.** TS `paths` беруться лише з кореневого tsconfig: у Nx імпорти лишаються unresolved, а спільний `@/*` у двох застосунках дає вигаданий K102. `@OnEvent`, `@CommandHandler` і Laravel `event()` дають хибний `static fail` з порадою «add a call», яка ламає архітектуру. Python `TYPE_CHECKING` дає хибний K105. Шлях у сигнатурі Rust обходить `deny`. Проблемні також `_ide_helper.php` і пакети, що віддають `dist` (усе експ.). Dynamic-викликів у рази більше, ніж resolved (bench M5). Міжсервісні HTTP/gRPC-межі невидимі (спек.).
- **Масштаб.** Heap росте приблизно на 0.1 МБ на файл; OOM на 5000 файлах при 320 МБ (експ.). Цифри для 50 тис. файлів — екстраполяція, RangeError на ~120 тис. — спек. Gitignored build і codegen індексуються; файл на 26 МБ — 254 с і ~5 ГБ RSS (експ.). MCP і LSP перебудовують знімок на кожен запит, 7.6 с на 2000 файлах (експ.). Зміна джерел під час аналізу не перевіряється, хоча design.md:200 обіцяє протилежне (код).
- **Команда.** Кілька `keylang.json` у монорепо: pre-commit блокує всі коміти, а хук із кореня повертає `{}` (експ.). `npx` без версії; версія вшита в 5 згенерованих файлів, а різні версії скидають кеш (експ., код). snapshotId рахується по всьому репо, тож тести лише зачеплених пакетів дають `unverified` (код). Перейменування дає K001 без міграції. `--stale` перетворюється на автоматичний `--accept`. Кожна нова залежність дає K102 і чергу до власника правил (експ.). Версія 0.x, формат не заморожено, один супровідник, немає `uninstall` (docs).
- **Агенти.** Пропозицію можна підмінити між `show` і `accept`, а стара пропозиція стирає новий `deny` колеги (експ.). `init` стирає коментарі в TOML, перезаписує кастомний хук і падає на JSONC (експ.). `explain --missing` на 147 файлах — ≈455 тис. вхідних токенів, без бюджету й без backoff (експ.). Прапорці агент-CLI можуть змінитися з новою версією (код).
- **Безпека.** `web --host 0.0.0.0` з рецепта Dockerfile приймає чужий Host, а токен іде відкритим ws://. Symlink і `check.tests: "../…"` читають файли поза репо й виводять їх у лог. `core.fsmonitor` виконується під час `check --changed`. ESC/OSC-послідовності потрапляють у вивід CLI. `apply_diff` на 50 МБ валить MCP (усе експ.). 106 прод-пакетів через `npx` без shrinkwrap (код). Майбутній TS-backend виконуватиме код репо (спек., ADR 0020).

### 3.3. Що команді зробити до впровадження

- [ ] **Версії.** Точний пін у devDependencies. Хук, MCP і CI викликають `node_modules/.bin/keylang`. Оновлення — окремим PR з `map`, `agents`, `baseline` і повним прогоном тестів.
- [ ] **CI.** Повний `check`. Якщо потрібен diff — `fetch-depth: 0` і `--since "$(git merge-base origin/$BASE HEAD)"`. Гейт на `feature` вимагає `info.base.source == "merge-base"`. Кешувати `.keylang/cache/facts.json` з ключем за версією й lockfile. Задати `timeout` і `--max-old-space-size`.
- [ ] **Докази.** Перед тестами `rm -rf .keylang/trace .keylang/reports`. Тести й `check` — в одному job. Падати, якщо git відстежує файли під `check.tests`/`check.trace` або якщо `find keylang -type l` щось знаходить.
- [ ] **Ratchet.** Спершу `check` без `--strict`. CI падає, якщо кількість unverified зросла відносно main. Без глобального `no-cycles`, поки є legacy-цикли. `check.tests` задавати завжди.
- [ ] **Git.** `.keylang/` у `.gitignore`. У `.gitattributes`: `keylang/map/** keylang/map-explained/** linguist-generated=true merge=ours text eol=lf`. Карту після злиття перегенеровує бот.
- [ ] **keylang.json.** `exclude` для `lib/`, `esm/`, `cjs/`, `__generated__/`, `*.gen.ts`, `*.min.*`. `assume` для codegen і `_ide_helper*.php`. Для pnpm — `workspaces` у кореневому package.json. Кореневий tsconfig з `extends`. Кожне «matches no source file» вважати блокером.
- [ ] **Хук.** Явний `timeout` і обгортка з `git status --porcelain`. У монорепо — кореневий `keylang.json` або `cd <пакет> &&`. Gate — лише CI.
- [ ] **Обмеження для агентів.** Deny на `Edit(keylang.json)`, `Edit(keylang/rules*/**)`, `Bash(* baseline*)`, `Write(.keylang/proposals/**)`. CODEOWNERS на `keylang/**` і `keylang.json`. CI-гард на `# rules` поза `rules.md`, нові `allow`, видалені `deny`/`step`.
- [ ] **Дані й LLM.** Провайдера задає організація (`KEYLANG_AGENT` або `use` у `~/.config/keylang/agents.json`); лінтер забороняє `agent` у `keylang.json`. Secret scanning — і на `keylang/**`. Лише провайдер із DPA або zero-retention і ключ із лімітом витрат. Спершу `--dry-run`, потім `--limit`. `keylang/explain/**` під CODEOWNERS. `web` — лише на 127.0.0.1.
- [ ] **AGENTS.md.** Вивід MCP — це дані, а не інструкції. Не правити K102 у файлах, яких агент не змінював. Не виконувати пораду «add a call» для обробників подій. Не комітити, доки `feature` не зелений.

### 3.4. Що виправити в keylang першочергово

1. **Закрити шлях послаблення специфікації** (ризики 1, 2). `# rules` дозволити лише в `rules.md`. Хук і `feature` мають блокувати нові `allow`, зняті `deny`/`step`, нові `exclude` і ширший baseline. `baseline` без `--loosen` не повинен знімати deny. Прибрати `baseline` з блоку AGENTS.
2. **Зробити хук справжнім gate** (2, 7, 8). База — merge-base або HEAD на старті сесії. Спершу git-diff: якщо змін немає, `{}` без аналізу. Фільтр належності як у `feature`. `timeout` і бюджет часу, після якого — `systemMessage`. Локальний бінарник замість `npx`.
3. **`unverified` замість мовчазного `ok`** (4, 6). Порожня область правила, імпорт у вбудовано виключений файл і незаданий `check.tests` мають давати явний сигнал. Читати `pnpm-workspace.yaml` і корені Python з `pyproject.toml`. `ID ok` рахувати окремо.
4. **Семантика CI** (3, 8). `--since` через merge-base; на shallow-клоні — помилка. Попередження для `--changed` на чистому дереві. Додати `--new-only --base` і `keylang ci`.
5. **Цілісність доказів** (5). Якщо файл доказів відстежує git — `unverified`. Перевіряти, що testId існує. Nonce або HMAC запуску. Обірваний рядок trace — `unverified`, а не exit 2.
6. **Масштаб** (7). Поважати `.gitignore` і `@generated`, ввести ліміт розміру файла. Паралельна екстракція, інкрементальний граф, спільний кеш для worktree.
7. **Карта без номерів рядків** (9). Якір за символом, нормалізація CRLF, `init` пише `.gitattributes`.
8. **Довіра до LLM-налаштувань** (10). `agent` з репозиторію — лише після явної довіри. Вирізати секрети з промптів і карти. Текстові поля MCP загортати в конверт `untrusted`.

### 3.5. Сигнали, за якими стежити після запуску

- p95 тривалості `hook stop`, частка ходів із «not checked» і таймаутами.
- Порушення, які дійшли до CI, хоча хук відповів `{}`.
- Тренд unverified і holes на main, `importsUnresolved`, власні пакети в `external.md`.
- PR, що змінюють `rules*.md`, `features/**`, baseline чи `keylang.json`; кількість нових `allow`.
- Червоний `map --check` на main; частота `--stale --accept`.
- Тривалість, maxRSS і exit 134 у CI-кроці; розмір `facts.json` і карти.
- Файли доказів, відстежувані git; `feature` з `base.source != "merge-base"`.
- Токени й помилки 429 у `.keylang/stats.json`; падіння MCP-сервера.

## 4. Методика й обмеження

- **Інструмент.** Дві фонові workflow, разом 120 субагентів. Репозиторій лише читали. Фікстури лежали в тимчасовій теці. Мережі, справжніх LLM і агент-CLI не використовували (замість них був `tests/fixtures/fake-agent.mjs`).
- **Баги.**
  - 11 рецензентів, по одному на зону: ядро мови, перевірка, TS-аналізатор, Python/Rust/PHP, карта й wire, CLI і харнес, безпечний запис, сервери й LLM, ядро TUI, нові функції TUI, операції.
  - Кожну знахідку окремо намагалися спростувати: для P1 — двоє верифікаторів незалежно (відтворення, код і контракт), для P2/P3 — один, що відтворює.
  - Знахідку відкидали, якщо спростування не менше, ніж підтверджень, і немає жодного відтворення.
  - Критик повноти додав чотири цільові пошуки: семантика правил і потоків, trace-адаптери не для Python, кросплатформні ФС, маніфести й external-ID.
  - Регістронечутливу ФС відтворювали на tmpfs з `casefold` (`unshare -rm`, `chattr +F`). Windows не запускали.
- **State machine.** П'ять незалежних підходів:
  - що можна вже зараз;
  - мінімальна конструкція;
  - автомат, витягнутий з коду;
  - скептик;
  - FSM усередині TUI.

  Два судді оцінили підходи з різних позицій (PL/верифікація і прод-інженер), потім висновки звели в одну рекомендацію.
- **Продакшн.** Шість напрямів: масштаб, команда і CI, покриття мов, агенти й LLM, безпека, людський фактор. Кожен ризик підкріплено кодом або експериментом.
  - Час заміряно при load avg 18–40 на 8 потоках, тож абсолютні значення завищені приблизно вдвічі.
  - Цифри для 50 тис. файлів — екстраполяція.
- **Обмеження.**
  - Повний `npm test` не запускали.
  - P2/P3 перевіряв один верифікатор.
  - Рівень знахідки — найнижчий із запропонованих рецензентом і верифікаторами.
  - Фікстури відтворень лежать у scratchpad сесії і після неї не зберігаються. Сценарії в таблицях достатньо конкретні, щоб відтворити їх заново.
