## 1. Навіщо

| Задача | Хто читає | Як keylang допомагає |
|---|---|---|
| Зрозуміти репозиторій | людина, AI | згенерована карта: шари, модулі, API, залежності — простим текстом з посиланнями на код |
| Виявити архітектурні порушення | CI | правила перевіряються на актуальному семантичному знімку; звіт показує види залежностей і повноту перевірки |

| Зібрати застосунок | рантайм (опційно) | `wiring` генерує DI-контейнер, як у Шемсединова |

## 2. Чотири режими однієї мови

Один Markdown-формат — чотири опційні режими. **Текстовий IR** зберігає написане, токени й spans для форматера та редактора. **Семантичний знімок (`AnalysisSnapshot`)** зберігає факти про код, їх походження й повноту аналізу. Правила та потоки компілюються з текстового IR у перевірювані твердження (`SpecIR`) і звіряються зі знімком. Компіляція вже відбувається: `compileSpec` (`src/spec-ir.ts`) будує SpecIR один раз у `assess`, і ця форма лишається внутрішньою — її немає в JSON. Парсер перевіряє форму рядка, `compileSpec` — форму твердження, check — те, що потребує знімка.

```
 код + конфіг → extract / resolve → AnalysisSnapshot
                                      ├→ 1. MAP + index.json
                                      │
 спеки *.md → текстовий IR → SpecIR ────┴→ check
                              ├ 2. RULES: що дозволено
                              ├ 3. FLOWS: заявлені сценарії
                              └ 4. WIRING → codegen → код
```

| Режим | Файли | Хто пише | Перевірка |
|---|---|---|---|
| **map** | `keylang/map/*.md` | генератор, **не редагувати** | представлення знімка; неповнота та актуальність видимі |
| **rules** | `keylang/rules.md` | людина | на семантичному графі з урахуванням покриття |
| **flows** | `keylang/flows/*.md` | людина (AI може чернетку) | статично + динамічно + тести |
| **wiring** | `keylang/wiring.md` | людина | компіляція згенерованого контейнера |

Чому map і specs окремо: генератор володіє лише файлами з маркером `keylang:generated`; ручні специфікації зберігаються. Spec-файли посилаються за **ID** на сутності коду або явні декларації `planned`. Видалення функції з повністю проіндексованого модуля дає K001 навіть тоді, коли це була його остання функція. Приклад помилки зі слайдів: `order: 'domain.aggregate'` при модулі `orderAggregate`.

Markdown-карта є вихідним представленням, а не сховищем доказів для `check`. Її повторний розбір не відновлює втрачені відомості про нерозв’язані імпорти, експорти чи точність ребер. Перевірка лише Markdown може підтвердити структуру документа й внутрішні посилання, але не відповідність поточному коду.

## 3. Синтаксис

Канонічна форма — Markdown. Файл має читатися в GitHub як звичайний документ і водночас бути однозначно розбірним.

### 3.1 Базові правила

- Вузол — елемент списку: `- <kind>? <name> <args…>`.
- Ієрархія задається відступом (2 пробіли), як у Шемсединова.
- **ID** — крапковий шлях від кореня: `application.purchase.buy`. Посилання в spec-файлах записуються через ID. Зміна рядків не змінює ID; перейменування або перенесення між шарами потребує явного оновлення посилань. Колізії нормалізованих імен діагностуються, а не зливають різні сутності мовчки.
- **Прив'язка до коду** — Markdown-посилання відносно файла карти: для `keylang/map/application.md` це `[buy](../../src/app/purchase.ts#L12)`. Індекс зберігає POSIX-шлях від кореня репозиторію; emitter рахує відносний URL та кодує спеціальні символи, наприклад `%28shop%29` для `(shop)`. Навігація декодує URL назад у шлях.
- Звичайний текст під вузлом, без `- `, вважається описом вузла. За змістом він не перевіряється, але отримує позначку `stale`, коли код описаного вузла змінився (§4).
- Основні ключові слова: `layer`, `module`, `fn`, `type`, `event`, `allow`, `deny`, `entry`, `flow`, `step`, `when`, `then`, `invariant`, `test`, `wire`; точний перелік за позиціями — у [format.md](format.md). `planned` та `assert` — цільові розширення M2. Верхньорівневий елемент без ключового слова означає шар (сумісність зі слайдами). Генератор не використовує зарезервовані в цій позиції слова як неявні aliases залежностей.

**Повнота модуля.** Знімок розрізняє `members: complete` і `members: opaque`. Порожній список у повністю проіндексованому модулі означає, що членів немає. `opaque` явно задається для невідомого вмісту, зокрема зовнішніх модулів, і означає `unverified` для посилання на невідомого члена. Сумісність зі слайдовим описом не дає підстав підтверджувати існування довільного символу в коді.

### 3.2 Map (генерується)

Приклад вмісту файла під `keylang/map/`; показано фрагмент карти, решта згаданих модулів міститься в інших згенерованих файлах.

```markdown
<!-- keylang:generated — не редагувати, `keylang map` -->
# map

- domain
  - module [orderAggregate](../../src/domain/order.ts#L1)
    - fn [create](../../src/domain/order.ts#L8) (items: Item[]) → Order
    - fn [total](../../src/domain/order.ts#L21) (order: Order) → Money
- infrastructure
  - module [logger](../../src/infra/logger.ts#L1)
    - options infrastructure.config.log
    - fn [log](../../src/infra/logger.ts#L14) (level, msg)
  - module [orderStore](../../src/infra/order-store.ts#L1)
    - fn [save](../../src/infra/order-store.ts#L9) (order: Order) → Promise<void>
- application
  - module [purchase](../../src/app/purchase.ts#L1)
    - order domain.orderAggregate
    - catalog infrastructure.products
    - orders infrastructure.orderStore
    - fn [buy](../../src/app/purchase.ts#L12) (cart: Cart) → Promise<Order>
      - calls domain.orderAggregate.create, infrastructure.orderStore.save
```

Рядок `alias path` під модулем позначає залежність, як на слайдах. `calls …` під функцією показує проєкцію ребер знімка; порядок переліку не задає порядок виконання. Повні відомості про ребра, нерозв’язані цілі й покриття зберігаються у знімку (§7).

**Контракт генератора:** до запису перевіряються всі цільові файли. Наявний файл без маркера генерації — конфлікт із діагностикою, а не дозвіл на перезапис; видаляються лише зайві згенеровані файли. Однакові джерела й конфігурація дають однакову карту. Згенеровані документи мають проходити власний парсер без структурних помилок: round-trip перевіряється зокрема для `type.ts`, імен із колізіями, пробілами та шляхів Next.js `(shop)/page.ts`.

Карта — це **модульно-залежнісний вигляд** коду (модулі, функції, ребра), а не компонентно-конекторна модель класичних ADL: семантику взаємодій вона не описує, це роблять flows. Якщо є SCIP-індекс, до вузла дописується його символ: `- fn [buy](…) (cart) → Promise<Order> <!-- scip: … -->` — так ID keylang детерміновано з'єднуються з іншими інструментами.

### 3.3 Rules (пише людина)

```markdown
# rules

- layers domain < application < presentation
  - infrastructure
- allow infrastructure presentation
- deny domain infrastructure
  Домен не залежить від infrastructure; це правило саме по собі не доводить відсутність будь-якого I/O.
- entry
  - infrastructure.server
  - presentation.terminal
- module application.purchase
  - exports buy, cancel
  - no-cycles
```

| Правило | Що перевіряє |
|---|---|
| `layers a < b` | між впорядкованими шарами залежності йдуть вниз; у невпорядкований шар — вільно, з нього у впорядкований — через `allow` |
| `allow a b` / `deny a b` | явний дозвіл або заборона залежності шару від шару чи модуля від модуля |
| `entry` | точки старту; недосягнуті модулі позначаються «не досягнуто в моделі» з поясненням покриття |
| `exports` | фактична таблиця публічних експортів відповідає переліку: функції, значення, класи, типи, aliases, default та re-exports |
| `no-cycles` | модуль не належить циклічній SCC у графі модульних `import` / `re-export`; маршрут циклу додається як пояснення |

**Політика невпорядкованих шарів — зберігаємо M1 (рішення 2026-09-27).** Без відповідного явного `allow` / `deny` діють такі правила:

| Залежність | Базова політика |
|---|---|
| усередині одного шару | дозволено |
| між впорядкованими шарами | вниз дозволено, вгору — порушення |
| у невпорядкований шар, зокрема `external` / `unassigned` | дозволено |
| з невпорядкованого у впорядкований | потрібен `allow` |
| порядок `layers` не задано | обмеження задають явні `allow` / `deny` |

Це узгоджує базову політику з [format.md](format.md) і M1. Водночас `unassigned` та пропущені файли залишаються явними у звіті покриття: дозвіл залежності не означає, що аналіз її цілі повний. `entry` обходить реальні ребра знімка; ієрархія ID сама по собі не робить батьків, дітей і сусідів досяжними. Навіть повна досяжність у цій моделі не є доказом виконання коду під час запуску.

**Які залежності бачать правила.** Цільові види ребер для `allow`/`deny`/`layers`: `import` (модуль → модуль, включно з літеральними `import()` / `require()` усередині функцій), `call` (fn → fn), `type` (посилання на тип) і `re-export`. Кожне ребро має власні позицію, походження та стан резолвінгу. Покриття обліковується за файлами, областями й видами ребер; непідтриманий вид не випадає мовчки. `keylang check --explain-edge a b` показує доказ у коді. Рефлексія, DI, event bus та обчислювані specifiers можуть залишити невизначеність (§4).

`exports` використовує таблицю експортів із резолвінгом aliases і re-exports, а не наявність коментаря `internal` біля fn. `no-cycles` перевіряє SCC, включно із self-loop; для правила на модуль достатньо його участі в циклі, навіть якщо інший DFS-маршрут знайшов цикл без цього модуля.

### 3.4 Flows — логіка застосунку (пише людина)

Один формат і для бізнес-логіки, і для технічної: ретраї, кеш, авторизація, міграції.

```markdown
# flow checkout
- kind business
- trigger presentation.terminal.checkout
- step application.purchase.buy
  - reads infrastructure.products.find
  - step domain.orderAggregate.create
  - step infrastructure.orderStore.save
  - emits event order.created
- invariant total = сума(price × qty) по позиціях
  - test tests/purchase.test.ts "computes total"
- when товару немає на складі
  - then application.purchase.OutOfStock
  - test tests/purchase.test.ts "rejects out of stock"
```

```markdown
# flow http-retry
- kind technical
- trigger infrastructure.http.request
- step infrastructure.http.send
- when status 5xx або timeout
  - then retry ≤ 3, backoff експоненційний
  - test tests/http.test.ts "retries 5xx"
```

`step` задає два різні твердження: **вкладеність** щодо батьківського кроку та **послідовність** сусідніх кроків. Статичний граф перевіряє перше як можливу досяжність; trace перевіряє фактичне вкладення й порядок для конкретного запуску. Для верхньорівневого `step` батьківським контекстом є `trigger`. Посилання на alias має однозначно зводитися до callable-цілі; інакше перевірка викликів — `unverified`.

Наприклад, у `buy() { validate(); save(); }` обидва кроки досяжні з `buy`. Шлях `validate → save` не потрібен і не описує послідовність. Для послідовних sibling-кроків trace має підтвердити завершення попереднього перед початком наступного; паралельне виконання не підміняється порядком часових міток. Синтаксис явних паралельних груп перевіряється до заморожування v1.

`reads` / `emits` описують заявлені ефекти; сама назва функції не доводить читання або емісії. Поведінкові `invariant` / `when` / `then` посилаються на тести; без доказу потрібний критерій лишається `unverified`. Успішний прив’язаний тест підтверджує його результат, а не автоматично істинність усієї прози.

- `assert` може зв’язати інваріант з ідентифікованою runtime-перевіркою: trace фіксує її виконання та результат. Ідентичність assertion і граматика посилання визначаються у наскрізному M2-сценарії; самого факту входу у функцію недостатньо.
- Потік може бути чернеткою, вести код або наздоганяти його. Майбутні вузли оголошуються як `planned` (§3.5); звичайне невідоме посилання лишається K001.
- Перевірюваний сценарій має однозначний `trigger` і прив’язку до тесту/гілки. Неповна чернетка та гілка `when`, яка не виконувалася в цьому тесті, не отримують підтвердження виконання.
- Дублювання потоків визначається з урахуванням порядку, вкладеності та умов, а не лише набору `step`. Попередження K007 — заплановане розширення, його контракт уточнюється в M2.

### 3.5 Заплановані вузли (`planned`)

`planned` — явна декларація наміру в ручній специфікації, окрема від фактів знімка. Вона задає ID, вид символу, очікувану сигнатуру та область/місце реалізації. Фрагмент цільового синтаксису (граматика уточнюється в M2):

```markdown
- planned fn application.purchase.refund (order: Order) → Promise<Refund>
- step application.purchase.refund
```

Шар і шлях реалізації беруться з конфігурації або задаються явно, якщо відображення неоднозначне. Посилання дозволене на наявний ID знімка чи на декларацію `planned` у наборі специфікацій. Відсутній ID без декларації у повністю проіндексованій області — K001; для явно неповної області діє `unverified` із §3.1. Дублікати декларацій і невідповідність наміру виду/контракту наявного символу діагностуються; збіг із реалізованим символом дозволяє закрити намір.

Planned-вузол показується як **заплановано**, а перевірка його реалізації — `unverified`. Він не додає виконуваних ребер до знімка й не задовольняє правило як уже реалізований модуль. Після появи коду звіряються вид і контракт символу; лише тоді намір можна закрити. Існування символу, успішність тесту та правильність порядку викликів перевіряються окремо.

## 4. Контракт перевірки та межі гарантій

### 4.1 Актуальність знімка й CI

`keylang check` перевіряє поточний код і вибрані специфікації на **актуальному `AnalysisSnapshot`**. Перед перевіркою звіряються manifest джерел, додані/видалені файли, конфігурація шарів та резолвера, версії екстрактора й граматик. Незакомічені зміни враховуються за вмістом файлів; одного SHA коміту недостатньо.

Застарілий знімок інкрементально перебудовується для перевірки без перезаписування ручних специфікацій чи Markdown-карти. Якщо джерела змінюються під час аналізу, результат не публікується як узгоджений: аналіз повторюється або завершується поясненою помилкою. За I/O-збою, що не дозволяє отримати знімок, немає успішного підсумку. `map --check` окремо перевіряє, чи відповідає закомічена карта поточним джерелам, і нічого не записує.

Нерозв’язані імпорти, динамічні виклики, помилки розбору, виключені файли та непідтримані конструкції зберігаються з позиціями й причинами. Вони впливають на покриття релевантної області правила. Загальна статистика не замінює цих записів.

Цільовий CI-запуск — `keylang check --strict --format sarif` (або інший формат). Коди: `1` — порушення, а зі `--strict` також `unverified` для потрібних критеріїв; `2` — некоректний виклик або I/O; `0` — немає блокувальних знахідок за вибраною політикою. У звичайному режимі `0` з неповною перевіркою супроводжується явним підсумком `unverified`, не зеленим `ok`. Формат звіту не змінює вердикт.

### 4.2 Докази та три значення

Кожен результат містить критерій, область, `snapshotId`, хеш специфікації та потрібні види доказів. `ok` означає підтвердження цього критерію в заявленій області; не загальну правильність застосунку.

| Доказ | Що перевіряє | Межі |
|---|---|---|
| **ID** | існування символу та відповідність виду посилання; окремо `planned` / `opaque` | існування ID не підтверджує виклик чи поведінку |
| **static** | залежності та можливу досяжність кожного `step` від його батьківського контексту; `--static=behavior` (типово) іде й через типове значення хука та значення, які хуку передають розв'язані виклики, `--static=shape` — лише через записані виклики. Режим задає `check.static`, прапорець його перевизначає, інакше `behavior`; типове значення змінюється лише з новою версією формату | не доводить порядок чи фактичне виконання; невизначені цілі зберігаються |
| **tests** | однозначно знайдений `test` має успішний результат у звіті для цього знімка | пропущений, неоднозначний або застарілий результат — `unverified`; якість тверджень залежить від тесту |
| **trace** | спостережені виклики, вкладення, порядок та результати assertions у конкретному тесті | потрібне достатнє інструментування й завершений trace; не доводить поведінку всіх запусків |

Очікуються насамперед e2e-сценарії: один flow може мати кілька тестів для різних гілок. Ідентичність тесту включає файл, suite і назву; неоднозначний рядок у JUnit/JSON-звіті не можна довільно прив’язати до твердження. Звіт тест-раннера та його адаптер зберігають `snapshotId` / `runId`; сторонній звіт без встановленого зв’язку зі знімком не підтверджує поточний код.

Правила агрегації:

- підтверджене порушення дає `fail`, навіть якщо інші докази неповні;
- без порушення, але з браком потрібних доказів — `unverified`;
- `ok` можливий лише коли всі потрібні критерії перевірені в заявленій області; непотрібний вид доказу не входить до агрегації;
- для `deny` підтверджене заборонене ребро — `fail`; відсутність такого ребра в неповній області — `unverified`;
- відсутність шляху в практичному статичному графі викликів — `unverified`, якщо шлях могла б дати конструкція, яку keylang не відстежує: виклик із невідомим отримувачем тієї ж назви, функція на маршруті до кроку, прочитана як значення, closure, `eval`, непрочитаний модуль. Якщо жодна не могла — `fail` (absence): крок і його виклики досяжні лише за назвою, і жодна назва не збігається. Відомо видалений символ у повністю проіндексованому модулі — K001 / `fail`; відсутній обов’язковий крок у завершеному й достатньо інструментованому сценарії також може дати `fail`;
- LLM, прийняття людиною та наявність `planned` не підвищують доказ до `ok`.

**Хуки й режим `static`.** Код часто викликає передану функцію з типовим значенням поруч: `const generate = request.generate ?? generateMap; generate()`, `function run(step = build)`, `this.analyzer = options.analyzer ?? analyze`. Синтаксичний прохід бачить і форму (виклик через локальне значення), і поведінку (що виконається): типове значення записане в тій самій функції, а передане значення — у розв'язаному виклику, що його передає (`analyze({ generate: worker.generate })`). Щоб доказ не змушував переписувати код під аналізатор, `static` за замовчуванням (`behavior`) іде й цими ребрами і називає їх у вердикті («through the default of the hook `generate`», «`generate` injected at file:line:col»); `--static=shape` показує лише записані виклики. Типове значення — `behavior`, бо саме воно відповідає на питання потоку «чи виконається крок», а кожне таке ребро має в коді і хук, і його значення; дірка виклику через хук при цьому лишається в `coverage`. Правила залежностей переданого значення не бачать: це залежність того, хто його передав. Поле `check.static` задає режим хука типового значення для репозиторію (`behavior` або `shape`); пріоритет — прапорець `--static`, потім поле, потім `behavior`. Його читають `check`, `feature`, `hook stop`, LSP, MCP, TUI і `keylang web`. Типове `behavior` змінюється лише з новою версією формату.

**Словник звіту:** **divergence** — підтверджена невідповідність; **absence** — відсутність обов’язкової сутності чи спостереження за достатніх доказів; **convergence** — підтверджений збіг. Дозволене через `allow` ребро не мусить існувати, тому його відсутність не є absence. Невизначеність показується окремо і не перейменовується на convergence.

### 4.3 Trace

Трасуються лише тести, позначені `@flow <name>`. Мінімальний TS/JS-адаптер у M2 працює через інструментовані e2e-тести або OpenTelemetry без залежності від майбутнього `wiring`. Пізніше контейнер дає додаткові точки інструментування; Rust використовує `tracing`, Python — `sys.monitoring`.

Спільний версійований JSONL-контракт розділяє **символ** та **окремий виклик**:

| Поле | Значення |
|---|---|
| `schemaVersion`, `snapshotId` | версія формату та знімок коду |
| `runId`, `testId`, `flow`, `traceId` | запуск, конкретний тест, сценарій і trace |
| `spanId`, `parentSpanId`, `symbolId` | унікальний виклик, батьківський виклик і ID символу; повтори й рекурсія мають різні `spanId` |
| `event`, `outcome` | початок/завершення; результат завершення або assertion |
| `clockId`, `seq`, `ts` | джерело годинника, порядок подій цього джерела й час; не глобальний порядок паралельних виконань |
| `links` | каузальні зв’язки для асинхронних викликів, потрібні для підтвердження порядку |

Метадані завершення запуску фіксують покриття інструментування, втрати/sampling і обірвані spans. Кроки зіставляються впорядкованим ін'єктивним включенням у межах конкретного тесту та гілки (норма — у format.md, «Flows: докази кроку», підрозділ «Семантика»); одна подія не задовольняє два різні кроки. Для порядку використовуються start/end і причинні зв’язки, а не сортування всіх `ts`. Брак таких даних — `unverified` для відповідного критерію.

Підпослідовність дозволяє додаткові виклики: вона сама не перевіряє «жодного другого списання», «не більше трьох retry» або дедлайн. Такі властивості потребують окремого машинно-перевірюваного предиката/тесту; точна граматика визначається до v1 на наскрізних сценаріях. Неповний trace не доводить відсутність кроку.

Динамічний доказ зберігається з `provenance: trace`, `snapshotId`, `runId` і `testId`. Він підтверджує спостереження цього запуску та може виявити порушення, але не робить статичний граф повним. Дані іншого знімка не переносяться до поточної перевірки як актуальні факти.

### 4.4 Стейлнес прози

Для описів, `when` / `then` / `invariant` і пояснень записується fingerprint **нормалізованого AST тіла, сигнатури, публічного контракту та релевантних залежностей**. Якщо нормалізація для конструкції недоступна, використовується консервативний хеш вихідного тексту. Зміна `total > 0` на `total >= 0` має інвалідувати опис навіть без зміни сигнатури та імпортів.

Інвалідація поширюється на залежні описи за транзитивними залежностями, включно з циклами; невідома залежність позначає неповноту цієї перевірки. Для ручних специфікацій baseline зберігається під версійним контролем разом зі специфікацією і оновлюється після її перегляду, а не під час кожного `map`. Для кешованих пояснень baseline зберігається з поясненням.

`check --stale` показує зміни під описами, `code-to-spec` пропонує diff. `stale` — причина перегляду, а не доказ хибності прози; незмінний fingerprint також не є перевіркою її змісту. Актуальність вихідних файлів для самого знімка визначається manifest із §4.1, окремо від цих fingerprint.

LLM у перевірці лише радить: `keylang review` оцінює відповідність коду тексту потоку й не блокує CI. Участь LLM у генерації описано в §5.

## 5. Генерація: алгоритм, LLM або обидва

Чернетки карти, описів, правил і потоків можна запропонувати трьома способами. **Канонічний `map` завжди є детермінованою проєкцією семантичного знімка.** LLM пропонує групування, описи й специфікації через `draft`; прийнята розкладка змінює конфігурацію, після чого карта генерується знову:

```
keylang map                         # актуальний знімок → карта
keylang draft map --mode algo|llm|hybrid
keylang draft flow --mode algo|llm|hybrid <trigger>
keylang draft rules --mode …
```

| | **algo** | **llm** | **hybrid** (за замовчуванням) |
|---|---|---|---|
| Джерело | tree-sitter/SCIP → граф | код + README + коміти → модель | обидва паралельно, потім звіряння |
| Добре дає | модулі, fn, сигнатури, імпорти, виклики, рядки коду | описи, групування в шари, назви потоків, наміри, інваріанти, гілки `when` | факти з algo, зміст з LLM |
| Погано дає | сенс, бізнес-назви, динамічні виклики | точні ID і зв'язки: вигадує, як NotebookLM зі слайдами | — |
| Детермінованість | так | ні | каркас так, текст ні |
| Вартість | секунди, без мережі | токени, мережа | токени лише на «м'які» поля |

### 5.1 Як працює hybrid

1. **algo** забезпечує актуальний семантичний знімок за контрактом §4.1 перед кожним draft-, explain- чи ghost-запитом. З кешу перевикористовуються незмінені факти; змінені й залежні від них дані перераховуються. Наявність факту в синтаксичному графі не скасовує його стану резолвінгу та обмежень. Запит фіксує `snapshotId`; результат для вже зміненого коду позначається застарілим і переперевіряється перед застосуванням.
2. **llm** отримує компактну карту з кроку 1 (а не весь код) плюс фрагменти коду на вимогу і пише кандидатів: описи, призначення шарів, потоки, інваріанти. У промпт завжди входять граматика keylang (§3) і 2–3 **схожі потоки з цього ж репозиторію** як приклади: нову DSL моделі генерують погано zero-shot, а приклади з того самого репо дають найбільший приріст.
3. **Обмеження:** посилатися можна на наявні ID знімка та явні `planned` у наборі специфікацій. Новий вузол пропонується разом із декларацією наміру в тому самому MERGE-фрагменті; він не видається за наявний код. Невідомий ID без декларації відхиляється як K001, і чернетка **один раз** повертається моделі з найближчими реальними ID (`did you mean`) або вимогою явно оголосити намір. Лише після цього кола результат показується.
4. **Шари ніколи не призначаються мовчки.** Автоматичне відновлення архітектури дає точність часто нижче 50 %, тому algo генерує факти, а розкладку по шарах LLM або евристики лише **пропонують** — вона приймається людиною через merge, як будь-яке `llm-only`.
5. **Звіряння** кожного твердження:

| Результат | Коли | Що робимо |
|---|---|---|
| `agree` | конкретне твердження LLM підтримане достатніми доказами знімка | позначаємо узгодженим; зміни ручної специфікації все одно проходять MERGE |
| `algo-only` | є в знімку, LLM пропустила | зберігаємо разом із походженням і станом резолвінгу |
| `llm-only` | LLM стверджує, у графі немає | `unverified`: або динамічний виклик, якого не бачить algo, або вигадка → на рев'ю |
| `conflict` | твердження суперечить перевіреним даним або прийнятій специфікації | на рев’ю, показуємо докази; статичний граф сам не доводить конфлікт порядку |

6. Розбіжності корисні: `llm-only` підказує, де аналіз неповний, а `algo-only` — де модель пропустила дані. Для неоднозначних і нерозв’язаних ребер LLM може ранжувати кандидатів, але не змінює `resolution`, покриття чи результат `check`. Статуси узгодження чернетки та вердикти перевірки — різні осі.
7. Відсоток прийняття `llm-only` і `conflict` записується у `.keylang/stats.json`. Це калібрування: якщо `llm-only` приймають рідко, TUI показує їх згорнутими.

### 5.2 Походження у файлі

Згенероване LLM позначається невидимим у рендері коментарем, щоб завжди було видно, звідки твердження:

```markdown
- step infrastructure.payments.charge <!-- keylang:llm model=claude-sonnet-5 status=llm-only -->
```

Карта містить ідентичність знімка; походження кожного факту зберігається у знімку. Після прийняття LLM-фрагмента запис про модель і походження зберігається, а стан review змінюється на прийнятий. Прийняття не є доказом: твердження перевіряється за §4 і може залишатися `unverified`. Позначка `planned` також зберігається до перевірки реалізації. CI не підвищує `llm-only` чи прийняте людиною твердження до `ok`.

### 5.3 Режими окремо

- **algo** — для CI, pre-commit і великих репозиторіїв: швидко, безкоштовно, відтворювано.
- **llm** — для чернетки опису непідтриманої кодової бази або першого знайомства з нею. Результат зберігається як пропозиція; перевірене посилання підтверджує лише існування ID, а не зміст твердження.
- **hybrid** — щоденний режим для `draft`: детерміновані факти знімка плюс пропозиції LLM. `map` у будь-якому середовищі лишається algo-проєкцією.

### 5.4 Пояснення вузла простою мовою (LLM)

Для **будь-якого вузла** (шар, модуль, fn, потік, правило, крок) можна подивитися пояснення звичайним текстом: що він робить, навіщо, з якими вузлами пов'язаний, які є крайні випадки.

- **Команда:** `keylang explain <id>`; у TUI — клавіша `e` на вузлі під курсором або вкладка «Пояснення» у спливаючій підказці.
- **Що отримує LLM:** код вузла; сигнатури його залежностей і тих, хто його викликає (з індексу); потоки й правила, де вузол згаданий; **словник спеки** — назву шару, бізнес-імена з flows, текст поруч із `deny`. Без доменної термінології промислові рецензенти відхиляють понад половину LLM-описів. Весь репозиторій не передається.
- **Обмеження:** посилання — лише на ID знімка або явні `planned`. У поясненні planned-вузла описується намір, а не нібито виконуваний код; статус видимий. Звичайний невідомий ID підсвічується як помилка.
- **Не змішується з мовою.** Пояснення зберігаються окремо, у `<dir>/explain/<id>.md`, і не потрапляють ні в канонічну карту, ні в flows. Канонічна карта лишається детермінованою проєкцією знімка, без прози. Сховище закомічене, тож пояснення однакові в кожному клоні ([ADR 0004](adr/0004-explained-map.md); до 0.1.1 — `.keylang/explain/`, який git ігнорував).
- **Карта з поясненнями** (`explain.map`, ADR 0004) — друге згенероване представлення, `<dir>/map-explained/`. Це те саме дерево з поясненням в одне-два речення під кожним вузлом: спершу коментар документації з коду, потім brief від моделі (`explain <id> --llm --brief`, `<dir>/explain/brief/<id>.md`) з видимою позначкою моделі, дати й `stale`. `keylang map` моделі не викликає, тож і ця карта — детермінована функція джерел і закомічених brief-ів. Вона не є специфікацією: `check` її не читає.
- **Актуальність:** пояснення використовує fingerprint і транзитивну інвалідацію з §4.4, включно зі змінами тіла. `keylang explain --stale` перелічує застарілі пояснення й brief-и. Brief-и генеруються пакетно: `keylang explain --missing --llm` пояснює вузли без коментаря документації й без brief, `keylang explain --stale --llm` перегенеровує застарілі, знизу вгору (fn і типи → класи й модулі → шари).
- **Мова пояснень** задається в `keylang.json` (`explain.lang = "uk"`). Рівень деталізації: `short` (2–3 речення про призначення; **за замовчуванням**, бо саме такий рівень люди вважають найкориснішим) або `full` (кроки, гілки, крайні випадки). Окремий рівень `brief` (одне-два речення одним абзацом) — для карти з поясненнями. Порядкового «рядок за рядком» немає.
- **Видиме походження.** У панелі пояснення завжди є рядок `модель · дата · stale?`. Полірований текст приховує помилки: у дослідженнях люди пропускали ~40 % хибних тверджень у відповідях LLM, тому статус і модель показуються, а не ховаються в коментар.
- **Кешування й офлайн:** уже згенероване пояснення читається без мережі. Без ключа LLM показується лише algo-зведення: сигнатура, залежності, де використовується.
- **Довіра:** пояснення — довідка для людини. Воно ніколи не впливає на `check` і CI.

### 5.5 code-to-spec і spec-to-code

Дві протилежні команди, і обидві працюють у режимах algo / llm / hybrid.

| | **code-to-spec** | **spec-to-code** |
|---|---|---|
| Вхід | виділений код: fn, модуль, файл або `git diff` | явні декларації `planned` або зміни контракту наявного вузла |
| algo | актуальна карта: модулі, fn, залежності, виклики та покриття | заготовка в дозволеному шарі з очікуваною сигнатурою; якщо шлях неоднозначний, потрібне його уточнення |
| llm | описи, потік (`step`/`when`/`then`), інваріанти | реалізація тіла + **e2e-сценарій** під потік |
| Результат | чернетка спеки в режимі MERGE (§5.1) | diff коду в режимі MERGE, по шматках (hunk): прийняти / відхилити |
| Перевірка | твердження про наявний код прив’язані до актуального знімка; нові наміри оголошені як `planned` | кандидат аналізується як новий знімок із diff; `allow`/`deny`, типи й потрібні докази перевіряються з явним показом неповноти |

Цикл: `planned` → spec-to-code → людина приймає/править diff → новий знімок і перевірка контракту → закриття наміру. `map` оновлює представлення. Поява ID закриває лише перевірку існування: тести, порядок і побічні ефекти отримують власні результати. Команди: `keylang spec-to-code <id|file>`, `keylang code-to-spec <path[:line]>`; у TUI — дія на `planned` або палітра `:`. На K001 спершу пропонується виправити посилання чи явно оголосити запланований вузол, без автоматичного генерування коду з можливої друкарської помилки.

## 6. Wiring — виконуваний режим (опційно)

Як у Шемсединова, але через **кодогенерацію, а не інтерпретацію**, щоб результат проходив перевірку типів.

```markdown
# wiring
- wire application.purchase
  - order domain.orderAggregate
    - when env.DEPT = accounting → domain.accountingOrder
- wire infrastructure.server
  - api presentation.api
    - compose infrastructure.logger   <!-- усі запити спершу логуються -->
```

`keylang wire` генерує `keylang.gen.ts` (далі `keylang.gen.rs`). Умовна підстановка та `compose` стають звичайним типізованим кодом. Двофазне зв’язування потребує окремого контракту фабрик, async-ініціалізації, завершення роботи та циклів: саме по собі воно не усуває доступу до ще не ініціалізованої залежності. Цей контракт перевіряється перед реалізацією wiring (§9).

Контейнер дає додаткові точки для `trace`, але мінімальний trace не залежить від нього. Wiring не ізолює модулі від довільних JS/TS-імпортів; відповідність залежностей перевіряється тим самим `check` на актуальному знімку.

## 7. Архітектура інструменту

```
                       keylang (TypeScript → npm JavaScript)
 код + конфіг → extract / resolve / layer → AnalysisSnapshot
                                            │           │
                                            │           └→ emit → map/index
 спеки *.md → parse → текстовий IR → SpecIR ──┤
 актуальні test-report / trace ──────────────┤
                                            ▼
                    check → результати + докази + покриття
                                    │
                         запити до спільних даних
                     ┌──────────────┼──────────────┐
                   CLI/CI          LSP         TUI/web/MCP
```

- **Глибокий модуль аналізу.** Спільний інтерфейс для CLI/LSP/TUI/MCP: `analyze(repo, specSources) → {snapshot, specs, findings, coverage}`. Оркестрація забезпечує свіжість і I/O; парсер та перевірка правил працюють із даними й лишаються незалежними від tree-sitter. Форму твердження перевіряє `compileSpec`, а не клієнт і не парсер. Клієнти не відновлюють власні графи з Markdown.
- **TypeScript + tree-sitter.** `web-tree-sitter` і готові WASM-граматики не потребують native-компіляції на встановленні. Вартість повного та інкрементального аналізу вимірюється на бенчмарку. Додавання мови потребує не лише `.scm`: її frontend визначає декларації, області видимості, імпорти, експорти й можливості аналізу. TS виконується напряму в розробці; npm-артефакт містить зібраний JS (§7.4).
- **Резолвінг.** Синтаксичний backend враховує локальні bindings і затінення; `run(target) { target(); }` не прив’язується до однойменної функції модуля. Для type-aware посилань є опційний backend SCIP. Його індекс також звіряється з джерелами; застарілий або непов’язаний зі знімком індекс не підвищує точність поточної перевірки.
- **Інкрементальність.** Кеш ключується вмістом файлу, версіями frontend/граматики й релевантною конфігурацією. Зміни імпортів, експортів і шарів інвалідують залежні резолвінги. `watch` публікує узгоджені знімки; довга побудова не блокує UI, застарілі результати скасовуються.
- **Єдине джерело фактів.** `.keylang/index.json` серіалізує знімок; map-файли та індекси навігації є похідними. Формат знімка версіонується; несумісний кеш перебудовується. Час генерації може бути службовим полем, але не входить у детермінований `snapshotId` чи порівняння змісту.

Мінімальний контракт знімка:

| Частина | Дані |
|---|---|
| ідентичність | версія схеми, `snapshotId`, manifest файлів/хешів, конфігурації та версії інструментів |
| вузли | ID, вид, файл/range, сигнатура, fingerprint тіла, повнота членів модуля |
| експорти | публічне ім’я → символ і вид, включно з aliases / default / re-exports |
| ребра | `kind`, джерело, ціль або кандидати, span у коді, `resolution`, `provenance`, прив’язка до знімка |
| невизначеність і покриття | нерозв’язані/непідтримані конструкції, причини, області, пропущені файли та види залежностей |
| похідні індекси | deps/dependents, calls/callers; посилання зі специфікацій додаються з їхнім хешем |

`resolution` розрізняє встановлену ціль, неоднозначність і нерозв’язаний випадок; `provenance` — синтаксичний, семантичний або trace-доказ. Це незалежні осі на **ребрі**, а не загальна позначка вузла `precision: syntactic`. Встановлена статична ціль не доводить, що виклик відбувся. Trace-докази додатково містять ідентичність запуску (§4.3). `planned` зберігається в `SpecIR` і спільному представленні для клієнта, але не в графі спостережених фактів.

`snapshotId` визначається входами аналізу коду: джерелами, конфігурацією, backend та версіями/хешами використаних індексів і граматик. Результати тестів, trace, специфікації й час генерації не змінюють цю ідентичність. Динамічні докази зберігаються окремо й поєднуються зі знімком у `check` та UI; вони не змінюють канонічну Markdown-карту. Збагачене trace-відображення явно називає запуск. Це зберігає детермінованість карти й не створює циклу між ID знімка та trace, який на нього посилається.

### 7.1 Інтерфейс — термінал, як Xcode

> Новий цільовий цикл «усі прикладні операції всередині TUI» описано в [tui-workspace.md](tui-workspace.md): повна палітра, параметри, результати, ініціалізація й генератори. Це заплановане розширення, не поточна поведінка; архітектурний спосіб — [ADR 0008](adr/0008-shared-workspace-operations.md).

Інтерактивний інтерфейс — **TUI `keylang`** (Node.js, власний рендерер клітинок і парсер SGR-подій мишки; мишка + клавіатура; чому не Ink — [ADR 0001](adr/0001-tui-without-ink.md)). Реалізовану поведінку й клавіші описує [`tools.md`](tools.md). Принцип як у Xcode: **у фокусі сам текст мови**, решта з'являється на вимогу. Спочатку той самий контракт аналізу перевіряється через CLI та LSP; повний редактор — наступний етап (§9).

```
┌ навігатор ─┬─ редактор: *.md з підсвіткою ───────────────┬─ навігація ─┐
│ (сховано,  │  - step infrastructure.orderStore.save  ✓   │ ▾ domain    │
│  F2)       │        ┌ hover ─────────────────────┐       │ ▾ infra…    │
│            │        │ fn save(order) → Promise    │       │   ▸ orderS… │
│            │        │ src/infra/order-store.ts:9  │       │ ПОТОКИ      │
│            │        └─────────────────────────────┘       │   checkout ✗│
├────────────┴─────────────────────────────────────────────┴─────────────┤
│ ✗ 2  ◌ 5   Enter код · Alt+Enter спека · / пошук · F5 check · ? клавіші │
└─────────────────────────────────────────────────────────────────────────┘
```

- **Редактор** показує сирий Markdown keylang з підсвіткою: шари кольорами, ключові слова, ID. Ніякого «рендеру в картки».
- **Жолоб**: `✓` / `✗` / `◌` для потрібних критеріїв твердження. Поруч або в розгорнутому рядку видно окремі `ID`, `static`, `tests`, `trace`, причину невизначеності, покриття й знімок. `ID ✓` не перетворюється на загальне `✓`, якщо потрібний trace відсутній. `planned` і `stale` показуються як окремі стани з поясненням.
- **Спливаючі підказки** при наведенні мишею або `K`: сигнатура, 4 рядки коду, де використовується.
- **Пояснення** (`e`): текст простою мовою від LLM про те, що робить вузол, з клікабельними ID. Див. §5.4.
- **Навігація праворуч** (одна панель; `Ctrl+1` термінали не передають, тож у реалізації — `F3`, навігатор файлів — `F2`): шари → модулі → fn, окремо потоки та правила зі статусами.
- **Переходи:** `Enter`/Ctrl+клік — у код: у вбудованому переглядачі, а якщо заданий `$EDITOR` / `code`, то там. `Alt+Enter` — у спеку, `Ctrl+O` — назад.
- **Генерація** (§5) відкривається як злиття: `=` agree, `+?` llm-only, `!` conflict. `a` приймає, `r` відхиляє. Це статуси чернетки; поряд зберігаються незалежні вердикти перевірки.
- Жодних окремих форм налаштувань: налаштування — це `keylang.json`, відкритий у тому ж редакторі з підказками.

Та сама логіка доступна **через LSP** (`keylang lsp`) для VS Code, Neovim, Zed, JetBrains:

| Вимога | Механізм LSP |
|---|---|
| навів на ID → що це | `hover` |
| Ctrl → стрибок у код | `definition` |
| перейти в спеку | `definition` на ID з `flow`/`rules`, `references` |
| навігація праворуч | `documentSymbol` |
| помилки | `diagnostics` |
| автодоповнення ID | `completion` |
| зворотний зв'язок з коду | CodeLens «flows: checkout» над функцією |

VS Code extension — тонкий LSP-клієнт. LSP, CLI та TUI використовують однакові результати з ідентичністю знімка та доказами; кожен клієнт не обчислює власний «зелений» статус.

### 7.2 Один TUI — два запуски: термінал і браузер

| | `keylang` | `keylang web` |
|---|---|---|
| Де | будь-який термінал (xterm-256color, truecolor) | вкладка браузера, `http://localhost:7070` |
| Як | власний рендерер (`src/tui/screen.ts`) пише кадр ANSI у stdout | той самий TUI у тому ж процесі: сесія пише ті самі кадри ANSI у WebSocket замість stdout, їх показує вшитий **xterm.js**, а події клавіатури й мишки йдуть назад |
| Мишка, hover | SGR mouse | xterm.js передає ті самі mouse-події |
| Перехід у код | вбудований переглядач; або `$EDITOR` / `code -g`, якщо є | вбудований переглядач; OSC 8-посилання `vscode://file/…:line` |
| Кому | щоденна робота | рев'ю, демо, віддалена машина, людина без налаштованого термінала |

Обидва варіанти використовують **спільну модель інтерфейсу й результати аналізу**. Браузерний транспорт — вшитий xterm.js + WebSocket без зовнішнього PTY (див. §7.4). Еквівалентність основних дій перевіряється окремо для термінала й браузера: resize, мишка, вставлення, виділення, Unicode/IME та перепідключення. Піксельна тотожність і однакові можливості всіх терміналів не є гарантією.

Пізніше можна додати статичну збірку без сервера для публікації карти як сторінки — простий HTML-експорт того самого знімка. Вона тільки для читання: `$EDITOR` там недоступний, лишаються тільки `vscode://`-посилання.

Чому не Ink і не OpenTUI — [ADR 0001](adr/0001-tui-without-ink.md): Ink потребує JSX без кроку збірки й не дає координат клітинок для жолоба й мишки, а OpenTUI під Node вимагає ≥ 26.4 з `--experimental-ffi`, що ламає `npx keylang` на поточних LTS. Стан, вхід, аналіз і транспорт від рендерера не залежать, тож заміна рендерера — це переписування `src/tui/view.ts`, а не сесії.

### 7.3 Редактор і співавторство з агентом

Мету сформульовано так: швидко будувати нові модулі та логіку, починаючи будь-з якого боку, від людини або від агента.

**Підказки (детерміновані, без LLM).** Джерело — актуальний знімок і декларації `planned` з відкритих специфікацій. Намір візуально відрізняється від наявного символу.
- Автодоповнення ID: `infrastructure.or…` → `orderStore.save · fn (order) → Promise<void>`. Список фільтрується за шаром (`allow`/`deny`), тож заборонене не пропонується.
- Ключові слова залежно від позиції: під `flow` — `trigger`/`step`/`when`…, під модулем — залежності.
- Signature help, помилки під час набору (K001 і K003 одразу), hover, перехід у код.

**Ghost-текст від агента.** Сірим продовженням з’являється коротка пропозиція, наприклад `- emits event order.refunded`. `Tab` приймає один рядок, `Alt+]` показує інший варіант, `Esc` прибирає. Посилання — лише на ID знімка або вже оголошені `planned`; новий намір із використаннями пропонується як MERGE-фрагмент (§5.1).

Два режими роботи з підказками розділені свідомо, за дослідженнями Copilot: у режимі *прискорення* людина знає наступний крок і хоче коротку підказку, у режимі *пошуку* — не знає і хоче варіанти. Тому:
- ghost-текст — лише для прискорення: до одного рядка, після паузи 400 мс і дешевого сигналу (курсор під `flow`, початок `- `, кандидат з достатніми даними в актуальному знімку). Пауза — параметр для usability-перевірки; без сигналу ghost не показується;
- пошук — це `Alt+]` (варіанти) і `Ctrl+Space` (повна чернетка як MERGE-diff);
- усе довше за один рядок іде **тільки** через MERGE по шматках, ніколи через `Tab`;
- спершу вимірюється користь детермінованого автодоповнення в LSP (M3), потім оцінюється приріст від ghost (M7): частка прийнятих пропозицій, час до перевіреного сценарію, час на відхилення. Статус `agree` сам по собі не є метрикою правильності коду.

**Співавторство в обидва боки:**
1. *Людина → агент.* Пишеш кілька рядків або звичайний текст, натискаєш `Ctrl+Space` («догенеруй»), і агент дописує решту як diff.
2. *Агент → людина.* Промпт на кшталт «додай повернення коштів». Агент пише чернетку, ти правиш руками, агент бачить правки в наступному запиті.

Будь-яка зміна від агента показується **як diff по шматках у тому ж редакторі** (режим MERGE): `a`/`r` на кожен шматок. Нічого не записується без підтвердження.

**Звичайний текст як вхід.** Будь-який вузол може мати опис вільним текстом (§3.1). Команда `Ctrl+G` («text → spec») перетворює виділений текст на структуру (`when`/`then`/`step`), а оригінал лишає описом.

**Голосовий ввід.** `Ctrl+R` у полі агента або на місці курсора в редакторі. Розпізнаний текст або йде в промпт, або вставляється як опис вузла. Два рушії, вибір у `keylang.json` (`voice.engine = "local" | "openrouter" | "auto"`):

| | **local** | **openrouter** |
|---|---|---|
| Як | whisper.cpp через `@fugood/whisper.node` (N-API, prebuilt-бінарники для Linux/macOS/Windows, варіанти CPU/CUDA/Metal/Vulkan), **опційна залежність**: без неї працює лише `openrouter` | аудіо (WAV 16 кГц, base64) іде в OpenRouter chat completions як `input_audio` до моделі з аудіовходом |
| Мережа | не потрібна | потрібна, ключ `OPENROUTER_API_KEY` або `~/.config/keylang/openrouter.key` (права 0600) |
| Модель | файл `ggml-large-v3-turbo.bin` або `ggml-small.bin` кладе користувач у `~/.cache/keylang/models` (завантажувача немає; `keylang doctor` показує, чого бракує), не входить у пакет | налаштовується: `voice.model = "…"` |
| Коли | офлайн, приватний код | слабке залізо, потрібна краща якість або змішана мова |

`auto` бере local, якщо рушій встановлено й модель лежить у кеші, інакше openrouter, якщо є ключ. Інакше `Ctrl+R` пояснює, що налаштувати.

Від `voice-transcriber` беремо **тільки ідеї, не код і не залежність**: вікна по ~25 с з перекриттям 1 с, глосарій ID з індексу як підказка (prompt) для Whisper, щоб `orderStore` не ставав «ордер стор», і ранню перевірку готовності моделі. Глосарій — **лише малий піднабір**: ID вузла під курсором, його сусідів у графі й поточного потоку (до ~30 термінів, найважливіші в кінці промпта). Довгі списки термінів погіршують розпізнавання, а не покращують.

Куди йде голос: за замовчуванням у **вільний текст** — опис вузла, промпт агенту, `when`/`then`. Диктувати структурні рядки з ID незручно і в дослідженнях програє набору з клавіатури. Для структури є крихітна командна граматика: «крок …», «коли … тоді …», «емітить …» перетворюються на `- step` / `- when` / `- then` / `- emits`, а ID підставляється через те саме автодоповнення з нечітким пошуком. Захоплення мікрофона — `decibri` (N-API, prebuilt; без `sox`, `arecord`, `pw-cat`), теж опційна залежність. У `keylang web` мікрофон захоплює браузер (getUserMedia), PCM іде тим самим WebSocket, далі той самий рушій на сервері — тому браузерний варіант голосу працює навіть там, де `decibri` не має збірки (macOS x64).

**Контекст агента видно й можна керувати.** Панель «Контекст» показує, що саме піде в модель, і скільки токенів займе кожен елемент:
- поточний буфер;
- вузли під курсором і їхні сусіди з графу;
- потоки й правила, де вони згадані;
- фрагменти коду;
- e2e-тести потоку.

`@id` додає вузол, `x` прибирає. Пакет кешується за `snapshotId`, хешем специфікацій і вибраних фрагментів; панель явно показує planned-вузли та неповноту даних.

**Зовнішні агенти через MCP.** `keylang mcp` віддає інструменти `search`, `node`, `code`, `flows`, `check`, `explain` і `apply_diff`. Тож Claude Code, Codex та інші агенти беруть той самий контекст самі; як `init` підключає їх до харнеса й замикає цикл «опис → код» — §7.6. `code` (фрагменти на вимогу) обов'язковий поряд із графом: агент лише на графі відповідає на ~10 п. гірше, ніж той, що читає файли, хоч і в 10 разів дешевше, тому граф — за замовчуванням, код — коли потрібно. Вбудований агент TUI користується тим самим MCP-шаром. Адаптер у `keylang.json`: `agent = "anthropic:claude-sonnet-5"`, `"openrouter:<model>"` або зовнішній CLI через MCP. Вбудований агент звертається до API напряму по HTTPS; `claude` чи `codex` для нього не потрібні. Ключ OpenRouter спільний для агента й голосу.

**Читання спек.** `v` перемикає редактор у режим читання. Markdown рендериться власним рендерером підмножини специфікацій (`src/tui/markdown.ts`, [ADR 0001](adr/0001-tui-without-ink.md)): заголовки, таблиці, блоки коду, посилання; кожен рядок пам'ятає рядок джерела, тож ID лишаються клікабельними, а статуси перевірок — видимими.

### 7.4 npm-пакет: без зовнішніх програм

Ціль: `npx keylang` працює одразу на будь-якій машині з Node ≥ 22.18. Жодних інших програм для встановлення; native-модулі лише з prebuilt-бінарниками і лише як **опційні** залежності (без них відповідна функція вимикається, а не весь інструмент).

| Потреба | У пакеті | Чого **не** вимагаємо |
|---|---|---|
| ядро: парсер, резолвер, `check`, `fmt` | зібраний JavaScript у `dist/`; вихідний TS — для розробки | TypeScript-компілятор чи TS-loader на машині користувача |
| розбір коду | `web-tree-sitter` + `.wasm`-граматики (`tree-sitter-wasms` / `@vscode/tree-sitter-wasm`) | компілятор C, `node-gyp`, CLI tree-sitter |
| точні посилання | вбудований резолвер імпортів; SCIP-індекс читається, **якщо він є** | `scip-*` (опційно) |
| маніфести Rust/Python | `smol-toml` (`Cargo.toml`, `pyproject.toml`) | — |
| git | не потрібен: свіжість знімка базується на хешах файлів; diff для `code-to-spec` — через `git` CLI, **якщо він є** (`--since <ref>`) | `git` як обов'язкова програма |
| TUI | власний рендерер (`src/tui/screen.ts`); мишка через SGR-послідовності в stdin. Ink 7 + `react` не взято: JSX без кроку збірки й layout без координат клітинок ([ADR 0001](adr/0001-tui-without-ink.md), [ADR 0002](adr/0002-dependencies-by-value-ws.md)) | Ink, React |
| веб-варіант | `node:http` + `ws` (без власних залежностей, [ADR 0002](adr/0002-dependencies-by-value-ws.md)); сесія TUI пише ANSI у сокет, xterm.js копіюється в `dist/web/` на `prepack` | `ttyd`, PTY, CDN |
| Markdown | власний рендерер підмножини специфікацій (`src/tui/markdown.ts`) замість `marked` + `marked-terminal` | `glow`, `mdcat` |
| підсвітка коду | ті самі tree-sitter-запити `highlights.scm` → ANSI | `bat`, `highlight.js`-теми з диска |
| голос | `@fugood/whisper.node` (prebuilt whisper.cpp) + `decibri` — обидва `optionalDependencies`; модель кладе користувач у кеш | `ffmpeg`, `sox`, `pw-cat`, Python |
| LLM / OpenRouter | `@anthropic-ai/sdk` для Claude; OpenRouter — вбудований `fetch` + `eventsource-parser` (SSE) | `curl`, `claude`/`codex` CLI |
| LSP | власна реалізація потрібної підмножини протоколу поверх stdio (`src/lsp.ts`); записаний виняток ([ADR 0006](adr/0006-lsp-transport.md)) | `vscode-languageserver` |
| MCP | `@modelcontextprotocol/sdk` + `zod` (схеми інструментів) | — |
| перехід у код | вбудований переглядач коду в TUI (read-only, з підсвіткою) | `$EDITOR`, `code` — лише якщо є |

**Збірка релізу.** Node не виконує type stripping для `.ts` усередині `node_modules` ([документація](https://nodejs.org/api/typescript.html#type-stripping-in-dependencies)). Тому `prepack` компілює TS у JS із переписуванням відносних `.ts`-імпортів; опублікований CLI-entrypoint завантажує `dist/*.js`. Прямий запуск TS лишається способом локальної розробки. На встановленні пакета компіляція TS не виконується.

**Критерій дистрибуції:** `npm pack` → встановлення tarball у чистий тимчасовий каталог → запуск CLI фізично з `node_modules` на мінімальній підтримуваній Node і актуальній LTS. Перевіряються `--version`, парсер і `map` з WASM-граматиками; локальний `npm link` не замінює цю перевірку.

Установка: `npm i -g keylang` або `npx keylang`. Розмір пакета 15–25 МБ з граматиками WASM — попередня оцінка, яку перевіряють на tarball; моделі голосу не включено. Опційні prebuilt-модулі завантажуються для підтримуваної платформи користувача.

Компроміс щодо single-binary плану (research.md §3): потрібен Node; старт включає runtime і завантаження знімка; native-addons залежать від prebuilt під платформу. Натомість доступні спільні модулі аналізу для CLI/LSP/TUI, SDK екосистеми й швидка локальна ітерація. Збірка відбувається при підготовці релізу, а не в користувача.

Правило залежностей ([ADR 0002](adr/0002-dependencies-by-value-ws.md)): ліміту на кількість пакетів немає. Протокол, формат, парсер беремо перевіреним пакетом, а не власною реалізацією, коли він закриває задачу; критерії — підтримуваність, розмір дерева, ліцензія. Обмеження одне: встановлення без компіляції native-коду. Supply chain — `package-lock.json`, `npm audit` у CI.

### 7.5 Developer experience

**Перші 60 секунд після надійного CLI (ціль):**
```
$ keylang init          # пропонує розкладку шарів і будує початковий знімок
$ keylang check         # перевіряє актуальний код; показує докази й покриття
$ keylang lsp           # інтеграція редактора з M3
$ keylang               # TUI з M4; keylang web — те саме в браузері
```
- **Початковий конфіг.** Шари за типовими теками (`domain/`, `app/`, `infra/`, `ui/`) — явно позначена пропозиція. Розкладка й виключені файли видимі для прийняття; евристика не робить покриття перевірки повним.
- **Швидкість.** Ціль холодного старту TUI — менше 300 мс із кешованим знімком. Бенчмарк M1 дає близько 2 с повної індексації 898 файлів storefront; потрібен інкрементальний кеш перед частими запитами. Латентність оновлення, пам’ять і чутливість UI вимірюються, а не виводяться з вибору WASM чи Node.
- **Відкриваність.** `?` показує всі клавіші в поточному режимі, `:` (у перегляді) або `Ctrl+P` — палітру дій з нечітким пошуком; `F6` — історію результатів операцій. Рядок стану завжди підказує 4–6 головних дій.
- **Помилки, які вчать.** `keylang explain K001`, а в TUI `?` на помилці показують причину, приклад і «чи мали на увазі…». На K001 пропонується виправити ID чи явно створити `planned`; spec-to-code запускається для оголошеного наміру.
- **Шаблони.** `keylang new flow refund`, `keylang new module payments --layer infrastructure` створюють заготовку з автодоповненням.
- **CI та хуки.** `keylang check --strict --format human|json|sarif|github` забезпечує свіжість знімка та політику §4.1. `keylang hook install` ставить pre-commit; `--changed` включає також залежні правила, символи й flows, а не лише змінені файли.
- **Середовище.** `keylang doctor` показує мови, граматики, кеш, ключі API, модель голосу та термінал: truecolor, мишку, OSC 8.
- **Інтеграції за бажанням.** `keylang lsp` для редакторів, `keylang mcp` для агентів, `keylang completions <shell>`.
- **Передбачуваність.** Жодна дія агента не пише у файли без diff і підтвердження. `u` відкочує останнє прийняте. Усе, що зробила LLM, позначено.

### 7.6 Харнеси агентів: опис → код

Ціль: після `init` на чужому репозиторії харнес (Claude Code, Codex, opencode, Cursor) додає фічу чи інтеграцію за описом у keylang, а keylang звіряє результат із наміром ([ADR 0005](adr/0005-harness-integration.md)). Код пише харнес своїми інструментами; keylang його не запускає. **Стан: реалізовано 2026-09-28** (M8), крім наскрізної перевірки з Claude Code і Codex на чужих репозиторіях (тікет 11, для людини); тікети — `.scratch/harness-integration/`.

**Адаптери.** `init` визначає харнеси за наявними `.claude/`, `.codex/`, `.cursor/`, `opencode.json`; `--agents=claude,codex,opencode,cursor|none` задає список явно, `keylang agents [--check]` повторює те саме для вже ініціалізованого репо.

| Харнес | Інструкції | MCP | Зворотний зв'язок у кінці ходу |
|---|---|---|---|
| Claude Code | блок в `AGENTS.md`; `@AGENTS.md` у `CLAUDE.md` (Claude Code читає `AGENTS.md` лише без `CLAUDE.md`) | `.mcp.json` | хук `Stop` у `.claude/settings.json` |
| Codex | блок в `AGENTS.md` (ліміт 32 KiB на всі файли) | `.codex/config.toml` (лише trusted-проєкт) | `.codex/hooks.json`, схвалюється в `/hooks` |
| Cursor | `AGENTS.md` | `.cursor/mcp.json` | хуки з `.claude/settings.json` (Third-Party Imports) |
| opencode | `AGENTS.md` | `opencode.json` (`mcp.keylang` у формі V1; перевірено — opencode V2.0.20 приймає її, `mcp list` дає `keylang connected`) | лише інструкція (v1) |

Блоки keylang стоять між маркерами, ідемпотентні й перевіряються `--check`; чужий текст не змінюється. Команда MCP — `npx -y keylang@<version> mcp`, де `<version>` — поле `version` з `package.json` keylang, що виконав `init` або `agents`. Skill `keylang-feature` (стандарт agentskills.io) лежить у `.agents/skills/` і копією в `.claude/skills/`: він описує цикл фічі нижче.

**Deny на `keylang/rules*.md`.** Проєктну заборону редагувати файли правил `agents` ставить лише для Claude: у `.claude/settings.json` додаються `permissions.deny` на `Edit(keylang/rules.md)`, `Write(keylang/rules.md)`, `Edit(keylang/rules.baseline.md)` і `Write(keylang/rules.baseline.md)`; наявні `permissions.allow` і `hooks` зберігаються. Для решти харнесів такого запису немає, і захист тримається на інструкції в `AGENTS.md` і skill: Codex має beta-профілі дозволів (`[permissions.<name>.filesystem]` зі значенням `read`/`write`/`deny`), але їх вибирає `default_permissions` і не можна поєднувати з `sandbox_mode`/`[sandbox_workspace_write]`; проєктний `permissions.deny` з `Write(pathOrGlob)` у Cursor є лише в CLI (`<project>/.cursor/cli.json`), не в агенті IDE; `opencode.json` уміє шляхові `deny` у `permission.edit`, але keylang пише в ньому лише власний ключ `mcp.keylang` і не чіпає `permission`.

**Фіча.** Рукописний файл `keylang/features/<slug>.md` зі звичайною граматикою: `planned`-вузли, потоки й правила фічі. Нова інтеграція — `planned module external.<pkg>` і крок потоку до нього. Після реалізації файл лишається: `planned` прибирається за K202, потоки перевіряються далі.

**Цикл.** Опис фічі → MCP `validate_spec` → `scaffold` (заготовка й тести текстом) → реалізація харнесом → `feature_status` / `check` → прибрати `planned`. Нові MCP-інструменти:
- `context <id|feature>` — пакет контексту панелі F4;
- `validate_spec <path, text>` — діагностики й вердикти чернетки без запису;
- `scaffold <id>` — результат `spec-to-code` режиму шаблону як текст, без LLM і без запису;
- `feature_status <slug>` — критерій готовності і прогалини з ID та spans.

**Критерій готовності фічі.** Кожен `planned` файла фічі реалізовано (K202, без K201); кожен крок її потоків має static `ok`; нових порушень правил і baseline немає. Тести й trace показуються, але не блокують.

**Рамки.** `init` пише згенерований `keylang/rules.baseline.md`: для кожного шару `deny` на шари, до яких залежностей зараз немає, і точкові `allow` для наявних пакетів `external`. Нова міжшарова залежність — K102, доки людина її не схвалить у `rules.md` чи регенерацією baseline. Правила агент змінює лише через пропозицію.

**Хук `Stop`.** `check --changed --format json`; блокує завершення ходу лише на нових порушеннях і не блокує двічі поспіль (`stop_hook_active`, `loop_limit`).

**Поза v1:** структуровані контракти й assertions (§10, п. 9), групування пакетів у систему, LLM-режим `scaffold` через MCP, плагін opencode, оркестрація харнесів, eval із реальним харнесом у CI.

## 8. Конфігурація

```json
{
  "languages": ["typescript"],
  "module": "file",
  "layers": {
    "domain":         ["src/domain/**"],
    "application":    ["src/app/**"],
    "infrastructure": ["src/infra/**", "src/live/audio/**"],
    "presentation":   ["src/ui/**", "src/cli/**"]
  },
  "check": {
    "tests": ".keylang/reports/*.json",
    "trace": ".keylang/trace/*.jsonl"
  }
}
```

Файл `keylang.json` (JSON, бо в Node немає вбудованого TOML, а зайва залежність у ядрі не потрібна); до нього додається JSON Schema. `check.tests` — шлях або глоб до звітів тест-раннера: JSON keylang (пише репортер `keylang/node-test-reporter` зі `snapshotId`) або JUnit XML із властивістю `keylang.snapshotId`; `check.trace` — шлях або глоб до JSONL trace (пише адаптер `node --import keylang/trace`). Формати звітів — `docs/format.md` §7; адаптери trace — `docs/tools.md`. Конфігурація валідується на вході й входить у manifest знімка. Імена шарів `external`, `unassigned` і ключові слова верху карти зарезервовано ([format.md](format.md) §7, «Імена шарів»). `module`: `"file"` — файл є модулем, тека з `index.ts` — модуль із підмодулями (дефолт для TS); `"dir"` — тека є модулем. Для Python і Rust дефолт — теж `"file"` з файлом-індексом `__init__.py` / `mod.rs`: так ID збігаються з модульними шляхами самих мов (`crate::domain::order` → `domain.order`, `app.services.bmr` → `app.services.bmr`), а тека з індексом — модуль із підмодулями. Об’єднання в режимі `dir` явне; колізія двох різних сутностей у режимі `file` не є дозволом злити їх мовчки.

## 10. Відкриті питання

1. ~~Гранулярність модуля за замовчуванням~~ — вирішено (§8): дефолт — файл із файлом-індексом мови (`index.*`, `mod.rs`, `__init__.py`), тека з індексом — модуль із підмодулями; `module: "dir"` перевизначає (M5, 2026-09-28).
2. **Мова описів.** Ключові слова англійською, опис вузлів будь-якою мовою. Чи потрібна локалізація ключових слів — ймовірно, ні.
3. **Lisp/JS-форми.** Чи потрібні окремі представлення, крім демонстрації еквівалентності? Семантичний знімок спільний, але точне відтворення текстового IR — окремий контракт.
4. **Зберігання трасування.** `snapshotId`, `runId`, `testId` та повнота обов’язкові незалежно від місця зберігання. Термін збереження CI-артефактів і доцільність комітування trace лишаються відкритими.
5. **ID анонімних сутностей:** замикання й обробники. Схема має переживати локальні зміни; простий порядковий `closure1` нестабільний. Остаточна граматика ID та assertions перевіряється в M2/M3.
6. **Спека в обидва боки.** `planned` дозволяє вести код, `code-to-spec` — наздоганяти його. Практична проба має показати, чи немає зайвої роботи з намірами й baseline; жоден напрям не є обов’язковим етапом перед написанням коду.
7. **Втома від `unverified`.** У TS/Python синтаксичне розв'язання методів дасть низький recall, і жолоб буде рясніти `◌`. Чи потрібен окремий згорнутий вигляд, чи SCIP має стати рекомендованим дефолтом для цих мов.
8. **Глоби й перейменування ID.** `map --relayer` може пропонувати зміни після переміщень через обраний git-backend. Потрібна явна міграція посилань зі збереженням наміру; колізії не виправляються мовчазним злиттям.
9. **Точна граматика нових контрактів.** `planned`, assertions, паралельні групи, кількісні/негативні властивості та формат baseline проходять M2 до заморожування v1. Неперевірювана проза лишається явно позначеною.
10. **Життєвий цикл wiring.** Фабрики, async init/dispose, області життя й допустимі цикли потребують окремого виконуваного прикладу перед M6.
