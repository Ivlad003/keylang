# keylang — дизайн v0.1

> Назва перевірена 2026-09-27: `keylang` вільна на crates.io, npm і PyPI. Схожі назви мають лише покинута C-подібна скриптова мова (GitHub, 4★, 2017), кілька навчальних репозиторіїв і privacy-розширення для браузера, якому належить домен keylang.org. Для домену потрібен інший варіант, наприклад keylang.dev.

Мова опису застосунку, прив'язана до репозиторію. Основа — Markdown-форма архітектурної мови Шемсединова (`architecture-language.md`): дерево **шар → модуль → залежність**. Розширено до API модулів, бізнес- і технічних потоків та перевірок.

> **Стек (рішення 2026-09-27): Node.js ≥ 22.18 + TypeScript, дистрибуція через npm/npx.** Дослідження ([research.md](research.md) §3) рекомендувало Rust за формальними критеріями, але автор обрав ближчий стек; вимогу «один бінарник без runtime» знято, вимога «мінімум зовнішніх програм» лишається. M0 перенесено на TS без змін формату й діагностик.
>
> Оновлено 2026-09-27 за результатами [research.md](research.md): термінологія reflexion models (§4), тризначні вердикти, стейлнес для прози, цикл перевірки до людини (§5), gating ghost-тексту та голосу (§7.3), уточнені крейти (§7.4), оцінка й usability-дослідження в дорожній карті (§9).

## 1. Навіщо

| Задача | Хто читає | Як keylang допомагає |
|---|---|---|
| Зрозуміти репозиторій | людина, AI | згенерована карта: шари, модулі, API, залежності — простим текстом з посиланнями на код |
| Не зламати архітектуру | CI | правила `allow` / `deny` / `entry` перевіряються на реальному графі імпортів і викликів |
| Не зламати логіку | CI, тести | потоки (`flow`) описують, що має статися; перевіряються статично (граф викликів) і динамічно (трасування тестів) |
| Економити токени | AI | карта + потоки замість тисяч рядків коду |
| Зібрати застосунок | рантайм (опційно) | `wiring` генерує DI-контейнер, як у Шемсединова |

## 2. Чотири режими однієї мови

Один формат, один IR — чотири рівні строгості. Кожен наступний опційний.

```
 ┌──────────────┐  генерується   ┌──────────────┐
 │  код + AST   │ ─────────────▶ │ 1. MAP       │  описує, що Є
 └──────────────┘                └──────┬───────┘
        ▲                               │ посилання за ID
        │ перевірка                     ▼
        │                        ┌──────────────┐
        ├─────────────────────── │ 2. RULES     │  що ДОЗВОЛЕНО
        │                        ├──────────────┤
        ├─────────────────────── │ 3. FLOWS     │  що має СТАТИСЯ
        │                        ├──────────────┤
        └─────── codegen ─────── │ 4. WIRING    │  як ЗІБРАТИ (опційно)
                                 └──────────────┘
```

| Режим | Файли | Хто пише | Перевірка |
|---|---|---|---|
| **map** | `keylang/map/*.md` | генератор, **не редагувати** | — (це факти) |
| **rules** | `keylang/rules.md` | людина | статично, на графі |
| **flows** | `keylang/flows/*.md` | людина (AI може чернетку) | статично + динамічно + тести |
| **wiring** | `keylang/wiring.md` | людина | компіляція згенерованого контейнера |

Чому map і specs окремо: згенероване перезаписується щоразу, а написане руками — ні. Spec-файли посилаються на вузли карти за **ID**, тому якщо в коді зникне функція, `keylang check` одразу покаже висяче посилання. Приклад такої помилки є навіть на слайді: `order: 'domain.aggregate'` при модулі `orderAggregate`.

## 3. Синтаксис

Канонічна форма — Markdown. Файл має читатися в GitHub як звичайний документ і водночас бути однозначно розбірним.

### 3.1 Базові правила

- Вузол — елемент списку: `- <kind>? <name> <args…>`.
- Ієрархія задається відступом (2 пробіли), як у Шемсединова.
- **ID** — крапковий шлях від кореня: `application.purchase.buy`. Посилання в spec-файлах записуються тільки через ID.
- **Прив'язка до коду** — звичайне Markdown-посилання: `[buy](src/app/purchase.ts#L12)`. Воно клікабельне будь-де. Номер рядка перегенеровується, а стабільним лишається ID.
- Звичайний текст під вузлом, без `- `, вважається описом вузла. За змістом він не перевіряється, але отримує позначку `stale`, коли код описаного вузла змінився (§4).
- Ключові слова: `layer`, `module`, `fn`, `type`, `event`, `allow`, `deny`, `entry`, `flow`, `step`, `when`, `then`, `invariant`, `test`, `wire`. Верхньорівневий елемент без ключового слова означає шар (сумісність зі слайдами).

### 3.2 Map (генерується)

```markdown
<!-- keylang:generated — не редагувати, `keylang map` -->
# map

- domain
  - module [orderAggregate](src/domain/order.ts#L1)
    - fn [create](src/domain/order.ts#L8) (items: Item[]) → Order
    - fn [total](src/domain/order.ts#L21) (order: Order) → Money
- infrastructure
  - module [logger](src/infra/logger.ts#L1)
    - options infrastructure.config.log
    - fn [log](src/infra/logger.ts#L14) (level, msg)
  - module [orderStore](src/infra/order-store.ts#L1)
    - fn [save](src/infra/order-store.ts#L9) (order: Order) → Promise<void>
- application
  - module [purchase](src/app/purchase.ts#L1)
    - order domain.orderAggregate
    - catalog infrastructure.products
    - orders infrastructure.orderStore
    - fn [buy](src/app/purchase.ts#L12) (cart: Cart) → Promise<Order>
      - calls domain.orderAggregate.create, infrastructure.orderStore.save
```

Рядок `alias path` під модулем позначає залежність, як на слайдах. Рядок `calls …` під функцією — це витягнуті виклики, з них будується граф для перевірки потоків.

Карта — це **модульно-залежнісний вигляд** коду (модулі, функції, ребра), а не компонентно-конекторна модель класичних ADL: семантику взаємодій вона не описує, це роблять flows. Якщо є SCIP-індекс, до вузла дописується його символ: `- fn [buy](…) (cart) → Promise<Order> <!-- scip: … -->` — так ID keylang детерміновано з'єднуються з іншими інструментами.

### 3.3 Rules (пише людина)

```markdown
# rules

- layers domain < application < presentation
  - infrastructure
- allow infrastructure presentation
- deny domain infrastructure
  Домен чистий: жодного I/O.
- entry
  - infrastructure.server
  - presentation.terminal
- module application.purchase
  - exports buy, cancel
  - no-cycles
```

| Правило | Що перевіряє |
|---|---|
| `layers a < b` | залежності йдуть лише вниз; шари без порядку (тут `infrastructure`) — лише через `allow` |
| `allow a b` / `deny a b` | явний дозвіл або заборона залежності шару від шару чи модуля від модуля |
| `entry` | точки старту; модулі, недосяжні від жодного `entry`, — попередження «мертвий код» |
| `exports` | публічний API модуля не розширюється непомітно |
| `no-cycles` | немає циклів у графі залежностей |

**Які залежності бачать правила.** `allow`/`deny`/`layers` перевіряються на чотирьох видах ребер: `import` (модуль → модуль), `call` (fn → fn, з `calls`), `type` (посилання на тип у сигнатурі) і `re-export`. Кожне ребро має вид і `precision`; `keylang check --explain-edge a b` показує, через що саме знайдено залежність. Що не потрапляє в ці чотири види (рефлексія, DI-контейнер, event bus), правила не бачать — див. §4.

### 3.4 Flows — логіка застосунку (пише людина)

Один формат і для бізнес-логіки, і для технічної: ретраї, кеш, авторизація, міграції.

```markdown
# flow checkout
- kind business
- trigger presentation.terminal.checkout
- step application.purchase.buy
  - reads infrastructure.products.find
  - step domain.orderAggregate.create
  - step infrastructure.orderStore.save
  - emits event order.created
- invariant total = сума(price × qty) по позиціях
  - test tests/purchase.test.ts "computes total"
- when товару немає на складі
  - then application.purchase.OutOfStock
  - test tests/purchase.test.ts "rejects out of stock"
```

```markdown
# flow http-retry
- kind technical
- trigger infrastructure.http.request
- step infrastructure.http.send
- when status 5xx або timeout
  - then retry ≤ 3, backoff експоненційний
  - test tests/http.test.ts "retries 5xx"
```

`step` задає порядок і вкладеність викликів, `reads`/`emits` — побічні ефекти, а `invariant`/`when`/`then` — поведінку. Кожне твердження має посилатися на тест. Без тесту воно лишається просто описом і в звіті позначається як `unverified`.

- `invariant` може додатково посилатися на runtime-перевірку в коді: `- assert domain.orderAggregate.total#nonNegative` — тоді `trace` підтверджує, що вона спрацювала під час e2e-тесту.
- Потік **не мусить бути повним**, щоб існувати: `step`, якого ще немає в коді, — це K001 з пропозицією spec-to-code (§5.5), а не блокер. Спека не є передумовою коду; вона наздоганяє його або веде його — обидва напрямки рівноправні.
- Два потоки з однаковим набором `step` дають попередження K007 «дублювання потоку», щоб набір flows не розповзався, як Gherkin-сценарії.

## 4. Як перевіряється логіка

Три рівні, від дешевого до точного. Кожне твердження отримує статус `ok` / `fail` / `unverified`, тому неповна перевірка не маскується під успіх.

| Рівень | Як | Ловить | Обмеження |
|---|---|---|---|
| **static** | ID існують; у графі `calls` є шлях trigger → step → вкладені step. Це **досяжність**, а не порядок: статично доводиться лише, що кожен крок досяжний з попереднього | висячі посилання, видалені або перейменовані кроки, «обхід» шару | динамічна диспетчеризація й колбеки не видно → `unverified`, а не `fail`; порядок доводить лише `trace` |
| **tests** | кожен `test` існує і проходить (читаємо JUnit/JSON-звіт тест-раннера). Очікуються насамперед **e2e-тести**: один потік відповідає одному або кільком e2e-сценаріям, а не набору юніт-тестів | поведінка, інваріанти, гілки `when` | якість залежить від тестів |
| **trace** | трасуються лише тести, позначені `@flow <name>`; записана послідовність звіряється зі `step` як **підпослідовність із вкладенням** (між кроками можуть бути інші виклики) | реальний порядок викликів, пропущені кроки | потрібен адаптер під мову (див. нижче) |

Адаптери трасування: TS/JS — обгортка DI-контейнера (`wiring`) або OpenTelemetry-спани. Rust — спани `tracing`. Python — `sys.monitoring`. Формат трасування спільний (JSONL: `{id, parent, ts}`), тож звіряння не залежить від мови. Ребро, яке підтвердив трейс, але не бачить static, записується в індекс як `precision: dynamic` і далі рахується фактом.

**Словник звіту** узято з reflexion models: `check` показує **divergence** (є в коді, заборонено правилами), **absence** (заявлено в потоці чи правилі, у коді немає) і **convergence** (збігається). Absence не менш важливий за divergence: саме його інструменти зазвичай пропускають.

**Три значення, без злиття.** Кожен практичний граф викликів неповний (у Python recall ~70 %, у JS інструменти розходяться між собою), тому відсутність статичного шляху ніколи не дає `fail`, лише `unverified`. І навпаки: `unverified` ніколи не показується як `ok` — ні в жолобі, ні в CI-підсумку, ні в SARIF. `keylang check --strict` перетворює `unverified` на помилку для тих, хто хоче повного покриття.

**Стейлнес прози.** Опис вузла (§3.1) і текст `when`/`then`/`invariant` не перевіряються за змістом, але до них, як і до пояснень (§5.4), записується хеш сигнатури описаного вузла та його прямих залежностей. `keylang check --stale` показує описи й кроки, під якими код змінився, а `code-to-spec` (§5.5) пропонує оновлення як diff.

LLM у перевірці лише радить: `keylang review` питає, чи відповідає код тексту потоку, і результат ніколи не блокує CI. Як LLM бере участь у **генерації**, описано в §5.

## 5. Генерація: алгоритм, LLM або обидва

Будь-який артефакт мови (карту, описи, правила, потоки) можна згенерувати трьома способами. Режим обирається для кожної команди окремо:

```
keylang map        --mode algo|llm|hybrid
keylang draft flow --mode algo|llm|hybrid <trigger>
keylang draft rules --mode …
```

| | **algo** | **llm** | **hybrid** (за замовчуванням) |
|---|---|---|---|
| Джерело | tree-sitter/SCIP → граф | код + README + коміти → модель | обидва паралельно, потім звіряння |
| Добре дає | модулі, fn, сигнатури, імпорти, виклики, рядки коду | описи, групування в шари, назви потоків, наміри, інваріанти, гілки `when` | факти з algo, зміст з LLM |
| Погано дає | сенс, бізнес-назви, динамічні виклики | точні ID і зв'язки: вигадує, як NotebookLM зі слайдами | — |
| Детермінованість | так | ні | каркас так, текст ні |
| Вартість | секунди, без мережі | токени, мережа | токени лише на «м'які» поля |

### 5.1 Як працює hybrid

1. **algo** будує граф та індекс. Це авторитетні факти: ID, прив'язки до коду, виклики. Індекс **перебудовується перед кожним** draft-, explain- чи ghost-запитом: застарілий контекст шкодить більше, ніж його відсутність (у дослідженнях 76–88 % доповнень із застарілого retrieval посилалися на неіснуючий код).
2. **llm** отримує компактну карту з кроку 1 (а не весь код) плюс фрагменти коду на вимогу і пише кандидатів: описи, призначення шарів, потоки, інваріанти. У промпт завжди входять граматика keylang (§3) і 2–3 **схожі потоки з цього ж репозиторію** як приклади: нову DSL моделі генерують погано zero-shot, а приклади з того самого репо дають найбільший приріст.
3. **Обмеження:** LLM може посилатися лише на ID з індексу. Невідомий ID відхиляється як K001, і чернетка **один раз** повертається моделі з найближчими реальними ID (`did you mean`) — це перевірка до людини, як у SpecGen/De-Hallucinator. Лише після цього кола результат показується.
4. **Шари ніколи не призначаються мовчки.** Автоматичне відновлення архітектури дає точність часто нижче 50 %, тому algo генерує факти, а розкладку по шарах LLM або евристики лише **пропонують** — вона приймається людиною через merge, як будь-яке `llm-only`.
5. **Звіряння** кожного твердження:

| Результат | Коли | Що робимо |
|---|---|---|
| `agree` | є і в графі, і в LLM | приймаємо автоматично |
| `algo-only` | є в графі, LLM пропустила | лишаємо, це факт |
| `llm-only` | LLM стверджує, у графі немає | `unverified`: або динамічний виклик, якого не бачить algo, або вигадка → на рев'ю |
| `conflict` | суперечать (інший порядок, інший шар) | на рев'ю, показуємо обидві версії |

6. Розбіжності самі по собі корисні: `llm-only` підказує, де algo сліпий (DI, колбеки, рефлексія), а `algo-only` — де LLM не зрозуміла код. Є й зворотний хід: для ребер з `precision: syntactic`, де algo не певен (динамічна диспетчеризація, DI), LLM може дати «голос» за конкретну ціль — це підвищує ранг кандидата, але не міняє результат `check`.
7. Відсоток прийняття `llm-only` і `conflict` записується у `.keylang/stats.json`. Це калібрування: якщо `llm-only` приймають рідко, TUI показує їх згорнутими.

### 5.2 Походження у файлі

Згенероване LLM позначається невидимим у рендері коментарем, щоб завжди було видно, звідки твердження:

```markdown
- step infrastructure.payments.charge <!-- keylang:llm model=claude-sonnet-5 status=llm-only -->
```

Факти від algo не позначаються: це карта за замовчуванням. Прийняте людиною твердження втрачає позначку, і далі воно перевіряється як будь-яке інше (§4). CI ніколи не приймає `llm-only` автоматично.

### 5.3 Режими окремо

- **algo** — для CI, pre-commit і великих репозиторіїв: швидко, безкоштовно, відтворювано.
- **llm** — для репозиторію, де tree-sitter-запитів для мови ще немає, або для першого знайомства з чужим кодом. Результат увесь `unverified`, поки `keylang check` не підтвердить посилання.
- **hybrid** — щоденний режим: `keylang map` у CI працює як algo, а `keylang draft` локально — як hybrid.

### 5.4 Пояснення вузла простою мовою (LLM)

Для **будь-якого вузла** (шар, модуль, fn, потік, правило, крок) можна подивитися пояснення звичайним текстом: що він робить, навіщо, з якими вузлами пов'язаний, які є крайні випадки.

- **Команда:** `keylang explain <id>`; у TUI — клавіша `e` на вузлі під курсором або вкладка «Пояснення» у спливаючій підказці.
- **Що отримує LLM:** код вузла; сигнатури його залежностей і тих, хто його викликає (з індексу); потоки й правила, де вузол згаданий; **словник спеки** — назву шару, бізнес-імена з flows, текст поруч із `deny`. Без доменної термінології промислові рецензенти відхиляють понад половину LLM-описів. Весь репозиторій не передається.
- **Обмеження:** у тексті можна посилатися лише на ID з індексу. Такі посилання стають клікабельними, а невідомий ID підсвічується як помилка.
- **Не змішується з мовою.** Пояснення зберігаються окремо, у `.keylang/explain/<id>.md`, і не потрапляють у map/flows. Карта лишається детермінованою.
- **Актуальність:** до пояснення записується хеш коду вузла та його залежностей. Змінився код — пояснення позначається `застаріло` і перегенеровується на вимогу (`R`) або пакетно: `keylang explain --stale`.
- **Мова пояснень** задається в `keylang.json` (`explain.lang = "uk"`). Рівень деталізації: `short` (2–3 речення про призначення; **за замовчуванням**, бо саме такий рівень люди вважають найкориснішим) або `full` (кроки, гілки, крайні випадки). Порядкового «рядок за рядком» немає.
- **Видиме походження.** У панелі пояснення завжди є рядок `модель · дата · stale?`. Полірований текст приховує помилки: у дослідженнях люди пропускали ~40 % хибних тверджень у відповідях LLM, тому статус і модель показуються, а не ховаються в коментар.
- **Кешування й офлайн:** уже згенероване пояснення читається без мережі. Без ключа LLM показується лише algo-зведення: сигнатура, залежності, де використовується.
- **Довіра:** пояснення — довідка для людини. Воно ніколи не впливає на `check` і CI.

### 5.5 code-to-spec і spec-to-code

Дві протилежні команди, і обидві працюють у режимах algo / llm / hybrid.

| | **code-to-spec** | **spec-to-code** |
|---|---|---|
| Вхід | виділений код: fn, модуль, файл або `git diff` | вузли спеки, яких ще немає в коді (K001 у написаних файлах) або змінені кроки потоку |
| algo | карта: модулі, fn, залежності, виклики | заготовка: файл у шарі за `keylang.json`, сигнатура з назви й аргументів, `todo!()` / `throw` |
| llm | описи, потік (`step`/`when`/`then`), інваріанти | реалізація тіла + **e2e-сценарій** під потік |
| Результат | чернетка спеки в режимі MERGE (§5.1) | diff коду в режимі MERGE, по шматках (hunk): прийняти / відхилити |
| Запобіжники | лише ID з індексу | код генерується тільки в дозволеному шарі; `allow`/`deny` перевіряються до показу diff |

Цикл замикається: spec-to-code → людина править → `keylang map` перегенерує карту → вузол у спеці тепер `agree`, і K001 зник. Команди: `keylang spec-to-code <id|file>`, `keylang code-to-spec <path[:line]>`; у TUI — `Enter` на K001 або палітра `:`.

## 6. Wiring — виконуваний режим (опційно)

Як у Шемсединова, але через **кодогенерацію, а не інтерпретацію**, щоб результат проходив перевірку типів.

```markdown
# wiring
- wire application.purchase
  - order domain.orderAggregate
    - when env.DEPT = accounting → domain.accountingOrder
- wire infrastructure.server
  - api presentation.api
    - compose infrastructure.logger   <!-- усі запити спершу логуються -->
```

`keylang wire` генерує `keylang.gen.ts` (далі `keylang.gen.rs`): двофазне завантаження, як на слайдах, спершу модулі, потім ін'єкція. Умовна підстановка та `compose` стають звичайним кодом. Контейнер одночасно дає точки для `trace`.

## 7. Архітектура інструменту

```
              keylang (Node.js + TypeScript, npm-пакет)
 ┌───────────────────────────────────────────────────────────┐
 │ extract   tree-sitter + queries/<lang>/*.scm → факти       │
 │           (symbols, imports, calls, exports, signatures)   │
 │ resolve   імпорти → модулі (tsconfig paths, mod-tree, pkg) │
 │ layer     keylang.json: glob → шар/модуль                    │
 │ graph     модулі, fn, залежності, виклики + рядки коду     │
 │ parse     *.md → IR (з позиціями для LSP)                  │
 │ check     rules + flows × graph × test-report × trace      │
 │ emit      map/*.md · .keylang/index.json · SARIF · wiring    │
 └───────┬───────────────────┬──────────────────┬────────────┘
         │ LSP (stdio)       │ ANSI · WS→xterm.js│ CLI / CI
   ┌─────▼──────┐     ┌──────▼───────┐    ┌─────▼─────┐
   │ VS Code,   │     │ keylang TUI    │    │ keylang     │
   │ Neovim…    │     │ термінал/web │    │ check     │
   └────────────┘     └──────────────┘    └───────────┘
```

- **TypeScript + tree-sitter.** Парсер коду — `web-tree-sitter` (WASM) з готовими `.wasm`-граматиками в пакеті: нічого не компілюється при `npm install`, працює на всіх ОС однаково; ціна — 2–5× повільніше за native, що для інкрементального індексу неістотно. Мова додається набором `.scm`-запитів без змін у ядрі. Ядро (`src/`) — чистий TS без залежностей, Node виконує його напряму (type stripping), тож кроку збірки немає.
- **Точність.** tree-sitter не знає типів, тому виклики резолвляться за імпортами та іменами. Для точних посилань є опційний бекенд, що читає **SCIP**-індекси (`scip-typescript`, `rust-analyzer scip`, `scip-python`). У кожного ребра графу є поле `precision: syntactic | semantic`.
- **Інкрементальність.** Розбираються лише змінені файли (кеш за хешем). `keylang watch` оновлює карту та індекс на льоту.
- **`.keylang/index.json`:** `id → {file, range, signature, doc, deps, dependents, flows}`. Це єдине джерело даних для обох переглядачів.

### 7.1 Інтерфейс — термінал, як Xcode

Головний інтерфейс — **TUI `keylang`** (Node.js, Ink 7 + власний парсер SGR-подій мишки; мишка + клавіатура). Принцип як у Xcode: **у фокусі сам текст мови**, решта з'являється на вимогу.

```
┌ навігатор ─┬─ редактор: *.md з підсвіткою ───────────────┬─ навігація ─┐
│ (сховано,  │  - step infrastructure.orderStore.save  ✓   │ ▾ domain    │
│  Ctrl+0)   │        ┌ hover ─────────────────────┐       │ ▾ infra…    │
│            │        │ fn save(order) → Promise    │       │   ▸ orderS… │
│            │        │ src/infra/order-store.ts:9  │       │ ПОТОКИ      │
│            │        └─────────────────────────────┘       │   checkout ✗│
├────────────┴─────────────────────────────────────────────┴─────────────┤
│ ✗ 2  ◌ 5   Enter код · Alt+Enter спека · / пошук · F5 check · ? клавіші │
└─────────────────────────────────────────────────────────────────────────┘
```

- **Редактор** показує сирий Markdown keylang з підсвіткою: шари кольорами, ключові слова, ID. Ніякого «рендеру в картки».
- **Жолоб** (як issue-gutter у Xcode): `✓` / `✗` / `◌` біля кожного твердження. Помилка розгортається рядком під ним.
- **Спливаючі підказки** при наведенні мишею або `K`: сигнатура, 4 рядки коду, де використовується.
- **Пояснення** (`e`): текст простою мовою від LLM про те, що робить вузол, з клікабельними ID. Див. §5.4.
- **Навігація праворуч** (одна панель, `Ctrl+1` ховає): шари → модулі → fn, окремо потоки та правила зі статусами.
- **Переходи:** `Enter`/Ctrl+клік — у код: у вбудованому переглядачі, а якщо заданий `$EDITOR` / `code`, то там. `Alt+Enter` — у спеку, `Ctrl+O` — назад.
- **Генерація** (§5) відкривається в тому ж редакторі як злиття: `=` agree, `+?` llm-only, `!` conflict. `a` приймає, `r` відхиляє.
- Жодних окремих форм налаштувань: налаштування — це `keylang.json`, відкритий у тому ж редакторі з підказками.

Та сама логіка доступна **через LSP** (`keylang lsp`) для VS Code, Neovim, Zed, JetBrains:

| Вимога | Механізм LSP |
|---|---|
| навів на ID → що це | `hover` |
| Ctrl → стрибок у код | `definition` |
| перейти в спеку | `definition` на ID з `flow`/`rules`, `references` |
| навігація праворуч | `documentSymbol` |
| помилки | `diagnostics` |
| автодоповнення ID | `completion` |
| зворотний зв'язок з коду | CodeLens «flows: checkout» над функцією |

VS Code extension — тонкий LSP-клієнт.

### 7.2 Один TUI — два запуски: термінал і браузер

| | `keylang` | `keylang web` |
|---|---|---|
| Де | будь-який термінал (xterm-256color, truecolor) | вкладка браузера, `http://localhost:7070` |
| Як | Ink рендерить у stdout | той самий TUI у тому ж процесі; Ink отримує замість stdout/stdin потоки, прив'язані до WebSocket: ANSI іде у вшитий **xterm.js**, а події клавіатури й мишки йдуть назад |
| Мишка, hover | SGR mouse | xterm.js передає ті самі mouse-події |
| Перехід у код | вбудований переглядач; або `$EDITOR` / `code -g`, якщо є | вбудований переглядач; OSC 8-посилання `vscode://file/…:line` |
| Кому | щоденна робота | рев'ю, демо, віддалена машина, людина без налаштованого термінала |

Обидва варіанти — **один і той самий код інтерфейсу**. Браузерна версія лише обгортка: вшитий xterm.js + WebSocket, без PTY, окремого фронтенду й зовнішніх утиліт (див. §7.4). Тому поведінка, клавіші й вигляд збігаються піксель у піксель, з точністю до шрифту.

Пізніше можна додати статичну збірку без сервера для публікації карти як сторінки: той самий React-код Ink на canvas-рендерері (Gridland / Ink Web) або простий HTML-експорт. Вона тільки для читання: `$EDITOR` там недоступний, лишаються тільки `vscode://`-посилання.

Чому Ink, а не OpenTUI: OpenTUI під Node вимагає ≥ 26.4 з `--experimental-ffi`, що ламає `npx keylang` на поточних LTS. Коли Node 26 стане базовим, перехід можливий — обидва на React, компоненти переносяться.

### 7.3 Редактор і співавторство з агентом

Мету сформульовано так: швидко будувати нові модулі та логіку, починаючи будь-з якого боку, від людини або від агента.

**Підказки з кодової бази (детерміновані, без LLM).** Джерело — `.keylang/index.json`, тобто вже наявний код.
- Автодоповнення ID: `infrastructure.or…` → `orderStore.save · fn (order) → Promise<void>`. Список фільтрується за шаром (`allow`/`deny`), тож заборонене не пропонується.
- Ключові слова залежно від позиції: під `flow` — `trigger`/`step`/`when`…, під модулем — залежності.
- Signature help, помилки під час набору (K001 і K003 одразу), hover, перехід у код.

**Ghost-текст від агента.** Сірим продовженням рядка з'являються наступні рядки потоку, наприклад `- emits event order.refunded`. `Tab` приймає, `Alt+]` показує інший варіант, `Esc` прибирає. Дозволено лише ID з індексу.

Два режими роботи з підказками розділені свідомо, за дослідженнями Copilot: у режимі *прискорення* людина знає наступний крок і хоче коротку підказку, у режимі *пошуку* — не знає і хоче варіанти. Тому:
- ghost-текст — лише для прискорення: до 3 рядків, з'являється не на кожне натискання, а після паузи 400 мс і лише коли є дешевий сигнал (курсор під `flow`, рядок починається з `- `, у індексі є кандидат з високою впевненістю). Без сигналу ghost не показується — половина часу з підказками інакше йде на їх читання й відкидання;
- пошук — це `Alt+]` (варіанти) і `Ctrl+Space` (повна чернетка як MERGE-diff);
- усе довше за один рядок іде **тільки** через MERGE по шматках, ніколи через `Tab`;
- у M6 спершу вимірюється, скільки дає детерміноване автодоповнення з індексу без LLM (частка прийнятих пропозицій, час до першого `agree`), і лише потім вмикається ghost. Дослідження показують, що більшість користі підказок — «менше клавіш, згадати синтаксис», а це індекс дає безкоштовно.

**Співавторство в обидва боки:**
1. *Людина → агент.* Пишеш кілька рядків або звичайний текст, натискаєш `Ctrl+Space` («догенеруй»), і агент дописує решту як diff.
2. *Агент → людина.* Промпт на кшталт «додай повернення коштів». Агент пише чернетку, ти правиш руками, агент бачить правки в наступному запиті.

Будь-яка зміна від агента показується **як diff по шматках у тому ж редакторі** (режим MERGE): `a`/`r` на кожен шматок. Нічого не записується без підтвердження.

**Звичайний текст як вхід.** Будь-який вузол може мати опис вільним текстом (§3.1). Команда `Ctrl+G` («text → spec») перетворює виділений текст на структуру (`when`/`then`/`step`), а оригінал лишає описом.

**Голосовий ввід.** `Ctrl+R` у полі агента або на місці курсора в редакторі. Розпізнаний текст або йде в промпт, або вставляється як опис вузла. Два рушії, вибір у `keylang.json` (`voice.engine = "local" | "openrouter" | "auto"`):

| | **local** | **openrouter** |
|---|---|---|
| Як | whisper.cpp через `@fugood/whisper.node` (N-API, prebuilt-бінарники для Linux/macOS/Windows, варіанти CPU/CUDA/Metal/Vulkan), **опційна залежність**: без неї працює лише `openrouter` | аудіо (WAV 16 кГц, base64) іде в OpenRouter chat completions як `input_audio` до моделі з аудіовходом |
| Мережа | не потрібна | потрібна, ключ `OPENROUTER_API_KEY` або `~/.config/keylang/openrouter.key` (права 0600) |
| Модель | завантажується на першому використанні в `~/.cache/keylang/models` (small / large-v3-turbo), не входить у бінарник | налаштовується: `voice.model = "…"` |
| Коли | офлайн, приватний код | слабке залізо, потрібна краща якість або змішана мова |

`auto` бере local, якщо модель уже завантажена, інакше openrouter, якщо є ключ. Інакше `Ctrl+R` пояснює, що налаштувати.

Від `voice-transcriber` беремо **тільки ідеї, не код і не залежність**: вікна по ~25 с з перекриттям 1 с, глосарій ID з індексу як підказка (prompt) для Whisper, щоб `orderStore` не ставав «ордер стор», і ранню перевірку готовності моделі. Глосарій — **лише малий піднабір**: ID вузла під курсором, його сусідів у графі й поточного потоку (до ~30 термінів, найважливіші в кінці промпта). Довгі списки термінів погіршують розпізнавання, а не покращують.

Куди йде голос: за замовчуванням у **вільний текст** — опис вузла, промпт агенту, `when`/`then`. Диктувати структурні рядки з ID незручно і в дослідженнях програє набору з клавіатури. Для структури є крихітна командна граматика: «крок …», «коли … тоді …», «емітить …» перетворюються на `- step` / `- when` / `- then` / `- emits`, а ID підставляється через те саме автодоповнення з нечітким пошуком. Захоплення мікрофона — `decibri` (N-API, prebuilt; без `sox`, `arecord`, `pw-cat`), теж опційна залежність. У `keylang web` мікрофон захоплює браузер (getUserMedia), PCM іде тим самим WebSocket, далі той самий рушій на сервері — тому браузерний варіант голосу працює навіть там, де `decibri` не має збірки (macOS x64).

**Контекст агента видно й можна керувати.** Панель «Контекст» показує, що саме піде в модель, і скільки токенів займе кожен елемент:
- поточний буфер;
- вузли під курсором і їхні сусіди з графу;
- потоки й правила, де вони згадані;
- фрагменти коду;
- e2e-тести потоку.

`@id` додає вузол, `x` прибирає. Зібраний пакет контексту кешується за хешем.

**Зовнішні агенти через MCP.** `keylang mcp` віддає інструменти `search`, `node`, `code`, `flows`, `check`, `explain` і `apply_diff`. Тож Claude Code, Codex та інші агенти беруть той самий контекст самі. `code` (фрагменти на вимогу) обов'язковий поряд із графом: агент лише на графі відповідає на ~10 п. гірше, ніж той, що читає файли, хоч і в 10 разів дешевше, тому граф — за замовчуванням, код — коли потрібно. Вбудований агент TUI користується тим самим MCP-шаром. Адаптер у `keylang.json`: `agent = "anthropic:claude-sonnet-5"`, `"openrouter:<model>"` або зовнішній CLI через MCP. Вбудований агент звертається до API напряму по HTTPS; `claude` чи `codex` для нього не потрібні. Ключ OpenRouter спільний для агента й голосу.

**Читання спек.** `v` перемикає редактор у режим читання. Markdown рендериться через **marked** + **marked-terminal** (ANSI-вивід: заголовки, таблиці, блоки коду з підсвіткою, посилання), обгорнутий в Ink-компонент, щоб ID лишалися клікабельними, а статуси перевірок — видимими.

### 7.4 npm-пакет, мінімум зовнішнього

Ціль: `npx keylang` працює одразу на будь-якій машині з Node ≥ 22.18. Жодних інших програм для встановлення; native-модулі лише з prebuilt-бінарниками і лише як **опційні** залежності (без них відповідна функція вимикається, а не весь інструмент).

| Потреба | У пакеті | Чого **не** вимагаємо |
|---|---|---|
| ядро: парсер, резолвер, `check`, `fmt` | чистий TS у `src/`, нуль залежностей | крок збірки (Node виконує `.ts` напряму) |
| розбір коду | `web-tree-sitter` + `.wasm`-граматики (`tree-sitter-wasms` / `@vscode/tree-sitter-wasm`) | компілятор C, `node-gyp`, CLI tree-sitter |
| точні посилання | вбудований резолвер імпортів; SCIP-індекс читається, **якщо він є** | `scip-*` (опційно) |
| git | `es-git` (prebuilt libgit2: diff, blame, status) або `isomorphic-git` (чистий JS, без blame) — вирішується в M2 | `git` CLI |
| TUI | Ink 7 + `react`; мишка через SGR-послідовності в stdin | — |
| веб-варіант | `node:http` + `ws`; Ink пише в потік, прив'язаний до WebSocket, xterm.js лежить у пакеті | `ttyd`, PTY, CDN |
| Markdown | `marked` + `marked-terminal` | `glow`, `mdcat` |
| підсвітка коду | ті самі tree-sitter-запити `highlights.scm` → ANSI | `bat`, `highlight.js`-теми з диска |
| голос | `@fugood/whisper.node` (prebuilt whisper.cpp) + `decibri` — обидва `optionalDependencies`; модель — на вимогу в кеш | `ffmpeg`, `sox`, `pw-cat`, Python |
| LLM / OpenRouter | вбудований `fetch` + SSE-парсер (~100 рядків) або `@anthropic-ai/sdk` | `curl`, `claude`/`codex` CLI |
| LSP | `vscode-languageserver` | — |
| MCP | `@modelcontextprotocol/sdk` | — |
| перехід у код | вбудований переглядач коду в TUI (read-only, з підсвіткою) | `$EDITOR`, `code` — лише якщо є |

Установка: `npm i -g keylang` або `npx keylang`. Розмір пакета орієнтовно 15–25 МБ з граматиками WASM, без моделей голосу. Prebuilt-бінарники (`whisper.node`, `decibri`, `es-git`) тягнуться лише для платформи користувача.

Що втрачено проти single-binary плану (research.md §3): потрібен установлений Node; холодний старт ~60–120 мс на запуск runtime плюс завантаження індексу; native-addons залежать від наявності prebuilt під платформу. Що виграно: нуль кроку збірки, той самий код у терміналі, браузері та VS Code-розширенні, канонічні SDK для LSP/MCP/LLM, значно швидша ітерація.

Правило залежностей: кожна нова залежність — з обґрунтуванням у PR; `npm ls --omit=dev` не повинен перевищувати ~30 пакетів у дереві ядра. Supply chain — `package-lock.json`, `npm audit` у CI, версії зафіксовані точно.

### 7.5 Developer experience

**Перші 60 секунд:**
```
$ keylang init          # знаходить мови, пропонує keylang.json (algo), будує карту
$ keylang               # відкриває TUI у поточному репо; індекс оновлюється у фоні
```
- **Нуль конфігурації за замовчуванням.** Шари вгадуються за типовими теками (`domain/`, `app/`, `infra/`, `ui/`), а `keylang.json` потрібен лише для уточнень.
- **Швидкість.** Холодний старт TUI менше 300 мс з кешованого індексу (Node ~60–120 мс + індекс). Інкрементальна переіндексація змінених файлів займає мілісекунди. `watch` вбудований у TUI.
- **Відкриваність.** `?` показує всі клавіші в поточному режимі, `:` — палітру команд з нечітким пошуком. Рядок стану завжди підказує 4–6 головних дій.
- **Помилки, які вчать.** Кожен код має довідку: `keylang explain K001`, а в TUI `?` на помилці. Там причина, приклад і «чи мали на увазі…». Є швидкі виправлення: `Enter` на K001 пропонує spec-to-code або найближчий ID.
- **Шаблони.** `keylang new flow refund`, `keylang new module payments --layer infrastructure` створюють заготовку з автодоповненням.
- **CI та хуки.** `keylang check --format human|json|sarif|github`, коди виходу 0/1/2. `keylang hook install` ставить pre-commit, `--changed` перевіряє лише зачеплене.
- **Середовище.** `keylang doctor` показує мови, граматики, кеш, ключі API, модель голосу та термінал: truecolor, мишку, OSC 8.
- **Інтеграції за бажанням.** `keylang lsp` для редакторів, `keylang mcp` для агентів, `keylang completions <shell>`.
- **Передбачуваність.** Жодна дія агента не пише у файли без diff і підтвердження. `u` відкочує останнє прийняте. Усе, що зробила LLM, позначено.

## 8. Конфігурація

```json
{
  "languages": ["typescript"],
  "module": "file",
  "layers": {
    "domain":         ["src/domain/**"],
    "application":    ["src/app/**"],
    "infrastructure": ["src/infra/**", "src/live/audio/**"],
    "presentation":   ["src/ui/**", "src/cli/**"]
  },
  "check": {
    "tests": "reports/junit.xml",
    "trace": ".keylang/trace/*.jsonl"
  }
}
```

Файл `keylang.json` (JSON, бо в Node немає вбудованого TOML, а зайва залежність у ядрі не потрібна); до нього додається JSON Schema, тож редактори підказують ключі. `module`: `"file"` — файл є модулем, тека з `index.ts` — модуль із підмодулями (дефолт для TS); `"dir"` — тека є модулем (дефолт для Python і Rust-`mod`).

## 9. Дорожня карта

| Етап | Результат | Критерій готовності |
|---|---|---|
| **M0** | специфікація формату, парсер MD → IR, `keylang fmt` | приклад зі слайдів розбирається; `domain.aggregate` дає помилку висячого посилання |
| **M1** | `extract` для TypeScript, `keylang map`, `index.json`, rules-перевірка; **власний e2e-бенчмарк conformance** (`bench/`: 3–5 репозиторіїв з відомими порушеннями і absences), бо готових бенчмарків для spec↔code немає | карта самого keylang (`src/`) генерується, `keylang check` ловить штучно доданий заборонений імпорт; бенчмарк: divergence і absence знаходяться, `unverified` не змішується з `ok` |
| **M2** | TUI `keylang` (редактор, жолоб, hover, навігація) + `keylang web` (той самий TUI у браузері) + `keylang lsp`; **usability-проба синтаксису**: 5–8 розробників пишуть flow для відомого репо, за результатами синтаксис фіксується | з карти Enter/Ctrl+клік відкриває потрібний рядок; у браузері те саме; після проби формат v1 заморожено |
| **M3** | flows: static + tests | потік `check` самого keylang (файли → парсер → резолвер → діагностики) проходить; видалений крок → `fail` |
| **M4** | Rust + Python queries, тонке VS Code extension | та сама карта в VS Code через LSP; карта `voice-transcriber` (Rust) генерується |
| **M5** | trace-адаптери, `keylang wire` (TS), `--mode llm` і `hybrid` (§5) | трасування e2e звіряється з потоком; hybrid-чернетка потоку показує agree / llm-only / conflict |
| **M6** | редактор: автодоповнення з індексу, ghost-текст, агент + панель контексту, `keylang mcp`, голос (Whisper), режим читання (tui-markdown), code-to-spec / spec-to-code | новий потік `refund` набирається з автодоповненням; spec-to-code створює заготовку + e2e, після `map` крок стає `agree` |

Перша мова — **TypeScript**: ядро теж на TS, тож keylang описує сам себе з M1, приклад Шемсединова зроблено на TS, а `wiring` для TS найпростіший. Rust іде другим (`voice-transcriber` як зовнішній полігон), Python третім.

## 10. Відкриті питання

1. ~~Гранулярність модуля за замовчуванням~~ — вирішено (§8): дефолт залежить від мови (TS — файл, Python/Rust — тека/`mod`), `module` перевизначає.
2. **Мова описів.** Ключові слова англійською, опис вузлів будь-якою мовою. Чи потрібна локалізація ключових слів — ймовірно, ні.
3. **Lisp/JS-форми.** IR спільний, тож `keylang fmt --to lisp|js` зробити легко. Чи потрібно це комусь, крім демонстрації еквівалентності?
4. **Де зберігати трасування.** Трасуються лише тести з `@flow` (§4), але чи комітити `.keylang/trace/*.jsonl`, чи тримати їх лише як CI-артефакт — відкрито.
5. **Назва ID для анонімних речей:** замикання, обробники подій, методи трейтів. Кандидат: `module.fn#closure1` з `precision: syntactic`.
6. **Як не скотитися у waterfall.** Головна скарга на Spec Kit і Kiro — специфікація перетворюється на етап «до коду» і дрейфує після реалізації. keylang дозволяє неповні потоки і має `--stale`, але чи вистачить цього, покаже лише практика на реальному репо: можливо, потрібен режим «спека наздоганяє код» як дефолт для нових фіч.
7. **Втома від `unverified`.** У TS/Python синтаксичне розв'язання методів дасть низький recall, і жолоб буде рясніти `◌`. Чи потрібен окремий згорнутий вигляд, чи SCIP має стати рекомендованим дефолтом для цих мов.
8. **Підтримка мапи глобів при реорганізації каталогів** — історична причина смерті conformance-інструментів. Кандидат: `keylang map --relayer` пропонує оновлені глоби після переміщень, знайдених через `gix`.
