# Семантичний знімок keylang

Частина специфікації формату keylang v0.2 (покажчик — [format.md](format.md)): що keylang читає з коду, `.keylang/index.json` і правила за мовами. Синтаксис — у [grammar.md](grammar.md), семантика правил і потоків — у [semantics.md](semantics.md). Розділи пронумеровано наскрізно для всіх трьох файлів.

## 11. Семантичний знімок (`.keylang/index.json`)

`keylang map` серіалізує `AnalysisSnapshot` (схема **7**) у `.keylang/index.json` і **рендерить Markdown-карту з цього знімка**. Індекс — кеш фактів, не текст для редагування. Шлях у вузлі знімка лишається POSIX-шляхом від кореня репозиторію; відносне кодоване посилання рахує emitter. Несумісна або зіпсована схема на диску не є помилкою: наступний `map` перезаписує файл без окремої діагностики.

`snapshotId` — SHA-256 канонічного JSON від схеми, версії екстрактора, версій граматик, конфігурації (`dir`, `languages`, `module`, `layers`, `exclude`, `outside`, `assume`, `guessed`) і SHA-256 вмісту кожного проіндексованого файла. Поле `generated` (час запису) у хеш не входить, і поле `format` теж. Два запуски на тих самих джерелах дають той самий `snapshotId`. Його змінює зміна проіндексованого файла або одного з перелічених полів конфігурації, а також оновлення рантайму чи граматик. Версія `web-tree-sitter` — з найближчого `package.json` з цим ім'ям над модулем, який резолвить Node (`exports` пакета не відкриває `./package.json`). Версія граматик — з `dist/wasm/grammars.json`, який `prepack` пише поруч зі скопійованими граматиками; у checkout — з встановленого `@vscode/tree-sitter-wasm`. Пакет, якого не знайдено, має версію `unknown`.

| Частина | Зміст |
|---|---|
| `manifest` | екстрактор, версії `web-tree-sitter` і `@vscode/tree-sitter-wasm`, конфігурація, `{path, sha256}` файлів |
| `nodes` | ID → вид (`layer` / `module` / `fn` / `type`), шар, файл і діапазон (`line`, `col`, `endLine`, `endCol`: колонки з 1 у кодових точках, як у [semantics.md](semantics.md) §7, кінець — позиція після фрагмента). У модуля й типу діапазон є так само, як у функції. У модуля `members`: `complete` або `opaque`; клас — модуль із `class: true` (у будь-якому файлі свого модуля, зокрема в модулі-теці), його члени — дочірні вузли, конструктор — `<клас>.constructor`. У fn члена класу `static: true` — статичний член (`X.m()`), `name` — ім'я, як його написано, коли сегмент ID інший (`m` для `X.m-static`, `go` для `Y.go-private`). Похідні `deps` / `dependents` / `calls` / `callers` (`calls` без ребер `injected`, кожна ціль один раз). У fn може бути `escapes: {file, line, col, reason}` — перше місце, де її може викликати код, що її не називає (читання як значення, accessor, неявний метод, виклик із коду поза оголошеннями, базовий клас, який keylang не прочитав, статичний ініціалізатор) |
| `exports` | публічне ім'я модуля (`name`, яким його імпортують; `default` для `export default …`, `export =`, `module.exports = …`) → `symbol` — вузол, який воно означає, через псевдоніми, ланцюжки re-export і `export *` (fn, клас, тип або модуль простору імен; `null`, коли це не оголошення, яке keylang індексує: `export default 3`, ім'я пакета), вид (`fn`, `class`, `type`, `value`), `form` (немає — оголошення під власним ім'ям; `alias` — `export { a as b }`; `default` — експорт за замовчуванням; `reexport` — ім'я іншого модуля; `namespace` — об'єкт модуля: `export * as ns from`, `import * as ns; export { ns }`, `export namespace N {}`), `local` — локальне чи вихідне ім'я, коли воно інше (`a` для `export { a as b }`, `main` для `export default function main`) і `from` — модуль, з якого ім'я реекспортовано (для `export *` — модуль, що його експортує). Рядок `*` з видом `reexport` і `reason` — `export *` з модуля з невідомим вмістом |
| `edges` | `kind` (`import`, `call`, `type`, `reexport`), `source`, `target` або `null`, `candidates` коли цілей кілька, `text` (фрагмент коду) і діапазон `line`/`col`/`endLine`/`endCol`, `resolution` (`resolved` / `ambiguous` / `unresolved`), `provenance` (`syntactic`). `ambiguous` означає кілька можливих цілей у `candidates` і порожній `target`. Необов'язкові поля виклику: `via` (`default` / `injected`), `hook` і `site` — ребро хука ([semantics.md](semantics.md) §7, «Хуки»); `closure: true` — виклик у вкладеній функції джерела; `typeOnly: true` — ребро `import` чи `reexport` інструкції, що називає лише типи (TypeScript `import type`, `export type … from`, `export type * from`; `import { type A }` і `export { type A } from`, де кожне ім'я — `type`, без `verbatimModuleSyntax` у tsconfig файла): `no-cycles` його не бачить |
| `coverage` | нерозв'язаний імпорт, динамічний виклик (зокрема «call through an expression» — виклик виразу, який keylang не називає: `f()()`, `(a || b)()`, `new (load())()`, ланцюжок довший за 80 символів), нерозв'язаний виклик, `unsupported construct` (namespace, `eval`, `new Function`, виклик `obj[expr]`, обчислюваний член класу `[key]() {}`, колізія ID модулів), обчислюваний specifier (`import(expr)`, `require(expr)`, `import.meta.resolve(expr)`, ``new URL(`./${n}.ts`, import.meta.url)`` чи `"./" + n`, `register(expr, import.meta.url)`; `new URL` з відомим немодульним закінченням, як `.png`, — не модуль; відносний `new URL("./worker", import.meta.url)` без розширення — ребро, коли за ним є файл коду, і нічого інакше), синтаксична помилка (зокрема синтаксис, вкладений глибше за 1000 рівнів: файл тоді `opaque`, а не падіння аналізу), файл поза шаром, пропущений файл (`skipped-file`) і файл поза архітектурою (`outside-file`) і імпорт файла, який називає `assume` (`assumed-import`, не прогалина) — кожен із діапазоном, `text` і `reason` |
| `stats` | лічильники проходу; вони не замінюють записи `coverage` |

Порожній проіндексований модуль має `members: "complete"` і жодного дочірнього символу. `opaque` не підтверджує існування довільного імені. Файл, виключений через `exclude` у `keylang.json`, стає модулем `members: "opaque"` свого шару, а файл поза всіма шарами — модулем шару `unassigned`; у карті він має коментар `<!-- excluded -->`, у `coverage` — запис `skipped-file`. Цей запис — прогалина рівня залежностей: рядок `layers`, глобальний `no-cycles` чи `deny`, в області якого лежить файл, отримує `unverified`, а не `ok` ([semantics.md](semantics.md) §7). Файл, який `outside` у `keylang.json` (масив глобів поруч з `exclude`) виводить поза архітектуру, — скрипт, бенчмарк, приклад — keylang теж не читає, але це не прогалина: файл стає модулем `members: "opaque"` синтетичного шару `outside` з ID за шляхом, як в `unassigned` (`scripts/run.ts` → `outside.scripts.run`), у карті — `<dir>/map/outside.md` з коментарем `<!-- outside -->`, у `coverage` — запис `outside-file` з причиною «outside the architecture (`outside` in keylang.json)». `layers`, `no-cycles`, `deny` і `entry` через нього `unverified` не стають; для `static` потоків такий модуль не є непрозорим кодом, що може викликати крок. Імпорт (і будь-яке інше ребро) з коду архітектури — модуля шару чи `unassigned` — у файл `outside` — порушення K107 (`fail`, критерій `outside`); ребра з файлів `outside` keylang не бачить, тож код поза архітектурою може імпортувати архітектуру. `outside` переважає шари й `exclude`: файл, що збігає і те, і те, — поза архітектурою; вбудований список (тести, файли оголошень) переважає `outside`, а `assume` — і `outside`, і `exclude`. `package.json` і `Cargo.toml` у теці `outside` пакетів не оголошують, як і в `exclude` (ADR 0010). Рішення й компроміс — ADR 0011. Файл, який називає `assume` у `keylang.json` (масив глобів поруч з `exclude` і `outside`), — код, який архітектура імпортує, але keylang не читає й не вимагає: згенерований код, конфігурація поза git. Він не індексується, навіть коли є на диску, і модулем не стає. Імпорт, що резолвиться в такий файл або, коли файла немає, назвав би його (відносний шлях, `paths`, `baseUrl` чи `#imports` з тими самими кандидатами розширень, що й резолвер; перевага — шляху з розширенням мови), не є ні ребром, ні прогалиною: у `coverage` він має запис `assumed-import` з позицією, `text` і причиною (``assumed import `../config` → `src/config.ts` (`assume` in keylang.json)``), а правила, `check --explain-edge` і рядок `not resolved` у `keylang explain` його прогалиною не вважають; попередження `unresolved import` і внеску в `stats.importsUnresolved` він не дає. Тож gitignored `src/config.ts` дає ті самі вердикти в CI, де файла немає, і локально, де він є. Чим `assume` відрізняється від сусідів: `exclude` робить файл непрозорим модулем і прогалиною рівня залежностей (`unverified`, а модуль в `unassigned` ще й порушує baseline), `outside` — модулем шару `outside`, залежність архітектури від якого — K107; `assume` не дає ні модуля, ні прогалини, ні порушення. Без `assume` відсутній файл — прогалина `unresolved import`. Для Python, Rust і PHP файл знаходиться, лише коли резолвер мови на нього вказує (файл є на диску). Імена такого імпорту прив'язані, як імена пакета: виклик через них — зовнішній (`stats.callsExternal`), а не дірка поведінки (`dynamic-call`), так само метод класу, база якого звідти, і ім'я з glob-імпорту такого файла; вузла й ребра він не дає, а реекспорт такого імені не має `from`. Маніфести в теках `assume` пакетів не оголошують. `init` і `draft map` поле не пишуть. Без `keylang.json` (вгадана розкладка) файл поза вгаданими шарами лишається поза графом; посилання на його члена — `unverified`, не K001. Тека джерел без дозволу на читання не зупиняє аналіз: `map` і `check` друкують попередження, а в `coverage` з'являється `skipped-file` з файлом-текою і `source` — ID області, яку мали б її файли. Правила над цією областю, вище чи нижче неї (`layers`, `deny`, `no-cycles`, `entry`), тоді `unverified`, не `ok`. Нечитабельний корінь репозиторію — помилка вводу-виводу з кодом 2. Нерозв'язаний імпорт і виклик локального значення є і в `coverage`, і ребром з `resolution: "unresolved"`. Імпорти резолвляться через `tsconfig.json` (або `jsconfig.json`), ланцюжок відносних `extends` і — для solution-конфігу з `references`, як у шаблоні Vite, — `paths` конфігів, на які він посилається; а також `package.json#imports` найближчого `package.json` над файлом (як Node визначає область пакета). Голий специфікатор, як у `tsc`, іде спершу через `paths` — лише найспецифічніший шаблон (точний ключ, інакше найдовший префікс до `*`, незалежно від порядку в JSON), — потім `baseUrl`, і лише тоді він вбудований модуль Node чи пакет: аліас на ім'я вбудованого модуля (`constants`, `events`, `util`) — файл проєкту. Успадковані `paths` резолвляться від `baseUrl` підсумкових опцій (дочірній `baseUrl` переносить і їх), інакше від теки конфігу, що їх оголосив. `./x.js` знаходить `x.ts`, `x.tsx` чи `x.jsx`, а `./x.jsx` — `x.tsx`. Файли аналізу, зокрема незбережені чи запропоновані й ще не записані на диск, для резолвера існують, тож той самий знімок резолвиться однаково до й після запису кандидата. Кожен файл конфігурації читається один раз, і `snapshotId` рахується з того самого тексту, який розібрано; джерела так само: хеш у `manifest`, ключ кешу й факти — з одного читання, а файл, видалений між переліком і читанням, у знімок не входить. Імпорт, що резолвиться у файл коду, якого немає серед модулів (мова, якої немає в `languages`, файл у теці збірки, файл, що з'явився після переліку джерел), — прогалина `unresolved import` з причиною, а не мовчазна відсутність ребра; тести, файли оголошень, `exclude`, файли поза вгаданими шарами й не-код (JSON, CSS) залишаються поза графом мовчки. Голий специфікатор — зовнішній пакет лише тоді, коли його оголошено в `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies` або встановлено в `node_modules` на рівні кореня чи вище, або — як шукає Node — оголошено в `package.json` чи встановлено в `node_modules` теки між файлом і коренем (`web/package.json` монорепозиторію діє лише на файли під `web/`); інакше це нерозв'язаний імпорт (аліас, якого keylang не знає), а не пакет. Пакет робочого простору внутрішній: запис `node_modules/<pkg>`, що після розкриття посилань веде в репозиторій (не в чийсь `node_modules`), або — без встановлення — тека з `workspaces` кореневого `package.json` із таким `name`. Файл дає його `package.json`: `exports` (рядок, підшляхи `./util`, шаблони `./*`, умови), інакше `module`, `main`, `index`; файл оголошень (`.d.ts`) — не джерело. Без такого файла імпорт нерозв'язаний, а файл, який keylang не індексує (`dist/index.js`), — прогалина `unresolved import`, не мовчазна відсутність ребра. `snapshotId` враховує вміст цих файлів конфігурації (зокрема `package.json` пакетів робочого простору, вкладені `package.json` на шляху голого імпорту й перелік тек `workspaces`) і для кожного голого пакета — чи є він у `node_modules` і куди веде, бо від них залежать ребра: після `npm install` знімок інший. Імпорт — також TypeScript `import y = require("./y")` (прив'язка всього модуля) і `import.meta.resolve("./w.ts")`; `require` параметра чи іншого локального значення — не імпорт, а виклик через локальне значення (`require`, створений `createRequire(…)`, — імпорт). Імпорт і `export { … } from` одного модуля — одна залежність із двома ребрами (`import` і `reexport`). ID зовнішнього модуля — ім'я пакета без `@`, з `/` → `-`; якщо два пакети дають один сегмент (`@scope/pkg` і `scope-pkg`), сегмент лишається пакету з точно таким ім'ям, а інші отримують `-2`, `-3`… за абеткою, з попередженням. Два файли з одним ID модуля й одним шляхом без розширення (`x.ts` і `x/index.ts`, файли однієї теки в `module: "dir"`) — один модуль; два різні шляхи, що санітизуються в один ID (`foo.bar.ts` і `foo_bar.ts`), — колізія (дужки в сегменті кодуються оборотно, [grammar.md](grammar.md) §4, тож `(shop)` і `[shop]` не зливаються): попередження, прогалина `unsupported` «module ID collision» і модуль `members: "opaque"`, доки один файл не перейменують. Коли файли потрапили в шар через різні глоби (`"core": ["app/core/**", "app/db/**"]` дає `core.__init__` з обох `__init__.py`, які не перейменуєш), повідомлення додає `or split layer \`core\` so \`app/core/**\` and \`app/db/**\` are separate layers`. У модулі-теці (`module: "dir"`) fn, типи, імпорти й виклики мають файл, де їх написано, а не перший файл модуля; файл модуля — його `index.*` (`mod.rs`, `__init__.py`), якщо він є, інакше перший за абеткою; тека з назвою `index` — окремий модуль, а синтетичний вузол теки має шлях своєї теки. У модулі з кількох файлів (модуль-тека, `x.ts` поруч з `x/index.ts`) кожен файл — окрема область видимості, як у самій мові: ім'я, яке оголошує інший файл модуля, файл бачить лише через імпорт, а без нього це виклик невідомого імені, не ребро. Імпорт іншого файла того самого модуля залежністю не є, але імена прив'язує. Те саме ім'я, оголошене у двох файлах модуля, — два вузли, а не один зі змішаними тілами: сегмент без суфікса лишається експортованому оголошенню, а серед рівних — першому файлу за шляхом; інші отримують `-2`, `-3`… (`app.a.helper-2`, `name` — `helper`); попередження буває, коли ім'я експортують два файли модуля, а однойменні приватні помічники файлів видно лише з ID. Перевантаження зливаються лише в межах одного файла. Імпорт файла такого модуля резолвиться за експортами саме цього файла, тож два файли теки з `export default` чи однойменним експортом не плутаються; таблиця `exports` знімка лишається одна на модуль. Виклик резолвиться з урахуванням областей видимості між місцем виклику й модулем: параметри (зокрема деструктуровані), `const`/`let`/`var` у будь-якому охопному блоці (тіло `switch` — один блок для всіх його `case`), деструктуризація, вкладені функції й класи, змінні `for…of` і `catch`. Якщо таке ім'я затіняє імпорт чи оголошення модуля, це `unresolved-call` з причиною `shadowed by parameter|local`; інакше — `dynamic-call` «call through a local value». Жодне з них не стає підтвердженим ребром. Імпортоване ім'я резолвиться за таблицею публічних імен модуля-джерела (та сама таблиця — `exports` знімка): `import go from` — його `export default` (зокрема `export default function step`, `export default x`, `export = x`, `module.exports = x`), і `go.m()` — статичний член цього експорту (`export default class A { static m() }` → `A.m`), а не іменований експорт `m`; лише модуль без `export default` (CommonJS) дає за default-імпортом `module.exports` з його іменами. `import * as ns` і `require()` — простір імен: `ns.m()` — іменований експорт `m`. Проте `ns` з `import * as ns` (як і `export * as ns`, `await import()`) — об'єкт простору імен ESM: не функція і не default-експорт. `ns()` — `unresolved-call` «call of the namespace object», а не ребро до `default`; `ns` як значення (`keep(ns)`) віддає кожен експорт модуля, тож кожна його fn (клас — конструктором) має `escapes` «`ns` is read as a value». `require()` і `import x = require()` дають `module.exports` модуля CommonJS: `x()` — його `default`, `x.m()` — іменований експорт або статичний член `default`, `keep(x)` — escape `default`. Звернення до члена (`ns.f()`, `new ns.X()`, `x.m`) читає член, а не саме `ns` чи `x`; `.call`, `.apply` і `.bind` читають саму функцію. `export { a as b }` — оголошення `a`, `export { x } from` / `export { x as y } from` і ім'я, імпортоване та експортоване знову, — ланцюжком до оголошення, `export * from` — іменами без `default`, `export * as ns from` — простором імен (`ns.f()`, тип `ns.T`, як і `NS.T` при `import * as NS`); ім'я без рядка експорту (CommonJS, неекспортований помічник) — оголошення з цим ім'ям. Кожен виклик у коді — ребро або прогалина: `new ns.X()` — виклик класу `X` модуля `ns`, `new X().m()` — член `m` класу `X`, `super()` — конструктор базового класу (через бази без власного конструктора), `super.m()` — член бази; виклик виразу, який keylang не називає (`f()()`, `(a || b)()`), — `dynamic-call` «call through an expression». Виклик тієї самої цілі кілька разів дає одне ребро, найсильніше: прямий виклик поглинає виклик у closure та ребро хука `default`. `interface Foo` і `class Foo` (злиття оголошень TypeScript) — один вузол-клас, хоч би що стояло першим; згадки типів інтерфейсу належать класу. Функцією модуля є й значення `(() => …) as T`, `(function () {}) satisfies T`, а в CommonJS — `exports.x = function () {}`, `module.exports.x = () => …`, функції й методи в `module.exports = { … }` та `module.exports = function () {}` (fn `default`). `const Cart = memo(() => …)`, `forwardRef((props, ref) => …)`, `lazy(() => import(…))` і `React.memo(…)` — fn обгорнутої функції з її викликами, лише коли обгортку імпортовано значенням із `react` (впізнається за імпортом, не за текстом). `react/jsx-runtime` цих імен не експортує, тож імпорт звідти обгортку не відкриває. Не розгортаються аргумент-ідентифікатор (`memo(CartImpl)`), вкладене `memo(forwardRef(…))` і `require("react")`. Значенням лишаються також `import type` і `import { type memo }`, `forwardRef` з `@nestjs/common`, локальна `memo`, `styled(…)` і `let`/`var`. Виклики поза тілами оголошень (верхній рівень модуля, методи об'єктних літералів, функція-значення, обгорнута викликом) жодній fn не належать і є `escapes` того, що вони викликають ([semantics.md](semantics.md) §7). Члени класу: метод і поле з функцією (`handler = () => later()`, `readonly generate = (…) => {…}`) — fn з власними викликами; getter і setter — fn з `escapes`. Ініціалізатори полів екземпляра (`private decoder = new InputDecoder()`) виконуються під час конструювання: їхні виклики належать `constructor`, а якщо його немає в коді — синтезованому `Class.constructor` без сигнатури з діапазоном від першого до останнього такого поля (лише коли ініціалізатори щось викликають). Ініціалізатори статичних полів і блоки `static {}` виконуються один раз під час обчислення класу: їхні виклики належать синтезованому `Class.static`, а не конструктору (якщо в класі вже є член `static`, це `unsupported`). Член з обчислюваним ключем (`[key]() {}`, `[key] = …`) — `unsupported construct` «computed class member»: його виклики — код поза оголошеннями. Сегмент ID члена — його ім'я без `#`; якщо ім'я вже має інший член класу, статичний член отримує суфікс `-static`, приватний `#name` — `-private`, статичний приватний — `-static-private` (жодне JS-ім'я не містить `-`, тож суфікс не збігається з іншим членом). Пріоритет — член екземпляра, статичний, `#`-приватний, статичний `#`-приватний: `static m()` поруч з `m()` — `X.m-static`, `#go()` поруч з `go()` — `Y.go-private`; без збігу ID лишається `X.work` для `#work`. Тож поява одноіменного члена з вищим пріоритетом перейменовує ID нижчого. `this.#work()` — виклик приватного члена, `this.m()` у статичному методі й `X.m()` — статичного, `w.m()` через екземпляр — члена екземпляра. Член шукається, як його шукає мова: у самому класі, потім у базах, які keylang прочитав, як для `super.m()`; тож `this.greet()` з `greet` бази — ребро до неї, а `X.m()` знаходить і статичний член бази. Коли ланцюжок баз закінчується класом пакета чи мови (`extends Component` з `react`), не знайдений `this.m()` — зовнішній виклик, як `super.setState()`; коли невідомою базою — `unresolved-call`. `this` означає клас, лише коли найближча охопна не-стрілкова функція — член класу (або це ініціалізатор поля чи `static {}`); `this.m()` у методі об'єктного літерала чи вкладеній `function` — `dynamic-call` «call through `this` of a function value». `new X()` у static-доказі — виклик `X.constructor`. Виклик методу через поле чи локальне значення відомого класу розв'язується: поле з анотацією `: X` чи ініціалізатором `new X()`, параметр-властивість `constructor(private readonly x: X)`, присвоєння `this.x = new X()` або `this.x = p` з `p: X` у конструкторі; `const w = new X()`, `const w: X`, параметр `w: X` — якщо ближча прив'язка того самого імені (змінна `for…of`, `catch`, вкладена функція) його не затіняє і саме `X` між оголошенням і модулем не перепризначено (`const X = Ctor`). `this.x.m()` і `w.m()` тоді — ребро до `X.m`, якщо `X` — клас цього файла чи імпортований і має член `m`; для глобального класу (`Map`, `Set`…) чи класу з пакета — зовнішній виклик; інакше (інтерфейс, generic-анотація, невідомий тип) лишається діркою. Ребро `type` — це згадка типу в сигнатурі, тілі типу, полі класу, heritage чи обмеженні параметра типу; правила `allow` / `deny` / `layers` бачать його разом із `import`, `call` і `reexport`. Ребро `type` від модуля до модуля — також залежність лише від типів, яку компілятор стирає з коду, що виконується: `import type …`, `export type { … } from`, `export type * from` (див. **TypeScript** нижче). Його бачать `allow`, `deny`, `layers` і `entry`, а `no-cycles` — ні; у `deps` модуля й рядком залежності карти воно не з'являється.

### Мови

`languages` у `keylang.json` — підмножина `javascript`, `php`, `python`, `rust`, `typescript`; інша назва — помилка конфігурації з кодом 2. Без поля мови визначаються за розширеннями файлів (`.php` — PHP). Без `module` береться гранулярність мов, якщо вона однакова, інакше `file`. Файл-індекс, що стоїть за модуль своєї теки: `index.*` для JS/TS, `mod.rs` для Rust, `__init__.py` для Python; у PHP його немає, бо `index.php` — скрипт входу. Шар членів не має, тож файл-індекс прямо під коренем шару зберігає своє ім'я: `<шар>.index`, `<шар>.mod`, `<шар>.__init__`. За замовчуванням не індексуються також `test_*.py`, `*_test.py`, `conftest.py`, класи тестів PHPUnit `*Test.php`, теки `venv`, `site-packages`, `vendor` і PHP, який фреймворки компілюють у свої кеші: `bootstrap/cache/`, `storage/framework/` (Laravel) і `var/cache/` (Symfony). Граф, знімок і перевірки для всіх мов спільні. Файл, якого немає серед проаналізованих (ще не збережений буфер, файл поза шарами), резолвер кожної мови бере з диска лише в точному написанні — кожен сегмент шляху є в переліку своєї теки (`readdir`), імена порівнюються в NFC: на APFS і NTFS `existsSync` знаходить `models/User.rs` через `user.rs`, keylang — ні, тож `use crate::models::User` і `from app.models import User` на macOS і Windows дають `models/mod.rs` і `models/__init__.py`, як на Linux, а не неіндексований `User.rs`/`User.py`; `./models/User` у TS з `user.ts` — нерозв'язаний імпорт, як у tsc. Кожна мова має frontend: екстрактор фактів файлу, резолвер імпортів і перелік глобальних імен мови, виклики через які зовнішні. Мова також каже, що запускає виклик класу (`constructor` у JS/TS, `__init__` у Python; у Rust виклику типу немає), і які члени класу вона викликає без виразу виклику з їхнім ім'ям: JS `then`, `next`, `toString`…; Python — dunder-методи, крім `__init__` (`__enter__`, `__iter__`, `__str__`, `__call__`…); Rust — методи `impl` тих трейтів `std`, які викликають оператори, `for`, `?`, форматування, кінець області й auto-deref (`impl Drop`, `impl fmt::Display`, `impl Add`, `impl Iterator`, `impl From<T>`…); власний метод `add` без трейту викликається лише за ім'ям. Такий член має `escapes` «is called implicitly». Кожен вираз виклику — ребро або дірка: виклик, отримувача чи callee якого keylang не може назвати (`self.db.save()`, `Order::new().total()`, `x[0].m()`, `super().m()`, `f()()`, `(self.handler)()`), — `dynamic-call` «call through a local value» з текстом виклику, тож `closure.complete` — `false`, а крок за ним — `unverified`, не `fail`. У `.tsx`, `.jsx` і `.js` тег JSX, що називає компонент, — виклик від функції, у чиєму тілі він стоїть, як `Cart()`: `<Cart />` і `<Cart></Cart>` — виклик `Cart` (закриваючий тег — не другий), `<Cart.Item />` — `Cart.Item`, `<Cart<Props> />` цілить у `Cart`; тег у колбеку (`items.map(() => <Cart />)`) має `closure`, тег через параметр чи локальне значення — дірка, як виклик параметра. Тег з малої літери (`<div />`, `<my-button />`), простір імен (`<svg:path />`) і фрагмент (`<>`) — не виклики, навіть якщо fn `div` існує. У `.ts` JSX немає: `<Foo>x` — type assertion, а літеральний тег — синтаксична помилка й `opaque`-файл, не ребро. Виклик `createElement(Cart)`, `jsx(Cart)`, `jsxs(Cart.Item)` і `jsxDEV(Cart)` — той самий виклик компонента (ребро `call`, без нового виду), коли callee імпортовано значенням з `react`, `react/jsx-runtime` або `react/jsx-dev-runtime` (впізнається за імпортом, не за текстом: `createElement as h`, `React.createElement`): перший аргумент — identifier з великої літери або member. Рядок (`"div"`) і identifier з малої літери — не виклик, навіть якщо fn `div` існує. Локальна функція з тим самим ім'ям, імпорт з іншого модуля і type-only імпорт (`import type React`, `import type * as React`, `import { type createElement }`) лишаються звичайним викликом зі своїми `passes` — те саме правило, що й для обгорток. Функція, прочитана як значення (`later(hit)`, `Handler { run: go }`, `.map(Order::total)`, `callback=self.save`, `{"save": save}`), має `escapes` «is read as a value».

**TypeScript.** Те саме — для JavaScript. Загальні правила резолвінгу TS/JS — в абзаці під таблицею вище; тут політики, про які найчастіше питають. Декоратор (`@Injectable()`, `@Get("/") handler()`) діркою не є: keylang вважає, що виклик декорованого класу чи методу виконує його тіло, бо декоратор фреймворку реєструє його, а не підміняє, — на відміну від декоратора Python поза списком відомих (`unsupported` «decorator may replace»). Виклики в аргументах декоратора виконуються під час обчислення класу, тобто це код модуля: те, що вони викликають, має `escapes` «is called from module-level code». Сам декоратор методу `escapes` не додає: виклик методу фреймворком за зареєстрованим іменем keylang не бачить. `import type …`, `export type { … } from` і `export type * from` компілятор стирає з коду, що виконується, тож ребро `import` чи `reexport` такої інструкції має `typeOnly: true`: `no-cycles` його не бачить, як і static-доказ кроку на `external.<pkg>` ([semantics.md](semantics.md) §7), а `allow`, `deny`, `layers`, `entry`, `deps` модуля, рядок залежності карти й `explain` бачать його як звичайний імпорт; імена такий імпорт прив'язує як звичайний. Залежність від модуля, який файл імпортує і type-only, і звичайним імпортом, — звичайна, з позицією звичайного імпорту. Інструкцію, у якій кожне ім'я в дужках має inline `type` (`import { type A, type B as C } from`, так само `export { type A } from`), а поруч немає default, простору імен чи значення, tsc і esbuild стирають повністю, якщо tsconfig, що керує файлом, не задає `compilerOptions.verbatimModuleSyntax: true`: тоді її ребро теж `typeOnly`. З `verbatimModuleSyntax` вона лишається `import {} from` і завантажує модуль — звичайний `import`, як і змішаний `import { type A, B }`, `import D, { type A }` чи порожній `import {} from` (до 2026-10-06 звичайним був кожен такий імпорт). Файлом керує найближчий `tsconfig.json` (інакше `jsconfig.json`) від його теки до кореня — разом із ланцюжком `extends` (відносний шлях або конфіг пакета в `node_modules` під коренем: `<пакет>/<шлях>.json`, файл з поля `tsconfig` його `package.json`, його `tsconfig.json`; пізніший запис масиву `extends`, що задає опцію, переважає раніший) і з конфігами з його `references` (solution-конфіг на кшталт Vite з `"files": []` віддає файли їм): опцію задано, якщо її задає будь-який із них. Конфіг, який keylang не може дочитати (немає файла, не JSON-об'єкт, пакет не встановлено, `extends` глибше п'яти рівнів), вважається таким, що опцію задає: імпорт лишається звичайним. Без жодного конфіга діє типове значення tsc — не задано. Прочитані конфіги входять у `snapshotId`, а факт про інструкцію лишається синтаксичним, тож зміна tsconfig змінює ребро без очищення кешу фактів. Node під type stripping лишає `import {} from` незалежно від tsconfig: проєкту, який Node запускає без збирання, варто задати `verbatimModuleSyntax` (так радить і документація Node), інакше keylang вважатиме імпорт стертим, хоча Node його виконає. `export type * from` і `export type * as NS from` (TypeScript 5.0) граматика `@vscode/tree-sitter-wasm` 0.3.1 (остання версія) не знає; keylang замінює це `type` пробілами тієї ж довжини й розбирає файл знову, тож позиції точні, файл не `opaque`, а реекспорт — type-only, з текстом інструкції як її написано. `import * as ns` (так само `export * as ns`, `await import()`) — об'єкт простору імен ESM, а не default-експорт: `ns.f()` — експорт `f`, `ns()` — `unresolved-call`, `keep(ns)` — `escapes` кожного експорту модуля; `require()` і `import x = require()` дають `module.exports`, тож `x()` — його `default`. Тіло `switch` — один блок: `const` чи `function` з одного `case` затіняє ім'я модуля в усіх його `case`. `this.m()` шукає член у класі, потім у прочитаних базах, як `super.m()`: метод бази — ребро; не знайдений член класу над базою пакета чи мови (`extends Component` з `react`) — зовнішній виклик, над невідомою базою — `unresolved-call`; `X.m()` знаходить і статичний член бази. У модулі з кількох файлів кожен файл — окрема область видимості (див. абзац під таблицею). Ім'я, яке generic зв'язує у своїй області, — параметр типу (`function f<T>(x: T)`, `class C<T> { m(x: T) }`), ключ mapped type (`[K in keyof T]`), `infer U`, — не посилання на тип і ребра `type` не дає. Обмеження й типове значення параметра типу класу (`class C<T extends Order, U = Item>`) — посилання класу, як і його heritage. Сигнатура методу в інтерфейсі чи об'єктному типі (`interface Repo { save(o: Order): void }`, `x: { load(): Order }`) — частина цього типу, тож її типи — посилання декларації, що його пише; сигнатура перевантаження в тілі класу належить своєму методу. Поле класу, що не тримає функцію, вузлом не є: типи його анотації й ініціалізатора (`repo!: Order`, `private readonly r: Repo`, `s = new Map<string, Item>()`) та індексної сигнатури (`[key: string]: Item`) — посилання класу; поле з функцією (`h = (o: Order) => …`) — fn зі своїми посиланнями.

**Rust.** Модуль — файл, як і в самому Rust: `src/domain/order.rs` — це `crate::domain::order` і ID `domain.order`, а `src/domain/mod.rs` — модуль теки. Члени: `fn`, `struct`/`enum`/`union` (як класи; їхні члени — функції з `impl` того самого файла, асоційована функція без `self` статична; `self: Box<Self>` — теж `self`), `trait` і `type` (як типи). Експорт — будь-яка видимість `pub…`, `pub use` — реекспорт: рядок таблиці експортів з `form: reexport`, символом, на який вказує шлях, і `from` — модулем, звідки він. Не індексуються тестовий код: елементи під `#[cfg(test)]` або `cfg`, що вимагає `test` (`cfg(all(test, unix))`), функції з `#[test]` (`#[tokio::test]`…) і файл із `#![cfg(test)]`; коментар між атрибутом і елементом цього не змінює. Кожен лист дерева `use` (`a::{b, c::d as e, f::*}`) — окремий імпорт, зокрема `use` у тілі функції. Ім'я з glob-імпорту `use m::*`, якого файл сам не оголошує й не імпортує явно, резолвиться за публічними іменами `m` (його таблицею `exports`), зокрема `Order::new()`; ім'я, яке мають два glob-и, — `ambiguous`. Glob крейту (`std`, залежність) робить такий виклик зовнішнім, а glob, чиїх імен keylang не знає (нерозв'язаний шлях, `use Kind::*` варіантів enum), — `dynamic-call` «a name from a glob import keylang does not follow». Fn з glob-імпорту, прочитана як значення, має `escapes`. Крейт — тека з `Cargo.toml` і `[package]`. Кожна ціль крейту — окреме дерево модулів із коренем у своєму файлі: бібліотека — `src/lib.rs` або `[lib] path` (сам файл, `a/b.rs` шукаються поруч із ним), бінарники — `src/main.rs`, `src/bin/*.rs`, `src/bin/*/main.rs` і `[[bin]] path`. `crate::` резолвиться від кореня цілі, до якої належить файл: у `main.rs` `crate::helper()` — його власна `helper`, а не бібліотеки. Файл під спільною текою бібліотеки й бінарника належить бінарнику, коли лише корінь бінарника оголошує його модуль верхнього рівня (`mod cli;`), інакше бібліотеці. `crate::`, `self::`, `super::` і шлях від дочірнього модуля (edition 2018) резолвляться у файл `a/b.rs` або `a/b/mod.rs`. Найдовший префікс шляху, що є модулем, дає файл; файл поза аналізом береться з диска лише в точному написанні (абзац «Мови»), тож `crate::models::User` при `models/user.rs` — це `models/mod.rs` на будь-якій ФС. Якщо модулем є весь шлях, імпорт прив'язує сам модуль, інакше останній сегмент є іменем члена. Шлях у власний файл (`crate::run()` у файлі, де `run` оголошено, `self::run()`) — ребро до його члена. Шлях, що після файла йде далі в модуль без власного файла, не прив'язує члена: у вбудований `mod inner { … }` цього файла — залежність від файла без ребра виклику (`dynamic-call`), у модуль із `#[path]` чи будь-який інший — нерозв'язаний імпорт. Ім'я члена `[workspace] members` (чи пакета з бінарника) означає бібліотеку цього крейту, ключ `[dependencies]`/`[dev-dependencies]`/`[build-dependencies]` — зовнішній пакет, `std`/`core`/`alloc` — зовнішні. Будь-яке інше ім'я дає нерозв'язаний імпорт. `mod x;` оголошує файл, але ребром не є: залежність — те, що код використовує. Шлях у виклику чи значенні, що починається з `crate`, `super`, `self` або з невідомого імені з малої літери (`tokio::spawn()`), є власним імпортом; шлях через прив'язку `use` довший за два сегменти (`order::Order::new()` при `use crate::domain::order`) — теж, від шляху цього `use`. Сегмент шляху в `CamelCase` після модулів — тип: `super::i18n::Message::raw()` — це член `Message.raw`. Виклик, чий останній сегмент у `CamelCase` (`Some(x)`, `Event::Progress(p)`), за конвенцією іменування є конструктором варіанта чи tuple-struct і викликом не є. Шлях від примітиву (`u64::from`) — зовнішній. `Self::f()` у `impl` — це член типу, `self.m()` — член `impl`. Виклик методу через значення (`order.total()`) — `dynamic-call`. Ім'я, яке fn прив'язує — параметр, `let`, змінна `for`, шаблон `if let` / `while let` і гілки `match` (без guard `if …`), параметр closure, — затіняє item модуля з тим самим ім'ям у всій fn: виклик через нього — `unresolved-call` «shadowed by local|parameter», а не ребро. Виклики у вкладеній `fn`, як і в closure, мають `closure: true`. Виклики в коді, який keylang не індексує як fn — ініціалізатор `const`/`static`, типові методи `trait`, вбудований `mod`, `impl` типу з іншого файла, — код поза оголошеннями: те, що вони викликають, має `escapes`. Невідомий макрос цього крейту (`audit!()`, `crate::m!()`) — `unsupported` «macro is not expanded». Макроси `std`, поширеного логування й макроси зі шляхом у чужий крейт (`serde_json::json!`) діркою не є. Файл поза всіма цілями (`build.rs`) — окремий корінь: `crate::` у ньому не резолвиться в `src/`. Вбудований `mod x { … }`, `impl` для типу з іншого файла і макрос на верхньому рівні — `unsupported`; шляхи всередині вбудованого модуля починаються від нього й імпортами файла не є. Атрибут-макрос на fn поза атрибутами мови й тими, що зберігають тіло (`#[tokio::main]`, `#[tracing::instrument]`, `#[async_trait]`), — `unsupported` «attribute may replace» із текстом `#[…]` і `source` — ID fn, а сама fn — `escapes` «is read as a value»: як і Python-декоратор, це дірка поведінки цієї fn, а не залежностей модуля. Rust-frontend дає ребра `import`, `call`, `reexport`; ребер `type` ще немає. `snapshotId` враховує вміст прочитаних `Cargo.toml`.

**Python.** Модуль — файл, пакет — `__init__.py` теки. Члени: `def` (зокрема `async`) і `class` (їхні методи й вкладені класи з їхніми членами; `@staticmethod` і `@classmethod` статичні, `@property`, `@cached_property` і `@x.setter` — accessor з `escapes`). Верхній рівень охоплює й тіла `if`/`try` модуля. Публічні імена — список літерала `__all__` (зокрема розширеного `+=`, `+`, `.extend([...])`, `.append("x")`), а без нього — імена без початкового `_`. Методи з `_` приватні, dunder-методи (`__init__`) публічні. Кожне імпортоване ім'я — окремий імпорт з крапковим шляхом, зокрема імпорт у тілі функції чи класу. `from ..pkg.mod import f` починається від пакета файла: одна крапка на рівень. `import a.b` прив'язує `a` і шлях `a.b`: `a.b.f()` — виклик `f` модуля `a.b`. Модуль, який прив'язує імпорт (`import m`, `import a.b as m`, `from pkg import m`), — об'єкт модуля, а не функція: `m.f()` — виклик `f`, `m()` — `unresolved-call` «call of the module object `m`, which is no function», а не виклик чогось у модулі (навіть fn `default`), і `keep(m)` дає `escapes` кожній функції модуля, як простір імен ESM. Абсолютний шлях шукається в корені репозиторію, потім у `src/`. Найдовший префікс, що є модулем (`p.py` або `p/__init__.py`), дає файл (файл поза аналізом — лише в точному написанні на диску, абзац «Мови»: `app.models.User` при `models/user.py` — це `models/__init__.py` на будь-якій ФС), але не коротший за модуль, який називає інструкція: `from .missing import f` і `from .missing import *` модуля, якого немає, — прогалина `unresolved import` (``unresolved import `.missing.f` ``, ``unresolved import `.missing.*` ``), а не ім'я пакета над ним. `from pkg import mod`, де `mod` — модуль, прив'язує сам модуль. `from m import *` прив'язує публічні імена `m` (його таблицю `exports`: `__all__` або імена без `_`): ім'я, якого файл не оголошує й не імпортує явно, — виклик чи база класу з `m`; ім'я, яке мають два таких джерела, — `ambiguous`. Glob модуля стандартної бібліотеки чи пакета робить такий виклик зовнішнім, а glob, чиїх імен keylang не знає, — `dynamic-call` «a name from a glob import keylang does not follow». Ім'я верхнього рівня, якого немає в жодному корені, — модуль стандартної бібліотеки, якщо його називає `sys.stdlib_module_names` (перелік CPython 3.10–3.14 зафіксовано в `src/python-stdlib.ts`; інтерпретатор keylang не запускає), інакше зовнішній пакет, бо path-аліасів у Python немає. Модуль стандартної бібліотеки — не `external.*`: ні вузла, ні ребра, ні K102, а виклик через нього рахується зовнішнім, як виклик у пакет. Модуль репозиторію з тим самим іменем має пріоритет. Реекспорт — імпорт верхнього рівня з ім'ям із `__all__`, а в `__init__.py` без `__all__` — будь-яке публічне імпортоване ім'я і `from .x import *`: ребро `reexport` і рядок таблиці експортів з `form: reexport`, символом і `from`. Тож `from shop.domain import place` при `from .order import place` у `shop/domain/__init__.py` — виклик `shop.domain.order.place`. `X()` — виклик класу, тобто його `__init__`. `self.m()` — член класу, для `@staticmethod`/`@classmethod` — статичний член; перший параметр `@staticmethod` отримувачем не є. Член, якого клас не оголошує, шукається в першій базі й далі її ланцюжком, як у TypeScript; через екземпляр (`self.m()`, `s.m()` з відомим класом `s`) знаходиться й `@staticmethod` чи `@classmethod`. `self.attr.m()` і `x.m()` через змінну — `dynamic-call`. Ім'я, яке `def` прив'язує — параметр, присвоєння, змінна `for` і comprehension, `with … as`, `except … as`, `:=`, захоплення `case` (`case (x,)`, `case {"k": x}`, `case [*x]`, `case P(k=x)`, `case str() as x`), вкладені `def` і `class`, параметри вкладених функцій і `lambda`, — затіняє ім'я модуля в усій функції: виклик через нього — `unresolved-call` «shadowed by local|parameter», а не ребро. Значення в шаблоні (`case Color.RED`) і клас (`case P()`) нічого не прив'язують. Код тіла класу поза методами і декоратори виконуються під час завантаження модуля: те, що вони викликають, має `escapes`. Декоратор поза списком тих, що зберігають функцію (`staticmethod`, `classmethod`, `property`, `dataclass`, `functools.wraps`, `lru_cache`, `total_ordering`…), — `unsupported` «decorator may replace» із `source` — ID декорованої fn чи класу, а сама fn — `escapes` «is read as a value» (декоратор тримає її як значення, як фреймворк — зареєстрований обробник). Це дірка поведінки цієї декларації, а не залежностей модуля: `deny` її не враховує. Так само `getattr` у тілі функції (`source` — її ID). `importlib.import_module`, `__import__`, `exec`, `eval` і `getattr` поза функцією — `unsupported` рівня залежностей. Python-frontend дає ребра `import`, `call` і `reexport`; ребер `type` ще немає.

**PHP.** Модуль — файл, як і в TypeScript: `src/Domain/Order.php` при шарі `Domain` = `src/Domain/**` — це модуль `Domain.Order`, клас `Order` у ньому — `Domain.Order.Order`, його метод — `Domain.Order.Order.place`. Сегменти зберігають регістр. Члени: `class`, `trait` і `enum` (як класи; члени — методи, `static` — статичний метод, `private` і `protected` — непублічні, абстрактний метод — член без тіла, як у TypeScript), `interface` (як тип: виклик через значення з типом-інтерфейсом — дірка, як у TypeScript) і функції. Верхній рівень охоплює й тіла `if` (`if (!function_exists('x')) { function x() {} }`). Експортується кожне оголошення верхнього рівня. PHP називає клас чи функцію повним іменем, а не файлом, тож імпорт резолвиться за оголошеннями проаналізованих файлів: `use App\Domain\Order` — це клас `Order` простору імен `App\Domain`, хоч би який файл його оголошував, як у class map composer; `autoload` для цього не читається. Ім'я, яке код пише без `use`, — теж імпорт за правилами PHP: клас свого простору імен (`Pricing::total()` у `App\Domain` — це `App\Domain\Pricing`), ім'я через псевдонім (`use App\Core;` і `Core\Repo`), повне ім'я (`\App\Repo`). Такий імпорт стоїть там, де ім'я вжито вперше, і дає ребро лише тоді, коли якийсь файл оголошує це ім'я; інакше він нічого не додає. Функцію без кваліфікації PHP шукає спершу у своєму просторі імен, потім у глобальному, і keylang теж: `legacy_total()` у `App\Web` — глобальна функція з `lib/legacy.php`. Ім'я, якого не оголошує жоден файл, належить пакету composer, коли його простір імен заявляє `autoload` (`psr-4`, `psr-0`) пакета в `composer.lock`, а без lock-файла — у `vendor/composer/installed.json`: `use Monolog\Logger` — залежність від `external.monolog-monolog`. Глобальне ім'я, якого не оголошує ніхто (`strlen`, `\DateTimeImmutable`), і власні простори імен PHP (`Random\`, `Dom\`) — стандартна бібліотека: ні вузла, ні ребра, виклик через нього зовнішній. Простір імен у `use` (`use App\Core;`) — не оголошення: він нічого не прив'язує і ребра не дає. Інше нерозв'язане ім'я з `use` — нерозв'язаний імпорт. Ім'я, оголошене у двох файлах, належить першому за шляхом. Імена порівнюються без регістру латинських літер A–Z, як у PHP (з 8.2 — незалежно від локалі), — і в імпорті, і у виклику, типі, `extends` чи `use` трейту: `new ORDER()` при `class Order` — виклик `Order`, `HELPER()` при `function helper` — виклик `helper`, а ID зберігає регістр оголошення. Регістр інших літер PHP розрізняє, і keylang теж: `äpfel::make()` при `class Äpfel` — не виклик `Äpfel`. Коли файл оголошує два імені, що різняться лише регістром (`class Twin` і `function twin`), ім'я в іншому написанні (`TWIN()`) — `unresolved-call`. `require`/`include` шляху, який код записує явно (рядок, `__DIR__`, `dirname(__DIR__[, n])`, `dirname(__FILE__)` через `.`), — імпорт файла; `vendor/…` (автозавантажувач composer) ребра не дає; шлях, обчислений під час виконання, — `unsupported` «an include of a path computed at run time». Виклики: `$this->m()` — член класу; `self::m()` і `static::m()` — статичний член, якщо `m` статичний, інакше член класу; `parent::m()` і `parent::__construct()` — член базового класу; `X::m()` — статичний член `X`; `new X()` — виклик класу, тобто його `__construct`; `f()` — функція. `$x->m()` через змінну — член класу, якщо синтаксис цей клас називає: параметр з типом-класом (`Store $s`) чи змінна, єдине присвоєння якої — `new X(…)`; `$this->store->m()` — так само через властивість із типом-класом, зокрема промоутед-параметр конструктора (`private Store $store`); `(new X())->m()` і `new X()->m()` PHP 8.4 — член `X`, поруч із викликом самого `X`. Інакше це `dynamic-call`, зокрема `->n()` у `(new X())->m()->n()`: клас результату `m` синтаксис не називає. `$this->m()`, `$x->m()` з відомим класом, `(new X())->m()` і `parent::m()` шукають метод, як PHP: у класі, потім у трейтах, які він `use`, потім у базовому класі та його трейтах; статичний метод знаходиться й через екземпляр (`$this->make()`). Ім'я методу порівнюється так само, без регістру A–Z: `$o->TOTAL()` і `self::Tax()` — виклики `total()` і `tax()`, `$o->GRÖßE()` — не виклик `größe()`, а ID методу зберігає регістр оголошення; так само назва в можливому маршруті й `escapes` потоку ([semantics.md](semantics.md) §7, «Static без шляху»). Не знайдений метод класу з базою пакета — зовнішній виклик, інакше — нерозв'язаний. `$f()`, `$obj->$m()`, `new $class()`, `$class::m()` — `dynamic-call`; `call_user_func`, `call_user_func_array`, `forward_static_call` і `eval` — `unsupported` із `source` — ID fn. Метод, прочитаний як callable (`[$this, 'save']`, `[OrderController::class, 'store']` у маршруті), функція з `f(...)` і клас з `X::class` мають `escapes` «is read as a value». Конструктор, записаний у будь-якому регістрі (`__CONSTRUCT`), — член `__construct`: його ID — `<клас>.__construct`, і саме його запускає `new X()`. Магічні методи, крім `__construct` (`__toString`, `__get`, `__call`, `__invoke`, `__destruct`…), мають `escapes` «is called implicitly». Код поза оголошеннями виконується під час `include` файла: те, що він викликає, має `escapes`. Типи параметрів, результату, властивостей, `extends`/`implements`, `use` трейту, `catch` і `instanceof` — ребра `type`. PHP-frontend дає ребра `import`, `call` і `type`; реекспорту в PHP немає. `snapshotId` враховує вміст прочитаного `composer.lock` чи `installed.json`.

**Fingerprint.** У fn і типу є `fingerprint` — SHA-256 сигнатури та синтаксису оголошення: типи вузлів tree-sitter і тексти токенів без коментарів і пробілів. Заміна `>` на `>=` його змінює, зміна коментаря чи переформатування — ні. Переміщення інструкції з блоку змінює, бо вкладеність — частина хешу. Перевантаження TS об'єднуються в один fingerprint. `closure: {fingerprint, complete}` — fingerprint вузла разом з усім, що він викликає транзитивно (`new C()` — з конструктором `C`). Він рахується знизу вгору за сильно зв'язаними компонентами графа викликів, тож цикл A ↔ B дає обом один `closure` і зміна будь-кого з них змінює обидва. `complete: false`, коли вузол або щось досяжне від нього має `dynamic-call` чи `unresolved-call`, дірку самої декларації (`unsupported` з `source` — ця fn чи її клас: декоратор або атрибут-макрос, що може її підмінити) або не має fingerprint: незмінний хеш тоді не означає незмінної поведінки. Fingerprint не входить у `snapshotId` (той залежить від вмісту файлів) і не є baseline прози: baseline і `check --stale` — тікет 21.

**Документація.** Кожен вузол має `doc`: коротке пояснення з коментаря документації в коді або `null`. Зовнішній модуль завжди має `null`. Шар описує його власна тека — та, якою володіють усі його глоби (`<D>/**` чи `<D>/**/<шаблон>`; шар, заданий переліком файлів або кількома теками, теки не має): її `README.md` (ім'я в будь-якому регістрі), інакше коментар документації індекс-модуля в ній (`index`, `mod`, `__init__` — індекс-імена мови). З README береться перший абзац прози, що читається як речення: заголовки, огороджений і відступлений код, HTML, списки, цитати й таблиці пропускаються, зображення й бейджі відкидаються, від посилань і наголосу лишаються слова; абзац зараховується, коли в ньому щонайменше чотири слова й кінець речення (`.`, `!`, `?`). Тож перемикач мов чи рядок бейджів угорі README шар не описують. Із коментаря прибирається синтаксис, береться перший абзац зі стиснутими пробілами й обрізається до двох речень. Речення закінчується на `.`, `!` чи `?` перед пробілом і великою літерою або в кінці тексту, тож `e.g. this` і `a.b()` речення не розривають. Понад ~280 символів текст обрізається по слову з `…`. Правило не залежить від ICU і версії Node. **TS/JS:** декларацію (fn, клас, тип, член класу) документує найближчий `/** … */` над нею чи над обгорткою (`export`, `const x =`). Між ними можуть стояти декоратори, порожні рядки й рядкові коментарі, але не інший код. Рядковий `//` над fn — нотатка, а не документація. Із JSDoc береться опис до першого блочного тегу (`@param` і далі); `{@link x}` стає `x`, а `{@link x text}` — `text`. Модуль документує перший блок коментарів файла після `#!` (`//` чи `/* */`; коментарі на сусідніх рядках — один блок), якщо цей блок не стоїть упритул над першою інструкцією, що не є `import` чи директивою (`"use strict"`): тоді він належить їй. Коментар, що починається з ліцензії (`SPDX-…`, `Copyright …`, `(c) 2024`, `©`) або містить `SPDX-License-Identifier`, — не документація; згадка слова copyright у тексті — документація. `/// <reference>` і блок без тексту теж пропускаються. Модуль-тека бере документацію свого файла-індексу (`index.ts`, `mod.rs`, `__init__.py`). **Rust:** item документують `///` і `/** … */` над ним; атрибути й звичайні коментарі між ними дозволені. Модуль документують `//!` і `/*! … */` його файла. `#[doc = "…"]` keylang не читає, тож такий item має `doc: null`. **Python:** docstring — перший рядковий літерал тіла модуля, `class` чи `def`, очищений як в `inspect.cleandoc`. f-рядок, bytes і склеєні рядки — код, а не документація (`doc: null`). **PHP:** оголошення документує `/** … */` прямо над ним; рядкові коментарі між ними дозволені, інший код — ні. Береться опис до першого тегу, як у JSDoc. Модуль документує перший `/** … */` файла після `<?php` і `declare`, якщо він не стоїть упритул над оголошенням: тоді він належить оголошенню, а коментар модуля оголошення не документує. Коментарі не входять у `fingerprint` і `closure`: зміна лише коментаря змінює `doc`, але не їх. Канонічна карта `doc` не показує, `keylang explain <id>` друкує його рядком `doc:`.

**Репозиторій.** Поле `system` — що репозиторій каже про себе, рівень «система» C4. Це вузол представлення, а не ID мови (ADR 0014). `name` — `name` першого кореневого маніфесту, що його має: `package.json`, `Cargo.toml` (`[package]`, інакше `[workspace.package]`), `pyproject.toml` (`[project]`), `composer.json`. `brief` — перший абзац прози кореневого `README.md` за правилом шару вище, інакше `description` маніфесту в тому ж порядку, обрізаний до двох речень. `source` — файл, з якого взято `brief`; без `brief` — `null`. Маніфест, що не розбирається, тут нічого не дає: його помилку повідомляє читання пакетів. README шарів і репозиторію та маніфести перечитуються кожним аналізом, але в `snapshotId` не входять: README — не код, тож його правка не робить застарілими звіти тестів і trace знімка. `map --check` бачить таку правку через карту з поясненнями. Поле додано без зміни номера схеми: значення наявних полів не змінилося.

`provenance: semantic` і `provenance: trace` лишаються дорожньою картою, не полями поточного знімка. Схема знімка — **7** (у 7 з'явився `doc` вузла; у 6 з'явилися `class` модуля, `static` і `name` fn, `local` і форма `namespace` в `exports`).

Карта з поясненнями описана в [cli.md](cli.md#explained-map).
