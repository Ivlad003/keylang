# Повний робочий простір keylang у TUI

> Дизайн 2026-09-29, реалізований у 2026-10-01: усі рядки матриці §3 мають дію в TUI. Схеми нижче ілюструють взаємодію; точні назви, клавіші та тексти — у [tui.md](tui.md#tui). Специфікація й критерії приймання — у трекері `.scratch/tui-workspace/spec.md`.

## 1. Головне рішення

Один запуск `keylang` відкриває всі прикладні можливості keylang. Людина обирає дію, задає параметри й бачить результат у тій самій сесії. CLI лишається другим способом виконати ті самі операції.

Спершу задум був скромніший: палітра лише повторює клавіші, а генератори запускаються зовні. Користувач попросив, щоб «все можна було в TUI», і цю вимогу прийнято. Тепер `:` відкриває повний каталог дій, а нові дії можуть не мати власних гарячих клавіш.

У центрі інтерфейсу й далі текст специфікації. Форма збирає лише кілька параметрів конкретної операції, а конфігурація проєкту лишається звичайним текстовим файлом. Вердикт, стан операції та готовність фічі — різні речі, і кожна має свій підпис, щоб їх не плутали.

## 2. Екрани

Схеми показують зміст і поведінку, а не точні тексти локалізації. У вузькому терміналі допоміжна панель займає місце редактора, і `Esc` повертає до попереднього тексту й курсора. Від 100 клітинок завширшки панелі можуть стояти збоку; вужчий термінал показує одну активну панель. Форми й результати прокручуються, але основна дія та спосіб повернутися завжди лишаються на екрані.

### 2.1 Перший запуск

```text
┌ keylang · /repo/shop ─────────────────────────────────────┐
│ keylang.json ще немає                                     │
│ Знайдено: TypeScript · шари: domain, app, infra            │
│                                                          │
│ > Налаштувати keylang…                                    │
│   Переглянути репозиторій із вгаданою конфігурацією        │
│   Діагностика оточення                                    │
│                                                          │
│ Enter обрати                 : усі дії   ? довідка  q вихід│
└──────────────────────────────────────────────────────────┘
```

Сам по собі перший запуск нічого не записує. Init показує корінь, вгадану розкладку й вибір харнесів: auto / конкретні / none. Видно й те, які файли буде записано: конфігурацію, карту, baseline, інтеграції. Кнопка «Ініціалізувати» запускає чинну операцію init, а після неї одразу відкривається робочий простір, без повторного запуску.

Якщо конфігурація вже є, init зберігає її за чинним контрактом. Якщо вона невалідна, початковий екран пропонує «Відкрити конфігурацію» й показує помилкове поле. Коли в репозиторії немає підтримуваних джерел, інтерфейсом однаково можна налаштувати проєкт, писати специфікації вручну й запускати діагностику; знімок коду при цьому не вигадується.

### 2.2 Робочий простір

```text
┌ FILES ──────────┬ checkout.md [+] · EDIT ────────┬ NAV ────┐
│ map/           │  1   # flow checkout          │ FLOWS    │
│ flows/         │  2 ✓ - trigger app.buy        │ checkout │
│   checkout.md  │  3 ◌ - step infra.save         │ RULES    │
│ features/      │                                │ …        │
│ rules.md       │                                │          │
├────────────────┴────────────────────────────────┴──────────┤
│ ID ✓  static ✓  tests —  trace ◌ · snapshot 13ab…          │
│ Аналіз буферів · незбережені входи · ✗ 0  ◌ 1             │
│ Ctrl+S запис · Esc перегляд · F5 аналіз · F6 результати    │
└───────────────────────────────────────────────────────────┘
```

Усе знайоме лишається на місці: `F2` файли, `F3` навігація, `F4` контекст, `i`, `v`, `m`, пошук, переходи й допомога. Нове — `F6` з результатами операцій і палітра: `Ctrl+P` відкриває її з будь-якого звичайного режиму редактора, а `:` — у перегляді. У полі тексту `:` лишається звичайним символом. Під час MERGE `Ctrl+P` показує каталог, але дії, які перервали б злиття або писали б у його цілі, пояснюють, чому вони заблоковані.

Рядок стану показує прогрес активної операції, навіть коли її панель закрито. Коли фонова дія завершується, з'являється повідомлення; воно не перемикає файл і не забирає фокус.

Незбережені специфікації входять в overlay-аналіз. Незбережена конфігурація ще не змінює параметрів перевірки, і її заголовок прямо пише «набуде чинності після збереження». Якщо F5 не вдався, попередні позначки тьмяніють, а повідомлення про помилку висить, доки аналіз не пройде успішно.

### 2.3 Палітра

```text
┌ Дії ──────────────────────────────────────────────────────┐
│ > map                                                     │
│ > Оновити файли карти                 map                 │
│   Перевірити актуальність карти       map --check         │
│   Запропонувати розкладку шарів       draft map           │
│   Показати карту з поясненнями        t                   │
│                                                          │
│ Оновить згенеровані файли й індекс. Модель не викликає.   │
│ Enter параметри · ↑↓ вибір · Esc назад                    │
└──────────────────────────────────────────────────────────┘
```

Палітра ділить дії на групи «Файли», «Перевірка», «Генерація», «Пояснення», «Проєкт та інтеграції», «Дані та експорт» і «Навігація». Пошук знаходить дію і за назвою, і за CLI-alias. Недоступні дії не зникають: у деталях видно причину й перехід до того, що треба зробити спершу. Для LLM це, наприклад, «Агент не налаштований → Відкрити конфігурацію / Діагностика»; алгоритмічна генерація лишається доступною окремо.

Enter відкриває параметри дії, а безпечну дію без параметрів, як-от відкриття панелі, одразу виконує. Дія, що записує файли, спершу показує свою ціль, тож випадковий Enter у результатах пошуку нічого не запише.

### 2.4 Форма дії

```text
┌ Чернетка потоку · draft flow ─────────────────────────────┐
│ Trigger:  app.checkout.buy              [пошук ID]        │
│ Назва:    checkout                                        │
│ Ціль:     keylang/flows/checkout.md                       │
│ Режим:    hybrid                                          │
│ Результат: пропозиція / лише перегляд                     │
│ Контекст: поточний потік + вибір F4                       │
│                                                          │
│ [Створити пропозицію]                                     │
│ Tab поле · Enter обрати/виконати · Esc назад               │
└──────────────────────────────────────────────────────────┘
```

Контекст лише заповнює видимі поля початковими значеннями. Списки ID показують вид і повний ID, а поле шляху — корінь, відносно якого шлях читають. Обов'язкові поля й взаємовиключні режими перевіряються так само, як у CLI. Помилку показано біля поля, і набрані значення не губляться.

### 2.5 Незбережені входи

```text
┌ Зберегти перед перевіркою готовності ─────────────────────┐
│ Операція читає стан на диску. Незбережені:                │
│   keylang/features/refund.md                             │
│   keylang/rules.md                                       │
│                                                          │
│ [Зберегти й продовжити]    [Повернутися]                  │
└──────────────────────────────────────────────────────────┘
```

Якщо зберегти не вдалося, сесія лишається на цьому кроці, і операція ще не починається. Read-only режими самі нічого не пишуть: запис буферів тут — окрема дія, яку користувач обирає явно. Хто хоче, щоб диск лишився зовсім незмінним, може повернутися, відкликати правки вручну або обмежитися аналізом буфера.

### 2.6 Прогрес і результат

```text
┌ Результати · F6 ──────────────────────────────────────────┐
│ > Оновити карту              завершено · код 0           │
│   Пояснити відсутні brief-и   виконується 12 / 40         │
│   Готовність refund          є прогалини · код 1         │
├──────────────────────────────────────────────────────────┤
│ Корінь /repo/shop · початок 14:21 · результат на диску    │
│ Записано: keylang/map/app.md, .keylang/index.json         │
│ Видалено: немає                                          │
│ [Відкрити файл] [Повторити з параметрами]                 │
│ Esc до редактора                                         │
└──────────────────────────────────────────────────────────┘
```

Результат показує операцію, параметри, стан, код, summary, діагностики й файли, які справді записано. Одночасно виконується лише одна прикладна операція; решта рядків на схемі — це історія. Активну операцію можна скасувати дією «Скасувати»; `Esc` її не скасовує. Частковий результат має списки completed/failed/skipped. Export зберігає структурований звіт у вибраному форматі без ANSI.

Першим у F6 закріплено «Поточний аналіз редактора»: повний список результатів, а не лише перша помилка біля курсора. У кожному рядку — файл, рядок, код або критерій і вердикт; Enter веде в текст або до місця в коді. Звідси, наприклад, можна дістатися K102, прив'язаного до імпорту у вихідному коді. Фільтри fail/unverified/warning/ok не змінюють сам звіт, а кількість прихованого видно. Лічильники рахують результати за тією самою політикою, що й CLI, а не рядки жолоба.

Наступний запуск не стирає останній корисний звіт. Чи він ще актуальний, видно з його входів: після правок з'являється напис «застарілий результат». Першій версії вистачає обережної інвалідації за поколінням аналізу й змінами файлів.

### 2.7 Готовність фічі

```text
┌ Feature · refund · збережений стан ─────────── Enter rerun · Tab gaps · m questions · Esc back ┐
│ 3 gap(s) · code 1 · snapshot 13ab…                                                         │
│ stage  idea › behavior › [structure] › ready › done                                        │
│ structure · 1 gap(s) · 1 hint(s), not blocking                                             │
│ question refund  …/refund.md:3:1  open question: who starts a refund?                      │
│ hint signature app.refund.run  …/refund.md:4:1  planned fn … has no signature               │
│ ready · 2 gap(s)                                                                           │
│ planned  app.refund.run  …/refund.md:4:1  planned `app.refund.run` is not implemented       │
│ static   app.refund.run  …/refund.md:6:3  …                                                 │
│ Info (not blocking): tests ◌ · trace —                                                     │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

Звіт про готовність — це запис операції `feature` у `F6` (у палітрі «Feature readiness»; `F3` лишається навігацією). Під підсумком іде драбина стадій `idea › behavior › structure › ready › done` з поточною стадією в дужках. Нижче — прогалини й підказки, згруповані за стадією, на якій їх усувають: спершу прогалини стадії, потім її підказки, які готовності не блокують. `Tab` переводить стрілки на ці рядки в тому ж порядку, `Enter` відкриває місце вибраного рядка, `Esc`/`Ctrl+O` повертає до звіту. Коли прогалин немає, звіт пише «Done · code 0», а на драбині стоїть `[done]`; підказки лишаються видимими. Відсутній файл чи некоректний slug — це помилка дії з кодом 2, а не «є прогалини». Успішно створений кандидат не робить фічу «готовою». Для planned-вузла є дія генерації коду з тим самим ID (`g`).

**Питання моделі (`m`).** Коли в `keylang.json` задано `agent`, заголовок звіту пропонує `m questions` (у палітрі — «Ask the model for questions» для відкритого файла фічі). Це один запит до моделі: файл фічі й пакет контексту навколо його ID. Відповідь стає пропозицією `.keylang/proposals/<файл фічі>` — до п'яти рядків `- ? …` на верхньому рівні першого потоку, після питань, якими він уже починається. Людина приймає їх у MERGE, а сам файл фічі до `w` не змінюється. Рядки відповіді не у формі `- ? …` і питання понад п'яте відкидаються, і повідомлення каже, скільки їх було. Якщо людина ще на тому самому звіті, MERGE відкривається сам; інакше пропозиція чекає (`m`, Proposals чи `Enter` на записі). Без налаштованої моделі `m` і дія палітри пояснюють, як її налаштувати, і нічого не запускають. Модель не втручається сама: немає спливаючих підказок, таймерів чи персонажа, питання з'являються лише на запит людини, а ghost-текст не змінюється.

**Жолоб і рядок стану.** Рядок `- ? …` має в жолобі позначку `?`, і це не вердикт. Для відкритого файла фічі рядок стану показує `feature <stage> · questions <n>`. Це звіт того самого `feature`, порахований на аналізі сесії проти плану на його типовій базі (merge-base з основною гілкою, інакше `HEAD`; [cli.md](cli.md#agents)). Значення оновлюється після збереження й аналізу; поки в буфері є незбережені правки, лишається попереднє.

### 2.8 Новий файл

Палітра → «Нова специфікація» → вид (flow / rules / wiring / feature / порожній Markdown), відносний шлях і, за бажання, ім'я потоку. Новий flow містить лише заголовок потоку, rules і wiring — відповідний заголовок, а feature починається з прозового заголовка без вигаданих planned-вузлів. Неповний потік не отримує підтвердження виконання.

Типово шлях лежить у налаштованому каталозі специфікацій. Новий буфер не може потрапити до згенерованих карт, пояснень або за межі цього каталогу. Якщо файл уже існує, він відкривається як є, а не очищається. Підтверджена форма відкриває dirty-буфер; теку й файл створює лише Ctrl+S.

### 2.9 Вибір пропозиції

Палітра → «Пропозиції» відкриває список усіх pending-цілей зі шляхом, типом spec/code і кількістю шматків. Enter відкриває вибрану ціль у чинному MERGE. `m` одразу відкриває пропозицію поточного файла, а якщо її немає, то цей список. Непридатні пропозиції показано з причиною, і вони не записуються. Завдяки цьому код і тест одного кандидата можна переглядати в будь-якому порядку, навіть коли першу пропозицію ще не вирішено.

### 2.10 Зум

Зум — окремий екран TUI, щоб читати репозиторій зверху вниз, як у зумі C4: система → шар → модуль → член → код (c4-zoom/07). Наявних екранів і клавіш він не змінює: `Enter` у перегляді карти так само веде в код, а зум відкривається клавішею `z`.

```text
┌ keylang › tui › app ─────────────────────────────── depth 1 ┐
│ The TUI application: one session for the terminal and …    │
│                                                            │
│ ▸ class  App · One session of the TUI: state, keys, …  ◌ ↔ 412 │
│   fn     runTerminal · Runs the TUI in this terminal…   ✓ ↔ 9 │
│   fn     map.analyze.analyze ·1 · One analysis …         ↔ 31 │
│   … 14 more at depth 2: > shows them                        │
└────────────────────────────────────────────────────────────┘
```

`+`/`Enter` — у вузол, `-`/`Esc` — вгору з курсором на вузлі, звідки прийшли, `>`/`<` — глибина сусідів, `s` — пошук вузла, `e` — пояснення, `q` — назад у перегляд на вибраному вузлі. `c` перемикає рівень на його зв'язки — ребра рядками `in`, `out`, `package`, `inside` і `◌ unresolved inside` — а `x` пояснює вибране ребро у `F6`. `f` накладає потік: кроки нумеруються в порядку запису, позначки беруться з жолоба, а на корені видно шари, якими він іде. Повний опис — [tui.md](tui.md), «Екран „Зум“».

## 3. Матриця прикладних можливостей

Ця матриця перелічує, як кожна можливість CLI виглядає в TUI. Назви дій тут — орієнтири для UI. «Перегляд» відповідає print/dry-run там, де він є; «Перевірити» відповідає `--check` і не запускає генератор неявно.

| CLI / можливість | Дія в TUI та параметри | Результат / запис |
|---|---|---|
| `init` | Налаштувати проєкт; auto/перелік/none харнесів; запис/перевірка | Конфіг, карта, baseline, інтеграції; чинний конфіг збережено |
| `map` | Оновити карту / перевірити карту | Ті самі map/index/cache та explained map за конфігом; check не пише |
| `check` | Перевірити; paths, strict, static, changed/since | Звіт human/json/sarif/github; без запису до явного Export |
| `check --explain-edge` | Пояснити ребро; два ID | Докази й невизначеність у панелі |
| `fmt` | Форматувати; поточний файл/вибрані шляхи; запис/перевірка | Канонічний текст або відмінності; збереження dirty перед запуском |
| `baseline` | Оновити / перевірити базові правила | Baseline за чинною політикою; коротко пояснити зміну дозволеної архітектури |
| `agents` | Налаштувати / перевірити інтеграції; auto/перелік/none | Керовані файли, та сама ідемпотентність |
| `feature` | Готовність фічі; slug із поточного файла або списку | Драбина стадій, gaps і hints за стадіями, код, посилання, інформаційні tests/trace; `m` — питання моделі як пропозиція |
| `draft flow` | Чернетка потоку; trigger, name, into, algo/llm/hybrid | Пропозиція або перегляд; F4-контекст при запуску з редактора |
| `draft rules` | Чернетка правил; into, algo/llm/hybrid | Пропозиція або перегляд, agree/conflict/llm-only окремо від вердиктів |
| `draft map` | Чернетка розкладки; algo/llm/hybrid | Перегляд; окремо перенести лише layers у буфер конфіга |
| `code-to-spec` | Потоки з коду; path[:line] або since, into, mode | Пропозиція/перегляд; порожній diff — нічого не створено |
| `spec-to-code` | Код із planned; ID, into, algo/llm | Diff коду/тестів і оцінка кандидата; proposals / preview / явне повне застосування |
| `wire` | Згенерувати / перевірити wiring; out | Генерований TypeScript або помилка без перезапису ручного файла |
| `explain <code>` | Пояснити діагностику | Офлайн-причина й виправлення |
| `explain <id>` | Пояснити вузол; офлайн | Зведення й збережене пояснення |
| `explain <id> --llm` | Попросити пояснення; short/full/brief | Кеш або запит; збереження пояснення, видимий provenance |
| `explain --missing/--stale` | Відсутні / застарілі пояснення | Список вузлів; stale також показує зниклі ID за чинним режимом |
| Пакетний `explain --llm` | Створити missing / оновити stale brief-и; limit/jobs; dry-run | Оцінка без запитів або batch із частковим прогресом |
| `doctor` | Діагностика оточення | Мови, агент/ключ, голос; переходи до конфіга й інтеграцій |
| `parse` | Показати Text IR; paths, tree/json | Прокручуваний результат і діагностики; за потреби Export |
| `trace-plan` | План trace; flow | JSON плану, snapshotId, хеші; за потреби Export |
| `export c4` | Export C4 diagram; формат, рівень, шар, файл | Діаграма у `F6` без запису або файл із маркером; чужий файл не перезаписується |
| `--help`, `--version` | Довідка / Про keylang | Повний каталог, клавіші, версія |
| `Ctrl+G`, `m`, `u` | Проза → пункти, злиття, відкат | Чинні редакторські контракти |
| Пропозиції | Повний список pending-цілей, вибір spec/code | Перехід у MERGE незалежно від поточного файла |
| Конфігурація, F4, навігація | Відкрити конфіг; контекст; пошук; код; explained map | Чинні можливості доступні з каталогу |
| Ghost і голос | Наявні підказки та голосові дії, з видимими передумовами | Чинна поведінка; автоматичні ghost-запити призупинено під час явної операції |

Export приймає відносний шлях усередині репозиторію, показує його й записує лише за явною дією. Наявну ціль він показує перед заміною, а якщо файл змінився після вибору, не перезаписує його. Це окрема TUI-операція запису результату, а не побічний ефект read-only обчислення.

### Транспорти та зовнішні інструменти

`lsp` і `mcp`, як і раніше, запускають їхні клієнти. TUI дає налаштування інтеграцій і чинну діагностику, але не додає doctor нової перевірки того, чи працюють віддалені клієнти. `hook stop` викликає харнес. `web` використовує той самий набір дій у своїй сесії; запуск web-сервера з термінального TUI в цей дизайн не входить. Тести й trace keylang читає, але тест-раннером не стає.

Отже, «все» тут означає конкретне: жодна прикладна операція keylang не потребує окремої команди. Протокольні точки входу та зовнішня робота лишаються за своїми клієнтами.

## 4. Стан і записи

| Стан | Що бачить людина | Дозволений перехід |
|---|---|---|
| Параметри | Вхідні поля, цілі, режим | Запустити / назад |
| Потрібне збереження | Перелік dirty-входів | Зберегти й продовжити / назад |
| Виконується | Етап або spinner, відома кількість, журнал прогресу | Згорнути панель / скасувати |
| Скасування | Завершення поточного безпечного кроку | Дочекатися canceled/partial |
| Завершено | Код, предметний звіт, фактичні записи | Відкрити результат / повторити / export |
| Помилка / частково | Причина, виконане, невиконане | Виправити / повторити з тими самими параметрами |
| Застарілий результат | Початковий звіт із позначкою outdated | Повторити; не застосовувати старий кандидат |

`Esc` закриває форму або панель, але не скасовує операцію і не стирає її результат. `q` чи інший вихід під час активної операції пропонує лишитися або скасувати й вийти; звичайне завершення чекає, доки скінчиться поточний запис файла. Якщо процес убито, діють звичайні гарантії термінала, а rollback не обіцяно.

Одна операція на сесію не означає глобального замка на репозиторій: інший TUI чи харнес може змінити файли. Тому потрібні наявні правила шляхів, повторна перевірка очікуваного тексту й обробка конфлікту. Генерація не може перекрити невирішений MERGE для тих самих цілей, а іншу готову пропозицію не буде непомітно перезаписано.

Поки виконується операція, правки лишаються в буферах. Дія, якій треба записати в зайняту ціль, повідомляє про активну операцію, а після її завершення ще раз перевіряє диск. Пізня LLM-відповідь належить початковій цілі й не вставляється в інший відкритий файл.

Завершений запис інвалідує аналіз, а повний повторний аналіз виконується, коли вся операція завершилась або частково впала. Проміжний результат неповного багатофайлового запису не видається за поточний. Редактор при цьому не блокується, і незалежні dirty-буфери не губляться.

Відкат `u` і далі означає «відкотити останній MERGE». Загальним undo для init, map, baseline чи багатофайлової генерації він не стає.

## 5. Архітектурний дизайн

```text
CLI argv ───────┐
                ├── прикладні операції ── аналіз / генератори / файлові адаптери
TUI actions ───┘          │
                         └── предметний результат + прогрес + фактичні записи

TUI buffers ── overlay analysis ── жолоб / навігація / контекст
Terminal / Web ── одна модель сесії ── renderer
```

Зараз оркестрація й форматування виводу здебільшого змішані в приватних обробниках `src/cli.ts`. Новий модуль операцій забирає оркестрацію, а предметні алгоритми лишаються в наявних модулях. CLI перетворює argv на запит, а результат — на stdout/stderr; TUI перетворює форму на той самий запит, а результат — на панель.

Інтерфейс модуля малий: він виконує відомий типізований запит з явним root, сигналом скасування й callback прогресу і повертає дискримінований результат. Спільний envelope містить ідентичність операції, код, повідомлення та записи, а payload має предметний тип: check report, feature status, draft candidate тощо. `any`, довільні рядки команд чи універсальний словник прапорців сюди не вводяться.

Стан сесії тримає окремо форму, активну операцію та історію результатів. Операція не володіє ні курсором, ні панелями, а renderer лише показує стан. Важкі обчислення виконує worker, і про завершення він повідомляє повідомленням, а не глобальним записом у stdout.

Для цього потрібен новий шар `operations` — нижче TUI та CLI і вище предметних можливостей. Імпортувати CLI-обробники в TUI не можна, бо чинні правила забороняють залежність TUI від CLI. Файлова оркестрація інтеграцій теж має бути доступна знизу, без залежності від CLI entry. Точні файли визначаються під час реалізації, а розкладка в `keylang.json`, правила та згенерована карта оновлюються разом. Ядро мови й правила лишаються незалежними від tree-sitter.

Технічне рішення записано в [ADR 0008](adr/0008-shared-workspace-operations.md). Формат мови й граматика CLI не змінюються. Коди й тексти CLI збережено, крім суворіших відмов запису: файл-ціль, написаний вручну або змінений під час роботи, не перезаписується, і команда повертає код 1. Ці відмови описано в [tools.md](tools.md). Нові публічні контракти TUI — це повний каталог, параметри, job results, новий файл і запуск прикладних операцій.

## 6. Перевірка і завершеність

Головна перевірка — відтворюваний користувацький сценарій: сесія у віртуальному терміналі на тимчасовому репозиторії. Той самий вхід через CLI має давати той самий звіт і ті самі записані файли. Копіювати реалізацію в тести чи знімати snapshot кожної рамки екрана не потрібно.

Обов'язковий наскрізний сценарій такий: репозиторій без конфігурації → init → нова фіча → редагування → перевірка → spec-to-code → MERGE → map → feature → виправлення прогалин → повторна перевірка. Модель у ньому замінює локальний mock, а статичний сценарій працює й без неї. Згенерований шаблон коду сам по собі ще не робить фічу готовою. Сценарій виконують два тести. `tests/tui-workspace.test.ts` проходить його в одній сесії й на кожному кроці звіряє байти та коди з CLI на копії репозиторію. `tests/web.test.ts` проходить той самий сценарій через справжній `keylang web` і порівнює записи F6 та файли з терміналом. Спільний сценарій лежить у `tests/cycle-fixture.ts`.

Окремо перевіряються: read-only режими без записів, dirty-конфлікти, зовнішня зміна під час LLM-запиту, частковий I/O-збій, скасування, живий ввід під час роботи, однакова прикладна поведінка terminal і web, а також незмінність stdout/stderr і кодів виходу CLI.

Поточну довідку (`docs/cli.md`, `docs/tui.md`) і CLI-help оновлюють разом із тим зрізом, який реалізовано. Цей документ не оголошує заплановане вже доступним.
