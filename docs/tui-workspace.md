# Повний робочий простір keylang у TUI

> Дизайн 2026-09-29, реалізований у 2026-10-01: усі рядки матриці §3 мають дію в TUI. Схеми нижче ілюструють взаємодію; точні назви, клавіші та тексти — у [tools.md](tools.md#tui). Специфікація й критерії приймання — у трекері `.scratch/tui-workspace/spec.md`.

## 1. Головне рішення

Один запуск `keylang` дає доступ до всіх прикладних можливостей keylang. Людина обирає дію, задає параметри й отримує результат у сесії. CLI лишається другим способом виконати ті самі операції.

Початкову ідею «палітра лише повторює клавіші, генератори запускаються зовні» замінено вимогою користувача «все можна було в TUI». `:` тепер відкриває повний каталог; нові дії можуть не мати персональних гарячих клавіш.

Текст специфікації залишається центром інтерфейсу. Форми — короткі параметри конкретної операції; конфігурація проєкту лишається звичайним текстовим файлом. Вердикт, стан операції та готовність фічі — три різні речі, кожна має свій підпис.

## 2. Екрани

Схеми показують зміст і поведінку, не точні тексти локалізації. У вузькому терміналі допоміжні панелі займають область редактора; `Esc` повертає до попереднього тексту й курсора. При ширині від 100 клітинок допускаються бічні панелі; при меншій ширині — одна активна панель. Форми й результати прокручуються; основна дія та спосіб повернутися лишаються видимими.

### 2.1 Перший запуск

```text
┌ keylang · /repo/shop ─────────────────────────────────────┐
│ keylang.json ще немає                                     │
│ Знайдено: TypeScript · шари: domain, app, infra            │
│                                                          │
│ > Налаштувати keylang…                                    │
│   Переглянути репозиторій із вгаданою конфігурацією        │
│   Діагностика оточення                                    │
│                                                          │
│ Enter обрати                 : усі дії   ? довідка  q вихід│
└──────────────────────────────────────────────────────────┘
```

Автоматичних записів немає. Init показує корінь, вгадану розкладку й вибір харнесів: auto / конкретні / none. Видно класи цільових файлів: конфігурація, карта, baseline, інтеграції. Кнопка «Ініціалізувати» запускає чинну операцію init; завершення відкриває робочий простір без повторного запуску.

Якщо конфігурація вже є, init зберігає її за чинним контрактом. Якщо вона невалідна, початковий екран дає «Відкрити конфігурацію» й показує помилкове поле. За відсутності підтримуваних джерел інтерфейс лишається доступним для конфігурації, ручних специфікацій і діагностики, без вигаданого знімка.

### 2.2 Робочий простір

```text
┌ FILES ──────────┬ checkout.md [+] · EDIT ────────┬ NAV ────┐
│ map/           │  1   # flow checkout          │ FLOWS    │
│ flows/         │  2 ✓ - trigger app.buy        │ checkout │
│   checkout.md  │  3 ◌ - step infra.save         │ RULES    │
│ features/      │                                │ …        │
│ rules.md       │                                │          │
├────────────────┴────────────────────────────────┴──────────┤
│ ID ✓  static ✓  tests —  trace ◌ · snapshot 13ab…          │
│ Аналіз буферів · незбережені входи · ✗ 0  ◌ 1             │
│ Ctrl+S запис · Esc перегляд · F5 аналіз · F6 результати    │
└───────────────────────────────────────────────────────────┘
```

Залишаються `F2` файли, `F3` навігація, `F4` контекст, `i`, `v`, `m`, пошук, переходи й допомога. Нове: `F6` — результати операцій; `Ctrl+P` — палітра з будь-якого звичайного режиму редактора, `:` — та сама палітра в перегляді. У полі тексту `:` лишається символом. `Ctrl+P` під час MERGE дає перегляд каталогу, але дії, що перервали б злиття або писали його цілі, пояснюють блокування.

У рядку стану видно прогрес активної операції, навіть коли її панель закрито. Завершення фонової дії додає повідомлення; воно не перемикає файл і не забирає фокус.

Незбережені специфікації входять в overlay-аналіз. Незбережена конфігурація ще не змінює параметри перевірки; її заголовок прямо пише «набуде чинності після збереження». Невдалий F5 лишає попередні позначки тьмяними з постійним повідомленням про помилку до успішного аналізу.

### 2.3 Палітра

```text
┌ Дії ──────────────────────────────────────────────────────┐
│ > map                                                     │
│ > Оновити файли карти                 map                 │
│   Перевірити актуальність карти       map --check         │
│   Запропонувати розкладку шарів       draft map           │
│   Показати карту з поясненнями        t                   │
│                                                          │
│ Оновить згенеровані файли й індекс. Модель не викликає.   │
│ Enter параметри · ↑↓ вибір · Esc назад                    │
└──────────────────────────────────────────────────────────┘
```

Групи: **Файли**, **Перевірка**, **Генерація**, **Пояснення**, **Проєкт та інтеграції**, **Дані та експорт**, **Навігація**. Пошук знаходить назву й CLI-alias. Недоступні дії не зникають: у деталях — причина й перехід до потрібної дії. Наприклад, для LLM — «Агент не налаштований → Відкрити конфігурацію / Діагностика»; алгоритмічна генерація доступна окремо.

Enter відкриває параметри, або одразу виконує безпечну дію без параметрів на кшталт відкриття панелі. Вибір дії запису спершу показує її ціль; випадковий Enter у результатах пошуку не записує файлів.

### 2.4 Форма дії

```text
┌ Чернетка потоку · draft flow ─────────────────────────────┐
│ Trigger:  app.checkout.buy              [пошук ID]        │
│ Назва:    checkout                                        │
│ Ціль:     keylang/flows/checkout.md                       │
│ Режим:    hybrid                                          │
│ Результат: пропозиція / лише перегляд                     │
│ Контекст: поточний потік + вибір F4                       │
│                                                          │
│ [Створити пропозицію]                                     │
│ Tab поле · Enter обрати/виконати · Esc назад               │
└──────────────────────────────────────────────────────────┘
```

Значення із контексту — лише початкові значення видимих полів. Списки ID показують вид і повний ID; поле шляху показує корінь, відносно якого його читають. Перевірки обов'язкових полів і взаємовиключних режимів збігаються з CLI. Помилка прив'язана до поля, набрані значення зберігаються.

### 2.5 Незбережені входи

```text
┌ Зберегти перед перевіркою готовності ─────────────────────┐
│ Операція читає стан на диску. Незбережені:                │
│   keylang/features/refund.md                             │
│   keylang/rules.md                                       │
│                                                          │
│ [Зберегти й продовжити]    [Повернутися]                  │
└──────────────────────────────────────────────────────────┘
```

Помилка збереження лишає сесію на цьому кроці; операція ще не почалася. Read-only режими самі нічого не пишуть: запис буферів тут — окремо й явно обрана користувачем дія. Для абсолютно незмінного диска можна повернутися, відкликати правки вручну або обмежитися аналізом буфера.

### 2.6 Прогрес і результат

```text
┌ Результати · F6 ──────────────────────────────────────────┐
│ > Оновити карту              завершено · код 0           │
│   Пояснити відсутні brief-и   виконується 12 / 40         │
│   Готовність refund          є прогалини · код 1         │
├──────────────────────────────────────────────────────────┤
│ Корінь /repo/shop · початок 14:21 · результат на диску    │
│ Записано: keylang/map/app.md, .keylang/index.json         │
│ Видалено: немає                                          │
│ [Відкрити файл] [Повторити з параметрами]                 │
│ Esc до редактора                                         │
└──────────────────────────────────────────────────────────┘
```

Результат показує операцію, параметри, стан, код, summary, діагностики й фактичні записи. У кожний момент виконується лише одна прикладна операція; схема ілюструє також записи історії. Для активної є «Скасувати»; це окрема дія, не `Esc`. Для часткового результату є списки completed/failed/skipped. Export зберігає структурований звіт у вибраному форматі без ANSI.

Перший закріплений пункт F6 — «Поточний аналіз редактора»: повний список результатів, а не лише перша помилка біля курсора. Список містить файл, рядок, код/критерій і вердикт; Enter веде в текст або до позиції коду. Зокрема K102, прив'язаний до імпорту у вихідному коді, доступний звідси. Фільтри fail/unverified/warning/ok не змінюють сам звіт; приховані кількості видно. Лічильники звіту рахують результати за тією самою політикою, що CLI, а не рядки жолоба.

Не стирати останній корисний звіт під час наступного запуску. Його актуальність перевіряється за входами; після правок напис «застарілий результат». У першій версії достатня консервативна інвалідація за поколінням аналізу й змінами файлів.

### 2.7 Готовність фічі

```text
┌ Feature · refund · збережений стан ────────────────────────┐
│ Є прогалини · код 1 · snapshot 13ab…                      │
│ planned   app.refund.run     ще не реалізовано            │
│ static    infra.pay.refund   виклик не підтверджено        │
│ rule      domain → infra    K102                          │
│                                                          │
│ Інформаційно: tests ◌ · trace —                           │
│ Enter до джерела · : дії · Esc назад                      │
└──────────────────────────────────────────────────────────┘
```

Якщо прогалин немає — «Готово · код 0». Відсутній файл чи некоректний slug — помилка дії з кодом 2, не «є прогалини». Успішне створення кандидата не змінює стан фічі на «готово». Перехід до прогалини використовує її файл/рядок; для planned доступна дія генерації коду з тим самим ID.

### 2.8 Новий файл

Палітра → «Нова специфікація» → вид (flow / rules / wiring / feature / порожній Markdown), відносний шлях, необов'язкове ім'я потоку. Для flow мінімальний вміст — заголовок потоку; для rules/wiring — відповідний заголовок; feature починається з прозового заголовка без вигаданих planned-вузлів. Неповний потік не отримує підтвердження виконання.

Шлях типово під налаштованим каталогом специфікацій. Нові буфери не можуть потрапити до згенерованих карт, пояснень або за межі цього каталогу. Існуюча ціль відкривається як існуючий файл, а не очищається. Прийняття форми відкриває dirty-буфер; теку й файл створює лише Ctrl+S.

### 2.9 Вибір пропозиції

Палітра → «Пропозиції» відкриває список усіх pending-цілей зі шляхом, типом spec/code і кількістю шматків. Enter відкриває вибрану ціль у чинному MERGE. `m` одразу відкриває пропозицію поточного файла, а якщо її немає — цей список. Непридатні пропозиції показуються з причиною й не записуються. Так код і тест одного кандидата можна переглянути в довільному порядку, навіть якщо перша пропозиція ще не вирішена.

### 2.10 Зум

Окремий екран TUI для читання репозиторію зверху вниз, як зум C4: система → шар → модуль → член → код (c4-zoom/07). Наявні екрани й клавіші він не змінює: `Enter` у перегляді карти так само веде в код, а зум відкриває `z`.

```text
┌ keylang › tui › app ─────────────────────────────── depth 1 ┐
│ The TUI application: one session for the terminal and …    │
│                                                            │
│ ▸ class  App · One session of the TUI: state, keys, …  ◌ ↔ 412 │
│   fn     runTerminal · Runs the TUI in this terminal…   ✓ ↔ 9 │
│   fn     map.analyze.analyze ·1 · One analysis …         ↔ 31 │
│   … 14 more at depth 2: > shows them                        │
└────────────────────────────────────────────────────────────┘
```

`+`/`Enter` — у вузол, `-`/`Esc` — вгору з курсором на вузлі, звідки прийшли, `>`/`<` — глибина сусідів, `s` — пошук вузла, `e` — пояснення, `q` — назад у перегляд на вибраному вузлі. `c` перемикає рівень на його зв'язки — ребра рядками `in`, `out`, `package`, `inside` і `◌ unresolved inside` — а `x` пояснює вибране ребро у `F6`. `f` накладає потік: кроки нумеруються в порядку запису, позначки беруться з жолоба, а на корені видно шари, якими він іде. Повний опис — [tools.md](tools.md), «Екран „Зум“».

## 3. Матриця прикладних можливостей

Назви дій — орієнтири для UI. «Перегляд» — відповідник print/dry-run там, де він є; «Перевірити» — відповідник `--check`, не неявний запуск генератора.

| CLI / можливість | Дія в TUI та параметри | Результат / запис |
|---|---|---|
| `init` | Налаштувати проєкт; auto/перелік/none харнесів; запис/перевірка | Конфіг, карта, baseline, інтеграції; чинний конфіг збережено |
| `map` | Оновити карту / перевірити карту | Ті самі map/index/cache та explained map за конфігом; check не пише |
| `check` | Перевірити; paths, strict, static, changed/since | Звіт human/json/sarif/github; без запису до явного Export |
| `check --explain-edge` | Пояснити ребро; два ID | Докази й невизначеність у панелі |
| `fmt` | Форматувати; поточний файл/вибрані шляхи; запис/перевірка | Канонічний текст або відмінності; збереження dirty перед запуском |
| `baseline` | Оновити / перевірити базові правила | Baseline за чинною політикою; коротко пояснити зміну дозволеної архітектури |
| `agents` | Налаштувати / перевірити інтеграції; auto/перелік/none | Керовані файли, та сама ідемпотентність |
| `feature` | Готовність фічі; slug із поточного файла або списку | Ready/gaps, код, посилання, інформаційні tests/trace |
| `draft flow` | Чернетка потоку; trigger, name, into, algo/llm/hybrid | Пропозиція або перегляд; F4-контекст при запуску з редактора |
| `draft rules` | Чернетка правил; into, algo/llm/hybrid | Пропозиція або перегляд, agree/conflict/llm-only окремо від вердиктів |
| `draft map` | Чернетка розкладки; algo/llm/hybrid | Перегляд; окремо перенести лише layers у буфер конфіга |
| `code-to-spec` | Потоки з коду; path[:line] або since, into, mode | Пропозиція/перегляд; порожній diff — нічого не створено |
| `spec-to-code` | Код із planned; ID, into, algo/llm | Diff коду/тестів і оцінка кандидата; proposals / preview / явне повне застосування |
| `wire` | Згенерувати / перевірити wiring; out | Генерований TypeScript або помилка без перезапису ручного файла |
| `explain <code>` | Пояснити діагностику | Офлайн-причина й виправлення |
| `explain <id>` | Пояснити вузол; офлайн | Зведення й збережене пояснення |
| `explain <id> --llm` | Попросити пояснення; short/full/brief | Кеш або запит; збереження пояснення, видимий provenance |
| `explain --missing/--stale` | Відсутні / застарілі пояснення | Список вузлів; stale також показує зниклі ID за чинним режимом |
| Пакетний `explain --llm` | Створити missing / оновити stale brief-и; limit/jobs; dry-run | Оцінка без запитів або batch із частковим прогресом |
| `doctor` | Діагностика оточення | Мови, агент/ключ, голос; переходи до конфіга й інтеграцій |
| `parse` | Показати Text IR; paths, tree/json | Прокручуваний результат і діагностики; за потреби Export |
| `trace-plan` | План trace; flow | JSON плану, snapshotId, хеші; за потреби Export |
| `--help`, `--version` | Довідка / Про keylang | Повний каталог, клавіші, версія |
| `Ctrl+G`, `m`, `u` | Проза → пункти, злиття, відкат | Чинні редакторські контракти |
| Пропозиції | Повний список pending-цілей, вибір spec/code | Перехід у MERGE незалежно від поточного файла |
| Конфігурація, F4, навігація | Відкрити конфіг; контекст; пошук; код; explained map | Чинні можливості доступні з каталогу |
| Ghost і голос | Наявні підказки та голосові дії, з видимими передумовами | Чинна поведінка; автоматичні ghost-запити призупинено під час явної операції |

Export приймає відносний шлях усередині репозиторію, показує його й записує лише за явною дією. Наявну ціль показує перед заміною; конфлікт зміни після вибору не перезаписує. Це окрема TUI-операція запису результату, а не побічний ефект read-only обчислення.

### Транспорти та зовнішні інструменти

`lsp` і `mcp` продовжують запускатися їхніми клієнтами; TUI надає налаштування інтеграцій і чинну діагностику, не приписує doctor нову перевірку працездатності віддалених клієнтів. `hook stop` надходить від харнеса. `web` використовує той самий набір дій у своїй сесії; запуск web-сервера з термінального TUI не входить у цей дизайн. Тести/trace keylang читає, але тест-раннером не стає.

Це конкретне тлумачення «все»: жодна прикладна операція keylang не потребує окремої команди. Протокольні точки входу та зовнішня робота лишаються у своїх клієнтів.

## 4. Стан і записи

| Стан | Що бачить людина | Дозволений перехід |
|---|---|---|
| Параметри | Вхідні поля, цілі, режим | Запустити / назад |
| Потрібне збереження | Перелік dirty-входів | Зберегти й продовжити / назад |
| Виконується | Етап або spinner, відома кількість, журнал прогресу | Згорнути панель / скасувати |
| Скасування | Завершення поточного безпечного кроку | Дочекатися canceled/partial |
| Завершено | Код, предметний звіт, фактичні записи | Відкрити результат / повторити / export |
| Помилка / частково | Причина, виконане, невиконане | Виправити / повторити з тими самими параметрами |
| Застарілий результат | Початковий звіт із позначкою outdated | Повторити; не застосовувати старий кандидат |

`Esc` закриває форму або панель. Він не скасовує операцію і не стирає її результат. `q`/вихід при активній операції пропонує лишитися або скасувати й вийти; нормальне завершення чекає поточного файлового запису. Невідворотне завершення процесу має чинні термінальні гарантії, не обіцянку rollback.

Одна операція на сесію — не глобальний замок репозиторію. Інший TUI чи харнес може змінити файли. Потрібні наявні правила шляхів, повторна перевірка очікуваного тексту й обробка конфлікту. Невирішений MERGE не можна перекривати генерацією для тих самих цілей; інша готова пропозиція не перезаписується непомітно.

Поки виконується операція, правки лишаються у буферах. Дія, яка потребує запису в зайняту ціль, повідомляє про активну операцію; після завершення повторно перевіряє диск. Пізня LLM-відповідь належить початковій цілі: не вставляється в інший відкритий файл.

Завершення запису інвалідує аналіз; повний повтор виконується після завершення всієї операції або її часткового збою. Проміжний результат із неповного багатофайлового запису не видається за поточний. Цей протокол не блокує редактор і не губить незалежні dirty-буфери.

Відкат `u` зберігає значення «відкотити останній MERGE». Він не стає загальним undo для init, map, baseline або багатофайлової генерації.

## 5. Архітектурний дизайн

```text
CLI argv ───────┐
                ├── прикладні операції ── аналіз / генератори / файлові адаптери
TUI actions ───┘          │
                         └── предметний результат + прогрес + фактичні записи

TUI buffers ── overlay analysis ── жолоб / навігація / контекст
Terminal / Web ── одна модель сесії ── renderer
```

Зараз багато оркестрації й форматування виводу поєднано в приватних обробниках `src/cli.ts`. Новий модуль операцій бере оркестрацію, зберігаючи предметні алгоритми в наявних модулях. CLI перетворює argv на запит і результат на stdout/stderr; TUI перетворює форму на той самий запит і результат на панель.

Малий interface: виконати відомий типізований запит з явним root, сигналом скасування й callback прогресу; повернути дискримінований результат. Спільний envelope містить ідентичність операції, код, повідомлення та записи, але payload має предметний тип — check report, feature status, draft candidate тощо. Не вводити `any`, довільні рядки команд чи універсальний словник прапорців.

Стан сесії окремо тримає форму, активну операцію та історію її результатів. Операція не володіє курсором або панелями. Renderer лише показує стан. Важкі обчислення виконує worker; завершення надходить повідомленням, а не глобальним записом у stdout.

Під час реалізації потрібен новий шар `operations` нижче TUI та CLI і вище предметних можливостей. Поточні правила забороняють залежність TUI від CLI, тому імпорт CLI-обробників не підходить. Файлова оркестрація інтеграцій також має бути доступна знизу, без залежності від CLI entry. Точні файли визначаються під час реалізації; розкладка в `keylang.json`, правила та згенерована карта оновлюються разом. Ядро мови й правила лишаються незалежними від tree-sitter.

Технічне рішення записано в [ADR 0008](adr/0008-shared-workspace-operations.md). Формат мови й граматика CLI не змінюються. Коди й тексти CLI збережено, крім суворіших відмов запису: ручний або змінений за час роботи файл-ціль не перезаписується, код 1. Їх описано в [tools.md](tools.md). Нові публічні контракти TUI: повний каталог, параметри, job results, новий файл і запуск прикладних операцій.

## 6. Перевірка і завершеність

Основна перевірка — відтворюваний користувацький сценарій через сесію та віртуальний термінал на тимчасовому репозиторії. Той самий вхід через CLI має давати той самий звіт і записані файли. Повні копії реалізації в тестах та snapshot кожної рамки екрана не потрібні.

Обов'язковий наскрізний сценарій: репозиторій без конфігурації → init → нова фіча → редагування → перевірка → spec-to-code → MERGE → map → feature → виправлення прогалин → повторна перевірка. Модель підміняється локальним mock; статичний сценарій працює без неї. Код шаблону сам по собі не гарантує готовність фічі. Цей сценарій виконують два тести. `tests/tui.test.ts` проходить його в одній сесії й на кожному кроці звіряє байти та коди з CLI на копії репозиторію. `tests/web.test.ts` проходить той самий сценарій через справжній `keylang web` і порівнює записи F6 та файли з терміналом. Спільний сценарій лежить у `tests/cycle-fixture.ts`.

Окремо перевірити read-only режими без записів, dirty-конфлікти, зовнішню зміну під час LLM, частковий I/O-збій, скасування, живий ввід під час роботи, однакову прикладну поведінку terminal/web і незмінність CLI stdout/stderr/exit codes.

Оновлення поточної довідки `docs/tools.md` і CLI-help виконується разом із відповідним реалізованим зрізом. Цей документ не оголошує заплановані можливості доступними сьогодні.
