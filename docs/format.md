# Формат keylang — специфікація v0.2

> Навчальний курс англійською: [docs/course](course/README.md). Той самий курс українською: [docs/course/uk](course/uk/README.md). Цей файл лишається нормативною граматикою.

Точна граматика Markdown-форми keylang, як її читає поточний CLI. Загальні ідеї — у [`design.md`](design.md) §3; тут записано, як саме парсер (`src/parser.ts`) розбирає файл і які неоднозначності як вирішено. Рішення позначено **Р1…Рn**, щоб на них можна було посилатися в рев'ю. Формат v1 не заморожено: те, чого в цій специфікації немає в розділі «Дорожня карта», не є поточною поведінкою.

Виконуваний приклад — група огорож. Огорожа `keylang` (шлях у `path=`, типово `keylang/example.md`, завжди під `keylang/`) і огорожа іншої мови з `path=` записують файли однієї теки. Остання огорожа групи — `diagnostics`: точні рядки stdout `keylang check`, у яких є K-код; порожня огорожа означає, що таких рядків немає. Огорожа `fmt` одразу після своєї `keylang` — або текст файла після `keylang fmt` (повторний `fmt` його вже не змінює), або рядки `K003`, коли `fmt` відмовляється з кодом 1 і лишає файл без змін. Токен `Рn` в info-рядку `keylang` прив'язує групу до рішення. Інші огорожі — ілюстрації.

## 1. Модель файлу

Файл — послідовність рядків (`\n` або `\r\n`). Кожен рядок належить до одного з класів, які перевіряються в такому порядку:

| Клас | Умова | Що стає в IR |
|---|---|---|
| рядок у code fence | між відкривною і закривною огорожею | `Item::Code` (рядки дослівно) |
| рядок у HTML-блоці типів 1–5 | від рядка початку до кінцевого маркера (нижче) | проза або опис відкритого елемента, дослівно |
| порожній | лише пробіли | закриває абзац прози; список **не** закриває |
| маркер генерації | перший непорожній рядок файлу, починається з `<!--` і містить `keylang:generated` | `Document.generated` |
| заголовок секції | відступ 0, `#` і далі пробіл або кінець рядка | нова `Section` |
| огорожа коду | `` ``` `` або `~~~` за **Р15** | відкриває `Item::Code`, закриває список |
| елемент списку | після відступу `-`, `*` або `+`, далі пробіл або кінець рядка | `Node` |
| опис | інший текст, відступ ≥ 2, і є відкритий елемент списку | `Node.description` |
| проза | усе інше | `Item::Prose`, закриває список |

**Р15. Огорожа закривається за CommonMark.** Відкривна огорожа — щонайменше три однакові символи `` ` `` або `~`. Закривна — той самий символ, довжина не менша за відкривну, після неї лише пробіли або таби. Її відступ не більший за 3 колонки і не більший за відступ відкривної; огорожа, відкрита під списком із більшим відступом (Р9), закривається й на своєму відступі. Info-рядок огорожі з бектиків, у якому є бектик, робить рядок не огорожею: він класифікується далі як звичайний текст. В info огорожі `~~~` бектики дозволені. Рядок огорожі з відступом ≥ 4 без відкритого списку — проза (у CommonMark це відступний блок коду). Незакрита огорожа триває до кінця файла.

Бектик в info не відкриває огорожу, тож рядок під ним лишається елементом списку. `fmt` розділяє цю прозу й список порожнім рядком:

````keylang Р15 path=keylang/map.md
```js has ` tick
- layer domain
```
````

````fmt
```js has ` tick

- layer domain

```
````

```diagnostics
```

Заголовки `##` і глибші, таблиці, цитати, нумеровані списки — це проза: вони не мають семантики, але зберігаються й форматуються дослівно.

**Р1. Власний рядковий парсер замість pulldown-cmark/comrak.** keylang використовує вузьку підмножину Markdown. CommonMark-парсери дають вузли з діапазонами байтів, але для LSP нам потрібні позиції кожного *слова* всередині елемента (ключове слово, ім'я, кожне ID у `calls a, b`), а також власні правила для лінивих продовжень, табів і відступів — їх однаково довелося б дописувати поверх AST. Рядковий парсер (`src/parser.ts`) дає точні `offset/line/col` для кожного токена і власні діагностики (K003) замість мовчазної «перебудови» дерева, як це робить CommonMark. Ціна — ми не розуміємо вкладених у елементи списку code fence (див. Р9).

Друге ID у `calls a, b` має власну колонку. Тут `b` — колонка 18:

```keylang Р1 path=keylang/map.md
- layer app
  - module checkout
    - fn buy
      - calls a, b
```

```diagnostics
keylang/map.md:4:15: K001 dangling reference `a`; declare `planned` if this is an intention
keylang/map.md:4:18: K001 dangling reference `b`; declare `planned` if this is an intention
```

**Розбіжність з CommonMark.** Порівнюються марковані елементи (рядок, глибина, рядок батька) і власник кожного непорожнього рядка тексту; нумеровані списки й цитати — проза, не елементи. Еталон — CommonMark без розширень GFM. Після `fmt` розбіжностей немає. До `fmt` лишаються три класи, і форматування їх прибирає: ліниве продовження (Р5) — рядок з відступом 0 одразу під елементом; HTML-блок типу 6, зокрема `<details>`, який тягнеться до порожнього рядка, що вставляє `fmt`; огорожа з відступом під елементом (Р9) — `fmt` знімає відступ огорожі й вмісту. Огорожа (Р15) і багаторядкові HTML-блоки типів 1–5 збігаються з CommonMark і до форматування.

## 2. Секції та види файлів

Граматика заголовка — у [Додатку А](#додаток-а-граматика).

| Заголовок | Вид секції | Типовий файл |
|---|---|---|
| `# map` | map | `keylang/map/*.md` (генерується) |
| `# rules` | rules | `keylang/rules.md` |
| `# flow <name>` | flow, `name` обов'язковий | `keylang/flows/*.md` |
| `# wiring` | wiring | `keylang/wiring.md` |

- **Р2. Вид визначає заголовок, а не шлях файлу.** Тому `rules.md` може лежати будь-де, а файл без жодного заголовка (як на слайдах) — це секція **map**.
- **Р3. В одному файлі може бути кілька секцій**: кожен `# …` починає нову (наприклад, кілька `# flow` в одному файлі). Вміст до першого заголовка — неявна секція map.
- Невідомий заголовок першого рівня (`# Shop`) — попередження **K006**, секція вважається map. Заголовок без виду (`#`, `# <!-- … -->`) — теж K006: «section heading without a kind».
- Зайві слова в заголовку — K005; `# flow` без імені — K005. Ім'я має лише `flow`: слово після `# rules`, `# map` чи `# wiring` (`# rules foo`) — K005, а не ім'я секції.
- Імена потоків — окремий простір імен: `# flow checkout` не конфліктує з ID карти, але два потоки з однаковим ім'ям — K002.

**Р2.** Файл у `keylang/flows/` із заголовком `# rules` — це правила, тож `layer` там невідомий. Файл без жодного заголовка — карта: голе ім'я є шаром.

```keylang Р2 path=keylang/flows/spec.md
# rules

- layer domain
```

```keylang path=keylang/slides.md
- domain
```

```diagnostics
keylang/flows/spec.md:3:3: K004 unknown keyword `layer` here; expected one of: layers, allow, deny, entry, module, no-cycles
```

**Р3.** Дві секції `# flow` в одному файлі — два потоки. Однакове ім'я — K002 на другому, з позицією першого.

```keylang Р3 path=keylang/flows/shop.md
# flow checkout
- step app.checkout.buy
# flow checkout
- step app.checkout.pay
```

```keylang path=keylang/map.md
- layer app
  - module checkout
    - fn buy
    - fn pay
```

```diagnostics
keylang/flows/shop.md:3:8: K002 duplicate flow `checkout` (first declared at keylang/flows/shop.md:1:8)
```

### Маркер генерації

```
<!-- keylang:generated — не редагувати, `keylang map` -->
```

Має бути першим непорожнім рядком. Текст після `keylang:generated` довільний. Парсер записує маркер в IR (`generated`), форматер зберігає його.

`keylang map` перевіряє **усі цільові файли** в `<dir>/map/` до будь-якого запису чи видалення. Файла ще немає — його буде створено. Перший непорожній рядок містить маркер — файл можна перезаписати. Інакше це конфлікт: повідомлення `manual file without keylang:generated marker` зі шляхом, код виходу 1, жоден файл карти й індекс не записуються і не видаляються. Зайвий файл видаляється лише тоді, коли він сам має маркер. `map --check` повідомляє той самий конфлікт окремо від застарілої карти (`stale`) і теж нічого не пише.

Коментар `<!-- keylang:llm … -->` (позначка, що фрагмент написав LLM) зарезервовано: парсер не надає йому семантики — як і будь-який інший HTML-коментар, він стає прозою, описом або коментарем елемента.

## 3. Відступи та ієрархія

- Глибина елемента = відступ / 2. Відступ — лише пробіли.
- Дочірній елемент може бути глибшим за батьківський рівно на один рівень.

| Помилка | Код | Відновлення |
|---|---|---|
| непарний відступ (`   - x`) | K003 | глибина = відступ / 2 з округленням вниз |
| стрибок більш ніж на рівень | K003 | елемент стає дитиною попереднього |
| таб у відступі елемента чи опису | K003 | таб рахується як 2 пробіли |
| порожній елемент (`- `) | K003 | рядок пропускається |

Таб у відступі прози чи блоку коду — текст, а не структура: K003 немає, `fmt` лишає рядок як є. Рядок із табом після відкритого списку — опис (відступ ≥ 2), тож там таб — K003.

**Р4. `keylang fmt` відмовляється форматувати файл з K003**: інакше форматер мовчки змінив би вкладеність. Семантичні помилки (K001, K002, K004, K005) форматуванню не заважають.

```keylang Р4 path=keylang/map.md
   - module b
```

```fmt
keylang/map.md:1:4: K003 indentation must be a multiple of 2 spaces, found 3
keylang/map.md:1:4: K003 item indented too deep: 3 spaces, at most 0 expected here
```

```diagnostics
keylang/map.md:1:4: K003 indentation must be a multiple of 2 spaces, found 3
keylang/map.md:1:4: K003 item indented too deep: 3 spaces, at most 0 expected here
keylang/map.md:1:13: K001 dangling reference `b`; declare `planned` if this is an intention
```

### Опис вузла

Текстовий рядок (не елемент списку) з відступом ≥ 2 стає описом найглибшого відкритого елемента, у якого колонка вмісту (`2·глибина + 2`) ≤ відступу рядка. Порожні рядки між елементом і описом дозволені.

Шари оголошені поруч, тож у прикладі немає K001: опис лишається описом.

```keylang path=keylang/rules.md
- deny domain infrastructure
  Домен чистий: жодного I/O.
```

```keylang path=keylang/map.md
- layer domain
- layer infrastructure
```

- **Р6. Опис завжди належить вузлу, а не місцю.** Опис, записаний після дітей вузла, `fmt` переносить одразу під рядок вузла.

- Багаторядковий HTML-блок типів 1–5 — проза або опис, не структура. Маркери початку: `<!--`, `<?`, `<!` і далі ASCII-літера, `<![CDATA[`, а також `<pre`, `<script`, `<style`, `<textarea>` (без урахування регістру, далі пробіл, `>` або кінець рядка). Кінець: `-->`, `?>`, `>`, `]]>`, або рядок, що містить `</pre>`, `</script>`, `</style>` чи `</textarea>` (без урахування регістру; тег кінця не мусить збігатися з тегом початку, і перед `>` немає пробілу). Рядок початку має відступ 0–3 поза елементом, або під відкритим елементом відступ ≥ 2 і не далі ніж на 3 колонки за колонкою вмісту: тоді рядки блоку — описи цього елемента. Рядок усередині не стає ні заголовком, ні огорожею, ні елементом; порожні рядки входять у блок. Блок під елементом закінчується й тоді, коли елемент закінчується: на першому непорожньому рядку з відступом, меншим за колонку вмісту. Незакритий блок верхнього рівня триває до кінця файла. Однорядковий коментар (початок і кінець в одному рядку) блоку не відкриває — це звичайний текст.

```markdown
# rules

<!--
- deny a b
-->
```

Цей `deny` не перевіряється: для GitHub рядок схований у коментарі, і парсер теж бачить його як прозу.

## 4. Елемент списку

Граматика елемента — у [Додатку А](#додаток-а-граматика).

- Кома — окремий токен, тому `a,b` і `a , b` означають те саме, що `a, b` (канонічна форма).
- Незакрита лапка — K005, токен читається як слово. `[`, що не відкриває посилання, — звичайне слово (сигнатури на кшталт `(errs: [Span, string][])`); K005 «malformed link» буває лише там, де очікується ім'я-посилання (`fn [name](path#Lnn)`) або посилання на ID (`calls [a.b](x.md)`, див. «Посилання як лінк»).
- `<!-- … -->` у кінці рядка — коментар до елемента (`Node.comment`), у семантиці не бере участі (приклад — `compose` у design.md §5).

### Ідентифікатори

Граматика сегмента й ID — у [Додатку А](#додаток-а-граматика).

Літери — будь-які Unicode, а знак — комбінований знак (`\p{M}`), тож розкладене `café` (NFD, `e` + U+0301) — теж сегмент. Дефіс дозволено (`http-retry`, `order-store`), `$` — теж, щоб JS-імена `$save` і `_save` лишались різними ID.

Сегмент шляху файла чи теки стає сегментом ID так. Ім’я, яке вже є сегментом (`_shop_`, `my-dir`, `$save`), лишається як є. Якщо в імені немає дужок `(` `)` `[` `]`, усе інше, крім літер, знаків, цифр, `_`, `$` і `-`, стає `_`, а ім’я, що не починається з літери, `_` чи `$`, отримує `_` спереду: `cats.controller` → `cats_controller`, `1st` → `_1st`, `my file` → `my_file`. Якщо ім’я не є сегментом і містить такі дужки, кодування оборотне. Ціла форма маршруту Next стає читабельним префіксом: `(x)` — `$g-x` (група), `[x]` — `$p-x` (параметр), `[...x]` — `$all-x`, `[[...x]]` — `$opt-x`, де `x` — лише літери, знаки, цифри, `_` і `-`. Тож `(shop)` — `$g-shop`, `[shop]` — `$p-shop`, `(id)` — `$g-id`, `[id]` — `$p-id`, `[...slug]` — `$all-slug`, `[[...slug]]` — `$opt-slug`. Будь-яке інше ім’я з дужками (`(my shop)`, `(.)photo`) кодується побайтно: кожен байт UTF-8, який не є літерою, знаком, цифрою, `_` чи `-`, і також перший символ, який не може починати сегмент, записується як `$` і дві малі шістнадцяткові цифри. Сам `$` так само (`$24`), щоб його було видно як escape. `(` — `$28`, `)` — `$29`, `[` — `$5b`, `]` — `$5d`, `.` — `$2e`, пробіл — `$20`: `(my shop)` — `$28my$20shop$29`. Префікси `$g-`, `$p-`, `$opt-`, `$all-` не є таким escape, тож декодування однозначне. Ці сегменти різні й усі валідні; каталог `_shop_` лишається `_shop_`. Ім’я, яке вже дорівнює такому запису (тека `$g-shop`), є валідним сегментом і не перекодовується, тож ділить ID з `(shop)`. `$` у такому ID в shell беріть в одинарні лапки: `'main.app.$g-shop.page'`. Колишній запис `(shop)` як `_shop_` більше не називає цей модуль: посилання на старий ID — K001. Вкладеність тек layout і page ребра не додає.

### Прив'язка до коду

`[name](path#Lnn)` на місці імені оголошення: `name` стає іменем вузла, `path` і `nn` зберігаються в `Node.link` (підтримується і `#L12-L20`, береться початковий рядок). У M0 існування файлу не перевіряється. Спан імені вказує на текст усередині `[…]`.

Згенероване посилання рахується **від файла карти**, не від кореня репозиторію: для `keylang/map/domain.md` джерело `src/domain/order.ts` дає `../../src/domain/order.ts#L1`. Кожен сегмент шляху, крім `.` і `..`, кодується через `encodeURIComponent`, а `(` і `)` додатково стають `%28` і `%29`: `encodeURIComponent` їх залишає, але вони обривають Markdown-посилання. Приклад: `src/app/(shop)/page.ts` → `../../src/app/%28shop%29/page.ts#L1`. Пробіл і `#` кодуються як `%20` і `%23`. Парсер декодує шлях: `link.path` і `link.target` містять уже розкодований текст (`(shop)`, а не `%28shop%29`). Індекс зберігає POSIX-шлях від кореня репозиторію без кодування. Зіпсований escape лишається як написано.

Alias залежності не збігається з контекстним ключовим словом цієї позиції (`module`, `fn`, `type`, `event`, `calls`). Генератор додає числовий суфікс (`type` → `type2`), інакше рядок `- type main.type` читається як оголошення типу.

## 5. Ключові слова за позицією

Значення елемента залежить від **батька** (або виду секції на верхньому рівні). Перше слово є ключовим, тільки якщо воно дозволене в цій позиції; інакше спрацьовує правило «без ключового слова», а якщо його немає — K004 зі списком очікуваних слів.

## 7. Діагностики

Формат виводу `keylang check`: `file:line:col: CODE message`, рядок і колонка з 1, колонка в символах Unicode.

| Код | Рівень | Значення |
|---|---|---|
| K001 | error | висяче посилання |
| K002 | error | дубльований ID (або ім'я потоку) |
| K003 | error | структура: відступ, таб, порожній елемент |
| K004 | error | ключове слово невідоме або недозволене в цій позиції |
| K005 | error | неправильні аргументи відомого ключового слова, невалідне ID/посилання/лапки |
| K006 | warning | невідомий заголовок секції |
| K008 | warning | `then` з одного слова без крапки збігається з останнім сегментом оголошеного ID і лишається текстом |
| K101 | error | divergence: залежність проти порядку `layers` (вгору або з шару поза порядком) |
| K102 | error | divergence: залежність, заборонена `deny` |
| K103 | warning | absence: модуль недосяжний з жодного `entry` |

| K201 | error | `planned` розходиться з реалізованим символом: інший вид або сигнатура |
| K202 | warning | `planned` реалізовано з тим самим видом і сигнатурою — декларацію можна прибрати |
| K301 | error | цикл між фабриками `wire`: одна з них отримала б ще не побудовану залежність |
| K302 | error | ціль `wire`, залежність чи `compose`, яку згенерований файл не збудує: не fn, не статичний метод і не клас (модуль, шар, тип; для `compose` — не fn чи статичний метод), метод екземпляра, неекспортоване ім'я, код не TS/JS |

K005 у `check --format json` і в `diagnostics` `parse --json` має поле `reason`. Інші коди цього поля не мають. Human-вивід і `--format github` його не друкують.

| `reason` | Коли |
|---|---|
| `arguments` | бракує аргументів, зайві чи не ті; форма рядка; умова wiring не `env.NAME = value` |
| `id` | токен не є ID чи ім'ям, зокрема ім'я секції |
| `link` | зламаний лінк |
| `quote` | незакрита лапка |
| `layer` | не шар, шар двічі, суперечність порядків, шар і в порядку, і вкладений |
| `scope` | fn, type, event чи аліас залежності в `allow` / `deny` |

**Вердикти.** Кожен результат перевірки — `ok` (критерій підтверджено в заявленій області), `fail` (підтверджене порушення; діагностика рівня error або вердикт `fail`) або `unverified` (порушення немає, але доказів бракує; причина друкується). Діагностика рівня warning (K006, K008, K103, K106, K202) у `--format json` має вердикт `warning` і не валить перевірку. Вердиктом `fail` вона не буває, тож CLI, JSON, LSP і TUI рахують її однаково; критерій і область такої діагностики правила вона несе сама (K103 — `entry` і модуль, K106 — текст `allow` і перетин областей). У повідомленнях: **divergence** — підтверджена невідповідність, **absence** — відсутність обов'язкової сутності за достатніх доказів, **convergence** — підтверджений збіг (повідомлення `ok`-вердикту правила, наприклад `convergence: no edge from …`); невизначеність ніколи не перейменовується на `ok`. Менше інформації (`exclude`, нерозв'язаний імпорт, режим `shape` — прапорець `--static` або поле `check.static`) переводить `ok` або `fail` лише в `unverified`, ніколи між `ok` і `fail` (предикати `hole` і `area` в «Семантика правил»). K103 остаточний нарівні з `ok` і `fail`: він не стає іншим вердиктом. Задокументований виняток один: маніфест Python не читається, тож пакет, відомий лише з імпорту, після `exclude` цього імпорту може дати K001. `warning` у JSON — не четвертий вердикт, а рівень діагностики: результат не валить перевірку. Кожен вердикт має `specHash` — SHA-256 канонічного тексту рядка правила чи потоку: усі результати одного рядка (`ok`, `unverified`, K102, K104, K105) ділять цей хеш. Результат із кількох рядків хешує їхні тексти в порядку (файл, рядок), з'єднані `\n`: K101 — рядки `layers` зв'язного порядку; K103 і `unverified` досяжності — усі рядки `entry`; «no snapshot» — усі рядки правил. Один рядок дає той самий хеш, що й текст цього рядка. Посилання, записане лінком, хеш не змінює. Діагностика без вердикту (K001, K003, K201…) і далі хешує код і повідомлення. K102 називає і ребро в коді, і правило `deny` з його файлом і рядком.

Команди CLI, MCP, LSP, TUI і web описано в [tools.md](tools.md#commands).

**Правила (K101–K105)** рахуються на ребрах актуального знімка. `keylang check` перебудовує аналіз у пам'яті і не записує карту чи `.keylang/index.json`. Згенеровані файли `map/` замінюються картою, відрендереною з цього знімка, тож ID у flows і rules резолвляться за поточним кодом, навіть якщо закомічена карта застаріла. Корінь репозиторію — найближчий вгору каталог із `keylang.json`; шлях до специфікацій можна записати як завгодно (`keylang`, `./keylang`, абсолютний, `.` зсередини). Діагностика вказує на файл і рядок коду, де є ребро. Якщо в каталозі немає коду (examples, слайд), правила дають `unverified` з причиною `no snapshot`, а резолвінг ID лишається. Підсумок у stderr: `N fail, M unverified, K ok`. Коди виходу: `0` — блокувальних знахідок немає; `1` — порушення, а з `--strict` також будь-який `unverified`; `2` — некоректний виклик або I/O.

Формати виводу `check` і `--explain-edge` описано в [tools.md](tools.md#formats).

Уточнення:

- **Імена шарів.** Ім'я шару в `keylang.json` — один сегмент ID. `external`, `unassigned` (синтетичні шари keylang) і ключові слова верху карти (`layer`, `layers`, `allow`, `deny`, `entry`, `module`, `no-cycles`: карта пише шар рядком `- <name>`) зарезервовано — такий шар є помилкою конфігурації з кодом 2, що називає файл і поле `layers.<name>`. `init` таких імен не вгадує: тека `src/external/` стає шаром `external_`, а друга тека, що санітизується в уже зайняте ім'я (`src/2fa/` і `src/_2fa/` — обидві `_2fa`), — `_2fa_2`; про кожне перейменування — примітка в stderr. `dir` нормалізується: `./keylang/` — це `keylang`.
- `layers a < b < c`: `a` найнижчий; залежність може йти лише вниз (`c` → `a` можна, `a` → `c` — K101). Вкладені під `layers` шари, а також `external` і `unassigned`, — без порядку: залежність *у* них вільна, якщо не заборонена `deny`. Усі рядки `layers` разом — один частковий порядок: `a < b` і `b < c` ставлять `c` над `a` (`a` → `c` — K101), а `a < b` і `c < d` нічого не кажуть про `a` і `d`. K005 (і рядок не перевіряється): шар двічі в одному рядку, ID з крапкою замість шару, рядок, що суперечить попереднім (`b < a` після `a < b`), шар, водночас впорядкований і вкладений. Кожен рядок `layers` має вердикт: `ok`, коли жодна залежність не порушує порядку його шарів і в області немає прогалини рівня залежностей; з прогалиною — `unverified` з її назвою; порушення — K101. Область — модулі шарів усієї зв'язної компоненти цього рядка (рядки `layers`, з'єднані спільними шарами) і модулі шарів поза будь-яким порядком (вкладені, `external`, `unassigned`). Прогалина `unassigned-file` сама область не робить `unverified`: ребра того файла відомі; інша прогалина в ньому — робить. Залежність угору, яку вирішив `deny`, не дає рядку ні `ok`, ні другої K101 (лишається одна K102). Залежність угору, яку дозволив `allow`, лишає `ok`, і доказ називає цей `allow`. Залежність униз, заборонена `deny`, лишає `ok` із доказом «points down». Предикати `above` і `k101` — у «Семантика правил».
- `allow`/`deny` приймають шари, модулі й їхні префікси; клас — модуль свого файла, тож його ID теж область: ребро до класу чи з його методу — доказ. ID fn, типу, події чи аліаса залежності (зокрема `planned fn`) — K005 з назвою модуля, бо ребра правил — між модулями, і таке правило нічого б не перевіряло. Правила впорядковані частково. Правило конкретніше за інше, коли жодна його область не ширша за відповідну область того й хоча б одна вужча (`app.purchase` — глибина 2 у сегментах, не довжина рядка). Рівні області вирішує `deny`: два `deny` з тією самою сумою глибин дають кожен свою K102. Непорівнювані — ті, де одне вужче за джерелом, а інше за ціллю. У форматі 1 таку пару вирішує лише сума глибин, і за рівності перемагає `deny`. Тож `deny app.x domain` (2 + 1) і `allow app domain.storefront` (1 + 2) непорівнювані з рівною сумою: перемагає `deny`, K106 немає. `allow app.x.y domain` (3 + 1) і `deny app domain.storefront` (1 + 2) теж непорівнювані: у форматі 1 перемагає `allow`, і K106 стоїть на рядку `allow`, доки немає правила на перетині `app.x.y domain.storefront`. У форматі 2 серед правил, яких ніхто не домінує, будь-який `deny` перемагає (deny-overrides): та сама пара лишає K106, але ребро забороняє `deny`. «more specific rules» пишеться лише коли ребро вирішило порівнюване вужче правило; непорівнюваний `allow` у доказі називається сам. `allow` знімає K101 для своєї пари. Одна залежність модуля від модуля — одна K102 на правило, скільки б ребер її не показували (імпорт, виклик, тип-клас). Кожне `deny` має власний вердикт: підтверджене заборонене ребро — `fail`; інакше `unverified`, якщо в області є прогалина рівня залежностей (нерозв'язаний чи обчислюваний імпорт, синтаксична помилка, виключений файл, тека, яку не вдалося прочитати, `eval`), і `ok` без неї. Дірка всередині однієї декларації (`unsupported` із `source` — ID fn чи класу, як Python-декоратор, що може підмінити fn) змінює, який код виконує виклик, а не що імпортує модуль, тож прогалиною рівня залежностей не є. Область без жодного модуля — `unverified` «planned», коли вона існує лише як `planned`, і `ok` «no module … yet» інакше (шар без модулів). Виклик через локальне значення залежності між модулями не створює: без імпорту код іншого модуля недосяжний. Предикати `within`, `score`, `dominates`, `winner`, `k102`, `k106` — у «Семантика правил».
- `entry`: досяжність іде лише ребрами `import` / `call` / `type` / `re-export` знімка, зокрема через `index.ts`, що реекспортує сусідів, і через модуль, названий відносно модуля: `new URL("./worker.ts", import.meta.url)` (як у `new Worker(…)`) та `register(spec, import.meta.url | { parentURL: import.meta.url })` — ребро `import`, коли специфікатор — рядок, тернарник рядків або `const`, прив'язаний до такого (`URL` — лише відносний шлях із розширенням JS/TS). Пункт `entry` з ID модуля, якого немає у знімку, — K001, тож видалений worker, записаний в `entry`, помітний; його нерозв'язаний `new URL(…)` — ще й прогалина `unresolved import` у модулі, що його завантажує. Ієрархія ID не робить сусідів досяжними, а тека-модуль без власного коду не звітується. Клас — частина модуля свого файла: досяжний файл робить досяжними його класи, і невикористаний експортований клас K103 не отримує. K103 вказує на файл модуля. Коли досяжні всі модулі, кожен рядок `entry` має вердикт `ok`. Прогалина рівня залежностей у досяжному модулі (нерозв'язаний імпорт тощо) перетворює недосяжність на `unverified` із назвою цієї прогалини, а не на K103. Модулі шарів без порядку не перевіряються. `entry` із шаром чи префіксом (`- domain`) — точки старту всі модулі під ним. Предикати `reach` і `k103` — у «Семантика правил».
- `exports` порівнюється з таблицею публічних експортів самого модуля знімка, не з fn без `<!-- internal -->` і не з таблицями його підмодулів: `purchase/buy.ts` поруч із `purchase.ts` — окремий модуль зі своїми експортами. Модуль правила, що існує лише як `planned`, — `unverified` «planned»; відомий ID, що не є модулем знімка (шар, fn), — `unverified`; невідомий — лише K001. Імена в `exports` — публічні імена модуля, а не ID карти, тож K001 вони не дають. `export { a as b }` порівнюється за `b`, `export default …` (включно з `export default function main`, `export default 3`), TypeScript `export = x` і CommonJS `module.exports = x` — за `default`, `export namespace N {}` і `export * as N from` — за `N`, `export * from "./x"` розкривається до імен `x` без `default` (транзитивно й через цикли `export *`; ім'я, яке два джерела `export *` дають різними оголошеннями, ESM не експортує). Зайве ім'я — K104 із видом і формою (`alias`, `default`, `namespace`, звідки re-export); заявлене відсутнє ім'я — absence. `export *` із модуля з невідомим вмістом (зовнішній пакет, нерозв'язаний або виключений файл, файл із синтаксичною помилкою) робить правило `unverified`, а не absence; так само непрозорий модуль правила (файл з `exclude`, помилка розбору) — заявлене відсутнє ім'я там `unverified`.
- Цикли — це SCC графа `import` / `re-export`. `no-cycles` під модулем спрацьовує, якщо модуль або його підмодуль входить у SCC; маршрут проходить через нього. Файл, що імпортує сам себе, — self-loop і теж цикл. Одна K105 на кожну SCC. Без циклу серед відомих імпортів, але з прогалиною залежностей в області — `unverified`, не `ok`. Для `no-cycles` під модулем область — цей модуль, його підмодулі й модулі, досяжні з них імпортом або реекспортом; `unassigned-file` там прогалиною не є. Глобальний `no-cycles` і далі рахує `unassigned-file`. Предикати `scc`, `k105`, `hole` і `area` — у «Семантика правил».
- `planned fn|module|type|event <id> [signature]` — намір (кандидат до v1): рядок верхнього рівня секції flow, сигнатура — довільний текст до кінця рядка. Посилання на нього не є K001: `ID` і `static` — `unverified` «planned», trace його не вимагає, ребер у знімок він не додає. Повторна декларація того самого ID — K002 (і в каталозі без коду). Коли в коді з'являється символ із цим ID, крок перевіряється як звичайний код, а декларація дає K202 (вид і сигнатура збігаються; сигнатури порівнюються без пробілів, `->` = `→`) або K201 (інший вид чи сигнатура). Виду `event` у знімку немає, тож fn, тип чи модуль з ID запланованої події — K201.

`keylang lsp` віддає ті самі коди, позиції й вердикти, що й `check`.

### Семантика правил

Нормативна модель поточної перевірки графа. Факти знімка: `module(M)` — модуль, клас включно; `unit(U)` — файл-модуль (не клас і не тека без власного коду); `edge(From, To)` — розв'язане ребро `import`, `call`, `type` або `re-export` між модулями різних файлів. Немає ребер `via: injected` і ребер усередині одного файла. Для `allow`/`deny` кінець ребра — найближчий модуль. Self-import файла — self-loop лише для циклів.

```text
within(M, A) :- M = A; M починається з A + ".".
score(R, From, To) = max (depth(A) + depth(B))
  для правила R «effect A B…», де within(From, A) і within(To, B).
depth(Id) = кількість сегментів.
dominates(R1, R2) :- джерело R1 у within джерела R2, збігла ціль R1 у within цілі R2,
  і хоча б одна область вужча.
incomparable(R1, R2) :- одне вужче за джерелом, інше — за ціллю.
winner(E) у форматі 1 = правила з найбільшим score на ребрі E;
  за рівності — кожен deny, а allow лише коли deny з тим самим score немає.
winner(E) у форматі 2 = правила, яких ніхто не dominates;
  якщо серед них є deny — лише ці deny (deny-overrides), інакше ці allow.
beaten(R, E) :- R — deny і R не входить у winner(E).
k102(R, U1, U2) :- R входить у winner, R — deny, ребро між файлами-модулями U1 і U2.
  Одна K102 на правило і пару файлів. Вердикт deny: fail, якщо є k102;
  інакше unverified, коли hole в area; інакше ok. «more specific rules» — лише коли
  переможець порівнюваний і вужчий. Непорівнюваний allow, що вирішив ребро сумою
  глибин, називається в доказі сам.
k106(Allow, Deny) :- пара incomparable хоча б на одній парі цілей, score(Allow) > score(Deny),
  і жодне правило не має областей рівно на перетині (вужче джерело і вужча ціль).
  Одна на пару рядків, на рядку allow, незалежно від знімка. Формат 1 каже, що переміг allow;
  формат 2 — що переміг deny. Правило на перетині прибирає K106.

above(L, H) — транзитивне замикання сусідніх пар усіх рядків layers (один порядок).
k101(U1, U2) :- ребро не вирішив winner, і або above(шар U1, шар U2),
  або шар U1 поза порядком, а шар U2 впорядкований і не unordered.
  Рядок layers без ok, якщо його шар — кінець такого ребра або ребра вгору, яке виграв deny.
  Інакше ok, а з hole в area — unverified. Дозвіл allow лишає ok і називає цей allow.

reach(U) — файли-модулі, досяжні з точок entry ребрами edge
  (шар або префікс, який сам не модуль, сіє кожен unit під ним).
k103(U) :- unit U має власний код, не reach, шар не unordered.
  hole серед reach перетворює такий U на unverified, не на K103.
  Рядок entry має ok, коли кожного такого unit досягнуто.

scc — сильні компоненти графа import / re-export плюс self-loop.
  Циклічна компонента має більше одного модуля або self-loop.
k105(R, C) :- одна на кожну таку C, що містить модуль правила чи його підмодуль
  (глобальне no-cycles — кожну C). ok, коли таких C немає.

hole(U) :- запис покриття unresolved-import, parse-error, unsupported,
  unassigned-file або skipped-file у U чи під ним, крім
  «unsupported construct `computed call`» і unsupported всередині однієї декларації.
  unassigned-file не є hole для layers і для no-cycles під модулем.
  Кілька hole — перша за відсортованим id модуля.
area(deny, U) :- U в області джерела.
area(layers, U) :- шар U в зв'язній компоненті рядка або поза будь-яким порядком.
area(no-cycles під M, U) :- U є M, підмодуль M, або досяжний з них import / re-export.
area(no-cycles глобальне, U) :- кожен unit.
area(entry, U) :- reach(U).
unverified(R) :- not fail(R), area(R, U), hole(U).
```

Приклад K106. Файла `keylang.json` немає, тож редакція 2: пара непорівнювана, перемагає `deny`, попередження стоїть на рядку `allow`.

```

```diagnostics

`external.<pkg>`, оголошений у `package.json` або `Cargo.toml`, не дає K001 і не додає вузол у знімок, доки якийсь файл його не імпортує. `exports` ця модель не описує. Сегмент ID береться з імені пакета: `@scope/pkg` → `scope-pkg`, `lodash.get` → `lodash_get`. Коли два імені дають один сегмент (`@scope/pkg` і `scope-pkg`), суфікси `-2`, `-3`… рахуються над оголошеними й імпортованими іменами разом: ім'я, що дорівнює сегменту, лишається без суфікса, інші отримують суфікс у порядку імен, і про кожне `map` попереджає. Тож ID пакета не залежить від того, який із двох пакетів код імпортує (ADR 0010).

### Flows: докази кроку

`step` задає **вкладеність** щодо батьківського кроку; сусідні кроки — **послідовність**. Для кроку верхнього рівня (поруч із `trigger` чи під ним) батьком є `trigger`. Кожен вид доказу друкується окремим рядком `file:line:col: <доказ> <verdict> <id>: <причина>`, а в `--format json` — окремим результатом із `criterion` (`ID` / `static` / `tests` / `trace`), `area` (ID кроку або текст твердження), `verdict`, `evidence` і `provenance` (`syntactic`, `test-report`, `trace`; для trace також `runId`, `testId`).

| Доказ | ok | unverified | fail |
|---|---|---|---|
| `ID` | символ є у свіжому знімку | `planned`, член `opaque`-модуля | K001 — відсутній у `complete`-модулі (`static` тоді не друкується) |
| `static` | шлях resolved-викликів від батька, жоден з яких не сидить у closure (сусідні кроки шляху не потребують; рекурсія — шлях); з `--static=behavior` (типово) — також через хук: «through the default of the hook `g`», «`g` injected at file:line:col»; крок на модуль `external.<pkg>` — resolved-імпорт цього пакета з модуля fn-батька («imported by») | шлях є, але проходить через тіло, що може не виконатися: fn під декоратором чи атрибутом, якого keylang не знає (`@replace` може повернути іншу функцію; у coverage — `@…` чи `#[…]` з `source` цієї fn або перед нею), або код модуля, що не розбирається («may not run its own body», «is in a module that does not parse» з позицією); шляху немає, але його могла б дати конструкція, яку keylang не відстежує (нижче): з нею та позицією; шляху немає, а досяжний код є в модулі, що не розбирається; батько чи крок — не функція (крім `external.<pkg>`, де немає імпорту з модуля батька: «no import of»); `planned`; прямий нащадок нереалізованого `planned`-кроку — «parent `<id>` is planned, not implemented» (глибші кроки рахуються від реалізованого батька) | `absence: no call path …` — крок і його виклики досяжні лише за назвою, і жоден виклик із досяжного коду не може їх назвати |
| `tests` | однозначний тест пройшов у звіті поточного знімка | звіту немає, тест не знайдено, неоднозначний (перелік кандидатів), пропущений, звіт іншого знімка або без `snapshotId`; твердження без `test` («no test evidence»; для кількісних чи заперечних — «needs a separate predicate or test») | тест провалився |
| `trace` | крок спостережено в завершеному запуску тесту з вкладенням і підтвердженим порядком | trace іншого знімка чи без нього; неповний запуск, навіть коли крок спостережено (`complete: false` у будь-якій події `run` чи її немає, `dropped > 0` або не вказано, відкриті spans; для відсутнього кроку — ще й символ не інструментовано); різні годинники без `links` (зокрема `end` попереднього на іншому годиннику); паралельні sibling-и; асинхронний крок без `link`; гілка `when` не виконувалась; span кроку є лише коренем іншого дерева викликів і не почався раніше за образ батька на тому самому годиннику («observed outside … in another call tree»); другий і наступні `trigger` і вузли під ними («a flow is matched from its first trigger only»); крок під `planned`-кроком («parent step … is planned») | обов'язковий крок відсутній у завершеному й інструментованому запуску: символу немає в жодному span, усі його spans у тому самому дереві викликів поза образом батька, або span в іншому дереві почався раніше за образ батька на тому самому годиннику; крок почався раніше за попереднього сусіда; образ кроку лежить у піддереві образу попереднього сусіда («nested in …, not after it»), синхронно і з `links` |

#### Семантика

Trace-доказ — впорядковане ін'єктивне включення дерева кроків потоку в дерево spans одного запуску `(runId, testId)`. Kilpeläinen і Mannila (1995) розв'язують булеве включення дерев; keylang бере максимальне часткове включення і дає вердикт кожному кроку. Тригер — корінь, батько кроку верхнього рівня — тригер. Образ кроку — нащадок образу батька на будь-якій глибині, тож зайві виклики дозволені. Ін'єктивність: один span є образом не більше одного вузла. Рекурсивний крок потребує власного вкладеного span (один span — `trace fail` «missing step», вкладений — `trace ok`; два рівні специфікації і два spans — `ok` першому кроку і `fail` найглибшому). Два однакові сусідні кроки потребують двох викликів: один span дає одному `trace ok`, другому `missing step`, а `static ok` — обом, бо static не рахує кратність.

Порядок сусідів причинний: `end` попереднього раніше за `start` наступного на тому самому `clockId`, або `links` на попереднього, коли span не лежить у його піддереві. Сортування `ts` порядок не доводить. Образ наступного сусіда в піддереві попереднього — `fail` «nested in `<попередній>`, not after it», і для синхронного вкладення, і для async-продовження з `links`. У неповному запуску цей `fail` стає `unverified`. Перекриття без відношення предок — нащадок лишається `unverified` «parallel». Різні годинники без `links` — `unverified`; `links` між ними — `ok`.

`when` прозорий: кроки гілки вкладаються під батька `when`, порядок усередині гілки зберігається, а відносно сусідів `when` — ні. Гілка, чий перший крок спостережено, має «branch exercised», навіть якщо цей крок стався перед сусіднім кроком поза гілкою.

Серед максимальних часткових включень перемагає те, де більше `ok`, потім менше `fail`, потім раніші spans. Trace `save, create, save` під `buy` дає `trace ok` обом крокам `create` і `save` (обрано другий `save`). Trace, де `save` лежить під `buy`, а `create` — під `later`, дає обом «missing step». Trace `buy`, `later`, `buy{create}`, `later{save}` дає всім крокам `trace ok` і `static ok`.

`fail` «missing step» лишається лише в трьох випадках завершеного інструментованого запуску: символу немає в жодному span; усі його spans у тому самому дереві викликів, що й образ батька, але поза ним; spans в іншому дереві почалися раніше за образ батька на тому самому годиннику. Span лише як корінь іншого дерева, що не почався раніше, — `unverified` «observed outside `<батько>` in another call tree (root `<корінь>`): nesting unknown». Інший `clockId` цього не вирішує: Rust і Python мають один годинник на процес, тож span іншого потоку — корінь, а не інший годинник. `links` такого кореня на батька вкладення не доводять.

Static-доказ — існування шляху у графі викликів знімка від батька, без порядку й кратності.

Перевірюваний сценарій має один `trigger`: trace зіставляє потік від першого. Другий і наступні `trigger` і вузли під ними — `trace unverified` «a flow is matched from its first trigger only». Кожен крок під нереалізованим `planned`-кроком, на будь-якій глибині, — `trace unverified` «parent step `<id>` is planned», де `<id>` — найближчий такий предок. Static прямої дитини — «parent `<id>` is planned, not implemented»; глибші кроки рахуються від реалізованого батька. Без `check.trace` цих рядків немає. `check --strict` рахує такий `unverified`.

**Static без шляху.** Коли resolved-шляху немає, пошук триває через виклики з кількома можливими цілями: виклик із невідомим отримувачем (`x.feed()`, `cb()`) може бути будь-якою fn тієї ж назви, розв'язаний виклик методу — перевизначенням тієї ж назви, неоднозначний — будь-яким кандидатом, ребро хука в режимі `shape` — своєю ціллю, а виклик у closure (`return () => hit()`, колбек `items.forEach(() => …)`) — своєю ціллю лише тоді, коли цю функцію-значення хтось викличе: маршрут, що доходить до кроку тільки так, — `unverified` «reached only through a closure of X». Знайдений так маршрут дає `unverified` із першим таким викликом на ньому (найближчим до батька; виклики з назвою кроку перевіряються раніше) і лічильником `(and N more unresolved calls in reachable code)`. Інакше `unverified` лишається, якщо fn на якомусь маршруті до кроку «тікає»: прочитана як значення (`later(save)`, `{ save }`, `obj.save` без виклику, `extends A` для конструктора `A`; за назвою, в усьому репозиторії), accessor, неявний метод (`then`, `next`, `return`, `throw`, `toString`, `valueOf`, `toJSON`), викликана з closure; викликана з коду поза оголошеннями — верхнього рівня модуля (він виконується під час завантаження, зокрема через `import()` чи `new Worker(new URL(…))`), методу об'єктного літерала, функції-значення, обгорнутої викликом (`export const load = cache(() => step())`), — «is called from module-level code» / «from a function value outside declarations» (виклик із невідомим отримувачем там робить такою кожну fn тієї ж назви); метод класу, чий базовий клас keylang не прочитав (пакет, глобальний, нерозв'язаний: `extends Readable`, `extends React.Component`, і їхні нащадки), — «may be called by the base class»; синтезований `Class.static` (виконується під час завантаження). Так само `eval`, `new Function`, `obj[k]()` чи `import(expr)` у коді, до якого веде доведений або можливий маршрут, обчислюваний член класу, `namespace` чи інша непрочитана конструкція, що згадує таку fn (ім'я — цілим ідентифікатором, зокрема з `$` чи не-ASCII літерами), і непрочитаний (`opaque`) модуль при будь-якій дірці. Повідомлення називає причину з позицією; нерозв'язаний виклик із досяжного коду воно називає лише тоді, коли той виклик є в fn, що передала значення далі, або в коді, який вона викликає. Лише коли нічого з цього немає — `fail`: він має бути надійним, тож за сумніву вердикт — `unverified`.

**Хуки (`--static`).** Хук — виклик через локальне значення, параметр чи поле з типовим значенням поруч: `const g = p.x ?? f` (або `||`), `const { x: g = f } = p`, параметр `g = f` чи `{ g = f }`, поле `this.g = options.g ?? f` у конструкторі (або параметр-властивість `private readonly g = f`). Виклик `g()` лишається діркою в `coverage` («call through the hook `g` (default `f`)») і дає ребро `call` з `via: "default"` до `f`. Якщо `p` — параметр самої функції (для поля — параметр конструктора), розв'язаний виклик, що передає за тим самим аргументом і властивістю функцію-значення (`analyze({ generate: worker.generate })`, `new App({ analyzer })`, `run(save)`), дає ребро `via: "injected"` з `site` — позицією того виклику; контекст виклику не розрізняється. `--static=behavior` (типово) доводить шлях і цими ребрами, `--static=shape` — лише записаними викликами; `--static` з іншим значенням — код 2. Ребро `default` карта друкує в `calls` і правила бачать (модуль і так імпортує `f`); `injected` — ні: це залежність того, хто передає значення. Режим хука типового значення задає `check.static` у `keylang.json` (`"behavior"` або `"shape"`). Пріоритет: прапорець `--static`, потім це поле, потім `behavior`. У режимі `shape` доказ називає джерело: `set by --static` або `set by keylang.json check.static`. Невалідне значення дає код 2 і називає файл і поле `check.static` для кожної команди, що читає конфіг. Те саме значення читають `check` (зокрема `--changed`), `feature`, `hook stop`, LSP, MCP, TUI і `keylang web`. `init` і `draft map` поле не пишуть. Типове `behavior` можна змінити лише з новою версією формату.

`tests` друкується на твердженні (`invariant`, `when`, `then`, `reads`, `emits`), до якого прив'язаний `test`. `trace` для `when` — «branch exercised» або «branch not exercised»; кроки невиконаної гілки в цьому тесті не обов'язкові. Вердикт кроку за кількома тестами: `fail`, якщо хоч один тест його порушив; інакше `ok`, якщо хоч один підтвердив. Без `check.tests` / `check.trace` відповідні докази не друкуються (зокрема «no test evidence» для твердження без `test`): непотрібний вид доказу не входить до агрегації й до `--strict`.

### Звіт тестів (`check.tests`)

`check.tests` у `keylang.json` — шлях (має існувати, інакше код 2) або глоб (може ще нічого не знаходити: тоді «no report»). Формат визначається за вмістом:

- **JSON keylang, схема 1** — `{"schemaVersion": 1, "snapshotId", "runId", "tests": [{"file", "suite"?, "name", "status": "pass"|"fail"|"skip"}]}`. Пише репортер `node:test` з пакета: `node --test --test-reporter=spec --test-reporter-destination=stdout --test-reporter=keylang/node-test-reporter --test-reporter-destination=stdout` (у цьому репозиторії — `./src/adapters/node-test.ts`, див. `npm test`). Він рахує `snapshotId` поточного коду і пише `.keylang/reports/node-test.json` (або `KEYLANG_TEST_REPORT`); suite — вкладені `describe`/`test`, через ` > `.
- **JUnit XML** — `<testcase file classname name>` з `<failure>` / `<error>` / `<skipped>` у `<testsuite>` (вкладених чи під `<testsuites>`); читається як XML: лапки обох видів, сутності, коментарі, CDATA. Зв'язок зі знімком — `<property name="keylang.snapshotId" value="…"/>` у `<properties>` самого testcase або найближчого suite навколо нього (так само `keylang.runId`): кожен suite злитого звіту має власний знімок. Без нього testcase не підтверджує поточний код. Некоректний XML — код 2 з `file:line`.

`test <file> "<name>"` зіставляється за файлом і назвою; `"Suite > name"` уточнює suite. Некоректний звіт — код 2 з назвою файла й поля.

### Trace (`check.trace`), JSONL схеми 1

`check.trace` — шлях або глоб до файлів JSONL. Кожен рядок — подія одного запуску тесту `(runId, testId)` для потоку `flow`. Файл запуск не розділяє: події процесів одного тесту можуть лежати в різних файлах, і це той самий запуск:

```jsonl
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s1","parentSpanId":null,"symbolId":"cli.cli.main","clockId":"pid-7","seq":1,"ts":12.5}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s2","parentSpanId":"s1","symbolId":"cli.cli.run","clockId":"pid-7","seq":2,"ts":12.6}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s2","outcome":"ok","clockId":"pid-7","seq":3,"ts":40.1}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s1","outcome":"ok","clockId":"pid-7","seq":4,"ts":40.2}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"run","complete":true,"dropped":0,"instrumented":["cli.cli.main","cli.cli.run"],"open":[]}
```

- `start`: `spanId` (унікальний на виклик — повтори й рекурсія мають різні), `parentSpanId`, `symbolId` (ID знімка), `clockId` + `seq` (порядок подій одного годинника), `ts`, необов'язкові `links` (каузальні зв'язки з іншими spans); `end`: `spanId`, `outcome`; `run` — метадані завершення: `complete` (boolean), `dropped` (невід'ємне ціле), `instrumented` (ID символів), `open` (ID spans). Кожен процес пише власну подію `run`: запуск завершений, лише коли завершені всі, `dropped` сумується, `open` об'єднується, а інструментованим вважається символ, який назвали всі. Без `dropped` кількість втрачених подій невідома — запуск неповний.
- Кроки зіставляються впорядкованим ін'єктивним включенням (підрозділ «Семантика» вище) у межах одного тесту: зайві виклики дозволені, одна подія задовольняє один крок. Кожен span тригера чи кроку — кандидат: тест може викликати його кілька разів (спершу з раннім `return`), і перемагає вибір spans, що спостерігає найбільше кроків (за рівності — з меншою кількістю `fail`, потім раніший). `missing step` означає, що символу немає ніде, усі його spans у тому самому дереві поза батьком, або span іншого дерева почався раніше на тому самому годиннику. Порядок сусідів підтверджує `end` попереднього раніше за `start` наступного на тому самому `clockId` або `links` на попереднього, якщо span не в його піддереві; вкладений у попереднього сусіда span — `fail` «nested in …, not after it». Сортування `ts` порядок не доводить. Дочірній span, що почався після завершення батька, підтверджує вкладення лише з `link` на батька.
- Невідома версія, некоректний рядок чи поле — код 2 з `file:line` і назвою поля.

Адаптери trace і `trace-plan` описано в [tools.md](tools.md#trace).

### Дорожня карта, не поточна поведінка

### Wiring (`# wiring`, `keylang wire`)

Контракт — [ADR 0003](adr/0003-wiring-lifecycle.md) (прийнято). `- wire <id>` — фабрика: fn (виклик з об'єктом іменованих залежностей) або клас (`new` з тим самим об'єктом). Дочірні `- <name> <id>` — залежність `name`, яку будує фабрика `<id>`. ID без власного `wire` — лист, він створюється без аргументів. Під залежністю `- when env.NAME = value → <id>` обирає іншу реалізацію, коли змінна середовища має саме це значення: `value` — одне слово, як його записано до `→` (кома — частина значення: `env.DB = a,b` порівнюється з `a,b`). Кілька `when` перевіряються в порядку запису, без збігу діє рядок залежності. `- compose <id>` обгортає значення fn одного аргументу; кілька `compose` застосовуються в порядку запису, перший найближчий до значення.

`check` перевіряє розділ разом з іншими специфікаціями. Невідомий ID — K001, повторний `wire` того самого ID — K002, як і дві залежності з одним ім'ям під одним `wire` (об'єкт аргументів мав би ключ двічі). Умова не у формі `env.NAME = value` — K005. Цикл між фабриками (через залежності та гілки `when`) — K301 з повним шляхом. K302 — те, що згенерований файл не може імпортувати чи викликати: модуль, шар чи тип як фабрика або залежність; `compose` не з fn (модуль, тип, клас); метод екземпляра класу (його нема на чому викликати). Статичний метод (`static` у знімку) — фабрика чи `compose`, що викликається на імпортованому класі: `Pool.open(deps)`; клас імпортується за своїм рядком експорту, default-клас удруге — як `default as`; ім'я, якого модуль не експортує; fn Python чи Rust (`wire` генерує TypeScript). Клас у знімку — вузол-модуль, оголошений у файлі свого батьківського модуля. Залежність (зокрема `when` і `compose`), яку забороняє `deny` між ID фабрики й залежності, — K102 з текстом правила та його `файл:рядок`.

Команда `keylang wire` описана в [tools.md](tools.md#wire).

`feature`, `baseline`, `agents`, `check --changed` і `hook stop` описано в [tools.md](tools.md#agents).

Інтеграція, якої ще немає в коді, — `planned module external.<pkg>` і крок потоку до цього модуля. Нового виду вузла немає. Доки пакет ніхто не імпортує, ID і static лишаються `unverified` «planned». Коли модуль кроку-батька імпортує пакет, `planned` дає K202, а static — `ok` («imported by»). Імпорт з іншого модуля K202 може дати (вузол пакета вже є), але static цього кроку лишається не `ok`, і `feature` має прогалину `static`.

### Версії формату

Поле `format` у `keylang.json` — редакція мови, за якою keylang читає специфікації. Назва збігається з прапорцем `check --format`, але той задає вигляд звіту (`human`, `json`, `sarif`, `github`), а не редакцію мови.

| Версія | Значення |
|---|---|
| 1 | Мова цього документа, v0.2. До заморожування v1 (design.md, етап M3, тікет 40 у `.scratch/design-v0.2/`) текст ще змінний. Непорівнювані `allow` і `deny` вирішує сума глибин; за рівності — `deny`. |
| 2 | Поточна редакція. Серед правил, яких ніхто не домінує, перемагає `deny` (deny-overrides). Щоб лишити переможцем `allow` із більшою сумою глибин, додайте правило на перетині: `allow` або `deny` з вужчим джерелом і вужчою ціллю. |

Поле відсутнє — редакція 1, тож уже написаний `keylang.json` не змінює значення після оновлення пакета. Файла `keylang.json` немає — поточна редакція (зараз 2): так читаються `examples/`, `validate_spec` у теці без конфігу і вгаданий конфіг. Ціле, більше за відому редакцію, — код 2 з назвою файла й поля `format` і порадою оновити keylang. Рядок, `null`, нуль, від'ємне чи дробове число — теж код 2: поле має бути додатним цілим. Відмовляє кожна команда, що читає конфіг, включно з `fmt` і `parse` (вони читають лише це поле).

Несумісна зміна значення вже написаних текстів потребує нової редакції. Редакція 1 підтримується до наступної мажорної версії пакета: прибрати її можна лише мажорним релізом. `fmt` мовчки не мігрує: не змінює поле `format` і не переписує тексти під іншу редакцію. Команди міграції немає; автор змінює текст сам. `init` на новому репозиторії і `draft map` без файла пишуть поточну редакцію першим ключем. Наявний `keylang.json` `init` не переписує.

## 8. Канонічна форма (`keylang fmt`)

`fmt` рендерить файл з IR, тож `fmt(fmt(x)) == fmt(x)`:

- маркер генерації, заголовки, списки, абзаци прози й блоки коду розділені рівно одним порожнім рядком; усередині списку порожніх рядків немає;
- маркер списку `-`, відступ `2·глибина`, токени елемента через один пробіл, кома — `a, b`, коментар через один пробіл;
- заголовок `# kind name`, коментар заголовка — через один пробіл (`# <!-- c -->`);
- опис — під рядком вузла з відступом `2·глибина + 2`, текст без кінцевих пробілів;
- проза й код — дослівно (без кінцевих пробілів), крім відступу огорожі: з відкривного й закривного рядка знімається весь відступ, з кожного рядка вмісту — стільки пробілів, скільки мала відкривна огорожа, але не більше, ніж їх є в рядку. Таб у відступі огорожі лишає блок як є. Порожні рядки всередині HTML-блоку типів 1–5 зберігаються;
- файл закінчується одним `\n`.

Неявні ключові слова **не** додаються: `- orderAggregate` під шаром лишається як є (слайдова форма рівноправна з `- module orderAggregate`).

`fmt <paths…>` форматує кожен файл окремо: файл, який не прочитати чи не записати, називається в stderr з причиною, а решта все одно форматуються; тоді код 2. Інакше код 1 — діагностики або, з `--check`, неформатований файл (з `--check` нічого не пишеться).

**Р9. Code fence всередині елемента списку не підтримується**: огорожа з будь-яким відступом закриває список і стає блоком коду секції. `fmt` знімає цей відступ, тож після форматування GitHub показує блок поза списком — там само, де його бачить keylang. Значення файлу не змінюється.

## 9. IR і позиції (для LSP)

`Document → Section → Item (Node | Prose | Code)`, `Node` рекурсивний. З цього текстового IR `compileSpec` будує внутрішній SpecIR — типізовані твердження правил, потоків і wiring. Парсер перевіряє форму рядка, `compileSpec` — форму твердження (порядок шарів, умова wiring), check — те, що потребує знімка. У JSON-виводі (`parse --json`, `check --format json`) SpecIR немає: назовні лишається текстовий IR і результати перевірки. `parse --json` серіалізує `diagnostics` як є, тож K005 парсера має там те саме `reason`, що й у `check --format json`. Кожен `Node` має `span` (рядок елемента від маркера до кінця), `keyword` (спан ключового слова або `null`, якщо воно неявне), `name.span`, `link.span`, `refs[*].span` (для лінка — ID усередині `[…]`, сам лінк — `refs[*].link`), `text.span`, `description[*].span`, а також сирі `tokens` зі спанами. `Pos = {offset (індекс у рядку JS, UTF-16), line, col (кодові точки)}`. `Index` (`src/resolve.ts`) відображає `id → Decl {file, span імені, kind}` — це вже дає `definition` (посилання → оголошення) і `hover`; `spanContains(span, offset)` — пошук вузла під курсором.

## 11. Семантичний знімок (`.keylang/index.json`)

`keylang map` серіалізує `AnalysisSnapshot` (схема **7**) у `.keylang/index.json` і **рендерить Markdown-карту з цього знімка**. Індекс — кеш фактів, не текст для редагування. Шлях у вузлі знімка лишається POSIX-шляхом від кореня репозиторію; відносне кодоване посилання рахує emitter. Несумісна або зіпсована схема на диску не є помилкою: наступний `map` перезаписує файл без окремої діагностики.

`snapshotId` — SHA-256 канонічного JSON від схеми, версії екстрактора, версій граматик, конфігурації (`dir`, `languages`, `module`, `layers`, `exclude`, `guessed`) і SHA-256 вмісту кожного проіндексованого файла. Поле `generated` (час запису) у хеш не входить, і поле `format` теж. Два запуски на тих самих джерелах дають той самий `snapshotId`. Його змінює зміна проіндексованого файла або одного з перелічених полів конфігурації.

| Частина | Зміст |
|---|---|
| `manifest` | екстрактор, версії `web-tree-sitter` і `@vscode/tree-sitter-wasm`, конфігурація, `{path, sha256}` файлів |
| `nodes` | ID → вид (`layer` / `module` / `fn` / `type`), шар, файл і діапазон (`line`, `col`, `endLine`, `endCol`: колонки з 1 у кодових точках, як у §7, кінець — позиція після фрагмента). У модуля й типу діапазон є так само, як у функції. У модуля `members`: `complete` або `opaque`; клас — модуль із `class: true` (у будь-якому файлі свого модуля, зокрема в модулі-теці), його члени — дочірні вузли, конструктор — `<клас>.constructor`. У fn члена класу `static: true` — статичний член (`X.m()`), `name` — ім'я, як його написано, коли сегмент ID інший (`m` для `X.m-static`, `go` для `Y.go-private`). Похідні `deps` / `dependents` / `calls` / `callers` (`calls` без ребер `injected`, кожна ціль один раз). У fn може бути `escapes: {file, line, col, reason}` — перше місце, де її може викликати код, що її не називає (читання як значення, accessor, неявний метод, виклик із коду поза оголошеннями, базовий клас, який keylang не прочитав, статичний ініціалізатор) |
| `exports` | публічне ім'я модуля (`name`, яким його імпортують; `default` для `export default …`, `export =`, `module.exports = …`) → `symbol` — вузол, який воно означає, через псевдоніми, ланцюжки re-export і `export *` (fn, клас, тип або модуль простору імен; `null`, коли це не оголошення, яке keylang індексує: `export default 3`, ім'я пакета), вид (`fn`, `class`, `type`, `value`), `form` (немає — оголошення під власним ім'ям; `alias` — `export { a as b }`; `default` — експорт за замовчуванням; `reexport` — ім'я іншого модуля; `namespace` — об'єкт модуля: `export * as ns from`, `import * as ns; export { ns }`, `export namespace N {}`), `local` — локальне чи вихідне ім'я, коли воно інше (`a` для `export { a as b }`, `main` для `export default function main`) і `from` — модуль, з якого ім'я реекспортовано (для `export *` — модуль, що його експортує). Рядок `*` з видом `reexport` і `reason` — `export *` з модуля з невідомим вмістом |
| `edges` | `kind` (`import`, `call`, `type`, `reexport`), `source`, `target` або `null`, `candidates` коли цілей кілька, `text` (фрагмент коду) і діапазон `line`/`col`/`endLine`/`endCol`, `resolution` (`resolved` / `ambiguous` / `unresolved`), `provenance` (`syntactic`). `ambiguous` означає кілька можливих цілей у `candidates` і порожній `target`. Необов'язкові поля виклику: `via` (`default` / `injected`), `hook` і `site` — ребро хука (§7, «Хуки»); `closure: true` — виклик у вкладеній функції джерела |
| `coverage` | нерозв'язаний імпорт, динамічний виклик (зокрема «call through an expression» — виклик виразу, який keylang не називає: `f()()`, `(a || b)()`, `new (load())()`, ланцюжок довший за 80 символів), нерозв'язаний виклик, `unsupported construct` (namespace, `eval`, `new Function`, виклик `obj[expr]`, обчислюваний член класу `[key]() {}`, колізія ID модулів), обчислюваний specifier (`import(expr)`, `require(expr)`, `import.meta.resolve(expr)`, ``new URL(`./${n}.ts`, import.meta.url)`` чи `"./" + n`, `register(expr, import.meta.url)`; `new URL` з відомим немодульним закінченням, як `.png`, — не модуль; відносний `new URL("./worker", import.meta.url)` без розширення — ребро, коли за ним є файл коду, і нічого інакше), синтаксична помилка (зокрема синтаксис, вкладений глибше за 1000 рівнів: файл тоді `opaque`, а не падіння аналізу), файл поза шаром і пропущений файл — кожен із діапазоном, `text` і `reason` |
| `stats` | лічильники проходу; вони не замінюють записи `coverage` |

Порожній проіндексований модуль має `members: "complete"` і жодного дочірнього символу. `opaque` не підтверджує існування довільного імені. Файл, виключений через `exclude` у `keylang.json`, стає модулем `members: "opaque"` свого шару, а файл поза всіма шарами — модулем шару `unassigned`; у карті він має коментар `<!-- excluded -->`, у `coverage` — запис `skipped-file`. Цей запис — прогалина рівня залежностей: рядок `layers`, глобальний `no-cycles` чи `deny`, в області якого лежить файл, отримує `unverified`, а не `ok` (§7). Без `keylang.json` (вгадана розкладка) файл поза вгаданими шарами лишається поза графом; посилання на його члена — `unverified`, не K001. Тека джерел без дозволу на читання не зупиняє аналіз: `map` і `check` друкують попередження, а в `coverage` з'являється `skipped-file` з файлом-текою і `source` — ID області, яку мали б її файли. Правила над цією областю, вище чи нижче неї (`layers`, `deny`, `no-cycles`, `entry`), тоді `unverified`, не `ok`. Нечитабельний корінь репозиторію — помилка вводу-виводу з кодом 2. Нерозв'язаний імпорт і виклик локального значення є і в `coverage`, і ребром з `resolution: "unresolved"`. Імпорти резолвляться через `tsconfig.json` (або `jsconfig.json`), ланцюжок відносних `extends` і — для solution-конфігу з `references`, як у шаблоні Vite, — `paths` конфігів, на які він посилається; а також `package.json#imports` найближчого `package.json` над файлом (як Node визначає область пакета). Голий специфікатор, як у `tsc`, іде спершу через `paths` — лише найспецифічніший шаблон (точний ключ, інакше найдовший префікс до `*`, незалежно від порядку в JSON), — потім `baseUrl`, і лише тоді він вбудований модуль Node чи пакет: аліас на ім'я вбудованого модуля (`constants`, `events`, `util`) — файл проєкту. Успадковані `paths` резолвляться від `baseUrl` підсумкових опцій (дочірній `baseUrl` переносить і їх), інакше від теки конфігу, що їх оголосив. `./x.js` знаходить `x.ts`, `x.tsx` чи `x.jsx`, а `./x.jsx` — `x.tsx`. Файли аналізу, зокрема незбережені чи запропоновані й ще не записані на диск, для резолвера існують, тож той самий знімок резолвиться однаково до й після запису кандидата. Кожен файл конфігурації читається один раз, і `snapshotId` рахується з того самого тексту, який розібрано; джерела так само: хеш у `manifest`, ключ кешу й факти — з одного читання, а файл, видалений між переліком і читанням, у знімок не входить. Імпорт, що резолвиться у файл коду, якого немає серед модулів (мова, якої немає в `languages`, файл у теці збірки, файл, що з'явився після переліку джерел), — прогалина `unresolved import` з причиною, а не мовчазна відсутність ребра; тести, файли оголошень, `exclude`, файли поза вгаданими шарами й не-код (JSON, CSS) залишаються поза графом мовчки. Голий специфікатор — зовнішній пакет лише тоді, коли його оголошено в `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies` або встановлено в `node_modules` на рівні кореня чи вище, або — як шукає Node — оголошено в `package.json` чи встановлено в `node_modules` теки між файлом і коренем (`web/package.json` монорепозиторію діє лише на файли під `web/`); інакше це нерозв'язаний імпорт (аліас, якого keylang не знає), а не пакет. Пакет робочого простору внутрішній: запис `node_modules/<pkg>`, що після розкриття посилань веде в репозиторій (не в чийсь `node_modules`), або — без встановлення — тека з `workspaces` кореневого `package.json` із таким `name`. Файл дає його `package.json`: `exports` (рядок, підшляхи `./util`, шаблони `./*`, умови), інакше `module`, `main`, `index`; файл оголошень (`.d.ts`) — не джерело. Без такого файла імпорт нерозв'язаний, а файл, який keylang не індексує (`dist/index.js`), — прогалина `unresolved import`, не мовчазна відсутність ребра. `snapshotId` враховує вміст цих файлів конфігурації (зокрема `package.json` пакетів робочого простору, вкладені `package.json` на шляху голого імпорту й перелік тек `workspaces`) і для кожного голого пакета — чи є він у `node_modules` і куди веде, бо від них залежать ребра: після `npm install` знімок інший. Імпорт — також TypeScript `import y = require("./y")` (прив'язка всього модуля) і `import.meta.resolve("./w.ts")`; `require` параметра чи іншого локального значення — не імпорт, а виклик через локальне значення (`require`, створений `createRequire(…)`, — імпорт). Імпорт і `export { … } from` одного модуля — одна залежність із двома ребрами (`import` і `reexport`). ID зовнішнього модуля — ім'я пакета без `@`, з `/` → `-`; якщо два пакети дають один сегмент (`@scope/pkg` і `scope-pkg`), сегмент лишається пакету з точно таким ім'ям, а інші отримують `-2`, `-3`… за абеткою, з попередженням. Два файли з одним ID модуля й одним шляхом без розширення (`x.ts` і `x/index.ts`, файли однієї теки в `module: "dir"`) — один модуль; два різні шляхи, що санітизуються в один ID (`foo.bar.ts` і `foo_bar.ts`), — колізія (дужки в сегменті кодуються оборотно, §4, тож `(shop)` і `[shop]` не зливаються): попередження, прогалина `unsupported` «module ID collision» і модуль `members: "opaque"`, доки один файл не перейменують. У модулі-теці (`module: "dir"`) fn, типи, імпорти й виклики мають файл, де їх написано, а не перший файл модуля; файл модуля — його `index.*` (`mod.rs`, `__init__.py`), якщо він є, інакше перший за абеткою; тека з назвою `index` — окремий модуль, а синтетичний вузол теки має шлях своєї теки. Виклик резолвиться з урахуванням областей видимості між місцем виклику й модулем: параметри (зокрема деструктуровані), `const`/`let`/`var` у будь-якому охопному блоці, деструктуризація, вкладені функції й класи, змінні `for…of` і `catch`. Якщо таке ім'я затіняє імпорт чи оголошення модуля, це `unresolved-call` з причиною `shadowed by parameter|local`; інакше — `dynamic-call` «call through a local value». Жодне з них не стає підтвердженим ребром. Імпортоване ім'я резолвиться за таблицею публічних імен модуля-джерела (та сама таблиця — `exports` знімка): `import go from` — його `export default` (зокрема `export default function step`, `export default x`, `export = x`, `module.exports = x`), і `go.m()` — статичний член цього експорту (`export default class A { static m() }` → `A.m`), а не іменований експорт `m`; лише модуль без `export default` (CommonJS) дає за default-імпортом `module.exports` з його іменами. `import * as ns` і `require()` — простір імен: `ns.m()` — іменований експорт `m`. `export { a as b }` — оголошення `a`, `export { x } from` / `export { x as y } from` і ім'я, імпортоване та експортоване знову, — ланцюжком до оголошення, `export * from` — іменами без `default`, `export * as ns from` — простором імен (`ns.f()`, тип `ns.T`, як і `NS.T` при `import * as NS`); ім'я без рядка експорту (CommonJS, неекспортований помічник) — оголошення з цим ім'ям. Кожен виклик у коді — ребро або прогалина: `new ns.X()` — виклик класу `X` модуля `ns`, `new X().m()` — член `m` класу `X`, `super()` — конструктор базового класу (через бази без власного конструктора), `super.m()` — член бази; виклик виразу, який keylang не називає (`f()()`, `(a || b)()`), — `dynamic-call` «call through an expression». Виклик тієї самої цілі кілька разів дає одне ребро, найсильніше: прямий виклик поглинає виклик у closure та ребро хука `default`. `interface Foo` і `class Foo` (злиття оголошень TypeScript) — один вузол-клас, хоч би що стояло першим; згадки типів інтерфейсу належать класу. Функцією модуля є й значення `(() => …) as T`, `(function () {}) satisfies T`, а в CommonJS — `exports.x = function () {}`, `module.exports.x = () => …`, функції й методи в `module.exports = { … }` та `module.exports = function () {}` (fn `default`). `const Cart = memo(() => …)`, `forwardRef((props, ref) => …)`, `lazy(() => import(…))` і `React.memo(…)` — fn обгорнутої функції з її викликами, лише коли обгортку імпортовано значенням із `react` (впізнається за імпортом, не за текстом). `react/jsx-runtime` цих імен не експортує, тож імпорт звідти обгортку не відкриває. Не розгортаються аргумент-ідентифікатор (`memo(CartImpl)`), вкладене `memo(forwardRef(…))` і `require("react")`. Значенням лишаються також `import type` і `import { type memo }`, `forwardRef` з `@nestjs/common`, локальна `memo`, `styled(…)` і `let`/`var`. Виклики поза тілами оголошень (верхній рівень модуля, методи об'єктних літералів, функція-значення, обгорнута викликом) жодній fn не належать і є `escapes` того, що вони викликають (§7). Члени класу: метод і поле з функцією (`handler = () => later()`, `readonly generate = (…) => {…}`) — fn з власними викликами; getter і setter — fn з `escapes`. Ініціалізатори полів екземпляра (`private decoder = new InputDecoder()`) виконуються під час конструювання: їхні виклики належать `constructor`, а якщо його немає в коді — синтезованому `Class.constructor` без сигнатури з діапазоном від першого до останнього такого поля (лише коли ініціалізатори щось викликають). Ініціалізатори статичних полів і блоки `static {}` виконуються один раз під час обчислення класу: їхні виклики належать синтезованому `Class.static`, а не конструктору (якщо в класі вже є член `static`, це `unsupported`). Член з обчислюваним ключем (`[key]() {}`, `[key] = …`) — `unsupported construct` «computed class member»: його виклики — код поза оголошеннями. Сегмент ID члена — його ім'я без `#`; якщо ім'я вже має інший член класу, статичний член отримує суфікс `-static`, приватний `#name` — `-private`, статичний приватний — `-static-private` (жодне JS-ім'я не містить `-`, тож суфікс не збігається з іншим членом). Пріоритет — член екземпляра, статичний, `#`-приватний, статичний `#`-приватний: `static m()` поруч з `m()` — `X.m-static`, `#go()` поруч з `go()` — `Y.go-private`; без збігу ID лишається `X.work` для `#work`. Тож поява одноіменного члена з вищим пріоритетом перейменовує ID нижчого. `this.#work()` — виклик приватного члена, `this.m()` у статичному методі й `X.m()` — статичного, `w.m()` через екземпляр — члена екземпляра. `this` означає клас, лише коли найближча охопна не-стрілкова функція — член класу (або це ініціалізатор поля чи `static {}`); `this.m()` у методі об'єктного літерала чи вкладеній `function` — `dynamic-call` «call through `this` of a function value». `new X()` у static-доказі — виклик `X.constructor`. Виклик методу через поле чи локальне значення відомого класу розв'язується: поле з анотацією `: X` чи ініціалізатором `new X()`, параметр-властивість `constructor(private readonly x: X)`, присвоєння `this.x = new X()` або `this.x = p` з `p: X` у конструкторі; `const w = new X()`, `const w: X`, параметр `w: X` — якщо ближча прив'язка того самого імені (змінна `for…of`, `catch`, вкладена функція) його не затіняє і саме `X` між оголошенням і модулем не перепризначено (`const X = Ctor`). `this.x.m()` і `w.m()` тоді — ребро до `X.m`, якщо `X` — клас цього файла чи імпортований і має член `m`; для глобального класу (`Map`, `Set`…) чи класу з пакета — зовнішній виклик; інакше (інтерфейс, generic-анотація, невідомий тип) лишається діркою. Ребро `type` — це згадка типу в сигнатурі чи heritage; правила `allow` / `deny` / `layers` бачать його разом із `import`, `call` і `reexport`.

### Мови

`languages` у `keylang.json` — підмножина `javascript`, `python`, `rust`, `typescript`; інша назва — помилка конфігурації з кодом 2. Без поля мови визначаються за розширеннями файлів. Без `module` береться гранулярність мов, якщо вона однакова, інакше `file`. Файл-індекс, що стоїть за модуль своєї теки: `index.*` для JS/TS, `mod.rs` для Rust, `__init__.py` для Python. Шар членів не має, тож файл-індекс прямо під коренем шару зберігає своє ім'я: `<шар>.index`, `<шар>.mod`, `<шар>.__init__`. За замовчуванням не індексуються також `test_*.py`, `*_test.py`, `conftest.py` і теки `venv`, `site-packages`. Граф, знімок і перевірки для всіх мов спільні. Кожна мова має frontend: екстрактор фактів файлу, резолвер імпортів і перелік глобальних імен мови, виклики через які зовнішні. Мова також каже, що запускає виклик класу (`constructor` у JS/TS, `__init__` у Python; у Rust виклику типу немає), і які члени класу вона викликає без виразу виклику з їхнім ім'ям: JS `then`, `next`, `toString`…; Python — dunder-методи, крім `__init__` (`__enter__`, `__iter__`, `__str__`, `__call__`…); Rust — методи `impl` тих трейтів `std`, які викликають оператори, `for`, `?`, форматування, кінець області й auto-deref (`impl Drop`, `impl fmt::Display`, `impl Add`, `impl Iterator`, `impl From<T>`…); власний метод `add` без трейту викликається лише за ім'ям. Такий член має `escapes` «is called implicitly». Кожен вираз виклику — ребро або дірка: виклик, отримувача чи callee якого keylang не може назвати (`self.db.save()`, `Order::new().total()`, `x[0].m()`, `super().m()`, `f()()`, `(self.handler)()`), — `dynamic-call` «call through a local value» з текстом виклику, тож `closure.complete` — `false`, а крок за ним — `unverified`, не `fail`. У `.tsx`, `.jsx` і `.js` тег JSX, що називає компонент, — виклик від функції, у чиєму тілі він стоїть, як `Cart()`: `<Cart />` і `<Cart></Cart>` — виклик `Cart` (закриваючий тег — не другий), `<Cart.Item />` — `Cart.Item`, `<Cart<Props> />` цілить у `Cart`; тег у колбеку (`items.map(() => <Cart />)`) має `closure`, тег через параметр чи локальне значення — дірка, як виклик параметра. Тег з малої літери (`<div />`, `<my-button />`), простір імен (`<svg:path />`) і фрагмент (`<>`) — не виклики, навіть якщо fn `div` існує. У `.ts` JSX немає: `<Foo>x` — type assertion, а літеральний тег — синтаксична помилка й `opaque`-файл, не ребро. Виклик `createElement(Cart)`, `jsx(Cart)`, `jsxs(Cart.Item)` і `jsxDEV(Cart)` — той самий виклик компонента (ребро `call`, без нового виду), коли callee імпортовано значенням з `react`, `react/jsx-runtime` або `react/jsx-dev-runtime` (впізнається за імпортом, не за текстом: `createElement as h`, `React.createElement`): перший аргумент — identifier з великої літери або member. Рядок (`"div"`) і identifier з малої літери — не виклик, навіть якщо fn `div` існує. Локальна функція з тим самим ім'ям, імпорт з іншого модуля і type-only імпорт (`import type React`, `import type * as React`, `import { type createElement }`) лишаються звичайним викликом зі своїми `passes` — те саме правило, що й для обгорток. Функція, прочитана як значення (`later(hit)`, `Handler { run: go }`, `.map(Order::total)`, `callback=self.save`, `{"save": save}`), має `escapes` «is read as a value».

**Rust.** Модуль — файл, як і в самому Rust: `src/domain/order.rs` — це `crate::domain::order` і ID `domain.order`, а `src/domain/mod.rs` — модуль теки. Члени: `fn`, `struct`/`enum`/`union` (як класи; їхні члени — функції з `impl` того самого файла, асоційована функція без `self` статична; `self: Box<Self>` — теж `self`), `trait` і `type` (як типи). Експорт — будь-яка видимість `pub…`, `pub use` — реекспорт: рядок таблиці експортів з `form: reexport`, символом, на який вказує шлях, і `from` — модулем, звідки він. Не індексуються тестовий код: елементи під `#[cfg(test)]` або `cfg`, що вимагає `test` (`cfg(all(test, unix))`), функції з `#[test]` (`#[tokio::test]`…) і файл із `#![cfg(test)]`; коментар між атрибутом і елементом цього не змінює. Кожен лист дерева `use` (`a::{b, c::d as e, f::*}`) — окремий імпорт, зокрема `use` у тілі функції. Крейт — тека з `Cargo.toml` і `[package]`. Кожна ціль крейту — окреме дерево модулів із коренем у своєму файлі: бібліотека — `src/lib.rs` або `[lib] path` (сам файл, `a/b.rs` шукаються поруч із ним), бінарники — `src/main.rs`, `src/bin/*.rs`, `src/bin/*/main.rs` і `[[bin]] path`. `crate::` резолвиться від кореня цілі, до якої належить файл: у `main.rs` `crate::helper()` — його власна `helper`, а не бібліотеки. Файл під спільною текою бібліотеки й бінарника належить бінарнику, коли лише корінь бінарника оголошує його модуль верхнього рівня (`mod cli;`), інакше бібліотеці. `crate::`, `self::`, `super::` і шлях від дочірнього модуля (edition 2018) резолвляться у файл `a/b.rs` або `a/b/mod.rs`. Найдовший префікс шляху, що є модулем, дає файл. Якщо модулем є весь шлях, імпорт прив'язує сам модуль, інакше останній сегмент є іменем члена. Шлях у власний файл (`crate::run()` у файлі, де `run` оголошено, `self::run()`) — ребро до його члена. Шлях, що після файла йде далі в модуль без власного файла, не прив'язує члена: у вбудований `mod inner { … }` цього файла — залежність від файла без ребра виклику (`dynamic-call`), у модуль із `#[path]` чи будь-який інший — нерозв'язаний імпорт. Ім'я члена `[workspace] members` (чи пакета з бінарника) означає бібліотеку цього крейту, ключ `[dependencies]`/`[dev-dependencies]`/`[build-dependencies]` — зовнішній пакет, `std`/`core`/`alloc` — зовнішні. Будь-яке інше ім'я дає нерозв'язаний імпорт. `mod x;` оголошує файл, але ребром не є: залежність — те, що код використовує. Шлях у виклику чи значенні, що починається з `crate`, `super`, `self` або з невідомого імені з малої літери (`tokio::spawn()`), є власним імпортом; шлях через прив'язку `use` довший за два сегменти (`order::Order::new()` при `use crate::domain::order`) — теж, від шляху цього `use`. Сегмент шляху в `CamelCase` після модулів — тип: `super::i18n::Message::raw()` — це член `Message.raw`. Виклик, чий останній сегмент у `CamelCase` (`Some(x)`, `Event::Progress(p)`), за конвенцією іменування є конструктором варіанта чи tuple-struct і викликом не є. Шлях від примітиву (`u64::from`) — зовнішній. `Self::f()` у `impl` — це член типу, `self.m()` — член `impl`. Виклик методу через значення (`order.total()`) — `dynamic-call`. Виклики у вкладеній `fn`, як і в closure, мають `closure: true`. Виклики в коді, який keylang не індексує як fn — ініціалізатор `const`/`static`, типові методи `trait`, вбудований `mod`, `impl` типу з іншого файла, — код поза оголошеннями: те, що вони викликають, має `escapes`. Невідомий макрос цього крейту (`audit!()`, `crate::m!()`) — `unsupported` «macro is not expanded». Макроси `std`, поширеного логування й макроси зі шляхом у чужий крейт (`serde_json::json!`) діркою не є. Файл поза всіма цілями (`build.rs`) — окремий корінь: `crate::` у ньому не резолвиться в `src/`. Вбудований `mod x { … }`, `impl` для типу з іншого файла і макрос на верхньому рівні — `unsupported`; шляхи всередині вбудованого модуля починаються від нього й імпортами файла не є. Атрибут-макрос на fn поза атрибутами мови й тими, що зберігають тіло (`#[tokio::main]`, `#[tracing::instrument]`, `#[async_trait]`), — `unsupported` «attribute may replace» із текстом `#[…]` і `source` — ID fn, а сама fn — `escapes` «is read as a value»: як і Python-декоратор, це дірка поведінки цієї fn, а не залежностей модуля. Rust-frontend дає ребра `import`, `call`, `reexport`; ребер `type` ще немає. `snapshotId` враховує вміст прочитаних `Cargo.toml`.

**Python.** Модуль — файл, пакет — `__init__.py` теки. Члени: `def` (зокрема `async`) і `class` (їхні методи й вкладені класи з їхніми членами; `@staticmethod` і `@classmethod` статичні, `@property`, `@cached_property` і `@x.setter` — accessor з `escapes`). Верхній рівень охоплює й тіла `if`/`try` модуля. Публічні імена — список літерала `__all__` (зокрема розширеного `+=`, `+`, `.extend([...])`, `.append("x")`), а без нього — імена без початкового `_`. Методи з `_` приватні, dunder-методи (`__init__`) публічні. Кожне імпортоване ім'я — окремий імпорт з крапковим шляхом, зокрема імпорт у тілі функції чи класу. `from ..pkg.mod import f` починається від пакета файла: одна крапка на рівень. `import a.b` прив'язує `a` і шлях `a.b`: `a.b.f()` — виклик `f` модуля `a.b`. Абсолютний шлях шукається в корені репозиторію, потім у `src/`. Найдовший префікс, що є модулем (`p.py` або `p/__init__.py`), дає файл. `from pkg import mod`, де `mod` — модуль, прив'язує сам модуль. Ім'я верхнього рівня, якого немає в жодному корені, — зовнішній пакет, бо path-аліасів у Python немає. Реекспорт — імпорт верхнього рівня з ім'ям із `__all__`, а в `__init__.py` без `__all__` — будь-яке публічне імпортоване ім'я і `from .x import *`: ребро `reexport` і рядок таблиці експортів з `form: reexport`, символом і `from`. Тож `from shop.domain import place` при `from .order import place` у `shop/domain/__init__.py` — виклик `shop.domain.order.place`. `X()` — виклик класу, тобто його `__init__`. `self.m()` — член класу, для `@staticmethod`/`@classmethod` — статичний член; перший параметр `@staticmethod` отримувачем не є. `self.attr.m()` і `x.m()` через змінну — `dynamic-call`. Код тіла класу поза методами і декоратори виконуються під час завантаження модуля: те, що вони викликають, має `escapes`. Декоратор поза списком тих, що зберігають функцію (`staticmethod`, `classmethod`, `property`, `dataclass`, `functools.wraps`, `lru_cache`, `total_ordering`…), — `unsupported` «decorator may replace» із `source` — ID декорованої fn чи класу, а сама fn — `escapes` «is read as a value» (декоратор тримає її як значення, як фреймворк — зареєстрований обробник). Це дірка поведінки цієї декларації, а не залежностей модуля: `deny` її не враховує. Так само `getattr` у тілі функції (`source` — її ID). `importlib.import_module`, `__import__`, `exec`, `eval` і `getattr` поза функцією — `unsupported` рівня залежностей. Python-frontend дає ребра `import`, `call` і `reexport`; ребер `type` ще немає.

**Fingerprint.** У fn і типу є `fingerprint` — SHA-256 сигнатури та синтаксису оголошення: типи вузлів tree-sitter і тексти токенів без коментарів і пробілів. Заміна `>` на `>=` його змінює, зміна коментаря чи переформатування — ні. Переміщення інструкції з блоку змінює, бо вкладеність — частина хешу. Перевантаження TS об'єднуються в один fingerprint. `closure: {fingerprint, complete}` — fingerprint вузла разом з усім, що він викликає транзитивно (`new C()` — з конструктором `C`). Він рахується знизу вгору за сильно зв'язаними компонентами графа викликів, тож цикл A ↔ B дає обом один `closure` і зміна будь-кого з них змінює обидва. `complete: false`, коли вузол або щось досяжне від нього має `dynamic-call` чи `unresolved-call`, дірку самої декларації (`unsupported` з `source` — ця fn чи її клас: декоратор або атрибут-макрос, що може її підмінити) або не має fingerprint: незмінний хеш тоді не означає незмінної поведінки. Fingerprint не входить у `snapshotId` (той залежить від вмісту файлів) і не є baseline прози: baseline і `check --stale` — тікет 21.

**Документація.** Кожен вузол має `doc`: коротке пояснення з коментаря документації в коді або `null`. Шар і зовнішній модуль завжди мають `null`. Із коментаря прибирається синтаксис, береться перший абзац зі стиснутими пробілами й обрізається до двох речень. Речення закінчується на `.`, `!` чи `?` перед пробілом і великою літерою або в кінці тексту, тож `e.g. this` і `a.b()` речення не розривають. Понад ~280 символів текст обрізається по слову з `…`. Правило не залежить від ICU і версії Node. **TS/JS:** декларацію (fn, клас, тип, член класу) документує найближчий `/** … */` над нею чи над обгорткою (`export`, `const x =`). Між ними можуть стояти декоратори, порожні рядки й рядкові коментарі, але не інший код. Рядковий `//` над fn — нотатка, а не документація. Із JSDoc береться опис до першого блочного тегу (`@param` і далі); `{@link x}` стає `x`, а `{@link x text}` — `text`. Модуль документує перший блок коментарів файла після `#!` (`//` чи `/* */`; коментарі на сусідніх рядках — один блок), якщо цей блок не стоїть упритул над першою інструкцією, що не є `import` чи директивою (`"use strict"`): тоді він належить їй. Коментар, що починається з ліцензії (`SPDX-…`, `Copyright …`, `(c) 2024`, `©`) або містить `SPDX-License-Identifier`, — не документація; згадка слова copyright у тексті — документація. `/// <reference>` і блок без тексту теж пропускаються. Модуль-тека бере документацію свого файла-індексу (`index.ts`, `mod.rs`, `__init__.py`). **Rust:** item документують `///` і `/** … */` над ним; атрибути й звичайні коментарі між ними дозволені. Модуль документують `//!` і `/*! … */` його файла. `#[doc = "…"]` keylang не читає, тож такий item має `doc: null`. **Python:** docstring — перший рядковий літерал тіла модуля, `class` чи `def`, очищений як в `inspect.cleandoc`. f-рядок, bytes і склеєні рядки — код, а не документація (`doc: null`). Коментарі не входять у `fingerprint` і `closure`: зміна лише коментаря змінює `doc`, але не їх. Канонічна карта `doc` не показує, `keylang explain <id>` друкує його рядком `doc:`.

`provenance: semantic` і `provenance: trace` лишаються дорожньою картою, не полями поточного знімка. Схема знімка — **7** (у 7 з'явився `doc` вузла; у 6 з'явилися `class` модуля, `static` і `name` fn, `local` і форма `namespace` в `exports`).

Карта з поясненнями описана в [tools.md](tools.md#explained-map).

## Додаток А. Граматика

Нормативна граматика цього документа. Таблиці §5 лишаються зведенням для читача. Фрагменти в §2 і §4 лише відсилають сюди.

```ebnf
(* Класи рядків, §1. Спрацьовує перший, що підійшов. *)
line = fence-line | html-block | blank | generated-marker | heading | fence-open | item | description | prose ;

heading = "#" " " kind [ " " name ] ;
kind = "map" | "rules" | "flow" | "wiring" ;
name = segment ;
segment = ( letter | "_" | "$" ) ( letter | mark | digit | "_" | "$" | "-" )* ;
id = segment ( "." segment )* ;

item = indent bullet " " head [ " " comment ] ;
bullet = "-" | "*" | "+" ;
head = token ( sep token )* ;
token = link | quoted | word | "," ;
link = "[" text "](" target ")" ;
quoted = '"' { not quote } '"' ;
word = { not space, tab, or comma } ;
comment = "<!--" { rest of line } ;

(* Позиції §5. Слово в лапках — ключове. `-> kind` — kind в IR, коли він не збігається зі словом. *)
map-top = "layer" | "layers" | "allow" | "deny" | "entry" | "module" -> rule-module | "no-cycles" ;
rules-top = "layers" | "allow" | "deny" | "entry" | "module" -> rule-module | "no-cycles" ;
flow-top = "kind" | "trigger" | "step" | "reads" | "emits" | "calls" | "invariant" | "when" | "test" | "planned" ;
wiring-top = "wire" ;
under-layer = "module" ;
under-module = "module" | "fn" | "type" | "event" ;
under-fn = "calls" ;
under-ref = (* під layers і під entry: голе id, без ключових слів *) ;
under-rule-module = "exports" | "no-cycles" ;
under-step = "step" | "reads" | "emits" | "calls" | "when" | "test" | "invariant" ;
(* under-step також під trigger *)
under-when = "then" | "step" | "test" ;
under-invariant = "test" ;
(* under-invariant також під then *)
under-wire = (* гола залежність alias id, без ключових слів *) ;
under-wire-dep = "when" | "compose" ;
under-other = (* K004: батько не може мати вкладених елементів *) ;

(* Форми аргументів, §5. *)
layer-args = "layer" segment ;
module-args = "module" ( segment | link ) ;
decl-args = ( "fn" | "type" | "event" ) ( segment | link ) signature ;
dep-args = alias id ;
calls-args = ( "calls" | "reads" ) id ( "," id )* ;
layers-args = "layers" id ( "<" id )* ;
allow-args = ( "allow" | "deny" ) id id ;
entry-args = "entry" ;
rule-module-args = "module" id ;
exports-args = "exports" segment ( "," segment )* ;
no-cycles-args = "no-cycles" ;
kind-args = "kind" ( "business" | "technical" ) ;
step-args = ( "trigger" | "step" ) id ;
planned-args = "planned" ( "fn" | "module" | "type" | "event" ) id [ signature ] ;
emits-args = "emits" [ "event" ] segment ;
invariant-args = "invariant" text ;
when-flow-args = "when" text ;
then-args = "then" ( id | text ) ;
test-args = "test" file [ '"' name '"' ] ;
wire-args = ( "wire" | "compose" ) id ;
when-wiring-args = "when" condition "→" id ;
```

Побічні умови, яких EBNF не виражає:

- Глибина = відступ / 2 (§3). Відступ — лише пробіли.
- Ключові слова контекстні (Р7): те саме слово в іншій позиції — не ключове.
- `then` вгадує форму (Р10): один токен-ID з крапкою — посилання, інакше текст.
- Під будь-чим іншим — K004 «не може мати вкладених елементів» (`under-other`).
