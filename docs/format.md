# Формат keylang — специфікація v0.2

Точна граматика Markdown-форми keylang, як її читає поточний CLI. Загальні ідеї — у [`design.md`](design.md) §3; тут записано, як саме парсер (`src/parser.ts`) розбирає файл і які неоднозначності як вирішено. Рішення позначено **Р1…Рn**, щоб на них можна було посилатися в рев'ю. Формат v1 не заморожено: те, чого в цій специфікації немає в розділі «Дорожня карта», не є поточною поведінкою.

## 1. Модель файлу

Файл — послідовність рядків (`\n` або `\r\n`). Кожен рядок належить до одного з класів, які перевіряються в такому порядку:

| Клас | Умова | Що стає в IR |
|---|---|---|
| рядок у code fence | між відкривною і закривною огорожею | `Item::Code` (рядки дослівно) |
| порожній | лише пробіли | закриває абзац прози; список **не** закриває |
| маркер генерації | перший непорожній рядок файлу, починається з `<!--` і містить `keylang:generated` | `Document.generated` |
| заголовок секції | відступ 0, `#` і далі пробіл або кінець рядка | нова `Section` |
| огорожа коду | після відступу `` ``` `` або `~~~` | відкриває `Item::Code`, закриває список |
| елемент списку | після відступу `-`, `*` або `+`, далі пробіл або кінець рядка | `Node` |
| опис | інший текст, відступ ≥ 2, і є відкритий елемент списку | `Node.description` |
| проза | усе інше | `Item::Prose`, закриває список |

Заголовки `##` і глибші, таблиці, цитати, нумеровані списки — це проза: вони не мають семантики, але зберігаються й форматуються дослівно.

**Р1. Власний рядковий парсер замість pulldown-cmark/comrak.** keylang використовує вузьку підмножину Markdown. CommonMark-парсери дають вузли з діапазонами байтів, але для LSP нам потрібні позиції кожного *слова* всередині елемента (ключове слово, ім'я, кожне ID у `calls a, b`), а також власні правила для лінивих продовжень, табів і відступів — їх однаково довелося б дописувати поверх AST. Рядковий парсер (`src/parser.ts`, ~830 рядків TypeScript) дає точні `offset/line/col` для кожного токена і власні діагностики (K003) замість мовчазної «перебудови» дерева, як це робить CommonMark. Ціна — ми не розуміємо вкладених у елементи списку code fence (див. Р9).

## 2. Секції та види файлів

```
heading  := "#" " " kind [" " name]
kind     := "map" | "rules" | "flow" | "wiring"
name     := segment
```

| Заголовок | Вид секції | Типовий файл |
|---|---|---|
| `# map` | map | `keylang/map/*.md` (генерується) |
| `# rules` | rules | `keylang/rules.md` |
| `# flow <name>` | flow, `name` обов'язковий | `keylang/flows/*.md` |
| `# wiring` | wiring | `keylang/wiring.md` |

- **Р2. Вид визначає заголовок, а не шлях файлу.** Тому `rules.md` може лежати будь-де, а файл без жодного заголовка (як на слайдах) — це секція **map**.
- **Р3. В одному файлі може бути кілька секцій**: кожен `# …` починає нову (наприклад, кілька `# flow` в одному файлі). Вміст до першого заголовка — неявна секція map.
- Невідомий заголовок першого рівня (`# Shop`) — попередження **K006**, секція вважається map. Заголовок без виду (`#`, `# <!-- … -->`) — теж K006: «section heading without a kind».
- Зайві слова в заголовку — K005; `# flow` без імені — K005. Ім'я має лише `flow`: слово після `# rules`, `# map` чи `# wiring` (`# rules foo`) — K005, а не ім'я секції.
- Імена потоків — окремий простір імен: `# flow checkout` не конфліктує з ID карти, але два потоки з однаковим ім'ям — K002.

### Маркер генерації

```
<!-- keylang:generated — не редагувати, `keylang map` -->
```

Має бути першим непорожнім рядком. Текст після `keylang:generated` довільний. Парсер записує маркер в IR (`generated`), форматер зберігає його.

`keylang map` перевіряє **усі цільові файли** в `<dir>/map/` до будь-якого запису чи видалення. Файла ще немає — його буде створено. Перший непорожній рядок містить маркер — файл можна перезаписати. Інакше це конфлікт: повідомлення `manual file without keylang:generated marker` зі шляхом, код виходу 1, жоден файл карти й індекс не записуються і не видаляються. Зайвий файл видаляється лише тоді, коли він сам має маркер. `map --check` повідомляє той самий конфлікт окремо від застарілої карти (`stale`) і теж нічого не пише.

Коментар `<!-- keylang:llm … -->` (позначка, що фрагмент написав LLM) зарезервовано: парсер не надає йому семантики — як і будь-який інший HTML-коментар, він стає прозою, описом або коментарем елемента.

## 3. Відступи та ієрархія

- Глибина елемента = відступ / 2. Відступ — лише пробіли.
- Дочірній елемент може бути глибшим за батьківський рівно на один рівень.

| Помилка | Код | Відновлення |
|---|---|---|
| непарний відступ (`   - x`) | K003 | глибина = відступ / 2 з округленням вниз |
| стрибок більш ніж на рівень | K003 | елемент стає дитиною попереднього |
| таб у відступі елемента чи опису | K003 | таб рахується як 2 пробіли |
| порожній елемент (`- `) | K003 | рядок пропускається |

Таб у відступі прози чи блоку коду — текст, а не структура: K003 немає, `fmt` лишає рядок як є. Рядок із табом після відкритого списку — опис (відступ ≥ 2), тож там таб — K003.

**Р4. `keylang fmt` відмовляється форматувати файл з K003**: інакше форматер мовчки змінив би вкладеність. Семантичні помилки (K001, K002, K004, K005) форматуванню не заважають.

### Опис вузла

Текстовий рядок (не елемент списку) з відступом ≥ 2 стає описом найглибшого відкритого елемента, у якого колонка вмісту (`2·глибина + 2`) ≤ відступу рядка. Порожні рядки між елементом і описом дозволені.

```markdown
- deny domain infrastructure
  Домен чистий: жодного I/O.
```

- **Р5. Рядок з відступом 0 завжди проза і закриває список**, навіть без порожнього рядка перед ним. CommonMark у цьому разі вважає рядок «лінивим продовженням» останнього елемента; keylang — ні, а `fmt` вставляє порожній рядок, тому GitHub показує те саме, що бачить keylang.
- **Р6. Опис завжди належить вузлу, а не місцю.** Опис, записаний після дітей вузла, `fmt` переносить одразу під рядок вузла.
- HTML-коментар в окремому рядку — це звичайний текст: опис або проза.

## 4. Елемент списку

```
item     := indent bullet " " head [" " comment]
bullet   := "-" | "*" | "+"                ; fmt замінює на "-"
head     := token (sep token)*
token    := link | quoted | word | ","
link     := "[" text "](" target ")"       ; target без пробілів
quoted   := '"' <будь-що, крім '"'> '"'
word     := <символи до пробілу, табу або коми>
comment  := "<!--" <до кінця рядка>
```

- Кома — окремий токен, тому `a,b` і `a , b` означають те саме, що `a, b` (канонічна форма).
- Незакрита лапка — K005, токен читається як слово. `[`, що не відкриває посилання, — звичайне слово (сигнатури на кшталт `(errs: [Span, string][])`); K005 «malformed link» буває лише там, де очікується ім'я-посилання (`fn [name](path#Lnn)`).
- `<!-- … -->` у кінці рядка — коментар до елемента (`Node.comment`), у семантиці не бере участі (приклад — `compose` у design.md §5).

### Ідентифікатори

```
segment  := (літера | "_" | "$") (літера | знак | цифра | "_" | "$" | "-")*
id       := segment ("." segment)*
```

Літери — будь-які Unicode, а знак — комбінований знак (`\p{M}`), тож розкладене `café` (NFD, `e` + U+0301) — теж сегмент. Дефіс дозволено (`http-retry`, `order-store`), `$` — теж, щоб JS-імена `$save` і `_save` лишались різними ID.

### Прив'язка до коду

`[name](path#Lnn)` на місці імені оголошення: `name` стає іменем вузла, `path` і `nn` зберігаються в `Node.link` (підтримується і `#L12-L20`, береться початковий рядок). У M0 існування файлу не перевіряється. Спан імені вказує на текст усередині `[…]`.

Згенероване посилання рахується **від файла карти**, не від кореня репозиторію: для `keylang/map/domain.md` джерело `src/domain/order.ts` дає `../../src/domain/order.ts#L1`. Кожен сегмент шляху, крім `.` і `..`, кодується через `encodeURIComponent`, а `(` і `)` додатково стають `%28` і `%29`: `encodeURIComponent` їх залишає, але вони обривають Markdown-посилання. Приклад: `src/app/(shop)/page.ts` → `../../src/app/%28shop%29/page.ts#L1`. Пробіл і `#` кодуються як `%20` і `%23`. Парсер декодує шлях: `link.path` і `link.target` містять уже розкодований текст (`(shop)`, а не `%28shop%29`). Індекс зберігає POSIX-шлях від кореня репозиторію без кодування. Зіпсований escape лишається як написано.

Alias залежності не збігається з контекстним ключовим словом цієї позиції (`module`, `fn`, `type`, `event`, `calls`). Генератор додає числовий суфікс (`type` → `type2`), інакше рядок `- type main.type` читається як оголошення типу.

## 5. Ключові слова за позицією

Значення елемента залежить від **батька** (або виду секції на верхньому рівні). Перше слово є ключовим, тільки якщо воно дозволене в цій позиції; інакше спрацьовує правило «без ключового слова», а якщо його немає — K004 зі списком очікуваних слів.

**Р7. Ключові слова контекстні.** Наприклад, під модулем `test foo.bar` — це залежність з аліасом `test`, бо `test` — ключове слово тільки в потоках. І навпаки: під модулем не можна назвати залежність `fn`, `type`, `event` чи `module`.

| Позиція | Ключові слова | Без ключового слова |
|---|---|---|
| верх секції map | `layer`, `layers`, `allow`, `deny`, `entry`, `module`, `no-cycles` | `<name>` — шар (сумісність зі слайдами) |
| верх секції rules | `layers`, `allow`, `deny`, `entry`, `module`, `no-cycles` | K004 |
| верх секції flow | `kind`, `trigger`, `step`, `reads`, `emits`, `calls`, `invariant`, `when`, `test`, `planned` | K004 |
| верх секції wiring | `wire` | K004 |
| під `layer` | `module` | `<name>` — модуль |
| під `module` (map) | `module`, `fn`, `type`, `event` | `<alias> <id>` — залежність |
| під `fn` | `calls` | K004 |
| під `layers`, `entry` | — | `<id>` — посилання |
| під `module` (rules) | `exports`, `no-cycles` | K004 |
| під `step` / `trigger` | `step`, `reads`, `emits`, `calls`, `when`, `test`, `invariant` | K004 |
| під `when` (flow) | `then`, `step`, `test` | K004 |
| під `invariant`, `then` | `test` | K004 |
| під `wire` | — | `<alias> <id>` — перевизначення залежності |
| під залежністю в `wire` | `when`, `compose` | K004 |
| під будь-чим іншим | — | K004 «не може мати вкладених елементів» |

**Р8. Верхній рівень map приймає і правила** (`allow`, `entry`…), бо на слайді карта й правила записані в одному файлі. Верхній рівень rules шарів не оголошує: шари існують лише в карті.

`module` означає різне за позицією: під шаром — оголошення модуля, на верхньому рівні — посилання на модуль, до якого застосовуються правила (`exports`, `no-cycles`).

### Аргументи

| Форма | Аргументи | Семантика |
|---|---|---|
| `layer <name>` / `<name>` | рівно одне ім'я | оголошує `name` |
| `module <name\|link>` / `<name\|link>` | рівно одне | оголошує `parent.name` |
| `fn\|type\|event <name\|link> <signature…>` | ім'я + довільний текст | оголошує `module.name`; решта — `text` (сигнатура) |
| `<alias> <id>` під модулем | два токени | оголошує `module.alias`; `id` — посилання |
| `calls\|reads <id>[, <id>…]` | ≥ 1 ID | посилання |
| `layers <a> < <b> < …` | ID шарів (без крапки), розділені `<` | посилання на шари; вкладені `<id>` — шари без порядку |
| `allow\|deny <a> <b>…` | ≥ 2 ID: шари, модулі (клас теж) або їхні префікси | посилання; перший — хто, решта — на що; ID fn, type, event чи аліаса залежності — K005 |
| `entry` | нічого; точки старту — вкладеними `<id>` | посилання |
| `module <id>` (rules) | одне ID | посилання |
| `exports <name>[, <name>…]` | ≥ 1 ім'я (`- exports ,` — K005) | публічні імена модуля (відносні); порівнюються з таблицею експортів знімка, K001 не дають |
| `no-cycles` | нічого | — |
| `kind business\|technical` | одне з двох слів | `text` |
| `trigger\|step <id>` | одне ID | посилання |
| `planned fn\|module\|type\|event <id> [signature]` | вид, ID, довільний підпис | намір; не оголошення в індексі і не ребро знімка |
| `emits [event] <name>` | ім'я події | `text`; не резолвиться |
| `invariant <текст>` | довільний текст | `text` |
| `when <текст>` (flow) | довільний текст | `text` |
| `then <id>` / `then <текст>` | один токен-ID з крапкою → посилання, інакше текст | |
| `test <file> ["<name>"]` | шлях + назва в лапках | `text` = файл, `label` = назва |
| `wire <id>`, `compose <id>` | одне ID | посилання |
| `when <умова> → <id>` (wiring) | текст, `→` або `->`, ID | `text` + посилання |

`text` вільного тексту (`invariant`, `when`, текстовий `then`) — канонічний, як його пише `fmt`: токени через один пробіл, кома — `a, b`. Тож `fmt` не змінює ні текст, ні `specHash` вердиктів над ним.

Порушення форми — K005. Приклад зі слайда: `- options infrastructure.config.server` на верхньому рівні — це шар `options` із зайвим аргументом, тож K005 з підказкою «залежність має бути вкладена в модуль».

**Р10. `then` вгадує форму**: `then application.purchase.OutOfStock` — посилання, `then retry ≤ 3, backoff …` — текст. Критерій — рівно один токен, який є ID і містить крапку.

**Р11. `emits event order.created`** — слово `event` необов'язкове, ім'я події не перевіряється: у design.md воно не є шляхом карти. Зв'язок з `event` у карті — питання M3.

## 6. ID та резолвінг

- ID оголошення — крапковий шлях від кореня: шар → модуль(і) → `fn`/`type`/`event`/аліас залежності. Приклад: `application.purchase.buy`, `presentation.terminal.checkout` (аліас).
- **Р12. Аліаси залежностей теж мають ID.** Так `trigger presentation.terminal.checkout` з design.md §3.4 резолвиться в залежність `checkout` модуля `terminal`, а `wire` може на них посилатися.
- Посилання всередині файлів завжди абсолютні, крім `exports` (відносно модуля).
- Резолвінг глобальний: `keylang check <dir>` збирає всі `*.md` під директорією (рекурсивно, крім прихованих директорій, `node_modules` і `target`), будує один індекс і перевіряє всі посилання. Символічне посилання на файл чи теку читається як його ціль (цикл посилань обходиться раз), а файл, до якого ведуть два шляхи, — один документ під шляхом без посилання.
- Шари оголошує `keylang.json`, а карта друкує шар, лише коли в ньому є модуль. Тому шар конфігурації без модулів (наприклад, `wiring` до першого `keylang wire`) і синтетичні `external` та `unassigned` — відомі ID: правило може їх назвати без K001 і до того, як у них щось з'явиться.

Правило пошуку ID:

1. Точний збіг з оголошенням — ok.
2. Інакше береться найдовший оголошений префікс. Без знімка модуль без членів непрозорий (**Р13**, слайди: `infrastructure.config.log`). Зі знімком вирішує він: `members: complete` дає K001 на невідомого члена, а `members: opaque` (зовнішній модуль, помилка розбору, файл із `exclude`) — `unverified`, не K001, навіть коли карта перелічує члени, які вдалося прочитати з частково розібраного файла. K001 має підказку `did you mean` і `declare `planned``.
3. Інакше — **K001** висяче посилання з підказкою найближчого сусіда (`did you mean domain.orderAggregate?`). Префікс-шар непрозорим не буває, тому `domain.aggregate` — помилка. Сусід — ім'я, що містить відсутнє (або навпаки; коротше з двох — від 3 символів), чи близьке за відстанню редагування: до 1 для імен до 5 символів, до 2 для довших, 0 для одно- і двосимвольних. Тож `zz` не підказує `ab`, а `banana` — шар `a`.

Дублікати:

- **Р14. Шар можна продовжувати в кількох файлах** (`keylang/map/domain.md`, `keylang/map/app.md`) і повторювати в одному. Будь-яке інше повторне оголошення — **K002** з посиланням на перше. `planned` — окремий простір імен: той самий ID двічі — K002 з кодом чи без.
- Посилання під `module <id>` у rules не перевіряються, якщо сам модуль не знайдено (щоб не дублювати помилку).

## 7. Діагностики

Формат виводу `keylang check`: `file:line:col: CODE message`, рядок і колонка з 1, колонка в символах Unicode.

| Код | Рівень | Значення |
|---|---|---|
| K001 | error | висяче посилання |

**Вердикти.** Кожен результат перевірки — `ok` (критерій підтверджено в заявленій області), `fail` (підтверджене порушення; діагностика рівня error або вердикт `fail`) або `unverified` (порушення немає, але доказів бракує; причина друкується). Діагностика рівня warning (K006, K103, K202) у `--format json` має вердикт `warning` і не валить перевірку. Вердиктом `fail` вона не буває, тож CLI, JSON, LSP і TUI рахують її однаково; критерій і область такої діагностики правила вона несе сама (K103 — `entry` і модуль). У повідомленнях: **divergence** — підтверджена невідповідність, **absence** — відсутність обов'язкової сутності за достатніх доказів, **convergence** — підтверджений збіг (повідомлення `ok`-вердикту правила, наприклад `convergence: no edge from …`); невизначеність ніколи не перейменовується на `ok`. `warning` у JSON — не четвертий вердикт, а рівень діагностики: результат не валить перевірку. Кожен вердикт має `specHash` — SHA-256 правила чи рядка потоку, як їх записано, тож зміна специфікації змінює хеш; K102 називає і ребро в коді, і правило `deny` з його файлом і рядком.

**Команди** (повний перелік — `keylang --help`): `init` пише `keylang.json` з вгаданими шарами й будує карту (про кожну теку, чий шар довелося перейменувати, — примітка в stderr, див. «Імена шарів» нижче); `map [--check]` генерує карту, знімок і кеш фактів (з `--check` лише порівнює); `check [paths…] [--static behavior|shape]` — ця секція; `explain <code>` друкує причину, приклад і виправлення коду (регістр не важливий; для K001 — підказка про `did you mean` і `planned`), невідомий код — 2. `explain <id>` без мережі друкує, що про вузол кажуть знімок і специфікації: вид, ID і сигнатура; `файл:рядок` і видимість; `calls` / `called by` / `depends on` / `used by`; потоки з цим ID; правила, що називають його чи охопну область; нерозв'язане всередині за видами; fingerprint і closure. Невідомий ID — 2 з `did you mean`. `wire` — §7 «Wiring»; `trace-plan` — §7 «План trace»; `explain <id> --llm [--full]` — пояснення простою мовою від моделі з `agent` у `keylang.json` (`"anthropic:<model>"` через офіційний SDK, для Claude Opus 5 / Fable з серверним `fallbacks: "default"`; `"openrouter:<model>"` через chat completions із SSE). Ключ береться з `ANTHROPIC_API_KEY` (або `ANTHROPIC_AUTH_TOKEN` чи профілю `ant auth login`) чи `OPENROUTER_API_KEY`, інакше з `~/.config/keylang/<provider>.key`; порожня змінна ключем не вважається. Файл ключа, який можуть читати інші, відхиляється. Запит, що не завершився за `KEYLANG_LLM_TIMEOUT_MS` (мілісекунди, за замовчуванням 600000; для OpenRouter — разом із потоком SSE), переривається; відповідь без тексту, помилка OpenRouter у JSON замість потоку чи некоректний JSON у SSE — теж помилка з назвою провайдера. Усе це — код 2, і нічого не зберігається. `ANTHROPIC_BASE_URL` / `OPENROUTER_BASE_URL` переносять запити, наприклад на локальний мок у тестах. `explain.lang` (за замовчуванням `en`) і `explain.detail` (`short` — 2–3 речення, за замовчуванням; `full`) задають мову й деталізацію. У модель іде зведення вузла, його код (довге тіло обрізається, і промпт про це каже), сигнатури тих, кого він викликає і хто його викликає, та шар. Репозиторій повністю не передається. Відповідь зберігається в `.keylang/explain/<id>.md` з рядком `<!-- keylang:explain agent=… date=… closure=… lang=… detail=… -->`. `closure` — baseline, тобто `closure.fingerprint` вузла на момент пояснення; модуль, клас чи шар власного closure не мають, і їхній baseline — хеш їхніх залежностей і closure кожного вузла під ними, тож зміна члена робить пояснення модуля `stale`. Свіже пояснення тієї ж мови й деталізації читається без запиту. Друкується текст і рядок `agent · дата · fresh|stale`. ID у зворотних лапках, що починаються з імені шару, яких немає ні у знімку, ні серед `planned`, перелічуються рядком `unknown ids: …`. Без ключа — повідомлення в stderr, офлайн-зведення в stdout, код 0. `explain <id>` без `--llm` додає до зведення збережене пояснення зі статусом. `explain --stale` перелічує пояснення, чий baseline змінився (`stale`), і ті, чий ID зник (`gone`). Пояснення ніколи не змінює вердикт `check`. `draft flow <trigger> [--mode algo] [--name n] [--into <spec.md>] [--print]` пише пропозицію `.keylang/proposals/<spec>`, за замовчуванням для `<dir>/flows/<name>.md`, де `name` — останній сегмент тригера. Сама специфікація змінюється лише через MERGE (`m` у TUI). Режим `algo` детермінований: розв'язаний виклик fn репозиторію (не `external`) стає вкладеним `step` у порядку виклику в коді, глибина — до 4 рівнів. Уже внесена fn не розгортається вдруге, тож цикл завершується. Нерозв'язані виклики fn записуються коментарем `<!-- keylang:algo unresolved: … -->` у її рядку, кроком вони не стають. Якщо цільовий файл уже має `# flow <name>` (коментар після імені в заголовку не заважає), пропозиція замінює цю секцію, інакше дописує нову; секції знаходить парсер, а файл із CRLF у всіх рядках отримує пропозицію з CRLF. Ціль поза каталогом специфікацій, у карті чи за посиланням назовні — код 2 з причиною; `--print` пише текст у stdout і нічого не створює — ні пропозиції, ні `.keylang/stats.json`. `--mode llm` і `--mode hybrid` (за замовчуванням) звертаються до моделі з `agent`. Модель отримує граматику потоку, компактну карту (fn потоку та їхніх модулів із сигнатурами, до 300 рядків, решта позначена) і до трьох ручних потоків репозиторію, спершу тих, що мають найбільше спільних ID. ID, якого немає ні у знімку, ні серед `planned` (у чернетці чи специфікаціях), повертає чернетку моделі рівно один раз, з найближчим реальним ID і вимогою виправити посилання або оголосити `planned`. Невідоме й після цього кола друкується в stderr і після MERGE стане K001. Відповідь звіряється на розібраному потоці, а не за рядками. ID у зворотних лапках в елементі — це ID. Елемент, що не розбирається там, де стоїть (крок під `invariant`, невідоме ключове слово), відкидається разом із вкладеним, і stderr його називає: `dropped from the model's draft: <рядок>: <причина>`. Без `trigger` із запитаним ID він стає першим елементом з `<!-- keylang:algo status=algo-only -->`. Кожен рядок `trigger`/`step` отримує `<!-- keylang:llm model=<agent> status=agree|llm-only|conflict -->`: `agree` — крок є в algo-проєкції і його батько в чернетці досягає його resolved-викликами (вкладеність теж перевіряється), `llm-only` — інакше, `conflict` — ID називає не fn (модуль чи тип). `hybrid` дописує кроки algo-проєкції, яких модель не назвала, під найближчого з їхніх викликачів в algo-проєкції, що є в чернетці (інакше під `trigger`), з `<!-- keylang:algo status=algo-only -->`. Прийнятий рядок моделі не є доказом: `check` перевіряє його як будь-який крок, і `llm-only` без ребра — `unverified` або `fail absence`, але не `ok`. `hybrid` без налаштованої моделі друкує примітку й працює як `algo`; `llm` без моделі — код 2. `.keylang/stats.json` (`{schema: 1, drafts: {<status>: {proposed, accepted, rejected}}, suggestions}`) рахує запропоновані рядки за статусом, щойно пропозицію записано (запис, що не вдався, лише попереджає), а MERGE у TUI — прийняті й відхилені, за коментарями походження в кожному вирішеному шматку. `draft rules [--print] [--into <spec.md>]` пропонує правила, які код уже виконує, для `<dir>/rules.md`. Якщо шари утворюють ациклічний граф, це `layers` у порядку, де кожна спостережена залежність іде вниз; інакше — `deny` для кожної пари, використаної лише в одному напрямку. `no-cycles` додається, якщо циклів модулів немає. У наявному файлі правила додаються в кінець його останньої секції `# rules`, а без неї — новою секцією `# rules` у кінці, тож хвостовий `# flow` їх не поглинає. Правило, яке файл уже має (без урахування коментарів), не повторюється. `draft map` друкує розкладку шарів, яку вгадав би keylang, у форматі `keylang.json` і нічого не пише. `--mode llm|hybrid` (за замовчуванням `hybrid`; без моделі — `algo` з приміткою) у `draft rules` передає моделі шари й кількість ребер між ними. Кожне запропоноване правило перевіряється одразу й окремо: знімок і специфікації без інших правил, з цим правилом і без нього. Нова помилка (K101, K102…) дає `conflict`, а в stderr іде рядок із доказом, наприклад `conflict: - deny app infra → src/app/checkout.ts:2: K102 …`. Нерозібране правило теж `conflict`. `unverified` дає `llm-only`, решта — `agree`. `hybrid` дописує правила `algo`, яких модель не дала. `draft map --mode llm` друкує розкладку моделі після тієї ж валідації, що й `keylang.json` (невалідна — код 2). Шари ніколи не призначаються без людини: `keylang.json` не змінюється. `code-to-spec <path[:line]> [--print] [--into <spec.md>]` робить потоки з коду. З рядком — найглибша fn, що його містить, стає тригером чернетки `algo`, як у `draft flow`. Без рядка — так само кожна експортована fn файла в порядку оголошення. Пропозиція йде для `<dir>/flows/<name>.md`, де `name` — fn або модуль файла. Однойменні fn (методи `A.save` і `B.save`) отримують імена потоків із кількох останніх сегментів ID: `# flow A-save`, `# flow B-save`. Нерозв'язані виклики позначаються коментарем. Рядок поза fn — код 2. `code-to-spec --since <git-ref>` замість шляху бере зміни робочого дерева відносно ref (`git diff --relative --no-renames --unified=0` зі шляхами без C-лапок, тож перенесений файл — це нові рядки: його fn мають нові ID) і файли, яких git ще не відстежує. Кожна fn, чий діапазон рядків перетинає зміну, стає чернеткою для `<dir>/flows/changes.md`. Fn, яку вже називає написаний вручну потік, не перечернетується: її перелічує stderr (`changed and already in flows (review those): …`). Fn, що є кроком чернетки іншої зміненої fn, лишається всередині неї. Без змінених fn — повідомлення й код 0 без запису. Без `git`, з невідомим ref чи разом зі шляхом — код 2. `spec-to-code <id> [--into <file>] [--apply]` будує заготовку для `planned fn`: функцію з оголошеною сигнатурою (`(a: A) → R`; для TS `async`, коли `R` — `Promise<…>`), що кидає `not implemented: <id>` (у Python — `NotImplementedError`, у Rust — `todo!`; оголошені параметри й результат переносяться як записано — у Python анотаціями, а новий файл отримує `from __future__ import annotations` — тож заготовка сама не дає K201; до файла з CRLF у всіх рядках дописується з CRLF). Файл — це файл модуля ID, якщо модуль є у знімку, інакше `<корінь глобу шару>/<сегменти>.<розширення першої мови>`. Шар із кількома коренями вимагає `--into`, а файл, що не дає цей модуль, — код 2. Цей файл і кожен шлях `test` потоків перевіряються правилами пропозиції коду (§12) ще до читання: шлях не простий відносний, у прихованій теці, через символічне посилання назовні (зокрема на ще не створену ціль) чи файл із маркером `keylang wire` — для коду код 2, для тесту примітка в stderr, і файл не читається. ID, що вже є в коді, — код 2 з місцем реалізації: повторний запуск не дописує другу заготовку. Кандидат перевіряється як overlay-знімок до запису: друкується diff і все, що кандидат додає до `check` порівняно з кодом без нього — вердикти й діагностики, де б вони не були (K102 чи K103 у новому файлі теж). Без прапорця кандидати стають пропозиціями `.keylang/proposals/<файл>` (код і тести), які зливаються по шматках `m` у TUI; `--print` лише друкує, `--apply` пише файли напряму: атомарно, зі збереженням прав і CRLF, і лише якщо кожен файл досі такий, яким кандидат його прочитав — правка, зроблена тим часом (наприклад, під час запиту до моделі), дає код 2 без жодного запису; разом з `--print` — код 2. Для кожного `test <файл> "<назва>"` потоків, що називають ID, якщо файла ще немає і код та тест — TS/JS, друкується й новий файл `node:test`: імпорт fn відносним шляхом і тест з оголошеною назвою, що падає (`assert.fail`), доки його не напишуть. Тож після запуску `tests` — `fail`, а не `ok`. Тест в уже наявному файлі або іншою мовою лишається людині: stderr каже, куди його дописати. Код і тести keylang сам не записує без MERGE або `--apply`. ID, якого немає ні серед `planned`, ні в коді, коду не отримує: код 2 з `did you mean` і пропозицією оголосити намір. Якщо в потоці є крок над цим ID, а `deny` забороняє ребро від нього, це теж код 2. Після `--apply` і `map` ID перевіряється як код: `ID ok`, K202 пропонує прибрати `planned`, а `tests` і `trace` лишаються `unverified`, доки тести не виконано. Файл overlay, якого ще немає на диску, входить у знімок як джерело. `code-to-spec --mode llm|hybrid` (за замовчуванням `hybrid`, як у `draft`) проводить кожну чернетку через модель за правилами `draft flow`: одне коло для невідомих ID, звіряння й коментарі походження. `spec-to-code --mode llm` просить у моделі всю функцію з оголошеними ім'ям і сигнатурою, а потім — файл e2e-тесту з назвами тестів потоку. Кандидат аналізується так само, як заготовка. Відповідь без функції з цим ім'ям або тест без оголошеної назви — код 2, і нічого не записується. `lsp` — §9; `parse [--json]`, `fmt [--check]` — §8–9.

**Правила (K101–K105)** рахуються на ребрах актуального знімка. `keylang check` перебудовує аналіз у пам'яті і не записує карту чи `.keylang/index.json`. Згенеровані файли `map/` замінюються картою, відрендереною з цього знімка, тож ID у flows і rules резолвляться за поточним кодом, навіть якщо закомічена карта застаріла. Корінь репозиторію — найближчий вгору каталог із `keylang.json`; шлях до специфікацій можна записати як завгодно (`keylang`, `./keylang`, абсолютний, `.` зсередини). Діагностика вказує на файл і рядок коду, де є ребро. Якщо в каталозі немає коду (examples, слайд), правила дають `unverified` з причиною `no snapshot`, а резолвінг ID лишається. Підсумок у stderr: `N fail, M unverified, K ok`. Коди виходу: `0` — блокувальних знахідок немає; `1` — порушення, а з `--strict` також будь-який `unverified`; `2` — некоректний виклик або I/O. `--format` не змінює вердикт і код виходу:

- `human` — рядки `file:line:col: CODE|verdict message` у stdout;
- `json` — лише JSON у stdout: `{snapshotId, results[], coverage[]}`; кожен результат має `criterion`, `area`, `verdict` (`fail` / `unverified` / `ok`; для діагностики рівня warning, як K006 чи K103, — `warning`: вона не валить перевірку), `evidence`, `snapshotId`, `specHash`, `provenance`, `file`, `line`, `col`, `code`; діагностика правила чи потоку бере критерій, область, `specHash` і `provenance` свого вердикту, а діагностика без вердикту (K003, K201…) — `specHash` як SHA-256 свого коду й повідомлення; `provenance` — `syntactic`, крім доказів `test-report` і `trace`;
- `sarif` — SARIF 2.1.0: `fail` → `error`, `warning` → `warning`, `unverified` → `note` з `ruleId: unverified` (зокрема докази потоків); `ruleId` іншого результату — K-код або вид доказу потоку (`static`, `tests`, `trace`); `properties` результату несуть verdict, criterion, area, `snapshotId`, `specHash` і `provenance`; run має `columnKind: "unicodeCodePoints"`, бо типова одиниця SARIF — UTF-16;
- `github` — workflow-команди `::error` / `::warning` / `::notice` з `title` — тим самим `ruleId`, з екранованими `%`, переносами, `:` і `,`; `col` — та сама колонка в символах Unicode (GitHub одиниці не задає).

У всіх форматах `line` і `col` починаються з 1, а `col` рахує символи Unicode (code points), для специфікацій і для коду.

`--explain-edge <a> <b>` друкує ребра знімка між `a` і `b` (або їхніми нащадками) — спершу `a → b`, потім `b → a`: вид, стан, походження, діапазон, фрагмент коду й кандидатів `ambiguous`; сортування — вид, файл, рядок, колонка. Без ребра друкує `no edge, coverage complete` або перелік нерозв'язаних конструкцій `a` із причинами. Невідомий ID (зокрема невідомий хвіст під відомим модулем) — код 2. Нічого не пише.

Уточнення:

- **Імена шарів.** Ім'я шару в `keylang.json` — один сегмент ID. `external`, `unassigned` (синтетичні шари keylang) і ключові слова верху карти (`layer`, `layers`, `allow`, `deny`, `entry`, `module`, `no-cycles`: карта пише шар рядком `- <name>`) зарезервовано — такий шар є помилкою конфігурації з кодом 2, що називає файл і поле `layers.<name>`. `init` таких імен не вгадує: тека `src/external/` стає шаром `external_`, а друга тека, що санітизується в уже зайняте ім'я (`src/2fa/` і `src/_2fa/` — обидві `_2fa`), — `_2fa_2`; про кожне перейменування — примітка в stderr. `dir` нормалізується: `./keylang/` — це `keylang`.
- `layers a < b < c`: `a` найнижчий; залежність може йти лише вниз (`c` → `a` можна, `a` → `c` — K101). Вкладені під `layers` шари, а також `external` і `unassigned`, — без порядку: залежність *у* них вільна, якщо не заборонена `deny`. Усі рядки `layers` разом — один частковий порядок: `a < b` і `b < c` ставлять `c` над `a` (`a` → `c` — K101), а `a < b` і `c < d` нічого не кажуть про `a` і `d`. K005 (і рядок не перевіряється): шар двічі в одному рядку, ID з крапкою замість шару, рядок, що суперечить попереднім (`b < a` після `a < b`), шар, водночас впорядкований і вкладений. Кожен рядок `layers` має вердикт: `ok`, коли жодна залежність не порушує порядку його шарів і в області (модулі його шарів і шарів поза будь-яким порядком) немає прогалини рівня залежностей; з прогалиною — `unverified` з її назвою; порушення — K101.
- `allow`/`deny` приймають шари, модулі й їхні префікси; клас — модуль свого файла, тож його ID теж область: ребро до класу чи з його методу — доказ. ID fn, типу, події чи аліаса залежності (зокрема `planned fn`) — K005 з назвою модуля, бо ребра правил — між модулями, і таке правило нічого б не перевіряло. Перемагає найконкретніше правило: специфічність — сума глибин обох ID у сегментах (`app.purchase` — 2), не довжина рядка; при рівності — `deny`. Тож `deny app.x domain` (2 + 1) і `allow app domain.storefront` (1 + 2) рівні, і перемагає `deny`, а `allow app.x.y domain` (3 + 1) перемагає `deny app domain.storefront`. `allow` знімає K101 для своєї пари. Одна залежність модуля від модуля — одна K102 на правило, скільки б ребер її не показували (імпорт, виклик, тип-клас). Кожне `deny` має власний вердикт: підтверджене заборонене ребро — `fail`; інакше `unverified`, якщо в області є прогалина рівня залежностей (нерозв'язаний чи обчислюваний імпорт, синтаксична помилка, виключений файл, тека, яку не вдалося прочитати, `eval`), і `ok` без неї. Дірка всередині однієї декларації (`unsupported` із `source` — ID fn чи класу, як Python-декоратор, що може підмінити fn) змінює, який код виконує виклик, а не що імпортує модуль, тож прогалиною рівня залежностей не є. Область без жодного модуля — `unverified` «planned», коли вона існує лише як `planned`, і `ok` «no module … yet» інакше (шар без модулів). Виклик через локальне значення залежності між модулями не створює: без імпорту код іншого модуля недосяжний.
- `entry`: досяжність іде лише ребрами `import` / `call` / `type` / `re-export` знімка, зокрема через `index.ts`, що реекспортує сусідів, і через модуль, названий відносно модуля: `new URL("./worker.ts", import.meta.url)` (як у `new Worker(…)`) та `register(spec, import.meta.url | { parentURL: import.meta.url })` — ребро `import`, коли специфікатор — рядок, тернарник рядків або `const`, прив'язаний до такого (`URL` — лише відносний шлях із розширенням JS/TS). Пункт `entry` з ID модуля, якого немає у знімку, — K001, тож видалений worker, записаний в `entry`, помітний; його нерозв'язаний `new URL(…)` — ще й прогалина `unresolved import` у модулі, що його завантажує. Ієрархія ID не робить сусідів досяжними, а тека-модуль без власного коду не звітується. Клас — частина модуля свого файла: досяжний файл робить досяжними його класи, і невикористаний експортований клас K103 не отримує. K103 вказує на файл модуля. Коли досяжні всі модулі, кожен рядок `entry` має вердикт `ok`. Прогалина рівня залежностей у досяжному модулі (нерозв'язаний імпорт тощо) перетворює недосяжність на `unverified` із назвою цієї прогалини, а не на K103. Модулі шарів без порядку не перевіряються. `entry` із шаром чи префіксом (`- domain`) — точки старту всі модулі під ним.
- `exports` порівнюється з таблицею публічних експортів самого модуля знімка, не з fn без `<!-- internal -->` і не з таблицями його підмодулів: `purchase/buy.ts` поруч із `purchase.ts` — окремий модуль зі своїми експортами. Модуль правила, що існує лише як `planned`, — `unverified` «planned»; відомий ID, що не є модулем знімка (шар, fn), — `unverified`; невідомий — лише K001. Імена в `exports` — публічні імена модуля, а не ID карти, тож K001 вони не дають. `export { a as b }` порівнюється за `b`, `export default …` (включно з `export default function main`, `export default 3`), TypeScript `export = x` і CommonJS `module.exports = x` — за `default`, `export namespace N {}` і `export * as N from` — за `N`, `export * from "./x"` розкривається до імен `x` без `default` (транзитивно й через цикли `export *`; ім'я, яке два джерела `export *` дають різними оголошеннями, ESM не експортує). Зайве ім'я — K104 із видом і формою (`alias`, `default`, `namespace`, звідки re-export); заявлене відсутнє ім'я — absence. `export *` із модуля з невідомим вмістом (зовнішній пакет, нерозв'язаний або виключений файл, файл із синтаксичною помилкою) робить правило `unverified`, а не absence; так само непрозорий модуль правила (файл з `exclude`, помилка розбору) — заявлене відсутнє ім'я там `unverified`.
- Цикли — це SCC графа `import` / `re-export`. `no-cycles` під модулем спрацьовує, якщо модуль або його підмодуль входить у SCC; маршрут проходить через нього. Файл, що імпортує сам себе, — self-loop і теж цикл. Одна K105 на кожну SCC. Без циклу серед відомих імпортів, але з прогалиною залежностей в області (обчислюваний `import()`, нерозв'язаний імпорт) — `unverified`, не `ok`.
- `planned fn|module|type|event <id> [signature]` — намір (кандидат до v1): рядок верхнього рівня секції flow, сигнатура — довільний текст до кінця рядка. Посилання на нього не є K001: `ID` і `static` — `unverified` «planned», trace його не вимагає, ребер у знімок він не додає. Повторна декларація того самого ID — K002 (і в каталозі без коду). Коли в коді з'являється символ із цим ID, крок перевіряється як звичайний код, а декларація дає K202 (вид і сигнатура збігаються; сигнатури порівнюються без пробілів, `->` = `→`) або K201 (інший вид чи сигнатура). Виду `event` у знімку немає, тож fn, тип чи модуль з ID запланованої події — K201.

`keylang lsp` віддає ті самі коди, позиції й вердикти, що й `check`.

### Flows: докази кроку

`step` задає **вкладеність** щодо батьківського кроку; сусідні кроки — **послідовність**. Для кроку верхнього рівня (поруч із `trigger` чи під ним) батьком є `trigger`. Кожен вид доказу друкується окремим рядком `file:line:col: <доказ> <verdict> <id>: <причина>`, а в `--format json` — окремим результатом із `criterion` (`ID` / `static` / `tests` / `trace`), `area` (ID кроку або текст твердження), `verdict`, `evidence` і `provenance` (`syntactic`, `test-report`, `trace`; для trace також `runId`, `testId`).

| Доказ | ok | unverified | fail |
|---|---|---|---|
| `ID` | символ є у свіжому знімку | `planned`, член `opaque`-модуля | K001 — відсутній у `complete`-модулі (`static` тоді не друкується) |
| `static` | шлях resolved-викликів від батька, жоден з яких не сидить у closure (сусідні кроки шляху не потребують; рекурсія — шлях); з `--static=behavior` (типово) — також через хук: «through the default of the hook `g`», «`g` injected at file:line:col» | шлях є, але проходить через тіло, що може не виконатися: fn під декоратором чи атрибутом, якого keylang не знає (`@replace` може повернути іншу функцію; у coverage — `@…` чи `#[…]` з `source` цієї fn або перед нею), або код модуля, що не розбирається («may not run its own body», «is in a module that does not parse» з позицією); шляху немає, але його могла б дати конструкція, яку keylang не відстежує (нижче): з нею та позицією; шляху немає, а досяжний код є в модулі, що не розбирається; батько чи крок — не функція; `planned` | `absence: no call path …` — крок і його виклики досяжні лише за назвою, і жоден виклик із досяжного коду не може їх назвати |
| `tests` | однозначний тест пройшов у звіті поточного знімка | звіту немає, тест не знайдено, неоднозначний (перелік кандидатів), пропущений, звіт іншого знімка або без `snapshotId`; твердження без `test` («no test evidence»; для кількісних чи заперечних — «needs a separate predicate or test») | тест провалився |
| `trace` | крок спостережено в завершеному запуску тесту з вкладенням і підтвердженим порядком | trace іншого знімка чи без нього; неповний запуск, навіть коли крок спостережено (`complete: false` у будь-якій події `run` чи її немає, `dropped > 0` або не вказано, відкриті spans; для відсутнього кроку — ще й символ не інструментовано); різні годинники без `links` (зокрема `end` попереднього на іншому годиннику); паралельні sibling-и; асинхронний крок без `link`; гілка `when` не виконувалась | обов'язковий крок відсутній у завершеному й інструментованому запуску за будь-якого вибору spans; крок почався раніше за попереднього сусіда |

**Static без шляху.** Коли resolved-шляху немає, пошук триває через виклики з кількома можливими цілями: виклик із невідомим отримувачем (`x.feed()`, `cb()`) може бути будь-якою fn тієї ж назви, розв'язаний виклик методу — перевизначенням тієї ж назви, неоднозначний — будь-яким кандидатом, ребро хука в режимі `shape` — своєю ціллю, а виклик у closure (`return () => hit()`, колбек `items.forEach(() => …)`) — своєю ціллю лише тоді, коли цю функцію-значення хтось викличе: маршрут, що доходить до кроку тільки так, — `unverified` «reached only through a closure of X». Знайдений так маршрут дає `unverified` із першим таким викликом на ньому (найближчим до батька; виклики з назвою кроку перевіряються раніше) і лічильником `(and N more unresolved calls in reachable code)`. Інакше `unverified` лишається, якщо fn на якомусь маршруті до кроку «тікає»: прочитана як значення (`later(save)`, `{ save }`, `obj.save` без виклику, `extends A` для конструктора `A`; за назвою, в усьому репозиторії), accessor, неявний метод (`then`, `next`, `return`, `throw`, `toString`, `valueOf`, `toJSON`), викликана з closure; викликана з коду поза оголошеннями — верхнього рівня модуля (він виконується під час завантаження, зокрема через `import()` чи `new Worker(new URL(…))`), методу об'єктного літерала, функції-значення, обгорнутої викликом (`export const load = cache(() => step())`), — «is called from module-level code» / «from a function value outside declarations» (виклик із невідомим отримувачем там робить такою кожну fn тієї ж назви); метод класу, чий базовий клас keylang не прочитав (пакет, глобальний, нерозв'язаний: `extends Readable`, `extends React.Component`, і їхні нащадки), — «may be called by the base class»; синтезований `Class.static` (виконується під час завантаження). Так само `eval`, `new Function`, `obj[k]()` чи `import(expr)` у коді, до якого веде доведений або можливий маршрут, обчислюваний член класу, `namespace` чи інша непрочитана конструкція, що згадує таку fn (ім'я — цілим ідентифікатором, зокрема з `$` чи не-ASCII літерами), і непрочитаний (`opaque`) модуль при будь-якій дірці. Повідомлення називає причину з позицією; нерозв'язаний виклик із досяжного коду воно називає лише тоді, коли той виклик є в fn, що передала значення далі, або в коді, який вона викликає. Лише коли нічого з цього немає — `fail`: він має бути надійним, тож за сумніву вердикт — `unverified`.

**Хуки (`--static`).** Хук — виклик через локальне значення, параметр чи поле з типовим значенням поруч: `const g = p.x ?? f` (або `||`), `const { x: g = f } = p`, параметр `g = f` чи `{ g = f }`, поле `this.g = options.g ?? f` у конструкторі (або параметр-властивість `private readonly g = f`). Виклик `g()` лишається діркою в `coverage` («call through the hook `g` (default `f`)») і дає ребро `call` з `via: "default"` до `f`. Якщо `p` — параметр самої функції (для поля — параметр конструктора), розв'язаний виклик, що передає за тим самим аргументом і властивістю функцію-значення (`analyze({ generate: worker.generate })`, `new App({ analyzer })`, `run(save)`), дає ребро `via: "injected"` з `site` — позицією того виклику; контекст виклику не розрізняється. `--static=behavior` (типово) доводить шлях і цими ребрами, `--static=shape` — лише записаними викликами; `--static` з іншим значенням — код 2. Ребро `default` карта друкує в `calls` і правила бачать (модуль і так імпортує `f`); `injected` — ні: це залежність того, хто передає значення.

`tests` друкується на твердженні (`invariant`, `when`, `then`, `reads`, `emits`), до якого прив'язаний `test`. `trace` для `when` — «branch exercised» або «branch not exercised»; кроки невиконаної гілки в цьому тесті не обов'язкові. Вердикт кроку за кількома тестами: `fail`, якщо хоч один тест його порушив; інакше `ok`, якщо хоч один підтвердив. Без `check.tests` / `check.trace` відповідні докази не друкуються (зокрема «no test evidence» для твердження без `test`): непотрібний вид доказу не входить до агрегації й до `--strict`.

### Звіт тестів (`check.tests`)

`check.tests` у `keylang.json` — шлях (має існувати, інакше код 2) або глоб (може ще нічого не знаходити: тоді «no report»). Формат визначається за вмістом:

- **JSON keylang, схема 1** — `{"schemaVersion": 1, "snapshotId", "runId", "tests": [{"file", "suite"?, "name", "status": "pass"|"fail"|"skip"}]}`. Пише репортер `node:test` з пакета: `node --test --test-reporter=spec --test-reporter-destination=stdout --test-reporter=keylang/node-test-reporter --test-reporter-destination=stdout` (у цьому репозиторії — `./src/adapters/node-test.ts`, див. `npm test`). Він рахує `snapshotId` поточного коду і пише `.keylang/reports/node-test.json` (або `KEYLANG_TEST_REPORT`); suite — вкладені `describe`/`test`, через ` > `.
- **JUnit XML** — `<testcase file classname name>` з `<failure>` / `<error>` / `<skipped>` у `<testsuite>` (вкладених чи під `<testsuites>`); читається як XML: лапки обох видів, сутності, коментарі, CDATA. Зв'язок зі знімком — `<property name="keylang.snapshotId" value="…"/>` у `<properties>` самого testcase або найближчого suite навколо нього (так само `keylang.runId`): кожен suite злитого звіту має власний знімок. Без нього testcase не підтверджує поточний код. Некоректний XML — код 2 з `file:line`.

`test <file> "<name>"` зіставляється за файлом і назвою; `"Suite > name"` уточнює suite. Некоректний звіт — код 2 з назвою файла й поля.

### Trace (`check.trace`), JSONL схеми 1

`check.trace` — шлях або глоб до файлів JSONL. Кожен рядок — подія одного запуску тесту `(runId, testId)` для потоку `flow`. Файл запуск не розділяє: події процесів одного тесту можуть лежати в різних файлах, і це той самий запуск:

```jsonl
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s1","parentSpanId":null,"symbolId":"cli.cli.main","clockId":"pid-7","seq":1,"ts":12.5}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"start","spanId":"s2","parentSpanId":"s1","symbolId":"cli.cli.run","clockId":"pid-7","seq":2,"ts":12.6}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s2","outcome":"ok","clockId":"pid-7","seq":3,"ts":40.1}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"end","spanId":"s1","outcome":"ok","clockId":"pid-7","seq":4,"ts":40.2}
{"schemaVersion":1,"snapshotId":"…","runId":"r1","testId":"tests/cli.test.ts > @flow check","flow":"check","traceId":"r1:t","event":"run","complete":true,"dropped":0,"instrumented":["cli.cli.main","cli.cli.run"],"open":[]}
```

- `start`: `spanId` (унікальний на виклик — повтори й рекурсія мають різні), `parentSpanId`, `symbolId` (ID знімка), `clockId` + `seq` (порядок подій одного годинника), `ts`, необов'язкові `links` (каузальні зв'язки з іншими spans); `end`: `spanId`, `outcome`; `run` — метадані завершення: `complete` (boolean), `dropped` (невід'ємне ціле), `instrumented` (ID символів), `open` (ID spans). Кожен процес пише власну подію `run`: запуск завершений, лише коли завершені всі, `dropped` сумується, `open` об'єднується, а інструментованим вважається символ, який назвали всі. Без `dropped` кількість втрачених подій невідома — запуск неповний.
- Кроки зіставляються як підпослідовність із вкладенням у межах одного тесту: зайві виклики дозволені, одна подія задовольняє один крок. Кожен span тригера чи кроку — кандидат: тест може викликати його кілька разів (спершу з раннім `return`), і перемагає вибір spans, що спостерігає найбільше кроків (за рівності — з меншою кількістю `fail`, потім раніший). Тож `missing step` означає, що жоден вибір цього кроку не спостеріг. Порядок сусідів підтверджує `end` попереднього раніше за `start` наступного на тому самому `clockId` або `links` на попереднього; сортування `ts` порядок не доводить. Дочірній span, що почався після завершення батька, підтверджує вкладення лише з `link` на батька.
- Невідома версія, некоректний рядок чи поле — код 2 з `file:line` і назвою поля.

**Адаптер TS/JS.** `node --import keylang/trace <script>` (у репозиторії — `./src/adapters/trace.ts`) з `KEYLANG_TRACE` (файл), `KEYLANG_TRACE_FLOW` (потік), `KEYLANG_TRACE_TEST` (ID тесту), необов'язково `KEYLANG_TRACE_RUN` і `KEYLANG_TRACE_ROOT`. Hooks модулів будують знімок в окремому потоці, знаходять `trigger` і `step` потоку й обгортають тіла цих функцій (генератори не інструментуються); вкладення — через `AsyncLocalStorage`, асинхронне продовження отримує `link` на батька. Файл, що не збігається з копією знімка, не інструментується. E2E-тест позначається `@flow <name>` у назві й запускає код з адаптером; у keylang це тест `@flow check` у `tests/cli.test.ts`, що пише `.keylang/trace/check.jsonl`. Assertions у trace і граматика паралельних груп — ще не частина схеми 1.

**План trace.** `keylang trace-plan <flow>` будує свіжий знімок і друкує JSON: `schemaVersion: 1`, `snapshotId`, `flow`, `symbols` — fn із `trigger` і `step` потоку з `id`, `name`, `file`, `line`, `col` і `sha256` файла, який бачив знімок. Сортування — за ID. Потоку немає ні в одній специфікації — код 2. Адаптери мов без hooks Node читають цей план замість специфікацій.

**Адаптер Python.** `python3 <keylang>/adapters/python/keylang_trace.py <script> [args…]` зі змінними `KEYLANG_TRACE`, `KEYLANG_TRACE_PLAN` (файл від `trace-plan`) і `KEYLANG_TRACE_TEST`, необов'язково `KEYLANG_TRACE_RUN` і `KEYLANG_TRACE_ROOT`. Потрібна лише стандартна бібліотека. На Python 3.12+ адаптер працює через `sys.monitoring` (`PY_START` / `PY_RETURN` / `PY_UNWIND`, помилка дає `outcome: "error"`), на старших версіях — через `sys.setprofile`, де будь-який span завершується `ok`. Записуються лише функції плану з файлів, чий `sha256` збігається: змінений після плану файл не інструментується і не потрапляє в `instrumented`. Код функції зіставляється точно: реальний шлях файла, ім'я і перший рядок коду, який адаптер бере з `ast` файла для оголошення з рядка плану (перший декоратор, інакше `def`). Однойменний метод іншого класу чи функція в іншому місці файла кроком плану не стає. Генератори й корутини (`async def`, функція з `yield` у власному тілі) не записуються і з `instrumented` виключаються одразу, навіть якщо їх не викликали чи не ітерували: їхні кадри призупиняються, тож стек викликів не дає вкладення. Вкладення будується за стеком викликів окремого потоку. Процес із неперехопленим винятком або з ненульовим `sys.exit` дає `complete: false`; `sys.exit()` і `sys.exit(0)` — ні.

**Адаптер Rust.** Runtime-хуків у Rust немає, тож функції потоку позначаються явно: `adapters/rust/keylang_trace.rs` (один файл без залежностей) підключається модулем (`#[path = "…/keylang_trace.rs"] mod keylang_trace;`). У синхронній функції пишеться `let _span = keylang_trace::span("<id>");`, в асинхронній тіло обгортається: `keylang_trace::instrument("<id>", async move { … }).await`; наприкінці `main` — `keylang_trace::finish()`, що дописує JSONL і запис `run`. Змінні ті самі, що в Python-адаптері. Без `KEYLANG_TRACE` нічого не записується. Записуються лише функції плану. `instrumented` — функції плану, в тілі яких (у коді, не в коментарі й не в рядку) є `span("<id>")` чи `instrument("<id>", …)`. Тому крок без span має `trace unverified` «not instrumented», а span, до якого виконання не дійшло, — `trace fail missing step`. Span, що завершується під час паніки, дає `outcome: "error"`, а `instrument`-future, скасована до завершення, — теж `error`. Вкладення будується за стеком потоку. `instrument`-future стоїть на ньому лише під час свого `poll`; батько її span — span, поточний там, де future створено, з `links` на нього, якщо він уже завершився. Guard `span()` у функції з `async` чи `.await` не записується й не інструментується: поки future призупинена, guard лишався б на стеку потоку і ставав би батьком інших future, які той самий потік опитує. Span, що завершується, коли почате після нього span ще відкрите (guard, утриманий через призупинення), робить запуск `complete: false`. Span в іншому потоці стає коренем. Зміну джерела після плану показує `stale trace`, бо свіжий знімок має інший `snapshotId`. Чи зібрано бінарник саме з цих джерел, адаптер не перевіряє.

### Wiring (`# wiring`, `keylang wire`)

Контракт — [ADR 0003](adr/0003-wiring-lifecycle.md) (прийнято). `- wire <id>` — фабрика: fn (виклик з об'єктом іменованих залежностей) або клас (`new` з тим самим об'єктом). Дочірні `- <name> <id>` — залежність `name`, яку будує фабрика `<id>`. ID без власного `wire` — лист, він створюється без аргументів. Під залежністю `- when env.NAME = value → <id>` обирає іншу реалізацію, коли змінна середовища має саме це значення: `value` — одне слово, як його записано до `→` (кома — частина значення: `env.DB = a,b` порівнюється з `a,b`). Кілька `when` перевіряються в порядку запису, без збігу діє рядок залежності. `- compose <id>` обгортає значення fn одного аргументу; кілька `compose` застосовуються в порядку запису, перший найближчий до значення.

`check` перевіряє розділ разом з іншими специфікаціями. Невідомий ID — K001, повторний `wire` того самого ID — K002, як і дві залежності з одним ім'ям під одним `wire` (об'єкт аргументів мав би ключ двічі). Умова не у формі `env.NAME = value` — K005. Цикл між фабриками (через залежності та гілки `when`) — K301 з повним шляхом. K302 — те, що згенерований файл не може імпортувати чи викликати: модуль, шар чи тип як фабрика або залежність; `compose` не з fn (модуль, тип, клас); метод класу (знімок не каже, статичний він чи ні); ім'я, якого модуль не експортує; fn Python чи Rust (`wire` генерує TypeScript). Клас у знімку — вузол-модуль, оголошений у файлі свого батьківського модуля. Залежність (зокрема `when` і `compose`), яку забороняє `deny` між ID фабрики й залежності, — K102 з текстом правила та його `файл:рядок`.

`keylang wire [--check] [--out <file>]` пише `keylang.gen.ts` (або `<file>` відносно кореня) з маркером `// keylang:generated`. `<file>` — простий відносний шлях із розширенням `.ts`, `.mts` чи `.cts` усередині репозиторію й після символічних посилань (зокрема ще не створеної цілі посилання); інакше код 2, і нічого не читається й не пишеться. Відсутню теку буде створено. Запис атомарний: тимчасовий файл і rename, права файла зберігаються. Файл без маркера не перезаписується (код 1). Будь-яка помилка на рядках розділу `# wiring` (з переліку вище, а також K003–K005 розбору) дає код 1, і нічого не записується. `--check` порівнює й нічого не пише: застарілий файл — код 1; файл, що відрізняється лише CRLF, застарілим не вважається. Згенерований файл експортує `async function wire(env)`: `env` за замовчуванням береться з `globalThis.process.env`, тож файл не потребує типів Node. Кожна фабрика має мемоізований builder і будується один раз на виклик `wire()`, лише коли її потребує обрана гілка, після своїх залежностей. Залежності очікуються по одній у порядку запису. Значення з методом `dispose()` реєструється, щойно його побудовано. `dispose()` результату викликає їх у зворотному порядку: всі, з `AggregateError` для помилок. Помилка фабрики звільняє вже побудоване у зворотному порядку й прокидається далі; якщо при цьому падає й звільнення — `AggregateError`, першим елементом якого є помилка фабрики. Результат — об'єкт, де ключ `"<id>"` для кожного `wire` веде на його значення, плюс `dispose`. Форма імпорту береться з таблиці експортів знімка: іменований експорт — `import { name }`, аліас `export { make as name }` — за публічним ім'ям, `export default` — default-імпорт. Локальні імена — ID із `_` замість неприпустимих символів; ID, що дають одне ім'я (`a-b.f`, `a_b.f`, `a.b.f`), отримують короткий хеш свого ID, тож ім'я не залежить від інших ID. Імпорти відносні: з розширенням джерела, якщо `tsconfig.json` (з відносними `extends`) має `allowImportingTsExtensions` чи `rewriteRelativeImportExtensions`; для `node16`/`nodenext` — розширення часу виконання (`.ts`/`.tsx` → `.js`, `.mts` → `.mjs`, `.cts` → `.cjs`, JS-джерело зберігає своє); інакше `.ts`/`.tsx`/`.js`/`.jsx` без розширення, решта — з розширенням часу виконання. Типи перевіряє `tsc` проєкту, а залежності — той самий `check`: згенерований файл — звичайний модуль у своєму шарі.

## 8. Канонічна форма (`keylang fmt`)

`fmt` рендерить файл з IR, тож `fmt(fmt(x)) == fmt(x)`:

- маркер генерації, заголовки, списки, абзаци прози й блоки коду розділені рівно одним порожнім рядком; усередині списку порожніх рядків немає;
- маркер списку `-`, відступ `2·глибина`, токени елемента через один пробіл, кома — `a, b`, коментар через один пробіл;
- заголовок `# kind name`, коментар заголовка — через один пробіл (`# <!-- c -->`);
- опис — під рядком вузла з відступом `2·глибина + 2`, текст без кінцевих пробілів;
- проза й код — дослівно (без кінцевих пробілів);
- файл закінчується одним `\n`.

Неявні ключові слова **не** додаються: `- orderAggregate` під шаром лишається як є (слайдова форма рівноправна з `- module orderAggregate`).

`fmt <paths…>` форматує кожен файл окремо: файл, який не прочитати чи не записати, називається в stderr з причиною, а решта все одно форматуються; тоді код 2. Інакше код 1 — діагностики або, з `--check`, неформатований файл (з `--check` нічого не пишеться).

**Р9. Code fence всередині елемента списку не підтримується**: огорожа з будь-яким відступом закриває список і стає блоком коду секції.

## 9. IR і позиції (для LSP)

`Document → Section → Item (Node | Prose | Code)`, `Node` рекурсивний. Кожен `Node` має `span` (рядок елемента від маркера до кінця), `keyword` (спан ключового слова або `null`, якщо воно неявне), `name.span`, `link.span`, `refs[*].span`, `text.span`, `description[*].span`, а також сирі `tokens` зі спанами. `Pos = {offset (індекс у рядку JS, UTF-16), line, col (кодові точки)}`. `Index` (`src/resolve.ts`) відображає `id → Decl {file, span імені, kind}` — це вже дає `definition` (посилання → оголошення) і `hover`; `spanContains(span, offset)` — пошук вузла під курсором.

### `keylang mcp`

MCP-сервер через stdio на `@modelcontextprotocol/sdk`. SDK завантажується лише для цієї команди, а stdout несе тільки протокол. Кожен виклик відповідає за поточним станом репозиторію тим самим `analyze()`, що й `check`: знімок перебудовується щоразу (його `snapshotId` хешує все, від чого залежить граф), а решта аналізу — специфікації, відрендерена карта, докази й вердикти — береться з попереднього виклику, поки `snapshotId`, `keylang.json`, специфікації й файли `check.tests` / `check.trace` ті самі. Інструменти:

- `search {query, limit?}` — ID знімка і `planned`-ID специфікацій, яких у коді ще немає, що містять запит (без урахування регістру), коротші першими, до 20: вид (`planned fn` тощо для наміру), сигнатура, файл, рядок (для наміру — рядок оголошення в специфікації).
- `node {id}` — зведення `explain <id>` як JSON, ребра з позиціями й вердикти про ID. Невідомий ID — помилка інструмента з `did you mean`.
- `code {id, context?}` — вихідний текст вузла з діапазоном рядків (`context` — рядки навколо, до 50).
- `flows {name?}` — потоки: кожен `trigger`/`step` з рядком і вердиктами.
- `check {}` — `{snapshotId, results, coverage}`, ті самі `results`, що в `check --format json`.
- `explain {id}` — збережене пояснення (`agent`, `date`, `stale`) або `null` і офлайн-зведення. Модель інструмент не викликає.
- `apply_diff {path, text}` — повний новий текст однієї ручної специфікації стає пропозицією `.keylang/proposals/<path>` за тими самими правилами, що й у TUI. Результат — `{status: "pending", proposal, diff}`, а сам файл специфікації не змінюється. Ціль поза специфікаціями, не-Markdown чи згенерована карта — помилка інструмента з причиною.

### `keylang lsp`

Сервер (`keylang lsp`, прапорець `--stdio`, який додають клієнти, приймається) говорить LSP через stdio (JSON-RPC без `vscode-languageserver`: потрібна підмножина протоколу мала, а кадрування й життєвий цикл сервер перевіряє сам; design §7.4). Позиції — UTF-16 (`positionEncoding: "utf-16"`); колонки IR і знімка (позиції в коді теж) рахують кодові точки й перераховуються в UTF-16 через текст рядка. Спани напіввідкриті: символ одразу після ID (кома, пробіл) до нього не належить. `rootUri` із кінцевим `/` — той самий корінь.

- **Синхронізація:** `didOpen` / `didChange` (повний текст) / `didClose` / `didSave`, `workspace/didChangeWatchedFiles`. Відкриті буфери — і специфікації, і `.ts`/`.js` — ідуть в `analyze()` як overlay; нічого не записується.
- **Свіжість:** кожна зміна — нове покоління; зміни, що прийшли разом (~60 мс), аналізуються раз. Запит чекає аналізу поточного покоління, а результати заміненого покоління не публікуються. Діагностики: pull (`textDocument/diagnostic`), а клієнтам без pull — push (`textDocument/publishDiagnostics` для відкритих буферів); pull-клієнт після нового аналізу отримує `workspace/diagnostic/refresh`, тож кожна знахідка показується раз. Вони збігаються з `check --format json` для файла: коди, повідомлення, позиції, `data.verdict` (`ok` — severity Hint). Аналіз, що не вдався (невалідний `keylang.json`), друкується в stderr і показується клієнту `window/showMessage` (помилка) раз, поки та сама причина; запити тим часом відповідають `-32603` з нею. Відкритий згенерований `map/*.md`, що відрізняється від свіжого рендера (застаріла закомічена карта), перевіряється як рендер, а позиції в ньому (`documentSymbol`, hover, definition, completion) беруться з буфера, який показує редактор.
- **hover:** вид, ID, сигнатура, файл:рядок, стан (`planned, not implemented`, `opaque`), рядки доказів (`ID`, `static`, `tests`, `trace`) і потоки, що використовують ID. **definition:** ID → код (рядок і колонка оголошення) або оголошення в специфікації; посилання карти `[name](path#Lnn)` → декодований файл і рядок. **references:** оголошення й посилання на ID у всіх специфікаціях (включно з відносними іменами `exports`); `context.includeDeclaration: false` лишає лише посилання. **documentSymbol:** дерево документа — шари → модулі → fn/type, потоки з кроками, правила; `detail` — найгірший вердикт вузла та його дітей.
- **completion:** на початку елемента — ключові слова, дозволені в цій позиції; після `step` / `trigger` — лише функції знімка й `planned fn`; після `calls`, `reads`, `emits`, `allow`, `deny`, `then` — ID, на які охопний модуль може залежати (заборонене `deny` не пропонується). Намір має `labelDetails.description: "planned"`. Кожен елемент має `textEdit`, що замінює все набране слово аж до пробілу чи коми разом із крапками, і `filterText` — повний ID: слово редактора (у Markdown) закінчується на крапці, тож вставка лише за ним повторила б набрані сегменти. **signatureHelp:** сигнатура останнього ID перед курсором. **codeLens:** над функцією коду — `flows: <імена>`, якщо потоки її називають; команда `keylang.flows` з іменами потоків (її реєструє клієнт).
- **Життєвий цикл:** `shutdown` + `exit` — код 0, `exit` без `shutdown` — 1; кадр без `Content-Length` (потік не розібрати далі) чи помилка вводу-виводу — 2 з причиною в stderr; пробіл після `Content-Length:` необов'язковий; `$/cancelRequest` одразу відповідає `-32800` на незавершений запит; невідомий метод — `-32601`.

Тонкий клієнт VS Code — `editors/vscode/` (лише запускає `keylang lsp`); `node editors/vscode/test/run.mjs` перевіряє його в справжньому VS Code (README клієнта).

## 11. Семантичний знімок (`.keylang/index.json`)

`keylang map` серіалізує `AnalysisSnapshot` (схема **6**) у `.keylang/index.json` і **рендерить Markdown-карту з цього знімка**. Індекс — кеш фактів, не текст для редагування. Шлях у вузлі знімка лишається POSIX-шляхом від кореня репозиторію; відносне кодоване посилання рахує emitter. Несумісна або зіпсована схема на диску не є помилкою: наступний `map` перезаписує файл без окремої діагностики.

`snapshotId` — SHA-256 канонічного JSON від схеми, версії екстрактора, версій граматик, конфігурації (`dir`, `languages`, `module`, `layers`, `exclude`, `guessed`) і SHA-256 вмісту кожного проіндексованого файла. Поле `generated` (час запису) у хеш не входить. Два запуски на тих самих джерелах дають той самий `snapshotId`; зміна файла або `keylang.json` змінює його.

| Частина | Зміст |
|---|---|
| `manifest` | екстрактор, версії `web-tree-sitter` і `@vscode/tree-sitter-wasm`, конфігурація, `{path, sha256}` файлів |
| `nodes` | ID → вид (`layer` / `module` / `fn` / `type`), шар, файл і діапазон (`line`, `col`, `endLine`, `endCol`: колонки з 1 у кодових точках, як у §7, кінець — позиція після фрагмента). У модуля й типу діапазон є так само, як у функції. У модуля `members`: `complete` або `opaque`; клас — модуль із `class: true` (у будь-якому файлі свого модуля, зокрема в модулі-теці), його члени — дочірні вузли, конструктор — `<клас>.constructor`. У fn члена класу `static: true` — статичний член (`X.m()`), `name` — ім'я, як його написано, коли сегмент ID інший (`m` для `X.m-static`, `go` для `Y.go-private`). Похідні `deps` / `dependents` / `calls` / `callers` (`calls` без ребер `injected`, кожна ціль один раз). У fn може бути `escapes: {file, line, col, reason}` — перше місце, де її може викликати код, що її не називає (читання як значення, accessor, неявний метод, виклик із коду поза оголошеннями, базовий клас, який keylang не прочитав, статичний ініціалізатор) |
| `exports` | публічне ім'я модуля (`name`, яким його імпортують; `default` для `export default …`, `export =`, `module.exports = …`) → `symbol` — вузол, який воно означає, через псевдоніми, ланцюжки re-export і `export *` (fn, клас, тип або модуль простору імен; `null`, коли це не оголошення, яке keylang індексує: `export default 3`, ім'я пакета), вид (`fn`, `class`, `type`, `value`), `form` (немає — оголошення під власним ім'ям; `alias` — `export { a as b }`; `default` — експорт за замовчуванням; `reexport` — ім'я іншого модуля; `namespace` — об'єкт модуля: `export * as ns from`, `import * as ns; export { ns }`, `export namespace N {}`), `local` — локальне чи вихідне ім'я, коли воно інше (`a` для `export { a as b }`, `main` для `export default function main`) і `from` — модуль, з якого ім'я реекспортовано (для `export *` — модуль, що його експортує). Рядок `*` з видом `reexport` і `reason` — `export *` з модуля з невідомим вмістом |
| `edges` | `kind` (`import`, `call`, `type`, `reexport`), `source`, `target` або `null`, `candidates` коли цілей кілька, `text` (фрагмент коду) і діапазон `line`/`col`/`endLine`/`endCol`, `resolution` (`resolved` / `ambiguous` / `unresolved`), `provenance` (`syntactic`). `ambiguous` означає кілька можливих цілей у `candidates` і порожній `target`. Необов'язкові поля виклику: `via` (`default` / `injected`), `hook` і `site` — ребро хука (§7, «Хуки»); `closure: true` — виклик у вкладеній функції джерела |
| `coverage` | нерозв'язаний імпорт, динамічний виклик (зокрема «call through an expression» — виклик виразу, який keylang не називає: `f()()`, `(a || b)()`, `new (load())()`, ланцюжок довший за 80 символів), нерозв'язаний виклик, `unsupported construct` (namespace, `eval`, `new Function`, виклик `obj[expr]`, обчислюваний член класу `[key]() {}`, колізія ID модулів), обчислюваний specifier (`import(expr)`, `require(expr)`, `import.meta.resolve(expr)`, ``new URL(`./${n}.ts`, import.meta.url)`` чи `"./" + n`, `register(expr, import.meta.url)`; `new URL` з відомим немодульним закінченням, як `.png`, — не модуль; відносний `new URL("./worker", import.meta.url)` без розширення — ребро, коли за ним є файл коду, і нічого інакше), синтаксична помилка (зокрема синтаксис, вкладений глибше за 1000 рівнів: файл тоді `opaque`, а не падіння аналізу), файл поза шаром і пропущений файл — кожен із діапазоном, `text` і `reason` |
| `stats` | лічильники проходу; вони не замінюють записи `coverage` |

Порожній проіндексований модуль має `members: "complete"` і жодного дочірнього символу. `opaque` не підтверджує існування довільного імені. Файл у шарі, виключений через `exclude` у `keylang.json`, стає модулем `members: "opaque"` з коментарем `<!-- excluded -->` у карті і записом `skipped-file` у `coverage`; посилання на його члена — `unverified`, не K001. Тека джерел без дозволу на читання не зупиняє аналіз: `map` і `check` друкують попередження, а в `coverage` з'являється `skipped-file` з файлом-текою і `source` — ID області, яку мали б її файли. Правила над цією областю, вище чи нижче неї (`layers`, `deny`, `no-cycles`, `entry`), тоді `unverified`, не `ok`. Нечитабельний корінь репозиторію — помилка вводу-виводу з кодом 2. Нерозв'язаний імпорт і виклик локального значення є і в `coverage`, і ребром з `resolution: "unresolved"`. Імпорти резолвляться через `tsconfig.json` (або `jsconfig.json`), ланцюжок відносних `extends` і — для solution-конфігу з `references`, як у шаблоні Vite, — `paths` конфігів, на які він посилається; а також `package.json#imports` найближчого `package.json` над файлом (як Node визначає область пакета). Голий специфікатор, як у `tsc`, іде спершу через `paths` — лише найспецифічніший шаблон (точний ключ, інакше найдовший префікс до `*`, незалежно від порядку в JSON), — потім `baseUrl`, і лише тоді він вбудований модуль Node чи пакет: аліас на ім'я вбудованого модуля (`constants`, `events`, `util`) — файл проєкту. Успадковані `paths` резолвляться від `baseUrl` підсумкових опцій (дочірній `baseUrl` переносить і їх), інакше від теки конфігу, що їх оголосив. `./x.js` знаходить `x.ts`, `x.tsx` чи `x.jsx`, а `./x.jsx` — `x.tsx`. Файли аналізу, зокрема незбережені чи запропоновані й ще не записані на диск, для резолвера існують, тож той самий знімок резолвиться однаково до й після запису кандидата. Кожен файл конфігурації читається один раз, і `snapshotId` рахується з того самого тексту, який розібрано; джерела так само: хеш у `manifest`, ключ кешу й факти — з одного читання, а файл, видалений між переліком і читанням, у знімок не входить. Імпорт, що резолвиться у файл коду, якого немає серед модулів (мова, якої немає в `languages`, файл у теці збірки, файл, що з'явився після переліку джерел), — прогалина `unresolved import` з причиною, а не мовчазна відсутність ребра; тести, файли оголошень, `exclude`, файли поза вгаданими шарами й не-код (JSON, CSS) залишаються поза графом мовчки. Голий специфікатор — зовнішній пакет лише тоді, коли його оголошено в `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies` або встановлено в `node_modules` на рівні кореня чи вище, або — як шукає Node — оголошено в `package.json` чи встановлено в `node_modules` теки між файлом і коренем (`web/package.json` монорепозиторію діє лише на файли під `web/`); інакше це нерозв'язаний імпорт (аліас, якого keylang не знає), а не пакет. Пакет робочого простору внутрішній: запис `node_modules/<pkg>`, що після розкриття посилань веде в репозиторій (не в чийсь `node_modules`), або — без встановлення — тека з `workspaces` кореневого `package.json` із таким `name`. Файл дає його `package.json`: `exports` (рядок, підшляхи `./util`, шаблони `./*`, умови), інакше `module`, `main`, `index`; файл оголошень (`.d.ts`) — не джерело. Без такого файла імпорт нерозв'язаний, а файл, який keylang не індексує (`dist/index.js`), — прогалина `unresolved import`, не мовчазна відсутність ребра. `snapshotId` враховує вміст цих файлів конфігурації (зокрема `package.json` пакетів робочого простору, вкладені `package.json` на шляху голого імпорту й перелік тек `workspaces`) і для кожного голого пакета — чи є він у `node_modules` і куди веде, бо від них залежать ребра: після `npm install` знімок інший. Імпорт — також TypeScript `import y = require("./y")` (прив'язка всього модуля) і `import.meta.resolve("./w.ts")`; `require` параметра чи іншого локального значення — не імпорт, а виклик через локальне значення (`require`, створений `createRequire(…)`, — імпорт). Імпорт і `export { … } from` одного модуля — одна залежність із двома ребрами (`import` і `reexport`). ID зовнішнього модуля — ім'я пакета без `@`, з `/` → `-`; якщо два пакети дають один сегмент (`@scope/pkg` і `scope-pkg`), сегмент лишається пакету з точно таким ім'ям, а інші отримують `-2`, `-3`… за абеткою, з попередженням. Два файли з одним ID модуля й одним шляхом без розширення (`x.ts` і `x/index.ts`, файли однієї теки в `module: "dir"`) — один модуль; два різні шляхи, що санітизуються в один ID (`foo.bar.ts` і `foo_bar.ts`), — колізія: попередження, прогалина `unsupported` «module ID collision» і модуль `members: "opaque"`, доки один файл не перейменують. У модулі-теці (`module: "dir"`) fn, типи, імпорти й виклики мають файл, де їх написано, а не перший файл модуля; файл модуля — його `index.*` (`mod.rs`, `__init__.py`), якщо він є, інакше перший за абеткою; тека з назвою `index` — окремий модуль, а синтетичний вузол теки має шлях своєї теки. Виклик резолвиться з урахуванням областей видимості між місцем виклику й модулем: параметри (зокрема деструктуровані), `const`/`let`/`var` у будь-якому охопному блоці, деструктуризація, вкладені функції й класи, змінні `for…of` і `catch`. Якщо таке ім'я затіняє імпорт чи оголошення модуля, це `unresolved-call` з причиною `shadowed by parameter|local`; інакше — `dynamic-call` «call through a local value». Жодне з них не стає підтвердженим ребром. Імпортоване ім'я резолвиться за таблицею публічних імен модуля-джерела (та сама таблиця — `exports` знімка): `import go from` — його `export default` (зокрема `export default function step`, `export default x`, `export = x`, `module.exports = x`), і `go.m()` — статичний член цього експорту (`export default class A { static m() }` → `A.m`), а не іменований експорт `m`; лише модуль без `export default` (CommonJS) дає за default-імпортом `module.exports` з його іменами. `import * as ns` і `require()` — простір імен: `ns.m()` — іменований експорт `m`. `export { a as b }` — оголошення `a`, `export { x } from` / `export { x as y } from` і ім'я, імпортоване та експортоване знову, — ланцюжком до оголошення, `export * from` — іменами без `default`, `export * as ns from` — простором імен (`ns.f()`, тип `ns.T`, як і `NS.T` при `import * as NS`); ім'я без рядка експорту (CommonJS, неекспортований помічник) — оголошення з цим ім'ям. Кожен виклик у коді — ребро або прогалина: `new ns.X()` — виклик класу `X` модуля `ns`, `new X().m()` — член `m` класу `X`, `super()` — конструктор базового класу (через бази без власного конструктора), `super.m()` — член бази; виклик виразу, який keylang не називає (`f()()`, `(a || b)()`), — `dynamic-call` «call through an expression». Виклик тієї самої цілі кілька разів дає одне ребро, найсильніше: прямий виклик поглинає виклик у closure та ребро хука `default`. `interface Foo` і `class Foo` (злиття оголошень TypeScript) — один вузол-клас, хоч би що стояло першим; згадки типів інтерфейсу належать класу. Функцією модуля є й значення `(() => …) as T`, `(function () {}) satisfies T`, а в CommonJS — `exports.x = function () {}`, `module.exports.x = () => …`, функції й методи в `module.exports = { … }` та `module.exports = function () {}` (fn `default`). Виклики поза тілами оголошень (верхній рівень модуля, методи об'єктних літералів, функція-значення, обгорнута викликом) жодній fn не належать і є `escapes` того, що вони викликають (§7). Члени класу: метод і поле з функцією (`handler = () => later()`, `readonly generate = (…) => {…}`) — fn з власними викликами; getter і setter — fn з `escapes`. Ініціалізатори полів екземпляра (`private decoder = new InputDecoder()`) виконуються під час конструювання: їхні виклики належать `constructor`, а якщо його немає в коді — синтезованому `Class.constructor` без сигнатури з діапазоном від першого до останнього такого поля (лише коли ініціалізатори щось викликають). Ініціалізатори статичних полів і блоки `static {}` виконуються один раз під час обчислення класу: їхні виклики належать синтезованому `Class.static`, а не конструктору (якщо в класі вже є член `static`, це `unsupported`). Член з обчислюваним ключем (`[key]() {}`, `[key] = …`) — `unsupported construct` «computed class member»: його виклики — код поза оголошеннями. Сегмент ID члена — його ім'я без `#`; якщо ім'я вже має інший член класу, статичний член отримує суфікс `-static`, приватний `#name` — `-private`, статичний приватний — `-static-private` (жодне JS-ім'я не містить `-`, тож суфікс не збігається з іншим членом). Пріоритет — член екземпляра, статичний, `#`-приватний, статичний `#`-приватний: `static m()` поруч з `m()` — `X.m-static`, `#go()` поруч з `go()` — `Y.go-private`; без збігу ID лишається `X.work` для `#work`. Тож поява одноіменного члена з вищим пріоритетом перейменовує ID нижчого. `this.#work()` — виклик приватного члена, `this.m()` у статичному методі й `X.m()` — статичного, `w.m()` через екземпляр — члена екземпляра. `this` означає клас, лише коли найближча охопна не-стрілкова функція — член класу (або це ініціалізатор поля чи `static {}`); `this.m()` у методі об'єктного літерала чи вкладеній `function` — `dynamic-call` «call through `this` of a function value». `new X()` у static-доказі — виклик `X.constructor`. Виклик методу через поле чи локальне значення відомого класу розв'язується: поле з анотацією `: X` чи ініціалізатором `new X()`, параметр-властивість `constructor(private readonly x: X)`, присвоєння `this.x = new X()` або `this.x = p` з `p: X` у конструкторі; `const w = new X()`, `const w: X`, параметр `w: X` — якщо ближча прив'язка того самого імені (змінна `for…of`, `catch`, вкладена функція) його не затіняє і саме `X` між оголошенням і модулем не перепризначено (`const X = Ctor`). `this.x.m()` і `w.m()` тоді — ребро до `X.m`, якщо `X` — клас цього файла чи імпортований і має член `m`; для глобального класу (`Map`, `Set`…) чи класу з пакета — зовнішній виклик; інакше (інтерфейс, generic-анотація, невідомий тип) лишається діркою. Ребро `type` — це згадка типу в сигнатурі чи heritage; правила `allow` / `deny` / `layers` бачать його разом із `import`, `call` і `reexport`.

### Мови

`languages` у `keylang.json` — підмножина `javascript`, `python`, `rust`, `typescript`; інша назва — помилка конфігурації з кодом 2. Без поля мови визначаються за розширеннями файлів. Без `module` береться гранулярність мов, якщо вона однакова, інакше `file`. Файл-індекс, що стоїть за модуль своєї теки: `index.*` для JS/TS, `mod.rs` для Rust, `__init__.py` для Python. Шар членів не має, тож файл-індекс прямо під коренем шару зберігає своє ім'я: `<шар>.index`, `<шар>.mod`, `<шар>.__init__`. За замовчуванням не індексуються також `test_*.py`, `*_test.py`, `conftest.py` і теки `venv`, `site-packages`. Граф, знімок і перевірки для всіх мов спільні. Кожна мова має frontend: екстрактор фактів файлу, резолвер імпортів і перелік глобальних імен мови, виклики через які зовнішні. Мова також каже, що запускає виклик класу (`constructor` у JS/TS, `__init__` у Python; у Rust виклику типу немає), і які члени класу вона викликає без виразу виклику з їхнім ім'ям: JS `then`, `next`, `toString`…; Python — dunder-методи, крім `__init__` (`__enter__`, `__iter__`, `__str__`, `__call__`…); Rust — методи `impl` тих трейтів `std`, які викликають оператори, `for`, `?`, форматування, кінець області й auto-deref (`impl Drop`, `impl fmt::Display`, `impl Add`, `impl Iterator`, `impl From<T>`…); власний метод `add` без трейту викликається лише за ім'ям. Такий член має `escapes` «is called implicitly». Кожен вираз виклику — ребро або дірка: виклик, отримувача чи callee якого keylang не може назвати (`self.db.save()`, `Order::new().total()`, `x[0].m()`, `super().m()`, `f()()`, `(self.handler)()`), — `dynamic-call` «call through a local value» з текстом виклику, тож `closure.complete` — `false`, а крок за ним — `unverified`, не `fail`. Функція, прочитана як значення (`later(hit)`, `Handler { run: go }`, `.map(Order::total)`, `callback=self.save`, `{"save": save}`), має `escapes` «is read as a value».

**Rust.** Модуль — файл, як і в самому Rust: `src/domain/order.rs` — це `crate::domain::order` і ID `domain.order`, а `src/domain/mod.rs` — модуль теки. Члени: `fn`, `struct`/`enum`/`union` (як класи; їхні члени — функції з `impl` того самого файла, асоційована функція без `self` статична; `self: Box<Self>` — теж `self`), `trait` і `type` (як типи). Експорт — будь-яка видимість `pub…`, `pub use` — реекспорт: рядок таблиці експортів з `form: reexport`, символом, на який вказує шлях, і `from` — модулем, звідки він. Не індексуються тестовий код: елементи під `#[cfg(test)]` або `cfg`, що вимагає `test` (`cfg(all(test, unix))`), функції з `#[test]` (`#[tokio::test]`…) і файл із `#![cfg(test)]`; коментар між атрибутом і елементом цього не змінює. Кожен лист дерева `use` (`a::{b, c::d as e, f::*}`) — окремий імпорт, зокрема `use` у тілі функції. Крейт — тека з `Cargo.toml` і `[package]`. Кожна ціль крейту — окреме дерево модулів із коренем у своєму файлі: бібліотека — `src/lib.rs` або `[lib] path` (сам файл, `a/b.rs` шукаються поруч із ним), бінарники — `src/main.rs`, `src/bin/*.rs`, `src/bin/*/main.rs` і `[[bin]] path`. `crate::` резолвиться від кореня цілі, до якої належить файл: у `main.rs` `crate::helper()` — його власна `helper`, а не бібліотеки. Файл під спільною текою бібліотеки й бінарника належить бінарнику, коли лише корінь бінарника оголошує його модуль верхнього рівня (`mod cli;`), інакше бібліотеці. `crate::`, `self::`, `super::` і шлях від дочірнього модуля (edition 2018) резолвляться у файл `a/b.rs` або `a/b/mod.rs`. Найдовший префікс шляху, що є модулем, дає файл. Якщо модулем є весь шлях, імпорт прив'язує сам модуль, інакше останній сегмент є іменем члена. Шлях у власний файл (`crate::run()` у файлі, де `run` оголошено, `self::run()`) — ребро до його члена. Шлях, що після файла йде далі в модуль без власного файла, не прив'язує члена: у вбудований `mod inner { … }` цього файла — залежність від файла без ребра виклику (`dynamic-call`), у модуль із `#[path]` чи будь-який інший — нерозв'язаний імпорт. Ім'я члена `[workspace] members` (чи пакета з бінарника) означає бібліотеку цього крейту, ключ `[dependencies]`/`[dev-dependencies]`/`[build-dependencies]` — зовнішній пакет, `std`/`core`/`alloc` — зовнішні. Будь-яке інше ім'я дає нерозв'язаний імпорт. `mod x;` оголошує файл, але ребром не є: залежність — те, що код використовує. Шлях у виклику чи значенні, що починається з `crate`, `super`, `self` або з невідомого імені з малої літери (`tokio::spawn()`), є власним імпортом; шлях через прив'язку `use` довший за два сегменти (`order::Order::new()` при `use crate::domain::order`) — теж, від шляху цього `use`. Сегмент шляху в `CamelCase` після модулів — тип: `super::i18n::Message::raw()` — це член `Message.raw`. Виклик, чий останній сегмент у `CamelCase` (`Some(x)`, `Event::Progress(p)`), за конвенцією іменування є конструктором варіанта чи tuple-struct і викликом не є. Шлях від примітиву (`u64::from`) — зовнішній. `Self::f()` у `impl` — це член типу, `self.m()` — член `impl`. Виклик методу через значення (`order.total()`) — `dynamic-call`. Виклики у вкладеній `fn`, як і в closure, мають `closure: true`. Виклики в коді, який keylang не індексує як fn — ініціалізатор `const`/`static`, типові методи `trait`, вбудований `mod`, `impl` типу з іншого файла, — код поза оголошеннями: те, що вони викликають, має `escapes`. Невідомий макрос цього крейту (`audit!()`, `crate::m!()`) — `unsupported` «macro is not expanded». Макроси `std`, поширеного логування й макроси зі шляхом у чужий крейт (`serde_json::json!`) діркою не є. Файл поза всіма цілями (`build.rs`) — окремий корінь: `crate::` у ньому не резолвиться в `src/`. Вбудований `mod x { … }`, `impl` для типу з іншого файла і макрос на верхньому рівні — `unsupported`; шляхи всередині вбудованого модуля починаються від нього й імпортами файла не є. Атрибут-макрос на fn поза атрибутами мови й тими, що зберігають тіло (`#[tokio::main]`, `#[tracing::instrument]`, `#[async_trait]`), — `unsupported` «attribute may replace» із текстом `#[…]` і `source` — ID fn, а сама fn — `escapes` «is read as a value»: як і Python-декоратор, це дірка поведінки цієї fn, а не залежностей модуля. Rust-frontend дає ребра `import`, `call`, `reexport`; ребер `type` ще немає. `snapshotId` враховує вміст прочитаних `Cargo.toml`.

**Python.** Модуль — файл, пакет — `__init__.py` теки. Члени: `def` (зокрема `async`) і `class` (їхні методи й вкладені класи з їхніми членами; `@staticmethod` і `@classmethod` статичні, `@property`, `@cached_property` і `@x.setter` — accessor з `escapes`). Верхній рівень охоплює й тіла `if`/`try` модуля. Публічні імена — список літерала `__all__` (зокрема розширеного `+=`, `+`, `.extend([...])`, `.append("x")`), а без нього — імена без початкового `_`. Методи з `_` приватні, dunder-методи (`__init__`) публічні. Кожне імпортоване ім'я — окремий імпорт з крапковим шляхом, зокрема імпорт у тілі функції чи класу. `from ..pkg.mod import f` починається від пакета файла: одна крапка на рівень. `import a.b` прив'язує `a` і шлях `a.b`: `a.b.f()` — виклик `f` модуля `a.b`. Абсолютний шлях шукається в корені репозиторію, потім у `src/`. Найдовший префікс, що є модулем (`p.py` або `p/__init__.py`), дає файл. `from pkg import mod`, де `mod` — модуль, прив'язує сам модуль. Ім'я верхнього рівня, якого немає в жодному корені, — зовнішній пакет, бо path-аліасів у Python немає. Реекспорт — імпорт верхнього рівня з ім'ям із `__all__`, а в `__init__.py` без `__all__` — будь-яке публічне імпортоване ім'я і `from .x import *`: ребро `reexport` і рядок таблиці експортів з `form: reexport`, символом і `from`. Тож `from shop.domain import place` при `from .order import place` у `shop/domain/__init__.py` — виклик `shop.domain.order.place`. `X()` — виклик класу, тобто його `__init__`. `self.m()` — член класу, для `@staticmethod`/`@classmethod` — статичний член; перший параметр `@staticmethod` отримувачем не є. `self.attr.m()` і `x.m()` через змінну — `dynamic-call`. Код тіла класу поза методами і декоратори виконуються під час завантаження модуля: те, що вони викликають, має `escapes`. Декоратор поза списком тих, що зберігають функцію (`staticmethod`, `classmethod`, `property`, `dataclass`, `functools.wraps`, `lru_cache`, `total_ordering`…), — `unsupported` «decorator may replace» із `source` — ID декорованої fn чи класу, а сама fn — `escapes` «is read as a value» (декоратор тримає її як значення, як фреймворк — зареєстрований обробник). Це дірка поведінки цієї декларації, а не залежностей модуля: `deny` її не враховує. Так само `getattr` у тілі функції (`source` — її ID). `importlib.import_module`, `__import__`, `exec`, `eval` і `getattr` поза функцією — `unsupported` рівня залежностей. Python-frontend дає ребра `import`, `call` і `reexport`; ребер `type` ще немає.

**Fingerprint.** У fn і типу є `fingerprint` — SHA-256 сигнатури та синтаксису оголошення: типи вузлів tree-sitter і тексти токенів без коментарів і пробілів. Заміна `>` на `>=` його змінює, зміна коментаря чи переформатування — ні. Переміщення інструкції з блоку змінює, бо вкладеність — частина хешу. Перевантаження TS об'єднуються в один fingerprint. `closure: {fingerprint, complete}` — fingerprint вузла разом з усім, що він викликає транзитивно (`new C()` — з конструктором `C`). Він рахується знизу вгору за сильно зв'язаними компонентами графа викликів, тож цикл A ↔ B дає обом один `closure` і зміна будь-кого з них змінює обидва. `complete: false`, коли вузол або щось досяжне від нього має `dynamic-call` чи `unresolved-call`, дірку самої декларації (`unsupported` з `source` — ця fn чи її клас: декоратор або атрибут-макрос, що може її підмінити) або не має fingerprint: незмінний хеш тоді не означає незмінної поведінки. Fingerprint не входить у `snapshotId` (той залежить від вмісту файлів) і не є baseline прози: baseline і `check --stale` — тікет 21.

`provenance: semantic` і `provenance: trace` лишаються дорожньою картою, не полями поточного знімка. Схема знімка — **6** (у 6 з'явилися `class` модуля, `static` і `name` fn, `local` і форма `namespace` в `exports`).

## 12. TUI (`keylang`) і `keylang web`

`keylang` без команди в терміналі (stdin і stdout — TTY) відкриває TUI; без TTY друкує usage з кодом 2, як раніше. `keylang web [--port N] [--host H]` показує той самий TUI у браузері (типово `127.0.0.1:7070`, `--port 0` — вільний порт) і друкує `keylang web: http://localhost:<port>/?t=<token>`. Обидва варіанти — одна сесія `App` (`src/tui/app.ts`) над тим самим `analyze()`, що й `check` та LSP: вердикти, діагностики, hover, definition, references і completion беруться з `lsp-features.ts`, власного «зеленого» статусу TUI не рахує.

**Екран.** Заголовок (файл, `[+]` — незбережені зміни, `[generated, read-only]` — згенерована карта), редактор із жолобом і номерами рядків, панель навігації праворуч (`F3`), файли ліворуч (`F2`), рядок знахідки й рядок стану (лічильники, стан аналізу, 4–6 головних клавіш). Редактор показує сирий Markdown з підсвіткою: ключові слова, заголовки, посилання на код, коментарі; ID і оголошення — кольором свого шару в порядку `keylang.json`.

**Жолоб.** Позначка рядка — найгірше серед усього, що звітовано на ньому: `✗` — діагностика-помилка або `fail`; `◌` — хоч один потрібний критерій `unverified`; `!` — лише попередження; `✓` — **усі** звітовані критерії `ok`. Отже `ID ✓` з відсутнім чи застарілим trace дає `◌`, а не `✓`. `◇` — `planned`: рядок оголошення наміру або крок, чиї докази бракують лише через те, що ціль запланована. Під рядком курсора — розгорнутий рядок: `ID`, `static`, `tests`, `trace` окремо (`—` — вид доказу не звітовано, бо не налаштований або не потрібний), інші критерії (правила, `entry`), коди діагностик, `planned`, `stale n/a` (стейлнес прози чекає тікета 21) і префікс `snapshotId`. Рядок знахідки нижче — повідомлення першої помилки чи `unverified` з підказкою `fix:` з `keylang explain`.

**Переіндексація.** Знімок будує окремий worker (`src/tui/analysis-worker.ts`); парсинг специфікацій і оцінка — у потоці UI. Поки аналіз іде, рядок стану пише `updating… results shown are stale`, позначки жолоба й навігації тьмяніють, клавіші та мишка працюють. Результат заміненого покоління (новий `F5`, нова правка) відкидається. Правка буфера одразу позначає результати `outdated` і запускає аналіз із буферами як overlay через ~120 мс після паузи; на диск нічого не пишеться до `Ctrl+S`.

**Клавіші** (`?` показує їх для поточного режиму, а на рядку з діагностикою — ще й `keylang explain` її коду):

| Режим | Клавіші |
|---|---|
| перегляд | `↑↓`/`jk`, `PgUp`/`PgDn`, `g`/`G`; `Enter` або Ctrl+клік — у код; `Alt+Enter` — до оголошення в специфікації (для ID коду — у згенеровану карту); `Ctrl+O` — назад; `K` або наведення мишею — hover; `Tab` — фокус редактор → навігація → файли; `F2`/`F3` — панелі; `F5` — аналіз заново; `v` — читання; `i` — редагування; `m` — MERGE пропозиції; `u` — відкотити останнє злиття; `/` і `n` — пошук; `:` — палітра команд з нечітким пошуком; `q` / `Ctrl+C` — вихід (з незбереженими змінами — повторне натискання) |
| редагування | друк, `Enter` (продовжує список: новий рядок після елемента має `- ` того ж відступу), `Backspace`/`Delete`, `Ctrl+Space` — доповнення, `Tab`/`Enter` приймає, `Shift+↑↓` — виділення рядків, `Ctrl+G` — text → spec, `Ctrl+Z` — відкат правки, `Ctrl+S` — запис, `Esc` — до перегляду |
| MERGE | `n`/`N`, `↑↓` — шматки; `a` — прийняти; `r` — відхилити; `u` — скасувати останнє рішення; `w` — застосувати; `Esc` — скасувати злиття, нічого не записавши |
| код | `↑↓`, `PgUp`/`PgDn`; `Esc` / `q` / `Ctrl+O` — назад |

`Ctrl+0` / `Ctrl+1` з design.md §7.1 термінали не передають, тож панелі перемикають `F2` / `F3`. Фокус панель отримує лише в перегляді; у редагуванні, MERGE і переглядачі коду `F2`–`F4` тільки показують чи ховають її, а клавіші й далі йдуть туди ж. `e` показує у спливаючому вікні офлайн-зведення ID під курсором і збережене пояснення з рядком `agent · дата · fresh|stale`; саме пояснення створює `keylang explain <id> --llm`. `F4` відкриває панель «Контекст» на місці навігації: що піде в модель для поточного буфера й рядка курсора — буфер, вузли рядка, їхні сусіди, код, потоки й правила з ними, тести цих потоків. Кожен елемент має оцінку токенів (≈ 4 символи на токен), заголовок — суму. `◇` — `planned`, `?` — вузол із неповними даними (непрозорий модуль, `closure.complete: false` або код, змінений після знімка). У панелі `@` додає ID (невідомий — повідомлення з `did you mean`), `x` прибирає вибраний елемент, клік вибирає рядок, `Esc` закриває. Усе береться з одного аналізу: специфікації — як їх розібрав аналіз, з незбереженими буферами; код — лише поки файл має ті байти, які хешував знімок (інакше коду в пакеті немає, а вузол позначено `?`). Пакет кешується в межах аналізу за буфером і вибором, до 16 варіантів; новий аналіз починає з порожнього кешу. `Ctrl+Space` у перегляді просить модель із `agent` (як `draft flow --mode hybrid`, з пакетом панелі «Контекст» у промпті) про чернетку потоку, в якому стоїть курсор, від його `trigger`. Чернетка стає пропозицією для цього файла й одразу відкривається як MERGE. До `a` і `w` нічого не пишеться. Без моделі чи поза потоком із `trigger`, а також коли файл має незбережені правки або вже має пропозицію, модель не питається, а TUI пояснює, що зробити. Якщо, поки модель відповідає, відкрито інший файл, змінено текст чи почато інше злиття, чернетка лишається пропозицією (`m`) і MERGE не відкривається; пропозицію, що з'явилася тим часом, чернетка не перезаписує. У редагуванні `Ctrl+Space`, як і раніше, відкриває доповнення. **Ghost-текст** з'являється в редагуванні, коли налаштовано `agent`. Сигнал такий: курсор у кінці нового елемента (`- ` і нічого далі) у `# flow` із `trigger`, відкритого доповнення немає. Після паузи `ghost.delay` у `keylang.json` (мс, за замовчуванням 400, від 0 до 10000) модель отримує потік до курсора й пакет контексту. Вона повертає до трьох варіантів одного рядка. Варіант, що називає ID, якого немає ні у знімку, ні серед `planned`, або що не розбирається там, де стоятиме (у буфері на місці курсора: крок під `invariant` — K004), відкидається до показу. Сірий текст показується, лише якщо буфер і рядок не змінилися за час запиту і новішого запиту не було. `Alt+]` дає наступний варіант, `Tab` ставить рядок (лише в той самий буфер з тим самим текстом), `Esc` чи будь-яка інша клавіша, клік, вставка й клавіші панелей прибирають його. У `.keylang/stats.json` поле `suggestions.ghost` і, для порівняння, `suggestions.completion` (детерміноване доповнення: показ, `Tab`/`Enter`, `Esc`) рахують `proposed` / `accepted` / `rejected` і `ms` від показу до рішення. Довше за один рядок — лише через MERGE (`Ctrl+Space`). **Голос** (`Ctrl+R` у редагуванні; у перегляді TUI просить спершу `i`, а запис, що йде, зупиняє) записує до другого `Ctrl+R` чи кінця джерела, розпізнає й вставляє текст. Другий `Ctrl+R`, поки мікрофон ще відкривається, зупиняє цей запис, а не відкриває другий; поки йде розпізнавання, новий запис не починається. Текст вставляється, лише поки відкрито той самий буфер у редагуванні з тим самим текстом, що й на початку запису; інакше рядок знахідки показує почуте й що його не вставлено. На порожньому рядку чи новому елементі `- ` командна граматика дає елементи: «крок …» / «step …» → `- step <id>` (ID за словами, як у доповненні: кожне слово є в останніх двох сегментах ID, розбитих за регістром; без однозначного збігу — жодного ID або кількох, серед яких рівно один не названо повністю, — слова лишаються як сказано), «коли A тоді B» → `- when A` з `  - then B`, «емітить X» → `- emits X`. Решта йде вільним текстом у курсор. `voice.engine` у `keylang.json` — `local` (whisper.cpp через опційний `@fugood/whisper.node` і модель `ggml-large-v3-turbo.bin` або `ggml-small.bin` у `~/.cache/keylang/models`), `openrouter` (`OPENROUTER_API_KEY` чи `~/.config/keylang/openrouter.key`; `voice.model`, за замовчуванням `openai/gpt-4o-audio-preview`) або `auto` (за замовчуванням: local, якщо модель і модуль є, інакше openrouter із ключем). Без рушія чи мікрофона `Ctrl+R` каже, що налаштувати. PCM — 16 кГц, моно, s16le, вікна по 25 с з перекриттям 1 с. Кожне вікно йде WAV у base64 як `input_audio` з підказкою «Terms that may occur: …» — до 30 ID з околу курсора: поточного потоку, сусідів ID рядка і самих ID рядка останніми. Слова, які повторило перекриття (до 8 слів, без урахування регістру й розділових знаків), при зшиванні вікон пропускаються. Порожній запис нікуди не надсилається; відповідь OpenRouter без тексту (не JSON, `error` з кодом 200) — помилка `voice:` з причиною. `keylang doctor` друкує, що налаштовано: мови, облікові дані `agent`, рушій голосу, модель, опційні `@fugood/whisper.node` і `decibri`. Команда нічого не змінює й повертає код 0: проблема, яку вона знаходить (файл ключа, який можуть читати інші, модуль без робочого бінарника), — рядок звіту, а не помилка. `@fugood/whisper.node` (whisper.cpp: `initWhisper({filePath, useGpu})` — ключ `filePath`, як у нативному модулі, хоч README пакета пише `model`; `transcribeData(PCM, {prompt: <глосарій>})`) і `decibri` (`Microphone({sampleRate: 16000, channels: 1})`) — `optionalDependencies` із prebuilt-бінарниками. Їхня форма перевіряється під час виконання. Без них (`npm install --omit=optional` або платформа без збірки) CLI і TUI працюють, а `Ctrl+R` і `doctor` кажуть, чого бракує. Пакет, що є, але не завантажується (немає prebuilt-бінарника для платформи, `@fugood/whisper.node` без робочого платформного пакета, неочікувана форма), — `unavailable: <причина>` у `doctor`, а не `installed`; рушій `auto` тоді його не обирає, а `console.warn` бібліотеки під час пошуку бінарника не малює поверх TUI. У `keylang web` мікрофон — браузерний. Сервер шле сторінці керуюче повідомлення — кадр, що починається з NUL (ANSI-кадр так не починається): `{"type":"mic","on":true|false}`. Сторінка записує через `getUserMedia` (`AudioContext` 16 кГц) і шле `{"type":"audio","data":<base64 s16le>}`, в кінці `{"type":"audio-end"}`, а за відмови — `{"type":"audio-error","data"}`. PCM іде тим самим WebSocket до того самого рушія, що й у терміналі. Один запис обмежено 10 хвилинами, повідомлення з непарною кількістю байтів відкидається. Вкладка, закрита під час запису, завершує його з повідомленням; мікрофон, який браузер дав уже після `mic off`, одразу вимикається.

**Hover:** вид, ID, сигнатура, файл:рядок, стан (`planned`, `opaque`), рядки доказів, потоки, до 4 рядків коду з місця оголошення і кількість посилань у специфікаціях. **Перехід у код:** у терміналі із заданим `$VISUAL` / `$EDITOR` — туди (`code`/`codium`/`cursor`/`windsurf` отримують `-g file:line` і не забирають екран; `subl`/`zed` — `file:line`; решта — `+line file` з передачею екрана й поверненням у TUI); без редактора і завжди у `web` — вбудований переглядач коду лише для читання з лексичною підсвіткою й OSC 8-посиланням `vscode://file/<abs>:<line>` у заголовку. **Навігація:** шари → модулі (класи вкладені у свій файл) → fn/type з файлами коду; `FLOWS` і `RULES` з найгіршою позначкою своїх рядків; `Enter` — код (для модуля й fn) або рядок специфікації, `Alt+Enter` — специфікація, `←`/`→` — згорнути/розгорнути.

**Читання (`v`).** Markdown рендериться в текст: заголовки, маркери, таблиці, блоки коду, inline-код, наголос, посилання (`http(s)` — OSC 8). Кожен рядок пам'ятає рядок джерела, тож позначки жолоба й `Enter` на ID працюють. Рендерер власний, а не `marked` + `marked-terminal` (ADR 0001).

**Доповнення й помилки під час набору.** Той самий `completions()`, що в LSP, над поточним буфером: після `- ` — ключові слова позиції, після `step`/`trigger` — функції знімка й `planned fn`, після `calls`/`reads`/`emits`/`allow`/`deny`/`then` — дозволені ID. Список фільтрується префіксом слова під курсором (спершу збіг з початку, потім входження). Невідомий ID дає K001 з «did you mean» і пропозицією `planned` одразу після аналізу overlay, до запису файла.

**text → spec (`Ctrl+G`).** Детерміновано, без LLM: виділені рядки (або абзац прози під курсором) діляться на речення; `when|if|коли|якщо … [then|тоді …]` → `- when …` з вкладеним `- then …` (або `- step`, якщо в частині `then` є відомий ID); `invariant: …` → `- invariant`; `emits [event] x` → `- emits x`; речення з ID знімка чи `planned` або зі словом, що є останнім сегментом рівно однієї функції, → `- step <id>`. Текст лишається на місці як опис; елементи додаються після нього з тим самим відступом. Результат — MERGE-пропозиція для буфера; без жодного елемента — повідомлення, без змін.

**MERGE і пропозиції.** Зовнішнє джерело (`draft`, `code-to-spec`, агент, MCP `apply_diff`) пише повний запропонований текст у `.keylang/proposals/<шлях специфікації від кореня>`, наприклад `.keylang/proposals/keylang/flows/checkout.md`; `spec-to-code` так само пропонує код і тест: `.keylang/proposals/src/app/refund.ts`. TUI показує `≈ N proposal(s): m`; `m` відкриває пропозицію поточного файла (або першу) як построковий diff по шматках **відносно файла на диску**.

Обмеження формату пропозицій специфікацій (порушення — пропозиція ігнорується, `m` називає її й причину; нічого не пишеться):

- ціль — `.md` під каталогом специфікацій (`dir` з `keylang.json`, типово `keylang/`); `README.md`, `docs/…` та інші файли поза ним не змінюються;
- не згенерована карта: ні `<dir>/map/…`, ні файл із маркером `keylang:generated` — карту пише лише `keylang map`;
- шлях простий відносний: без `..`, `.`, порожніх сегментів, без прихованих тек, `node_modules` і `target` (тих, звідки `check` не читає специфікацій); символічне посилання не виводить запис за межі каталогу специфікацій;
- новий файл (зокрема в теці, якої ще немає) дозволено — теку буде створено;
- файл із незбереженими правками в TUI не зливається: спершу `Ctrl+S` або відкат, інакше diff містив би шматки, що відкочують набране.

Пропозиція будь-якого іншого файла — це **код** (`MERGE <файл> · code`). Обмеження: розширення мови, яку keylang читає (TS/JS, Rust, Python); простий відносний шлях без прихованих тек, `node_modules` і `target`; не `keylang.gen.ts` з маркером `keylang wire`; символічне посилання не виводить запис за межі репозиторію. Код не відкривається як буфер TUI: diff іде відносно файла на диску, прийняті шматки пишуться туди ж (нова тека створюється), `u` у перегляді відкочує запис, поки файл містить саме результат, і повертає пропозицію. Після запису знімок перебудовується, тож жолоб специфікацій одразу показує, що дав новий код.

`w` застосовує лише прийняті шматки. Для пропозиції результат записується на диск (це і є підтвердження) атомарно — тимчасовий файл і rename, з тими самими правами й закінченнями рядків (файл з CRLF у всіх рядках лишається CRLF; зі змішаними — не нормалізується). Якщо файл на диску змінився, поки йшло злиття, нічого не пишеться. Пропозиція має ідентичність — свій текст на момент `m`: переписану за час злиття (агентом) `w` не застосовує й не видаляє, а просить `m` ще раз. Файл пропозиції видаляється, коли всі шматки вирішено (`a` або `r`); поки є невирішені, у пропозиції лишаються тільки вони (відхилені з неї прибираються), тож наступний `m` покаже лише невирішені. `w` без жодного вирішеного шматка нічого не робить; з відхиленими, але без прийнятих, — лише прибирає їх із пропозиції, файл не змінюється. Порядок запису: файл (помилка тут нічого не змінює), потім пропозиція, потім стан сесії; лічильники `.keylang/stats.json` — останніми, і незаписуваний файл лічильників злиття не зупиняє. Для `Ctrl+G` результат іде в буфер, який записує `Ctrl+S`. `w` і `Esc` повертають у режим, з якого почалося злиття (`Ctrl+G` у редагуванні — у редагування). `Esc` нічого не змінює і лишає пропозицію. `u` у MERGE повертає попереднє рішення шматка. `u` у перегляді відкочує останнє злиття — на диску теж, і повертає пропозицію такою, якою вона була, — але лише поки файл містить саме результат злиття: будь-яка пізніша правка чи зміна на диску скасовує можливість `u` (для правок є `Ctrl+Z`). Новішу пропозицію, записану після злиття, `u` не перезаписує. Клік мишею під час MERGE злиття не кидає.

**Запис і термінал.** `Ctrl+S` поверх файла, зміненого на диску іншою програмою, спершу попереджає; другий `Ctrl+S` перезаписує. Помилка запису (немає прав, тека на місці файла) — повідомлення в рядку знахідки, сесія й незбережені буфери лишаються. Запис TUI (`Ctrl+S`, `w`, `u`) не виходить за межі репозиторію (злиття специфікації — за межі каталогу специфікацій), зокрема через символічне посилання, чия ціль ще не існує: такий запис відмовляється з повідомленням, нічого не створюється. Вставка без bracketed paste (багато надрукованих клавіш в одному чанку) — одна правка; поза редагуванням (перегляд, MERGE, код) такий чанк — теж вставка, а не низка команд, і відкидається з підказкою `press i`; кілька (до 32) однакових клавіш в одному чанку — утримана клавіша, це команди. Керувальні символи й escape-послідовності (кольоровий вивід, вставлений з термінала) у текст не потрапляють, як і обірвана послідовність. Позиція курсора рахується в графемах: літера з комбінованими знаками, ZWJ-emoji, прапор — одна клітинка курсора; emoji з `Emoji_Presentation` (✅, 🚀) займають дві клітинки. Робота на клавішу пропорційна довжині рядка, а не її квадрату: рядок у сотні тисяч символів і кадр `keylang web` на 1 МіБ не зупиняють ні сесію, ні сервер. Поки працює термінальний `$EDITOR` і поки процес зупинено `Ctrl+Z`, keylang не читає stdin і нічого не малює (ні завершений аналіз, ні зміна розміру); повернення перемальовує кадр цілком. SIGTERM, SIGHUP, SIGINT і SIGQUIT відновлюють термінал (raw mode, alt-screen, мишка, bracketed paste) і завершують сесію, як `q`, з кодом 0 (незбережені буфери губляться); SIGINT і SIGQUIT, поки працює термінальний `$EDITOR`, належать редактору. Збій (неперехоплений виняток) відновлює термінал, друкує помилку в stderr і дає код 2. SIGTSTP відновлює, зупиняє, а SIGCONT повертає TUI. `keylang.json` відкривається в тому ж редакторі (останній у списку файлів) як текст без підсвітки й доказів; після `Ctrl+S` його читає наступний аналіз.

**`keylang web`.** `node:http` віддає сторінку й вшиті xterm.js, `xterm.css`, addon-fit (`/assets/…`; у пакеті — `dist/web/`, у чекауті — з `node_modules`), без CDN і PTY. WebSocket `/ws` (пакет `ws`, [ADR 0002](adr/0002-dependencies-by-value-ws.md); повідомлення до 1 МіБ; ping кожні 30 с, з'єднання без pong розривається) несе ANSI-кадри до xterm.js, а назад — JSON `{"type":"hello","session","cols","rows"}`, `{"type":"input","data"}` (клавіатура, SGR-мишка, bracketed paste, текст IME) і `{"type":"resize","cols","rows"}`. Розмір обмежено 1000 × 400 клітинок; некоректний JSON, не-об'єкт і бінарний кадр ігноруються. HTTP-запит, чия ціль не є URL (`GET //[`), отримує 400, сервер працює далі. Сесія, яку не вдалося відкрити, пише причину у вкладку й закривається з кодом 4001. Перший кадр вмикає ті самі режими, що й термінал: SGR-мишку з рухом і bracketed paste. OSC 8-посилання `vscode://` сторінка відкриває (`allowNonHttpProtocols`). Сесія живе 10 хвилин після розриву: перезавантаження вкладки чи обрив з'єднання повертає той самий стан (ID сесії — у `sessionStorage`). Інша вкладка з тією ж сесією забирає її: стара отримує код закриття 4000 і чекає кліку, щоб забрати сесію назад (без взаємного перехоплення), а її ввід далі не доходить; сесія при цьому не від'єднується і не завершується. Кінець сесії — код 4001. Доступ: друкований URL `http://localhost:<port>/#t=<token>` несе токен у фрагменті, який браузер серверу не надсилає; сторінка переносить його в `sessionStorage`, прибирає з адресного рядка й історії та передає як WebSocket-підпротокол `keylang.t.<token>` поруч із `keylang` (сервер відповідає лише `keylang`). Cookie немає: вони не розрізняють порти, і токен отримав би будь-який інший сервер на localhost. Сторінка статична й даних не містить; сокет без токена, з неправильним токеном чи з чужим `Origin` — 403; на loopback запит з чужим `Host` — 421 (захист від DNS rebinding). Токен порівнюється за сталий час. `Ctrl+C` сервера з незбереженими буферами в сесіях спершу попереджає, другий — зупиняє; `SIGTERM` зупиняє одразу. `--host` з іншою адресою відкриває сервер у мережу під захистом лише токена — для віддаленої машини надійніший SSH-тунель до localhost.
