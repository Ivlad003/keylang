# keylang — рев’ю рішень, дизайну й архітектури

Дата: 2026-09-27. Охоплення: `docs/design.md`, `docs/format.md`, `src/`, CLI, тести та макети в `design/png/`.

**Висновок:** основа вдала, але перевірка відповідності коду специфікації може давати хибний успіх. Перші пріоритети — працездатна npm-дистрибуція, актуальний семантичний знімок і явна неповнота аналізу.

## Контекст перевірки

- Робоче дерево змінювалося паралельно. Контрприклади зафіксовано на окремому WIP-знімку від **2026-09-27 13:59 UTC**, під час реалізації M1.
- Середовище: **Node v24.20.0**. На знімку **10/10 тестів** і `npm run typecheck` проходять.
- M1 згодом оформлено комітом `6f7bcab`; [бенчмарк](../../bench/results.md) підтверджує генерацію карти й виявлення доданого імпорту після регенерації. Це вужча перевірка, ніж відсутність усіх наведених нижче прогалин.
- Тут збережено результати рев’ю та мінімальні умови відтворення. Оновлення [дизайну](../design.md) фіксує цільові контракти; закриття кожної знахідки потребує перевірки реалізації.
- **P1** — блокер дистрибуції, втрата даних або хибний успіх основної перевірки. **P2** — суттєва помилка чи обмеження окремого правила, графа або представлення.

## Підтверджені проблеми реалізації

### RV01 · P1 — npm/npx-пакет не запускається

**Місце:** [`bin/keylang.js`](../../bin/keylang.js), імпорт `../src/cli.ts`; [`package.json`](../../package.json), поле `files`.

**Відтворення:** розмістити вміст пакета фізично в `node_modules/keylang` і запустити `node node_modules/keylang/bin/keylang.js --version`.

**Результат:** код виходу 1, `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`. Node відмовляється виконувати `.ts` під `node_modules`; локальний запуск із репозиторію цього не виявляє. Обмеження описане в [документації Node](https://nodejs.org/api/typescript.html#type-stripping-in-dependencies).

**Рекомендація:** прямий запуск TS у розробці; `prepack` компілює JavaScript у `dist/`, опублікований entrypoint завантажує JS. Перевірка релізу — встановлення tarball із `npm pack` у чистий тимчасовий каталог і запуск справжнього CLI з `node_modules`.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `packed tarball runs the CLI from node_modules`; tarball на Node 22.18 і 24 — `bench/results.md` (M1.1).

### RV02 · P1 — `check` пропускає порушення на застарілій карті

**Місце:** [`src/cli.ts`](../../src/cli.ts), `cmdCheck`.

**Відтворення:**

1. Створити модулі `domain.order` і `infrastructure.io` та правило `deny domain infrastructure`.
2. Виконати `map`.
3. Додати в домен імпорт і виклик `save` з `infrastructure.io`.
4. Виконати `check` без регенерації.

**Результат:** `check` повертає 0 і «0 error(s), 0 warning(s)». `map --check` повертає 1; після `map` перевірка знаходить K102.

**Рекомендація:** єдиний CI-контракт — перевірка джерел на актуальному знімку. `check` має сам перевіряти свіжість та оновлювати аналіз; ручне поєднання команд не повинно бути прихованою передумовою правильності.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `check sees a new denied import without writing the map`, `check sees a layer moved in keylang.json without map`, `check finds the snapshot for any spelling of the spec path`.

### RV03 · P1 — видалення останньої функції не ламає посилання

**Місце:** [`src/resolve.ts`](../../src/resolve.ts), `Index.lookup`; правило Р13 у [форматі](../format.md).

**Відтворення:**

1. `src/order.ts` містить `export function create() {}`; flow посилається на `main.order.create`.
2. Замінити функцію на `export const marker = 1` і перегенерувати карту.

**Результат:** `check` знову повертає 0. Модуль без оголошених членів стає `opaque`, тому довільний залишок ID приймається як допустимий.

**Рекомендація:** відрізняти відомо порожній модуль від модуля з невідомим вмістом. Непрозорість задавати явно; вона не підтверджує існування довільної функції.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `removing the last function of a complete module is K001`, `a flow id resolves against current code, not the committed map`; проба `removed-fn` у бенчмарку.

### RV04 · P1 — генератор перезаписує ручний файл

**Місце:** [`src/map.ts`](../../src/map.ts), `writeMap`.

**Відтворення:** створити ручний `keylang/map/main.md` без `keylang:generated`, додати джерело для шару `main`, виконати `map`.

**Результат:** ручний текст замінено згенерованим. Маркер перевіряється при видаленні зайвих файлів, але не при перезаписі однойменного файла.

**Рекомендація:** перевіряти належність усіх цільових файлів генератору до початку запису. Конфлікт — діагностика зі шляхом; ручні правила, потоки та описи зберігаються.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `map refuses to overwrite a manual map file`; проба `manual-map` у бенчмарку.

### RV05 · P1 — неповний аналіз стає чистим результатом

**Місце:** [`src/extract/ts.ts`](../../src/extract/ts.ts), `extractTs`; [`src/graph.ts`](../../src/graph.ts), `buildGraph`; [`src/cli.ts`](../../src/cli.ts), `cmdCheck`.

**Відтворення A:** усередині доменної функції виконати літеральний імпорт:

```ts
export async function create() {
  const { save } = await import("../infrastructure/io.ts");
  save();
}
```

Після `map` правило `deny domain infrastructure` не спрацьовує: імпорт не потрапив до залежностей.

**Відтворення B:** додати `import { missing } from "./missing.ts"`. `map` повідомляє `unresolved import`, але повертає 0; наступний `check` також повертає 0, уже без попередження.

**Рекомендація:** витягувати літеральні `import()`/`require()` з усього дерева; нерозв’язані та непідтримані конструкції зберігати разом із причиною й позицією. Повнота аналізу має впливати на вердикт конкретного правила; одних агрегованих лічильників недостатньо.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `unresolved import makes deny unverified unless --strict`, `a literal import() inside a function is a denied dependency`, `a computed import specifier is coverage, not an edge`, `one failing deny does not hide the verdicts of other denies`.

### RV06 · P2 — `exports` пропускає фактичні експорти

**Місце:** [`src/extract/ts.ts`](../../src/extract/ts.ts), `facts.exports`; [`src/rules.ts`](../../src/rules.ts), `exportedFns`.

**Відтворення:** для модуля з правилом `exports allowed` використати:

```ts
export function allowed() {}
function extra() {}
export { extra };
export const secretFlag = true;
export class ExtraClass {}
export type ExtraType = string;
```

**Результат:** K104 немає. Функція `extra` лишається `internal` у карті; інші види експортів не входять у порівняння.

**Рекомендація:** окрема таблиця публічних експортів із локальними іменами, aliases, default, re-exports і видами символів. Порівнювати її, а не список fn без HTML-коментаря `internal`.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `exports lists extra public names and a missing one`, `exports compares aliases, default, and export * names, not map ids`, `export * from an opaque module leaves exports unverified`.

### RV07 · P2 — затінення імен породжує хибний виклик

**Місце:** [`src/graph.ts`](../../src/graph.ts), `resolveCallee`.

**Відтворення:**

```ts
export function target() {}
export function run(target: () => void) {
  target();
}
```

**Результат:** індекс містить `run → main.a.target`, хоча викликається переданий параметр.

**Рекомендація:** враховувати лексичні області видимості й затінення. Якщо ціль параметра невідома, зберігати невизначеність замість підтвердженого ребра. Позначка `syntactic` сама по собі не робить ребро достовірним.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `a shadowed parameter is not a confirmed call edge`, `a local binding in any enclosing scope hides the module function`; проба `shadowed-call` у бенчмарку.

### RV08 · P2 — локальний `no-cycles` пропускає цикл

**Місце:** [`src/rules.ts`](../../src/rules.ts), `findCycles` і фільтрація за `rule.under`.

**Відтворення:** задати ребра `a → b → c → a` та `a → d → c`; застосувати `no-cycles` до `d`.

**Результат:** діагностики немає, хоча існує цикл `d → c → a → d`. DFS знаходить цикл через `b`, а під час обходу `d` вершина `c` уже оброблена.

**Рекомендація:** знаходити сильно зв’язні підграфи (SCC) та перевіряти належність модуля до них. Конкретний маршрут циклу добирати окремо для пояснення.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `no-cycles reports the component that contains d`, `no-cycles: a self-import is a cycle, two cycles are two findings, an acyclic graph is quiet`, `no-cycles under a directory module routes through that module`; юніт-тести `tests/scc.test.ts`.

### RV09 · P2 — зарезервований alias робить карту невалідною

**Місце:** [`src/graph.ts`](../../src/graph.ts), вибір alias; [`src/emit.ts`](../../src/emit.ts), `renderModule`.

**Відтворення:** імпортувати функцію з `src/type.ts`.

**Результат:** рядок `- type main.type` інтерпретується як оголошення типу і дає K005.

**Рекомендація:** враховувати контекстні ключові слова при генерації alias, перевіряти унікальність ID та round-trip згенерованої карти через власний парсер.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `map links are relative, encoded, and round-trip` (імпорт із `src/type.ts`), `generated maps of the repo and the fixture parse`.

### RV10 · P2 — шлях із дужками ламає round-trip

**Місце:** [`src/emit.ts`](../../src/emit.ts), посилання; [`src/parser.ts`](../../src/parser.ts), `linkEnd`.

**Відтворення:** створити `src/app/(shop)/page.ts` з експортованою функцією та виконати `map`.

**Рекомендація:** узгоджене URL-кодування шляхів і декодування для навігації; перевірки для дужок, пробілів, `#` та інших допустимих символів імен файлів.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `map links are relative, encoded, and round-trip` (`src/app/(shop)/page.ts`).

### RV11 · P2 — неправильна база Markdown-посилань

**Місце:** [`src/emit.ts`](../../src/emit.ts), `renderModule` / `renderFn`.

**Рекомендація:** індекс зберігає шлях від кореня репозиторію; emitter рахує відносний шлях від конкретного Markdown-файлу, наприклад `../../src/a.ts#L1`.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `map links are relative, encoded, and round-trip` (`../../src/…#L1`).

### RV12 · P2 — ієрархія каталогів підміняє досяжність

**Місце:** [`src/rules.ts`](../../src/rules.ts), обхід `entry`.

**Відтворення:** оголосити `main.pkg.live` і `main.pkg.dead` без ребер між ними та `entry main.pkg.live`.

**Результат:** попередження для `dead` немає: `live` досягає батька `pkg`, а той — усіх дітей. Це задокументована поведінка M1, але вона не підтверджує використання файлу.

**Рекомендація:** ієрархія ID не утворює виконуваних ребер. Результат називати «не досягнуто в моделі», із зазначенням покриття, а не доведеним мертвим кодом.

**Закрито 2026-09-27 (M1.1).** Тести в `tests/cli.test.ts`: `entry does not treat a sibling as reachable`, `entry follows re-exports, skips directory modules, and names the hole`.

## Прогалини дизайну й контрактів

### RV13 — суперечлива політика невпорядкованих шарів

Початковий `design.md` §3.3 вимагає явного `allow`; `format.md` і `rules.ts` дозволяють залежності **в** невпорядкований шар, якщо немає `deny`.

**Рекомендація:** вибрати одну політику й зафіксувати таблицю для залежностей усередині шару, між впорядкованими, у невпорядкований і з нього. Окремо визначити `external` та `unassigned`; відсутність класифікації файлу не повинна приховувати прогалину аналізу.

**Прийняте рішення (2026-09-27):** зберегти чинну політику M1 — у невпорядкований шар вільно за відсутності `deny`, з нього у впорядкований потрібен `allow`. Рішення внесено в дизайн §3.3; неповнота аналізу обліковується окремо від дозволу залежності.

### RV14 — семантичні факти втрачаються при проході через Markdown

Поточний шлях: `код → Graph → Markdown → IR → відновлений граф правил`. У Markdown не передається достатньо відомостей про вид ребра, точність резолвінгу, позицію в коді та невизначеність. JSON-індекс і перевірка використовують різні проєкції даних.

**Рекомендація:** семантичний знімок із manifest, вузлами, ребрами, експортами, походженням та покриттям. `check` працює з ним безпосередньо. Текстовий IR зі spans служить парсеру, форматеру й редактору; Markdown-карта є представленням знімка.

### RV15 — послідовність flow не визначається шляхом між сусідніми викликами

```ts
function buy() {
  validate();
  save();
}
```

У графі викликів немає шляху `validate → save`, хоча порядок правильний. Статично треба перевіряти досяжність від відповідного батьківського кроку, а порядок — окремо за trace.

Формат `{id, parent, ts}` також не визначає повторні виклики, рекурсію, паралельність, завершення й зв’язок із конкретним тестом та версією коду. Збіг підпослідовності не забороняє зайве списання коштів чи четвертий retry.

**Рекомендація:** розділити symbol ID та унікальний span ID, додати run/test/snapshot, початок і завершення, outcome та правила каузального порядку. Відсутній крок у неповному trace — `unverified`; негативні й кількісні твердження потребують окремого перевірюваного предиката або тесту.

### RV16 — spec-first суперечить правилу «лише наявні ID»

Первісний §5.1 відхиляє невідомі ID LLM, а §5.5 використовує їх для створення нового коду. K001 одночасно означає друкарську помилку, видалений код і заплановану можливість.

**Рекомендація:** явні декларації `planned` у ручних специфікаціях, із видом символу, очікуваною сигнатурою та місцем реалізації. Звичайне невідоме посилання лишається помилкою. Planned-вузол не є доказом реалізації та не отримує `ok` до перевірки коду.

### RV17 — хеш сигнатури не виявляє зміну поведінки

Зміна `total > 0` на `total >= 0` може зберегти сигнатуру й усі прямі залежності. Початковий механізм `stale` її не помітить.

**Рекомендація:** fingerprint нормалізованого AST тіла, сигнатури, контракту експорту та релевантних залежностей. Визначити транзитивну інвалідацію й збереження baseline разом із ручною специфікацією; регенерація карти не означає прийняття нового змісту прози.

### RV18 — UI й дорожня карта випереджають контракт перевірки

Макети вдало тримають у центрі текст, діагностики й diff. Проте загальна зелена галочка не пояснює, чи підтверджено лише ID, статичний зв’язок, тест або trace. Заморожування v1 перед наскрізною реалізацією flows/trace залишає основні неоднозначності неперевіреними.

**Рекомендація:** показувати джерело доказу, актуальність і покриття; спочатку завершити один flow `код → специфікація → тест → trace`, потім usability-пробу та стабілізацію граматики/LSP. Повний TUI-редактор, wiring і голос розвивати після цього.

## Рішення, які варто зберегти

- TypeScript/Node як близький автору стек; збірка npm-артефакту розв’язує проблему RV01.
- Repo-local Markdown і розділення згенерованої карти та ручних правил/потоків.
- Точні spans для діагностик, форматера й майбутнього LSP.
- Дорадча роль LLM: запропоноване або прийняте людиною твердження не стає автоматично підтвердженим фактом.
- Поведінкові перевірки через справжній CLI та мінімальні контрприклади поряд із бенчмарком на реальних репозиторіях.

## Рекомендований критичний шлях

1. **Надійність M1:** npm tarball; актуальний семантичний знімок; явна неповнота; захист ручних файлів; закриття RV01–RV12 регресійними перевірками.
2. **Один наскрізний flow:** static + tests + мінімальний TS trace; `planned`; стейлнес; сценарії видалення кроку, зайвого виклику й паралельності.
3. **Граматика й LSP:** узгодження `format.md`, реалізації та дизайну; usability-проба; заморожування v1 після перевірки семантики.
4. **Розширення продукту:** TUI/web, інші мови, LLM/MCP, wiring та голос на тому самому контракті аналізу.

## Межі гарантій

- Синтаксичний граф має неповне покриття; сама наявність або відсутність ребра не завжди є доказом поведінки.
- Успішний тест і trace підтверджують конкретні спостережені сценарії. Перевірка існування ID не підтверджує зміст інваріанта природною мовою.
- Тризначний вердикт має стосуватися явного критерію та області перевірки. Відомий контрприклад дає `fail`; брак необхідних доказів — `unverified`.
- Зелений бенчмарк базових імпортів не вимірює автоматично повноту резолвінгу, відсутність хибних ребер або правильність усіх flows.
