# 0003. Життєвий цикл wiring: пряма згенерована функція, без контейнера й без циклів

**Дата:** 2026-09-28 · **Статус:** прийнято 2026-09-28 (реалізовано в M6: `src/wiring.ts`, `src/wire-gen.ts`, `tests/wiring.test.ts`) · **Джерело:** design §6, §10.10; тікет `.scratch/m5-m7/issues/08`; прототип [`examples/wiring-lifecycle/`](../../examples/wiring-lifecycle/)

## Контекст

Design §6 обіцяє `keylang wire`: із розділу `# wiring` генерується типізований `keylang.gen.ts`. До реалізації треба визначити те, що саме двофазне зв'язування не вирішує. Це фабрики, асинхронна ініціалізація, завершення роботи, області життя й цикли. Потрібен також доступ до залежності, яку ще не ініціалізовано. Контейнер у runtime (реєстр, резолвінг за ключем, проксі) ховає цей порядок від `tsc` і від `check`. Помилка в зв'язуванні тоді проявляється лише під час запуску.

## Рішення

1. **Немає контейнера в runtime.** `keylang wire` генерує одну функцію `wire(env)` з прямим кодом: для кожної фабрики — мемоізований builder, який очікує свої залежності й викликає фабрику з об'єктом іменованих залежностей (`createStore({ db: await buildDb() })`). Так гілка `when`, яку не обрано, не будується, а спільна залежність будується один раз. Генерований файл імпортує модулі як звичайний код. Тому типи перевіряє `tsc`, а заборонені залежності — той самий `check` на тих самих імпортах. Окремий рантайм keylang не потрібен.
2. **Фабрика** — fn (виклик з об'єктом залежностей) або клас (`new` з тим самим об'єктом). Результат, що є `Promise`, очікується через `await`: це і є асинхронна ініціалізація. Лист без рядка `wire` створюється без аргументів.
3. **Порядок ініціалізації** — топологічний: залежності перед залежними, серед рівних — порядок оголошення, вузли по одному. Порядок детермінований і видимий у згенерованому коді, тож паралельної ініціалізації в v1 немає.
4. **Завершення роботи.** Значення з методом `dispose()` реєструється в момент створення. `Symbol.asyncDispose` не використовується: він потребує `lib` `esnext.disposable` у проєкті користувача. `dispose()` контейнера викликає їх у зворотному порядку. Виконуються всі, а помилки збираються в `AggregateError`.
5. **Помилка ініціалізації.** Уже створені вузли звільняються у зворотному порядку, потім вихідна помилка прокидається далі. Напівзібраного контейнера не буває.
6. **Цикли заборонено.** Цикл у графі `wire` — діагностика з повним шляхом ще до генерації: `keylang wire` нічого не пише, а `check` повідомляє про цикл. Лінивих проксі й двофазного зв'язування немає: обидва дозволяють звернутися до неініціалізованої залежності. Цикл розривається в коді: колбеком, подією або спільною залежністю.
7. **Область життя в v1 одна:** виклик `wire()`. Кожен вузол створюється один раз на виклик. Область на запит — окремий виклик згенерованої функції. Оголошених областей (`scoped`, `transient`) у v1 немає.
8. **`when env.X = v → id`** обирає реалізацію залежності під час виклику `wire(env)`. Обидві гілки мають бути сумісні з параметром фабрики, і це перевіряє `tsc`. Непокрите значення лишає реалізацію за замовчуванням, тобто рядок самої залежності.
9. **`compose id`** обгортає значення залежності: `const api = logger(apiRaw)`. Декоратор — fn одного аргументу. Кілька `compose` застосовуються в порядку запису, перший — найближчий до значення.

## Прототип

`node examples/wiring-lifecycle/demo.ts` — написаний вручну код тієї форми, яку генерує `wire`:

```
order: {"order":["db","store","purchase"]}
cycle: {"cycle":["a","b","a"]}
lifecycle: init db → init store → init purchase → rows(insert) → dispose store → dispose db
init failure: init db → init store → init payments (fails) → dispose store → dispose db → error: payments: no API key
```

## Наслідки

- Відповідність залежностей перевіряє `check` на знімку, де `keylang.gen.ts` — звичайний модуль у своєму шарі. Контейнер не отримує окремої влади над архітектурою.
- Функція, згенерована для TS, — перша ціль. Для Rust (`keylang.gen.rs`) діють ті самі правила 1–9: `Drop` замість `dispose`, `?` замість `try/catch`.
- Паралельної ініціалізації, лінивих залежностей і областей на запит немає. Кожне з них потребує окремого рішення з прикладом, який показує, що звернення до неініціалізованого неможливе.
- Для trace контейнер дає додаткові точки: згенерований виклик фабрики можна обгорнути span. Мінімальний trace від контейнера не залежить (§6).
