# 0020. Опційний семантичний backend для TypeScript: `typescript` з репозиторію, ребра з походженням `semantic`

**Дата:** 2026-10-06 · **Статус:** прийнято 2026-10-06, не реалізовано; окрема фіча після релізу 0.6.0 (`.scratch/ts-semantic-backend/`, design §9, M10) · **Джерело:** [рев'ю 2026-10-05](../review-2026-10-05.md), «DX для coding agents» п. 7 і «Що не зроблено і чому»; design §7 «Резолвінг», §10 п. 7; [research.md](../archive/research.md) (SCIP, stack graphs); рішення автора 2026-10-06.

## Контекст

keylang розв'язує виклики синтаксично: tree-sitter і власний резолвер бачать локальні імена, затінення, імпорти, експорти й типізованого отримувача. Типізований отримувач — це анотований параметр чи локальне значення, `new X()` або тип поля класу. Тип, який TypeScript виводить сам, keylang не бачить. Тож кожен виклик `x.m()` через значення з виведеним типом стає діркою покриття.

Факти, виміряні 2026-10-06 на самому keylang (коміт `bcc4f2b`):

- `keylang map`: 165 файлів; викликів 4 176 resolved, 3 373 external, 7 070 dynamic, 323 unresolved.
- Відтворений приклад:

  ```ts
  // src/infra/db.ts
  export class OrderRepo { save(order: string): void { console.log(order); } }
  export function openRepo() { return new OrderRepo(); }
  // src/app/orders.ts
  import { openRepo } from "../infra/db.ts";
  export function place(): void {
    const repo = openRepo();
    repo.save("order");
  }
  ```

  Потік `- trigger ui.cli.main` / `  - step app.orders.place` / `    - step infra.db.OrderRepo.save` дає: ``static unverified infra.db.OrderRepo.save: no resolved path from app.orders.place; call through a local value `repo.save` at src/app/orders.ts:4:3 may reach it``. З анотацією `const repo: OrderRepo = openRepo()` той самий крок — `static ok`. Виходить, що аналізатор змушує переписувати код під себе, хоча режим `--static=behavior` для хуків (design §4.2) зроблено саме проти цього. Звідси й «втома від `◌`» (design §10 п. 7).
- Прототип-вимір: разовий скрипт поза репозиторієм, `typescript` 5.9.3 з `node_modules` keylang, опції з `tsconfig.json` плюс `allowJs`. Program над 165 файлами знімка (565 файлів разом із lib і `@types`) будується за 1,5–1,7 с. `getResolvedSignature` для 7 393 дірок викликів (dynamic і unresolved) займає 1,9–2,6 с. Теплий `check` зараз — ~1,0 с. Із 7 393 дірок за позицією зіставлено 7 371. Checker назвав:

  | Що назвав checker | Скільки | Що з цим робить це рішення |
  |---|---|---|
  | fn чи метод репозиторію з тілом (200 function, 56 method) | 256 | ребро `semantic` |
  | замикання, оголошене в тій самій fn | 1 060 | не дірка: його виклики вже записано за fn з `closure` |
  | замикання іншої fn | 6 | дірка |
  | метод чи функція поза репозиторієм: методи інтерфейсів lib (`Array`, `Map`, `Promise`…) — 4 996, методи класів пакетів — 331, `@types/node` — 177, інше — 3 | 5 507 | зовнішній виклик |
  | лише сигнатура типу: у репозиторії 505 (303 типи функцій, 201 метод інтерфейсу, 1 тип конструктора), поза ним 36 (типи функцій і сигнатури виклику) | 541 | дірка з назвою типу |
  | нічого | 1 | дірка |

  Отже, на самому keylang головний ефект — не нові ребра (до +256, тобто +6 %), а шум. Приблизно 6,8 тис. із 7,4 тис. дірок стають відомими викликами, діркою лишаються близько 570. Число 256 — верхня межа: вкладена `function` усередині fn вузлом знімка не є. На коді з сервісами й репозиторіями частка ребер до методів, імовірно, вища. Це гіпотеза: її перевіряє вимір на `bench/` (тікет 04).
- design §7 цілився в опційний backend SCIP (research.md: точний шлях, але «потрібен toolchain на мову → не дефолт»). Його не реалізовано.

## Рішення

1. **Опційний backend на пакеті `typescript` з репозиторію.** keylang бере `typescript` з `node_modules` аналізованого репозиторію: розв'язання Node від його кореня (`createRequire`), тобто ту саму копію, яку бачить `tsc` проєкту. Пакет ніколи не стає залежністю keylang: ні в `dependencies`, ні в `peerDependencies`, і копія з установки самого keylang не береться. Немає пакета або він не завантажився — усе як зараз: manifest записує `null`, а `doctor` каже чому.
2. **Що розв'язує backend.** Лише виклики у файлах TS/JS знімка, які синтаксичний прохід лишив діркою (`dynamic-call`, `unresolved-call`) або неоднозначним ребром (`ambiguous`). Розв'язане синтаксичне ребро backend не замінює. Оголошення, яке повертає `getResolvedSignature(call).declaration`, дає таке:
   - **fn, метод, конструктор чи accessor з тілом у файлі знімка**, який keylang індексує як вузол → ребро `call`, `resolution: resolved`, `provenance: semantic`. Для `ambiguous` — лише коли це оголошення є серед `candidates`.
   - **Замикання, оголошене в тій самій fn** → ні ребра, ні дірки. Його виклики вже записано ребрами цієї fn з позначкою `closure`. Виклик рахується в `stats`.
   - **Метод чи функція поза знімком** (lib, `node_modules`, `.d.ts`), зокрема член бібліотечного інтерфейсу на кшталт `Array.map` → зовнішній виклик, як типізований отримувач класу пакета зараз. Виняток: коли клас репозиторію реалізує чи розширює цей тип, дірка лишається, бо виконатися може код репозиторію.
   - **Лише сигнатура типу** (тип функції, сигнатура виклику, параметр типу — де б їх не оголосили; член інтерфейсу репозиторію) **або нічого** → дірка лишається. Значенням такого типу може бути функція репозиторію, тож зовнішнім цей виклик не стає: інакше `fail` за відсутністю шляху втратив би надійність (design §4.2). Причина дірки називає тип, наприклад «a member of the interface `Repo`: keylang does not know which implementation runs».
3. **Походження.** `provenance` ребра знімка стає `syntactic | semantic`. Вердикт, доведений через semantic-ребро (крок `static`, `fail` правила `deny`), несе `provenance: semantic`. Semantic-ребро — такий самий підтверджений статичний факт, як ребро типізованого отримувача сьогодні. Тому заборонене semantic-ребро дає `fail` (design §4.2). `--static=shape` і `behavior` бачать його однаково: це записаний у коді виклик, а не хук.
4. **Ідентичність.** Manifest знімка записує backend: версію `typescript` або `null` і хеш опцій компілятора. Ці дані входять у `snapshotId`, тож схема знімка зростає (7 → 8). Кеш фактів файлів зберігає свій ключ: синтаксичні факти від `typescript` не залежать. Результати backend зберігає окремий кеш у `.keylang/cache/`. Його ключ містить версію `typescript`, опції компілятора, хеші всіх файлів знімка й входи поза manifest (відкрите питання 5). Program читає ті самі тексти, що й екстрактор: файл із диска або overlay незбереженого буфера в LSP і TUI.
5. **Детермінізм.** Ті самі входи дають ті самі ребра в тому самому порядку й той самий `snapshotId`. Backend не залежить ні від часу, ні від порядку обходу файлової системи. Інкрементальний прохід дає той самий результат, що й повний; це перевіряє тест.
6. **Бюджет часу** (ціль; перевіряє й записує в `bench/results.md` тікет 04). Теплий `check` на keylang без змін у джерелах — не більше +10 %, тобто ≤ 1,1 с замість ~1,0 с. Після зміни одного файла TS — ≤ 3 с. LSP і TUI тримають Program між поколіннями аналізу (`oldProgram`). Холодний запуск вимірюється й записується, але не обмежується.
7. **Межі шарів.** Завантаження `typescript` і запити до checker живуть у шарі `extract`: адаптер повертає прості дані «позиція виклику → позиція й вид оголошення». Зіставлення з ID і заміна дірок — у `graph`/`snapshot` (шар `map`). `lang`, `base` і `check` не імпортують ні `typescript`, ні tree-sitter. У `keylang/rules.md` з'являються `deny` на `external.typescript` для цих шарів.
8. **Граматика не змінюється.** Змінюються лише факти знімка та їхнє походження.

## Розглянуті варіанти

- **Імпорт SCIP-індексу (`scip-typescript`).** Точний формат, спільний для багатьох мов (є й `scip-python`), — колишня рекомендація research.md. Для TypeScript відхилено. Це окремий індексатор, який користувач має поставити й запустити, а він сам будує ту саму Program TypeScript. Його protobuf-файл має власний життєвий цикл, і свіжість індексу довелося б звіряти зі знімком: застарілий індекс точності не додає (design §7). Ще знадобилися б розбір protobuf і зіставлення символів SCIP з ID. Для Python, Rust і PHP SCIP лишається варіантом.
- **Не робити: лишити синтаксичний резолвер і радити анотації.** Нуль вартості й залежностей. Відхилено: код переписували б під аналізатор, на самому keylang лишилося б 7 тис. дірок, а «втома від `◌`» вчить агентів і людей не помічати `unverified`.
- **Зробити `typescript` залежністю keylang** (`dependencies`, optional чи peer). Відхилено. Кожен користувач, зокрема Python, Rust і PHP, отримав би +23 МБ. Версія була б версією keylang, а не проєкту, хоча можливості TS і `tsconfig` проєкту прив'язані до його власної версії.
- **Власний вивід типів у синтаксичному резолвері** (тип повернення локальної fn: `openRepo()` повертає `new OrderRepo()`). Закрив би найпростіші випадки без залежності. Відхилено як основний шлях: generics, союзи, звуження, перевантаження й типи `this` швидко перетворюють його на другий type checker. Дрібні синтаксичні покращення лишаються можливими.
- **tsserver чи language service окремим процесом.** Керування процесом і протоколом без виграшу проти Program у тому самому процесі для пакетного аналізу. Відхилено.

## Наслідки

- Recall. На keylang ~6,8 тис. із 7,4 тис. дірок викликів стають відомими (оцінка прототипу), ребер — до +256. Кроки на кшталт `repo.save()` дають `static ok` без анотацій.
- Вартість. Program на keylang будується ~1,5 с, тож без кешу backend не вкладається в бюджет. Перший `check` після зміни файла TS повільніший за наступні.
- Знімок залежить від того, чи встановлено `typescript`. CI без `npm ci` отримає інший `snapshotId` та іншу карту, а можливо й інші вердикти, тож `map --check` стане `stale`. keylang варто запускати після встановлення залежностей, як і тести. Manifest показує, яким backend побудовано знімок.
- Звіти тестів і trace одного разу стануть `stale`: змінюються схема й manifest, як і за кожної зміни екстрактора. Репортер `node:test` і hooks trace рахують `snapshotId` повним аналізом, тож теж завантажать `typescript`. Їхню вартість стримує той самий кеш.
- Правила бачать більше ребер. `deny`, `layers` і `no-cycles` можуть дати нові знахідки на тому самому коді, і це очікувано: про це має сказати опис релізу.
- Безпека. keylang уперше виконує код із каталогу аналізованого репозиторію (`node_modules/typescript`). Довіра та сама, що до `tsc` чи `npm test` у цьому репозиторії. Але досі `keylang check` лише читав файли. Як на це відповісти — відкрите питання 1.
- Python, Rust і PHP не змінюються. Backend для них — окреме рішення.
- Речення snapshot.md §11 «`provenance: semantic` … лишаються дорожньою картою» зміниться разом із реалізацією.

## Відкриті питання

1. **Вимикач і вимога.** Чи потрібне поле `keylang.json` `"typescript": "auto" | "off" | "require"` або змінна середовища? `require` гарантує CI той самий знімок, що й локально, і дає код 2 без пакета. `off` потрібен для неперевіреного репозиторію й для порівнянь. Рекомендація: поле з типовим `auto`. Це зміна формату конфігурації, тож вирішує автор. Від відповіді залежить тікет 01.
2. **Monorepo з кількома `tsconfig`.** v1 бере одну Program з кореневим `tsconfig.json` (або `jsconfig.json`; без них — типові опції з `allowJs`). Чи потрібні окремі Program за найближчим `tsconfig`, як проєкти tsserver? Вартість тоді множиться.
3. **JS-файли.** v1 бере JS-файли знімка коренями Program з `allowJs: true`. `checkJs` не потрібен: діагностики backend не читає, а JSDoc дає типи. Чи брати JS, коли `tsconfig` проєкту `allowJs` не вмикає?
4. **Вартість Program на великих репозиторіях** (storefront, 898 файлів). Якщо бюджет не вкладається: інкрементальна Program у процесі, запити лише для файлів із дірками, окремий процес-демон?
5. **Входи поза manifest.** `.d.ts` пакетів і `@types` впливають на виведення типів. Що брати в ключ кешу: хеш lock-файла чи хеші всіх файлів, які прочитала попередня Program? Другий варіант точний, але потребує списку з попереднього запуску.
6. **Союзи й реалізації.** Чи давати отримувачу-союзу кількох класів репозиторію (`A | B`) ребро `ambiguous` з `candidates` замість дірки? Те саме питання — для члена інтерфейсу з відомими реалізаціями в репозиторії. Окремо: бібліотечний інтерфейс, який реалізує не клас, а об'єктний літерал репозиторію. Правило п. 2 такого не бачить, і виклик стає зовнішнім.
7. **Замикання, яке викликає сама fn.** Коли `f` прямо викликає своє замикання `push`, виклики в `push` справді виконуються разом із `f`. Чи можуть тоді ребра `closure` такого замикання доводити `static ok`? Це зміна семантики design §4.2, тож окреме рішення.
8. **Інші мови.** SCIP чи власні backend-и для Python, Rust і PHP?
