# 0008. Повний TUI через спільні прикладні операції з CLI

**Дата:** 2026-09-29 · **Статус:** proposed; продуктова вимога «все можна було в TUI» задана користувачем, технічний спосіб обрано агентом за делегуванням. Ще не реалізовано.

TUI має надавати всі прикладні операції keylang, включно з ініціалізацією, генерацією та готовністю фічі. Щоб довгоживуча сесія й одноразовий CLI не мали різної семантики, CLI-оркестрацію виділяємо в транспортно-незалежний модуль операцій із типізованими запитами, предметними результатами й прогресом; CLI та TUI стають його callers. Виклик вкладеного CLI з розбором stdout відхилено: він ускладнює роботу з dirty-буферами, структурованими результатами, скасуванням та ідентичністю операції, а дублювання обробників створює другий контракт.

## Наслідки

- Поточні генератори, перевірка, файлові контракти й CLI-коди зберігаються; новий модуль володіє оркестрацією, а не повторює предметні алгоритми.
- TUI не імпортує CLI-вхід. Під час реалізації модуль операцій отримує власний шар між предметними можливостями та транспортами; інтеграційні адаптери, потрібні обом транспортам, виходять із шару CLI.
- Синхронна важка робота йде у worker, UI отримує події. Код завершення окремої операції не завершує TUI.
- Запис працює зі збереженими входами; аналіз редактора й далі підтримує overlays. Підготовлений результат перевіряє актуальність входів перед застосуванням.
- Немає загальної транзакції чи відкату всього репозиторію: частковий запис має явний звіт. Read-only режими не пишуть файлів.
- ADR 0005 про зовнішні харнеси лишається чинним: операція `agents` налаштовує інтеграцію, а не запускає харнес. Доступ до чинного `spec-to-code` у TUI не означає оркестрацію довільної реалізації фічі.

Деталі: [дизайн робочого простору](../tui-workspace.md). Це цільова зміна архітектури, а не опис поточного розміщення коду.
