# 0018. Trace: запуски без тригера не судять потік; `instrumented` — увесь план процесу

**Дата:** 2026-10-05 · **Статус:** прийнято, реалізовано 2026-10-05 · **Джерело:** [рев'ю 2026-10-05](../review-2026-10-05.md), «LSP, докази й адаптери» п. 2 і 4

## Контекст

Канал trace (semantics.md §7) добре працював лише в одному запуску одного процесу. Багато запусків і багато процесів давали два хибні результати:

- `fail` з будь-якого запуску перекривав `ok` з іншого. Юніт-тест, що викликав лише `save`, давав тригеру потоку `missing step in unit-save`, хоча e2e-запуск довів увесь потік. У режимі PHPUnit кожен тест — окремий запуск, тож будь-який юніт-тест ламав тригер.
- `instrumented` рахувався як перетин множин процесів. Процес звітував лише символи файлів, які завантажив. Worker, що завантажив один файл, робив перетин порожнім. Тоді крок, якого справді не було, ставав `unverified not instrumented` замість `fail missing step`.

## Рішення

1. **Запуск судить потік, лише коли спостеріг його тригер.** Запуск без span-а тригера дає дереву потоку `unverified` «trigger not observed in <testId>». Він не впливає на вердикт, якщо інший запуск тригер спостеріг. Серед запусків із тригером правило як раніше: крок `fail`, якщо його порушив хоч один такий запуск, інакше `ok`, якщо хоч один підтвердив.
2. **Процес звітує як `instrumented` увесь план, який він обгорнув би**, незалежно від того, чи завантажив файл. Код, якого процес не завантажував, у ньому й не викликався. Виключаються символи файлів із іншим `sha256` і символи, які адаптер не вміє інструментувати (генератори тощо). Перетин між процесами лишається. Адаптери TS/JS, Python і PHP передають свій ID запуску дочірнім процесам і воркерам (`KEYLANG_TRACE_RUN`), тож це один запуск. Rust лишається явним: `instrumented` — функції зі `span()`/`instrument()` у тілі.

## Розглянуті варіанти

- **Обирати для кожного кроку найкращий запуск.** Ховало б справжнє порушення: другий e2e-тест іншою гілкою, де крок справді пропущено, мав би `ok` з першого.
- **Об'єднання (`union`) замість перетину для `instrumented`.** Процес, який завантажив змінений файл, тоді рахував би символ інструментованим.

## Наслідки

- Юніт-тести поруч з e2e-тестами більше не ламають trace потоку.
- Крок, виконаний лише у воркері, — один запуск із головним процесом. Його вкладення невідоме, тож він дає `unverified` «observed outside…», а не хибний `missing step`.
- Trace, записаний адаптерами до цієї зміни, має вужчий `instrumented` (лише завантажені файли). Його перетин може лишити крок `unverified`, доки тест не перезапущено з новим адаптером.
