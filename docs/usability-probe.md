# Протокол usability-проби

Людина проводить сесію за цим файлом, без додаткових пояснень від автора протоколу. Результати — у `docs/usability-probe-results-<дата>.md` за шаблоном нижче. Сесії й тріаж знахідок — тікет design-v0.2/28. Цей файл сесій не проводить.

Команди запускаються на поточному HEAD keylang, офлайн: з кореня keylang — `node bin/keylang.js …`, з іншої теки — `node <keylang>/bin/keylang.js …`, де `<keylang>` — шлях до кореня keylang. Глобальне встановлення не потрібне.

## Мета

Дізнатися, чи нотація keylang дає розробнику описати один потік свого репозиторію й довести його до перевіреного стану, і де шість вимірів Cognitive Dimensions (Blackwell і Green, [research-pl](research-pl.md) §2 «Зручність нотації», §7.1 №10) заважають. Виміри в тексті — англійською, як у джерелі.

## Учасники й добір

5–8 розробників, які вже відкривають свій репозиторій у редакторі й можуть поставити тонкий клієнт `editors/vscode/` (він лише запускає `keylang lsp`) або TUI `node bin/keylang.js` у терміналі. Не автори keylang і не люди, яким перед сесією пояснювали граматику. Спершу одна пілотна сесія на цьому протоколі; після неї — щонайменше 5 сесій, чий протокол уже не змінюють. Мова сесії — та, якою учаснику зручно; нотатки ведучий пише українською.

## Сценарії

**Основний.** Учасник на своєму репозиторії описує один потік через доповнення LSP і доводить його до перевіреного стану: файл у `keylang/flows/`, кроки — ID зі знімка або `planned`, `node bin/keylang.js check` для цього файла більше не дає `fail` на нових рядках потоку. Ведучий не підказує ключові слова. Якщо учасник працює в TUI, доповнення те саме (`completions()`), і це записується в метриці доповнень окремо від VS Code.

**Контроль, для порівнянності.** Перед сесією ведучий копіює `examples/shop-fixed`, `tests/fixtures/repo` і `tests/fixtures/spec-forms/valid` в тимчасові теки й не чіпає оригінали. На перших двох копіях, цим самим HEAD, з кореня keylang:

```
node bin/keylang.js check <копія>/shop-fixed
node bin/keylang.js check <копія>/shop-fixed --format json
node bin/keylang.js check <копія>/repo
node bin/keylang.js check <копія>/repo --format json
```

На HEAD 2026-09-29 копія `shop-fixed` завершується з кодом 0: один вердикт `unverified` (немає знімка), без K001, K101, K102 і K103. Копія `repo` друкує в stderr `6 fail, 1 unverified, 0 ok`. Інший підсумок — факт цього HEAD, його записують, сесію не зупиняють. Ці команди з кореня keylang читають `keylang.json` самого keylang, а не копії (з кореня копії `repo` дає `0 fail, 0 unverified, 4 ok`). Для контролю це байдуже: він фіксує, що підсумок на відомому корпусі не змінився.

`shop-fixed` — лише специфікації, без коду й `keylang.json`. Тому LSP на ній повертає порожні completion і hover, і завдання «через доповнення» на ній невиконуване. Для нього є третя копія — `spec-forms/valid`: у ній є `keylang.json`, код і потік. Її `check` запускають із кореня самої копії, щоб прочитати її `keylang.json` (той самий, що бачить редактор, відкритий на цій теці):

```
cd <копія>/valid
node <keylang>/bin/keylang.js check
node <keylang>/bin/keylang.js check --format json
```

На HEAD 2026-10-04 вона завершується з кодом 1 і друкує в stderr `4 fail, 2 unverified, 10 ok`. Усі чотири `fail` — K102 у `keylang/wiring.md` і `src/app/buy.ts`, а не в потоці: фікстура навмисно містить порушення.

Контрольне завдання учасника — на копії `spec-forms/valid`, відкритій як окрема тека в редакторі (або `node <keylang>/bin/keylang.js` з її кореня), файл `keylang/flows/buy.md`: дописати один вкладений рядок під `step domain.order.create` через доповнення (у VS Code або в TUI) і зупинитися. Доповнення після `step ` там пропонує п'ять ID, зокрема `app.buy.refund — planned fn`. Ведучий знову запускає `check` цієї копії і зберігає підсумок поруч із базовим. Копії `shop-fixed` і `repo` учасник у контрольному завданні не редагує: вони лише фіксують, що `check` на відомому корпусі відповідає. `shop-fixed` ще знадобиться в опитувальнику (error-proneness).

## Метрики

Рахує ведучий. Команди — офлайн. `check` читає `keylang.json` поточної теки, тому для репозиторію учасника і копії `spec-forms/valid` його запускають із їхнього кореня: `node <keylang>/bin/keylang.js check …`. Решта команд (`explain`, контроль `shop-fixed` і `repo`) — з кореня keylang.

- **Час до перевіреного сценарію** — секундомір від першого натискання в редакторі у файлі потоку до моменту, коли ведучий бачить підсумок `check` без нового `fail` на рядках цього потоку. Секунди, одне число. `init` у час не входить: якщо keylang у репозиторії ще немає, ведучий до старту запускає з кореня keylang `node bin/keylang.js init <репозиторій> --agents=none` (без `--agents=none` `init` пише ще й файли харнесів, напр. `AGENTS.md`). Якщо учасник викликає `init` сам, секундомір стартує після того, як `init` завершився.
- **Кількість `unverified`** — `node <keylang>/bin/keylang.js check --format json` з кореня репозиторію учасника, до сесії й після. У JSON масив `results`; рахуються елементи з `"verdict": "unverified"`. Той самий підсумок є в stderr: `N fail, M unverified, K ok`. «До» — одразу після `init` (у репозиторії без keylang раніше його не визначено), і в результат воно йде з позначкою `після init`. Окремим числом ведучий записує, скільки з них дає згенерований baseline: елементи з `"file": "keylang/rules.baseline.md"`. Для контролю — команди з розділу «Сценарії» на тимчасових копіях.
- **Прийняття доповнень.** У TUI (`node bin/keylang.js`) лічильник пише `.keylang/stats.json`, поле `suggestions.completion`: `accepted` — скільки разів учасник поставив детерміноване доповнення (`Tab` / `Enter`). Поруч `proposed`, `rejected`, `ms`. Опис поля — [format.md](format.md) §12, який відсилає до [tools.md](tools.md#tui). LSP-доповнення у VS Code цього файла не пишуть: лічильники є лише в `src/tui/assist.ts`. У сесії у VS Code ведучий рахує прийняті доповнення сам (скільки разів учасник вставив пункт списку доповнення) і ставить позначку `vscode, ручний підрахунок`.
- **Зрозумілість кожної K-діагностики** — оцінка 1–5 до і після `node bin/keylang.js explain <K-код>` (наприклад `explain K008`). 1 — з тексту діагностики незрозуміло, що змінити; 5 — зрозуміло без `explain`.

## Опитувальник

Кожен вимір — одне завдання в keylang і одне питання. Відповіді дослівно, коротко. Джерело вимірів — [research-pl](research-pl.md) §2.

**viscosity.** Завдання: перейменувати один модуль у специфікації учасника (або, якщо свого модуля ще немає, `orderAggregate` у копії `shop-fixed/map.md` не чіпати — це згенерована карта; перейменувати ID у `flows/checkout.md`, наприклад крок `domain.orderAggregate.create`). LSP не оголошує `renameProvider` (`src/lsp.ts`, об'єкт `capabilities` відповіді `initialize`). Питання: скільки місць довелося знайти й виправити вручну, і чи ви пропустили посилання?

**hidden dependencies.** Завдання: у потоці використати ID, оголошений в іншому файлі (крок або `calls` на функцію з карти чи з `planned` в іншому файлі). Питання: звідки ви дізналися, що таке ID існує — з доповнення, з hover, з файла, чи вгадали?

**role-expressiveness.** Завдання: той самий вкладений рядок під двома батьками. Три багатозначності з [research-pl](research-pl.md) §4.2 п. 6 (прийнята ціна Markdown; проба перевіряє, чи вистачає LSP-hover):

- вкладеність має щонайменше 10 значень залежно від батька (spec «Виправлення дослідження», Р-9): покласти `- test …` під крок потоку і під `invariant` і сказати, що означає відступ у кожному місці;
- `module` під шаром — оголошення, а в `# rules` — посилання: порівняти `- module [orderAggregate](…)` під шаром `domain` у `map.md` копії `shop-fixed` (рядок 9) і `- module application.purchase` у її `rules.md` (під ним — `exports` і `no-cycles`). У `rules.md` рядка `- module` під шаром немає. Hover на копії `shop-fixed` порожній (немає `keylang.json`, див. «Контроль»): питання про hover ставлять на репозиторії учасника;
- `when` у потоці — текст, а у wiring — `умова → id`: рядок `- when …` у `flows/checkout.md` і, якщо в репозиторії учасника є `# wiring`, рядок `- when env.… = … → …`.

Питання: чи видно з самого рядка його роль, і чи змінив відповідь hover?

**error-proneness.** Завдання — на копії `shop-fixed`, файл `flows/checkout.md`: під `- when товару немає на складі` дописати `- then OutOfStock` (одне слово без крапки). Питання: чи помітили ви попередження K008 до того, як ведучий показав вивід `check`? Сесії проводять після pl-theory/39, тож K008 уже є попередженням, а не мовчанням. K008 спрацьовує, лише коли якийсь оголошений ID закінчується цим словом (format.md §5, Р10). У `shop-fixed` таке є, і `node bin/keylang.js check <копія>/shop-fixed` друкує `` K008 `then OutOfStock` is read as text, not a reference (did you mean `then application.purchase.OutOfStock`?) `` (перевірено на HEAD 2026-10-04). У репозиторії учасника такого ID зазвичай немає: тоді `check` мовчить, і це відповідає специфікації, а не є пропущеним K008. Якщо учасник хоче повторити на своєму репозиторії, ведучий просить узяти останній сегмент наявного ID з його карти.

**premature commitment.** Завдання: почати опис у новій порожній теці, де ще немає тек коду (`node bin/keylang.js init` учасник може викликати сам). У порожній теці `init` очікувано відмовляє: `no supported source files found under . (…)`, код 2. `new module <name> --layer <шар>` теж відмовляє з кодом 2, доки шару немає в `keylang.json`. `new flow <name>` працює й без `keylang.json`. Отже, щоб записати `planned` у фічі, учасник має сам створити `keylang.json` з `"layers"`. Це очікувана поведінка цього HEAD, а не збій сесії, і вона якраз і є відповіддю на питання виміру; ведучий її не виправляє й не підказує. У репозиторії, де теки вже є, `init` вгадує шари з тек — це інший випадок, його позначають `init вгадав шари`. Питання: чи довелося вибирати шари раніше, ніж ви розуміли межі коду?

**secondary notation.** Завдання: дописати до потоку прозу, заголовок `##` і переставити два рядки місцями, не змінюючи ID. Питання: що з цього допомогло читати файл, а що keylang, на вашу думку, перевіряє?

## Питання для відкритих рішень

Після опитувальника, тими самими словами. Поруч — розділ, куди ляже відповідь.

- **Р-8.** З двох непорівнюваних правил (`allow` і `deny`, де ні область джерела, ні область цілі не вкладені одна в одну) яке ви вважаєте переможцем? Дані для K106 і редакції 2 ([research-pl](research-pl.md) §5 Р-8; тікети pl-theory/36 і 37).
- **Р-9.** Чого ви чекаєте від `- then` з одним словом без крапки: текст, посилання на ID, чи помилку? ([research-pl](research-pl.md) §5 Р-9; pl-theory/39).
- **Р-14.** Яке правило ви хотіли записати й не змогли виразити наявними словами? Порожня відповідь теж записується. Дані для умови повернення pl-theory/49 ([research-pl](research-pl.md) §5 Р-14).
- **design §10.6.** Чи була зайва робота вести намір через `planned` і baseline, чи наздоганяти код через `code-to-spec`? Жоден напрям не є обов'язковим кроком перед кодом ([design.md](design.md) §10.6).
- **design §10.7.** Чи заважає кількість `unverified` (у тому числі `◌` у TUI) довіряти перевірці? ([design.md](design.md) §10.7).

## Шаблон результатів

- Р-14 невиражене правило:

Після щонайменше п'яти сесій ведучий додає `## Зведення`: по одному абзацу на кожен із шести вимірів, рішення для Р-9, стан умови повернення pl-theory/49, що відповіли про Р-8, і список змін граматики (окремі тікети або рядок «без змін»).

## Правила приватності

У файл результатів не потрапляють ім'я, контакт, роботодавець, фрагменти коду учасника, шляхи й назви чужих репозиторіїв, вміст `keylang.json` учасника. Контрольні копії лежать у тимчасовій теці ведучого і видаляються після сесії. `.keylang/stats.json` читають лише поле `suggestions.completion` і в результат переносять числа. Запис сесії (екран, термінал) не зберігається в репозиторії.
