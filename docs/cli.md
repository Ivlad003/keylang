# CLI keylang

Команди, формати виводу, trace, wire, export c4, clone і Docker, харнеси агентів, baseline, фічі, пропозиції й модель. MCP і LSP — у [mcp-lsp.md](mcp-lsp.md), TUI і web — у [tui.md](tui.md), мова специфікацій — у [grammar.md](grammar.md) і [semantics.md](semantics.md). Покажчик — [tools.md](tools.md).

**Команди** (повний перелік — `keylang --help`): `init` пише `keylang.json` з вгаданими шарами й будує карту (як шари вгадуються — «Вгадані шари» у [format.md](format.md); про кожну теку, чий шар довелося перейменувати, — примітка в stderr, див. «Імена шарів» там само). Без `keylang.json` той самий вгаданий конфіг читають `check` і `map`, тож у Python-репо, де весь код — один пакет у корені з підпакетами, шар — кожен підпакет, а не весь пакет, і ID змінились (`app.api.routes.get_user` → `api.routes.get_user`); репо з `keylang.json` не зачеплені; `map [--check]` генерує карту, знімок і кеш фактів (з `--check` лише порівнює); глоби шарів `keylang.json`, що перетинаються або не збігають жодного файла, — попередження в stderr, не зміна коду виходу («Глоби шарів» у [semantics.md](semantics.md) §7); з полів `keylang.json` склад аналізу задають `exclude` (непрозорий модуль і прогалина), `outside` (код поза архітектурою, K107 на залежність від нього) і `assume` (файли, які архітектура імпортує, а keylang не читає й не вимагає: імпорт — запис `assumed-import` у `coverage`, без ребра й без прогалини; [snapshot.md](snapshot.md) §11); `check [paths…] [--static behavior|shape]` — ця секція; `explain <code>` друкує причину, приклад і виправлення коду (регістр не важливий; для K001 — підказка про `did you mean` і `planned`; для K005 — шість значень `reason`, кожне з помилкою й правильною формою, і рядок про `planned` як окрему декларацію; текст самодостатній і не відсилає до `docs/`, якого в npm-пакеті немає), невідомий код — 2. `explain <id>` без мережі друкує, що про вузол кажуть знімок і специфікації: вид, ID і сигнатура; `файл:рядок` і видимість; `calls` / `called by` / `depends on` / `used by`; потоки з цим ID; правила, що називають його чи охопну область; нерозв'язане всередині за видами; fingerprint і closure. Невідомий ID — 2 з `did you mean`. `wire` — [semantics.md](semantics.md) §7 «Wiring»; `trace-plan` — розділ «План trace»; `explain <id> --llm [--full]` — пояснення простою мовою від моделі з `agent` у `keylang.json` (`"anthropic:<model>"` через офіційний SDK, для Claude Opus 5 / Fable з серверним `fallbacks: "default"`; `"openrouter:<model>"` через chat completions із SSE; `"cli:<name>[:<model>]"` — встановлений агент-CLI без API-ключа, див. [Модель: API або агент-CLI](#model)). Ключ береться з `ANTHROPIC_API_KEY` (або `ANTHROPIC_AUTH_TOKEN` чи профілю `ant auth login`) чи `OPENROUTER_API_KEY`, інакше з `~/.config/keylang/<provider>.key`; порожня змінна ключем не вважається. Файл ключа, який можуть читати інші, відхиляється. Запит, що не завершився за `KEYLANG_LLM_TIMEOUT_MS` (мілісекунди, за замовчуванням 600000; для OpenRouter — разом із потоком SSE, для Anthropic — разом із повторами SDK), переривається; відповідь без тексту, помилка OpenRouter у JSON замість потоку чи некоректний JSON у SSE — теж помилка з назвою провайдера. Усе це — код 2, і нічого не зберігається. `ANTHROPIC_BASE_URL` / `OPENROUTER_BASE_URL` переносять запити, наприклад на локальний мок у тестах. `explain.lang` (за замовчуванням `en`) і `explain.detail` (`short` — 2–3 речення, за замовчуванням; `full`) задають мову й деталізацію. У модель іде зведення вузла, його код (довге тіло обрізається, і промпт про це каже), сигнатури тих, кого він викликає і хто його викликає, та шар. Репозиторій повністю не передається. Відповідь зберігається в `<dir>/explain/<id>.md` з рядком `<!-- keylang:explain agent=… date=… closure=… lang=… detail=… -->`. Перед збереженням з неї знято обгортки: перший абзац-ремарку, коли після нього є ще текст (закінчується на `:` або має менше чотирьох слів: «Sure, here is the brief:»), і огорожу (```` ``` ````, ```` ```markdown ````, ```` ```text ````), що охоплює всю відповідь; заголовки, списки й код лишаються як написано. Сховище закомічене поруч із картою (ADR 0004). До 0.1.1 воно було в `.keylang/explain/`, і ця тека більше не читається: `explain` пише в stderr одну примітку з командою для перенесення, `doctor` — рядок `explanations:`. `--brief` просить до двох коротких речень одним абзацом, близько 200 символів (менше за 280, на яких текст обрізається), без ремарок про те, чого у вводі немає, і пише `<dir>/explain/brief/<id>.md` з `detail=brief`. Промпт `--brief` не входить у baseline, тож його зміна не робить збережені brief-и `stale`. Код перевантаженої функції в промпті — усі сигнатури перевантажень разом із тілом реалізації: діапазон рядків вузла тягнеться до реалізації, коли перевантаження стоять поспіль. Довша відповідь обрізається правилом коментарів документації (snapshot.md §11) без позначки. `--brief` разом із `--full` — код 2. Якщо вузол — модуль, клас чи шар, у промпт ідуть його прямі члени з їхніми поясненнями (коментар документації або brief), до 80 рядків. `closure` — baseline, тобто `closure.fingerprint` вузла на момент пояснення; модуль, клас чи шар власного closure не мають, і їхній baseline — хеш їхніх залежностей і closure кожного вузла під ними, тож зміна члена робить пояснення модуля `stale`. Свіже пояснення тієї ж мови й деталізації читається без запиту. Друкується текст і рядок `agent · дата · fresh|stale`. ID у зворотних лапках, що починаються з імені шару, яких немає ні у знімку, ні серед `planned`, перелічуються рядком `unknown ids: …`. Без ключа — повідомлення в stderr, офлайн-зведення в stdout, код 0. `explain <id>` без `--llm` додає до зведення збережене пояснення зі статусом. `explain --stale` перелічує пояснення й brief-и (`<id> (brief)`), чий baseline змінився (`stale`), і ті, чий ID зник (`gone`). `explain --missing --llm` пише brief для кожного вузла карти з поясненнями без коментаря документації й без свіжого brief. Зовнішні пакети пропускаються. `explain --stale --llm` перегенеровує лише застарілі brief-и вузлів без коментаря документації. Порядок — знизу вгору: fn і типи, потім класи й модулі від найглибших, потім шари. Тож промпт батька вже містить brief-и своїх членів, і шар пояснюється через свої модулі. `--jobs N` (типово 4, з агент-CLI — 2) задає, скільки запитів іде одночасно в межах одного рівня. `--limit N` бере лише перші N вузлів цього порядку. Прогрес іде в stderr рядками `[k/n] <id>`. Кожен brief записується атомарно, щойно прийшла відповідь, тож перерваний запуск нічого не губить, а повторний продовжує з місця зупинки. Перед кожним записом batch перевіряє, що файл brief-а досі має байти, прочитані під час планування (інакше вузол не вдався, а новіший файл лишився), і що `keylang.json`, джерела знімка й специфікації не змінились: якщо змінились, жоден наступний brief не запитується й не записується, причини йдуть у stderr, код 1, а вже записані brief-и лишаються. Порожня відповідь моделі — помилка вузла, порожній brief не записується. У stdout — `explained k of n node(s)` і рядок `failed: <id>: <причина>` для кожного вузла, який не вдалося пояснити. Код 0, якщо все зроблено; 1, якщо частина вузлів не вдалася (зокрема запис окремого brief-а); 2 — помилка виклику, некоректне `--limit`/`--jobs` чи відсутній ключ. `--dry-run` друкує кількість вузлів за рівнями й оцінку токенів (~4 символи на токен промпту, ~80 токенів на відповідь) і нічого не запитує й не пише. Без `--llm` команда перелічує вузли рядками `<id> (<рівень>)`. Пояснення ніколи не змінює вердикт `check`. `draft flow <trigger> [--mode algo] [--name n] [--into <spec.md>] [--print]` пише пропозицію `.keylang/proposals/<spec>`, за замовчуванням для `<dir>/flows/<name>.md`, де `name` — останній сегмент тригера. Сама специфікація змінюється лише через MERGE (`m` у TUI). Режим `algo` детермінований: розв'язаний виклик fn репозиторію (не `external`) стає вкладеним `step` у порядку виклику в коді, глибина — до 4 рівнів. Уже внесена fn не розгортається вдруге, тож цикл завершується. Нерозв'язані виклики fn записуються коментарем `<!-- keylang:algo unresolved: … -->` у її рядку, кроком вони не стають. Якщо цільовий файл уже має `# flow <name>` (коментар після імені в заголовку не заважає), пропозиція замінює цю секцію, інакше дописує нову; секції знаходить парсер, а файл із CRLF у всіх рядках отримує пропозицію з CRLF. Ціль поза каталогом специфікацій, у карті чи за посиланням назовні — код 2 з причиною; `--print` пише текст у stdout і нічого не створює — ні пропозиції, ні `.keylang/stats.json`. `--mode llm` і `--mode hybrid` (за замовчуванням) звертаються до моделі з `agent`. Модель отримує граматику потоку, компактну карту (fn потоку та їхніх модулів із сигнатурами, до 300 рядків, решта позначена) і до трьох ручних потоків репозиторію, спершу тих, що мають найбільше спільних ID. ID, якого немає ні у знімку, ні серед `planned` (у чернетці чи специфікаціях), повертає чернетку моделі рівно один раз, з найближчим реальним ID і вимогою виправити посилання або оголосити `planned`. Невідоме й після цього кола друкується в stderr і після MERGE стане K001. Відповідь звіряється на розібраному потоці, а не за рядками. ID у зворотних лапках в елементі — це ID. Елемент, що не розбирається там, де стоїть (крок під `invariant`, невідоме ключове слово), відкидається разом із вкладеним, і stderr його називає: `dropped from the model's draft: <рядок>: <причина>`. Без `trigger` із запитаним ID він стає першим елементом з `<!-- keylang:algo status=algo-only -->`. Кожен рядок `trigger`/`step` отримує `<!-- keylang:llm model=<agent> status=agree|llm-only|conflict -->`: `agree` — крок є в algo-проєкції і його батько в чернетці досягає його resolved-викликами (вкладеність теж перевіряється), `llm-only` — інакше, `conflict` — ID називає не fn (модуль чи тип). `hybrid` дописує кроки algo-проєкції, яких модель не назвала, під найближчого з їхніх викликачів в algo-проєкції, що є в чернетці (інакше під `trigger`), з `<!-- keylang:algo status=algo-only -->`. Прийнятий рядок моделі не є доказом: `check` перевіряє його як будь-який крок, і `llm-only` без ребра — `unverified` або `fail absence`, але не `ok`. `hybrid` без налаштованої моделі друкує примітку й працює як `algo`; `llm` без моделі — код 2. `.keylang/stats.json` (`{schema: 1, drafts: {<status>: {proposed, accepted, rejected}}, suggestions}`) рахує запропоновані рядки за статусом, щойно пропозицію записано (запис, що не вдався, лише попереджає), а MERGE у TUI — прийняті й відхилені, за коментарями походження в кожному вирішеному шматку. `draft rules [--print] [--into <spec.md>]` пропонує правила, які код уже виконує, для `<dir>/rules.md`. Якщо шари утворюють ациклічний граф, це `layers` у порядку, де кожна спостережена залежність іде вниз; інакше — `deny` для кожної пари, використаної лише в одному напрямку. `no-cycles` додається, якщо циклів модулів немає. У наявному файлі правила додаються в кінець його останньої секції `# rules`, а без неї — новою секцією `# rules` у кінці, тож хвостовий `# flow` їх не поглинає. Правило, яке файл уже має (без урахування коментарів), не повторюється. `draft map` друкує розкладку шарів, яку вгадав би keylang, у форматі `keylang.json` і нічого не пише. `--mode llm|hybrid` (за замовчуванням `hybrid`; без моделі — `algo` з приміткою) у `draft rules` передає моделі шари й кількість ребер між ними. Кожне запропоноване правило перевіряється одразу й окремо: знімок і специфікації без інших правил, з цим правилом і без нього. Нова помилка (K101, K102…) дає `conflict`, а в stderr іде рядок із доказом, наприклад `conflict: - deny app infra → src/app/checkout.ts:2: K102 …`. Нерозібране правило теж `conflict`. `unverified` дає `llm-only`, решта — `agree`. `hybrid` дописує правила `algo`, яких модель не дала. `draft map --mode llm` друкує розкладку моделі після тієї ж валідації, що й `keylang.json` (невалідна — код 2). Шари ніколи не призначаються без людини: `keylang.json` не змінюється. `code-to-spec <path[:line]> [--print] [--into <spec.md>]` робить потоки з коду. З рядком — найглибша fn, що його містить, стає тригером чернетки `algo`, як у `draft flow`. Без рядка — так само кожна експортована fn файла в порядку оголошення. Пропозиція йде для `<dir>/flows/<name>.md`, де `name` — fn або модуль файла. Однойменні fn (методи `A.save` і `B.save`) отримують імена потоків із кількох останніх сегментів ID: `# flow A-save`, `# flow B-save`. Нерозв'язані виклики позначаються коментарем. Рядок поза fn — код 2. `code-to-spec --since <git-ref>` замість шляху бере зміни робочого дерева відносно ref (`git diff --relative --no-renames --unified=0` зі шляхами без C-лапок, тож перенесений файл — це нові рядки: його fn мають нові ID) і файли, яких git ще не відстежує. Кожна fn, чий діапазон рядків перетинає зміну, стає чернеткою для `<dir>/flows/changes.md`. Fn, яку вже називає написаний вручну потік, не перечернетується: її перелічує stderr (`changed and already in flows (review those): …`). Fn, що є кроком чернетки іншої зміненої fn, лишається всередині неї. Без змінених fn — повідомлення й код 0 без запису. Без `git`, з невідомим ref чи разом зі шляхом — код 2. `spec-to-code <id> [--into <file>] [--apply]` будує заготовку для `planned fn`: функцію з оголошеною сигнатурою (`(a: A) → R`; для TS `async`, коли `R` — `Promise<…>`), що кидає `not implemented: <id>` (у Python — `NotImplementedError`, у Rust — `todo!`; оголошені параметри й результат переносяться як записано — у Python анотаціями, а новий файл отримує `from __future__ import annotations` — тож заготовка сама не дає K201; до файла з CRLF у всіх рядках дописується з CRLF). Файл — це файл модуля ID, якщо модуль є у знімку, інакше `<корінь глобу шару>/<сегменти>.<розширення першої мови>`. Шар із кількома коренями вимагає `--into`, а файл, що не дає цей модуль, — код 2. Цей файл і кожен шлях `test` потоків перевіряються правилами цілі пропозиції ([пропозиції](#proposals)) ще до читання: шлях не простий відносний, у прихованій теці, через символічне посилання назовні (зокрема на ще не створену ціль) чи файл із маркером `keylang wire` — для коду код 2, для тесту примітка в stderr, і файл не читається. ID, що вже є в коді, — код 2 з місцем реалізації: повторний запуск не дописує другу заготовку. Кандидат перевіряється як overlay-знімок до запису: друкується diff і все, що кандидат додає до `check` порівняно з кодом без нього — вердикти й діагностики, де б вони не були (K102 чи K103 у новому файлі теж). Без прапорця кандидати стають пропозиціями `.keylang/proposals/<файл>` (код і тести), які зливаються по шматках `m` у TUI; `--print` лише друкує, `--apply` пише файли напряму: атомарно, зі збереженням прав і CRLF, і лише якщо кожен файл досі такий, яким кандидат його прочитав — правка, зроблена тим часом (наприклад, під час запиту до моделі), дає код 1 без жодного запису; разом з `--print` — код 2. Для кожного `test <файл> "<назва>"` потоків, що називають ID, якщо файла ще немає і код та тест — TS/JS, друкується й новий файл `node:test`: імпорт fn відносним шляхом і тест з оголошеною назвою, що падає (`assert.fail`), доки його не напишуть. Коли код і тест — PHP, це клас PHPUnit з іменем файла (`final class RefundTest extends TestCase`), у просторі імен, який мають файли поруч або який кореневий `composer.json` відображає на теку (`autoload-dev`, PSR-4). Назва тесту — ім'я методу; метод без префікса `test` отримує `#[Test]`, а назва, що не є іменем методу (`"refunds the order"`), лишається людині. Тож після запуску `tests` — `fail`, а не `ok`. Тест в уже наявному файлі або іншою мовою лишається людині: stderr каже, куди його дописати. Заготовка PHP — публічний метод у тілі класу чи функція наприкінці файла з оголошеною сигнатурою й `throw new \LogicException(…)`. Новий файл PHP починається з `<?php`, `declare(strict_types=1);`, коли його мають файли поруч, і їхнього простору імен (або простору з PSR-4 `composer.json`), щоб клас автозавантажувався, а його імпорти резолвились. Код і тести keylang сам не записує без MERGE або `--apply`. ID, якого немає ні серед `planned`, ні в коді, коду не отримує: код 2 з `did you mean` і пропозицією оголосити намір. Якщо в потоці є крок над цим ID, а `deny` забороняє ребро від нього, це теж код 2. Після `--apply` і `map` ID перевіряється як код: `ID ok`, K202 пропонує прибрати `planned`, а `tests` і `trace` лишаються `unverified`, доки тести не виконано. Файл overlay, якого ще немає на диску, входить у знімок як джерело. `code-to-spec --mode llm|hybrid` (за замовчуванням `hybrid`, як у `draft`) проводить кожну чернетку через модель за правилами `draft flow`: одне коло для невідомих ID, звіряння й коментарі походження. `spec-to-code --mode llm` просить у моделі всю функцію з оголошеними ім'ям і сигнатурою, а потім — файл e2e-тесту з назвами тестів потоку. Кандидат аналізується так само, як заготовка. Відповідь без функції з цим ім'ям або тест без оголошеної назви — код 2, і нічого не записується. `lsp` — розділ «LSP»; `parse [--json]`, `fmt [--check]` — [grammar.md](grammar.md) §8–§9.

<a id="formats"></a>
## Формати виводу check

`--format` не змінює вердикт і код виходу:

- `human` — рядки `file:line:col: CODE|verdict message` у stdout;
- `json` — лише JSON у stdout: `{snapshotId, results[], coverage[]}`; кожен результат має `criterion`, `area`, `verdict` (`fail` / `unverified` / `ok`; для діагностики рівня warning, як K006, K103 чи K106, — `warning`: вона не валить перевірку), `evidence`, `snapshotId`, `specHash`, `provenance`, `file`, `line`, `col`, `code`; результат K005 має ще `reason` (`arguments`, `id`, `link`, `quote`, `layer`, `scope`), інші коди — ні; `unverified` правила, яке лишила неперевіреним дірка покриття, має ще `hole` — `file:line:col` цього запису `coverage` (одна дірка — той самий `hole` у кожному правилі, в області якого вона є, а підсумок у stderr тоді рахує дірки: `2 unverified (from 1 hole)`, [semantics.md](semantics.md) §7), інші результати — ні; діагностика правила чи потоку бере критерій, область, `specHash` і `provenance` свого вердикту, а діагностика без вердикту (K003, K201…) — `specHash` як SHA-256 свого коду й повідомлення; `provenance` — `syntactic`, крім доказів `test-report` і `trace`;
- `sarif` — SARIF 2.1.0: `fail` → `error`, `warning` → `warning`, `unverified` → `note` з `ruleId: unverified` (зокрема докази потоків); `ruleId` іншого результату — K-код або вид доказу потоку (`static`, `tests`, `trace`); `properties` результату несуть verdict, criterion, area, `snapshotId`, `specHash` і `provenance`, а для K005 ще `reason`; run має `columnKind: "unicodeCodePoints"`, бо типова одиниця SARIF — UTF-16;
- `github` — workflow-команди `::error` / `::warning` / `::notice` з `title` — тим самим `ruleId`, з екранованими `%`, переносами, `:` і `,`; `col` — та сама колонка в символах Unicode (GitHub одиниці не задає).

**Вердикти одного файла.** `check` без шляхів перевіряє всю теку `keylang/`, і підсумок у stderr (`N fail, M unverified, K ok`) один на весь запуск: у ньому змішано вердикти згенерованого `rules.baseline.md` і ручних специфікацій. `check <файл>…` друкує вердикти й підсумок лише названих файлів, тож `check keylang/flows/buy.md` показує, чи перевірено саме цей потік. У `--format json` поле `file` кожного результату дає ту саму розбивку.

У всіх форматах `line` і `col` починаються з 1, а `col` рахує символи Unicode (code points), для специфікацій і для коду.

`--explain-edge <a> <b>` друкує ребра знімка між `a` і `b` (або їхніми нащадками) — спершу `a → b`, потім `b → a`: вид, стан, походження, діапазон, фрагмент коду й кандидатів `ambiguous`; сортування — вид, файл, рядок, колонка. Без ребра друкує `no edge, coverage complete` або перелік нерозв'язаних конструкцій `a` із причинами. Запис `assumed-import` (імпорт файла з `assume`) нерозв'язаною конструкцією не є: `--explain-edge` його не перелічує, а `keylang explain` не показує його в `not resolved`. Невідомий ID (зокрема невідомий хвіст під відомим модулем) — код 2. Нічого не пише.

<a id="trace"></a>
## Trace: адаптери і план

**Адаптер TS/JS.** `node --import keylang/trace <script>` (у репозиторії — `./src/adapters/trace.ts`) з `KEYLANG_TRACE` (файл), `KEYLANG_TRACE_FLOW` (потік), `KEYLANG_TRACE_TEST` (ID тесту), необов'язково `KEYLANG_TRACE_RUN` і `KEYLANG_TRACE_ROOT`. Без `KEYLANG_TRACE_RUN` ID запуску — час і pid; адаптер (так само Python і PHP) записує його в `KEYLANG_TRACE_RUN`, тож воркери й дочірні процеси під адаптером успадковують його, і процеси одного тесту — один запуск. Без `KEYLANG_TRACE` адаптер нічого не робить, тож `--import` можна лишити в конфігурації тестів; з `KEYLANG_TRACE`, але без `KEYLANG_TRACE_FLOW` чи `KEYLANG_TRACE_TEST` процес падає з помилкою, що називає змінну. Hooks модулів будують знімок в окремому потоці, знаходять `trigger` і `step` потоку й обгортають тіла цих функцій (генератори не інструментуються); вкладення — через `AsyncLocalStorage`, асинхронне продовження отримує `link` на батька. Файл CommonJS (`.cjs`, `.js` пакета з `"type": "commonjs"`) hooks віддають Node обгорнутим, тож і його `require` проходять через hooks. Воркер пише власні корені зі своїм `clockId`: вкладення такого span невідоме, і крок, спостережений лише там, дає `trace unverified`, не `missing step`. Файл, що не збігається з копією знімка, не інструментується. `instrumented` процесу — усі обгорнуті функції плану, завантажив процес їхній файл чи ні; без файла, що завантажився з іншим вмістом, і без файла, копію якого в кеші CommonJS прочитав завантажувач CommonJS повз hooks (`require` з модуля, якого hooks не бачили, чи `require` ES-модуля раніше за його `import`). Тому воркер, що завантажив лише свій файл, не робить кроки головного процесу неінструментованими ([semantics.md](semantics.md) §7). E2E-тест позначається `@flow <name>` у назві й запускає код з адаптером; у keylang це тест `@flow check` у `tests/cli-repository.test.ts`, що пише `.keylang/trace/check.jsonl`. Assertions у trace і граматика паралельних груп — ще не частина схеми 1.

**План trace.** `keylang trace-plan <flow>` будує свіжий знімок і друкує JSON: `schemaVersion: 1`, `snapshotId`, `flow`, `symbols` — fn із `trigger` і `step` потоку з `id`, `name`, `file`, `line`, `col` і `sha256` файла, який бачив знімок. Сортування — за ID. Потоку немає ні в одній специфікації — код 2. Адаптери мов без hooks Node читають цей план замість специфікацій.

**Адаптер Python.** `python3 <keylang>/adapters/python/keylang_trace.py <script> [args…]` зі змінними `KEYLANG_TRACE`, `KEYLANG_TRACE_PLAN` (файл від `trace-plan`) і `KEYLANG_TRACE_TEST`, необов'язково `KEYLANG_TRACE_RUN` і `KEYLANG_TRACE_ROOT`. Без `KEYLANG_TRACE` обгортка нічого не записує: скрипт виконується так само, як `python3 <script>`, і процес виходить з його кодом, тож обгортку можна лишити в команді тестів; з `KEYLANG_TRACE`, але без `KEYLANG_TRACE_PLAN` чи `KEYLANG_TRACE_TEST` вона виходить з кодом 2 і називає відсутню змінну. Потрібна лише стандартна бібліотека. На Python 3.12+ адаптер працює через `sys.monitoring` (`PY_START` / `PY_RETURN` / `PY_UNWIND`, помилка дає `outcome: "error"`), на старших версіях — через `sys.setprofile`, де будь-який span завершується `ok`. Записуються лише функції плану з файлів, чий `sha256` збігається: змінений після плану файл не інструментується і не потрапляє в `instrumented`. Решта функцій плану — в `instrumented`, імпортував процес їхній модуль чи ні. Код функції зіставляється точно: реальний шлях файла, ім'я і перший рядок коду, який адаптер бере з `ast` файла для оголошення з рядка плану (перший декоратор, інакше `def`). Однойменний метод іншого класу чи функція в іншому місці файла кроком плану не стає. Генератори й корутини (`async def`, функція з `yield` у власному тілі) не записуються і з `instrumented` виключаються одразу, навіть якщо їх не викликали чи не ітерували: їхні кадри призупиняються, тож стек викликів не дає вкладення. Вкладення будується за стеком викликів окремого потоку. У Python один годинник на процес, тож потік не відрізняється годинником: span іншого потоку стає коренем, його вкладення невідоме, і крок, спостережений лише там, дає `trace unverified`, не `missing step`. Процес із неперехопленим винятком або з ненульовим `sys.exit` дає `complete: false`; `sys.exit()` і `sys.exit(0)` — ні.

**Адаптер Rust.** Runtime-хуків у Rust немає, тож функції потоку позначаються явно: `adapters/rust/keylang_trace.rs` (один файл без залежностей) підключається модулем (`#[path = "…/keylang_trace.rs"] mod keylang_trace;`). У синхронній функції пишеться `let _span = keylang_trace::span("<id>");`, в асинхронній тіло обгортається: `keylang_trace::instrument("<id>", async move { … }).await`; наприкінці `main` — `keylang_trace::finish()`, що дописує JSONL і запис `run`. Змінні ті самі, що в Python-адаптері. Без `KEYLANG_TRACE` нічого не записується. Записуються лише функції плану. `instrumented` — функції плану, в тілі яких (у коді, не в коментарі й не в рядку) є `span("<id>")` чи `instrument("<id>", …)`. Тому крок без span має `trace unverified` «not instrumented», а span, до якого виконання не дійшло, — `trace fail missing step`. Span, що завершується під час паніки, дає `outcome: "error"`, а `instrument`-future, скасована до завершення, — теж `error`. Вкладення будується за стеком потоку. `instrument`-future стоїть на ньому лише під час свого `poll`; батько її span — span, поточний там, де future створено, з `links` на нього, якщо він уже завершився. Guard `span()` в асинхронному коді — в `async fn`, в `async`-блоці чи `async`-замиканні тіла або поруч із `.await` поза ними (асинхронний код, який зробив макрос) — не записується й не інструментується: поки future призупинена, guard лишався б на стеку потоку і ставав би батьком інших future, які той самий потік опитує. Guard синхронної функції, яка лише створює асинхронний код (`rt.spawn(async move { … })`), записується: `async` поза сигнатурою його не стосується. Span, що завершується, коли почате після нього span ще відкрите (guard, утриманий через призупинення), робить запуск `complete: false`. Span в іншому потоці стає коренем. У Rust один годинник на процес, тож інший потік — не інший годинник: вкладення такого кореня невідоме, і крок, спостережений лише там, дає `trace unverified`, не `missing step`. Зміну джерела після плану показує `stale trace`, бо свіжий знімок має інший `snapshotId`. Чи зібрано бінарник саме з цих джерел, адаптер не перевіряє.

**Адаптер PHP.** PHP не викликає хуків на виклик функції без розширення, тож адаптер інструментує джерело. `adapters/php/keylang_trace.php` — один файл без залежностей; потрібні PHP 8.1+ з розширенням tokenizer і вимкнений для CLI OPcache (як за замовчуванням). Скрипт: `php <keylang>/adapters/php/keylang_trace.php <script> [args…]` з тими самими змінними, що в Python-адаптері (`KEYLANG_TRACE`, `KEYLANG_TRACE_PLAN`, `KEYLANG_TRACE_TEST`, необов'язково `KEYLANG_TRACE_RUN` і `KEYLANG_TRACE_ROOT`). Під тестовим раннером файл підключається раніше за будь-який інший: `php -d auto_prepend_file=<keylang>/adapters/php/keylang_trace.php vendor/bin/phpunit`. Підключений так, без `KEYLANG_TRACE` адаптер нічого не робить, тож його можна лишити в конфігурації. Запуск як скрипт без `KEYLANG_TRACE`, `KEYLANG_TRACE_PLAN` чи `KEYLANG_TRACE_TEST` виходить з кодом 2, на відміну від Python-обгортки. Поки адаптер записує, `file://` — його власний stream wrapper. Файл плану, що підключається з тим `sha256`, який бачив знімок, віддається з span навколо тіла кожної функції чи методу плану, на тих самих рядках: номери рядків, `__LINE__` і стеки винятків не зсуваються. Решта файлів і операцій проходить через рідний wrapper PHP без змін. Функція зіставляється за файлом, іменем і першим рядком: перша функція з цим іменем, не вище рядка плану. Однойменний метод іншого класу кроком плану не стає. Генератор (тіло з `yield`) не інструментується і з `instrumented` виключається, бо його кадри призупиняються; `yield` у стрілковій функції (`fn () => …`) тіла теж зараховується тілу, бо межі стрілкової функції без дужок сканер не бачить. Решта функцій плану з файлів, чий `sha256` збігається, — в `instrumented`, підключив процес файл чи ні. Абстрактний метод тіла не має. Виняток, що виходить із функції, дає `outcome: "error"`. Вкладення будується за стеком викликів, годинник один на процес. Фатальна помилка чи неперехоплений виняток, а також span, відкритий наприкінці процесу, дають `complete: false`. Код виходу `exit()` PHP функціям завершення не повідомляє, тож `exit(3)` після кроків запуск неповним не робить.

**PHPUnit.** `adapters/php/keylang_phpunit.php` — розширення PHPUnit 10 і новіших: `<extensions><bootstrap class="Keylang\PHPUnit\Extension"/></extensions>` у `phpunit.xml`, а сам файл підключається в bootstrap PHPUnit (чи в `autoload-dev.files` composer). Воно пише звіт keylang схеми 1 у `KEYLANG_TEST_REPORT`, інакше в `.keylang/reports/phpunit.json`. Рядок — тест: файл відносно кореня, коротке ім'я класу як suite, метод як назва; `pass`, `fail` (провал чи помилка в будь-якому наборі даних) або `skip` (пропущений чи незавершений). У потоці його називає `test tests/BuyTest.php "testBuy"`. Звіт прив'язаний до `KEYLANG_SNAPSHOT_ID`, інакше до знімка плану trace (`KEYLANG_TRACE_PLAN`), інакше до знімка, який `keylang map` востаннє записав у `.keylang/index.json`. Тож `keylang map` треба запустити після останньої зміни коду й перед тестами, інакше звіт застарілий. Коли під тим самим PHPUnit записує адаптер trace, кожен тест, що дійшов хоча б до однієї функції плану, — окремий запуск trace з ID `<файл> > <Клас> > <метод>`. Тест, що не дійшов до жодної, виконував щось інше і запуском потоку не є: він нічого не записує, тож не дає `missing step`. Тест, що дійшов до кроку, але не до тригера (юніт-тест одного кроку), — `unverified` «trigger not observed in …» і не впливає на вердикт, коли тригер спостережено в іншому тесті ([semantics.md](semantics.md) §7).

**JUnit від інших раннерів.** `check.tests` читає й JUnit XML ([semantics.md](semantics.md) §7). `test <file>` зіставляється з атрибутом `file` testcase: абсолютний шлях під коренем репозиторію стає відносним. PHPUnit (`--log-junit`) пише `file` завжди; pytest — лише з `-o junit_family=xunit1` (типовий xunit2 його не пише); jest-junit — з `addFileAttribute: "true"`. Без `file` вердикт каже «no report: `<звіт>` has the test without a `file` attribute». Знімок звіт отримує властивістю `keylang.snapshotId` у `<properties>` suite чи testcase.

<a id="wire"></a>
## wire

`keylang wire [--check] [--out <file>]` пише `keylang.gen.ts` (або `<file>` відносно кореня) з маркером `// keylang:generated`. `<file>` — простий відносний шлях із розширенням `.ts`, `.mts` чи `.cts` усередині репозиторію й після символічних посилань (зокрема ще не створеної цілі посилання); інакше код 2, і нічого не читається й не пишеться. Відсутню теку буде створено. Запис атомарний: тимчасовий файл і rename, права файла зберігаються. Файл без маркера не перезаписується (код 1). Будь-яка помилка на рядках розділу `# wiring` (з переліку вище, а також K003–K005 розбору) дає код 1, і нічого не записується. `--check` порівнює й нічого не пише: застарілий файл — код 1; файл, що відрізняється лише CRLF, застарілим не вважається. Згенерований файл експортує `async function wire(env)`: `env` за замовчуванням береться з `globalThis.process.env`, тож файл не потребує типів Node. Кожна фабрика має мемоізований builder і будується один раз на виклик `wire()`, лише коли її потребує обрана гілка, після своїх залежностей. Залежності очікуються по одній у порядку запису. Значення з методом `dispose()` реєструється, щойно його побудовано. `dispose()` результату викликає їх у зворотному порядку: всі, з `AggregateError` для помилок. Помилка фабрики звільняє вже побудоване у зворотному порядку й прокидається далі; якщо при цьому падає й звільнення — `AggregateError`, першим елементом якого є помилка фабрики. Результат — об'єкт, де ключ `"<id>"` для кожного `wire` веде на його значення, плюс `dispose`. Форма імпорту береться з таблиці експортів знімка: іменований експорт — `import { name }`, аліас `export { make as name }` — за публічним ім'ям, `export default` — default-імпорт. Локальні імена — ID із `_` замість неприпустимих символів; ID, що дають одне ім'я (`a-b.f`, `a_b.f`, `a.b.f`), отримують короткий хеш свого ID, тож ім'я не залежить від інших ID. Імпорти відносні: з розширенням джерела, якщо `tsconfig.json` (з відносними `extends`) має `allowImportingTsExtensions` чи `rewriteRelativeImportExtensions`; для `node16`/`nodenext` — розширення часу виконання (`.ts`/`.tsx` → `.js`, `.mts` → `.mjs`, `.cts` → `.cjs`, JS-джерело зберігає своє); інакше `.ts`/`.tsx`/`.js`/`.jsx` без розширення, решта — з розширенням часу виконання. Типи перевіряє `tsc` проєкту, а залежності — той самий `check`: згенерований файл — звичайний модуль у своєму шарі.

<a id="export-c4"></a>
## export c4

`keylang export c4 [--format plantuml|mermaid] [--level component|container] [--layer <name>] [--out <file>]` друкує діаграму C4 знімка й збережених brief-ів — без моделі, тож ті самі входи дають ті самі байти ([ADR 0014](adr/0014-one-model-many-views.md): ще одне представлення тієї самої моделі). Типовий рівень `component`: кожен шар — `Container_Boundary` з brief-ом шару (у PlantUML — `$descr`, що є в C4-PlantUML з v2.10; у Mermaid межа опису не має, тож brief — коментар `%%` над нею), кожен модуль верхнього рівня шару — `Component` з файлом і brief-ом, пакети `external.*`, які використовує намальований код, — `System_Ext`. Зв'язки `Rel` зводять ребра між модулями різних шарів: підпис — види ребер із кількістю (`call ×2, import ×1`), а ребра всередині шару не малюються. `--layer <x>` малює лише модулі шару `x` разом зі зв'язками, що їх торкаються, зокрема всередині шару; модулі інших шарів на другому кінці — `Component_Ext`. Невідомий шар — код 2 з переліком шарів, `--layer` з `--level container` — теж 2. Рівень `container` — `System_Boundary` репозиторію з одним `Container`: назва з маніфесту, мови як технологія, brief репозиторію, плюс `System_Ext` на кожен пакет, з яким є ребра. Шар не стає контейнером: у C4 контейнер — застосунок чи сховище, що запускається окремо, а шар однієї програми таким не є. Код поза шарами (`outside`) не малюється; ребра, які keylang не розв'язав, теж, а їхня кількість стоїть у коментарі. Brief, застарілий щодо коду, у діаграму не потрапляє. PlantUML підключає бібліотеку через `!include <C4/C4_Component>` (`C4_Container` для рівня `container`); Mermaid пише `C4Component`/`C4Container` з коментарем, що C4 у Mermaid експериментальний.

Перший рядок діаграми — маркер `' keylang:generated — keylang export c4` (PlantUML) чи `%% keylang:generated — keylang export c4` (Mermaid). Без `--out` діаграма йде в stdout. `--out <file>` (відносно кореня, всередині репозиторію) пише файл через спільний протокол запису і друкує в stderr `<file>: written`; stdout лишається порожнім. Політику запису шлях проходить до аналізу й до будь-якого читання цілі, як у `wire`: шлях поза репозиторієм (абсолютний чи з `..`) або через посилання назовні — код 2 `export c4: --out <file>: <причина>; nothing written`, і файл там не відкривається. Перезаписується лише новий файл або файл, що починається маркером цієї команди (у будь-якому з двох форматів). Будь-який інший файл, зокрема згенерований іншою командою, — код 2, файл не змінено. Ці маркери знає й `isGeneratedText`, тож інші записувачі keylang (зокрема експорт звіту з `F6`) такий файл не перезаписують. Коди: 0 — діаграму надруковано чи записано, 2 — неправильний виклик, немає коду для малювання, відмовлено в записі або помилка I/O. У TUI та сама операція — дія палітри «Export C4 diagram» (група Map): форма вибирає формат, рівень і шар стрілками ←→, у рядку `out` набирається файл. Без файла діаграма показується у `F6`, нічого не записано. Примітка форми спершу проходить ту саму політику запису (`c4OutProblem`): шлях поза репозиторієм чи через посилання назовні показує відмову CLI дослівно, і файл там не читається; лише файл усередині репозиторію форма читає, щоб сказати, чи це діаграма цієї команди.

<a id="clone"></a>
## clone, `web <url>` і Docker

`keylang clone <url> [--dir D] [--explain map-only|map-and-ai|all] [--dry-run]` робить карту чужого репозиторію без ручного `git clone`. Джерело — URL `https://`, `http://`, `ssh://`, `git://`, `file://`, scp-форма `git@host:owner/repo.git` або шлях до локальної теки; інші схеми, зокрема `ext::`, відхиляються (git до того ж запускається з `protocol.ext.allow=never` і без запиту пароля, `GIT_TERMINAL_PROMPT=0`, тож приватний URL без облікових даних падає, а не висне). Клон лягає в `$XDG_CACHE_HOME/keylang/repos/<host>/<шлях>` (без змінної — `~/.cache/…`; порт хоста — як `host_port`, суфікс `.git` відкинуто), локальна тека — у `local/<ім'я>-<8 hex sha256 абсолютного шляху>`; `--dir` кладе клон в іншу теку. Сегмент, що не може бути ім'ям теки (не `[A-Za-z0-9._~-]`, `.` чи `..`), — код 2 з порадою `--dir`. Аргументи перевіряються до клонування: неправильний виклик нічого не пише.

Клон неглибокий (`git clone --depth 1`) і має маркер `.keylang/clone.json` з URL. Повторний запуск у тій самій теці робить `git fetch --depth 1 origin HEAD` і `git reset --hard FETCH_HEAD`, тобто бере новий коміт гілки за замовчуванням і скидає зміни відстежених файлів; невідстежені (`keylang.json`, `keylang/`, `.keylang/`) лишаються. Скидає лише теку з маркером (`{url, key}`) того самого репозиторію: той самий ключ — хост і шлях — має й інше написання (`…/repo` і `…/repo.git`, `https://` і `git@host:`), тоді fetch іде з `origin` першого клону. Непорожня тека без маркера чи клон іншого репозиторію — код 2, нічого не змінено. Маркер пишеться за загальними правилами `src/safe-write.ts` (у межах клону й `.keylang/` з урахуванням посилань): якщо клонований репозиторій закомітив `.keylang` як посилання за межі клону, маркер не пишеться — `clone: .keylang/clone.json: leads out of the repository through a link; the clone of <url> was removed`, код 2, свіжий клон прибрано, і поза клоном нічого не створено й не перезаписано; маркер за таким посиланням і не читається, тож така тека для keylang — «не його клон». Через неглибоку історію `feature --since` і `check --changed` у клоні бачать лише останній коміт.

Далі — ті самі кроки й рядки, що в `init <клон> --agents=none` (харнес у клон не ставиться; наявний `keylang.json` лишається, карта перебудовується). Перший рядок stdout — `<тека>: cloned|updated from <url>`. `--explain`:

| Режим | Що додає | Модель |
|---|---|---|
| map-only (типово) | лише `keylang/map/*.md` і `.keylang/index.json` | ні |
| map-and-ai | вмикає `explain.map` у `keylang.json` клону, `explain --missing --llm` (брифи в `keylang/explain/brief/`), потім `map` — `keylang/map-explained/` | так |
| all | те саме і `explain <шар> --llm --full` для кожного шару з `keylang.json` — `keylang/explain/<шар>.md` | так |

Модель — та, що налаштована для keylang ([модель](#model)); `keylang.json` клону пише keylang, тож на практиці це `KEYLANG_AGENT` або `use` в `~/.config/keylang/agents.json`. Без моделі `map-and-ai` і `all` (не `--dry-run`) після карти дають код 2 з цією порадою, і `explain.map` не вмикається. `--dry-run` з `map-and-ai` чи `all` друкує оцінку `explain --missing --llm --dry-run` (для `all` ще рядок `and <n> full layer explanation(s): <шари>`) і не робить запитів; `keylang.json` клону лишається таким, як його написав `init`. `--dry-run` без режиму з моделлю — код 2. Код 1 — частина пояснень не вдалася (написані лишаються, повтор продовжує), 2 — помилка виклику, git чи запису.

`keylang web <url> [--dir D] [--explain MODE] [--port N] [--host H]` спершу робить те саме, що `clone`, а потім віддає TUI над клоном, як `keylang web` у його корені. Без URL `web` працює як раніше — над поточним репозиторієм.

**Docker.** `Dockerfile` у корені збирає образ з упакованого npm-пакета (`npm pack`, ті самі файли, що ставить `npm install keylang`) на `node:22-slim` з git; `ENTRYPOINT` — `keylang`, робоча тека `/work`, кеш клонів — том `/cache` (`XDG_CACHE_HOME=/cache`), користувач `node`. У контейнері git довіряє будь-якій теці (`safe.directory '*'`), бо змонтований `/work` належить користувачу хоста.

```sh
docker build -t keylang .
docker run --rm -v keylang-cache:/cache keylang clone https://github.com/owner/repo
docker run --rm -p 7070:7070 -v keylang-cache:/cache keylang web https://github.com/owner/repo --host 0.0.0.0
docker run --rm -v "$PWD":/work keylang check
```

`--host 0.0.0.0` потрібен, щоб порт був досяжний з хоста; тоді доступ стереже лише одноразовий токен в URL (перевірки `Host` на loopback немає), тож публікуйте порт лише на `127.0.0.1` (`-p 127.0.0.1:7070:7070`), якщо машина в спільній мережі. У надрукованому URL замініть `0.0.0.0` на `localhost`.

## Агенти, baseline і фічі

`keylang/features/<slug>.md` — звичайна рукописна специфікація. `check` читає її разом з іншими файлами під каталогом специфікацій. Фіча готова, коли виконано п'ять умов: файл щось стверджує — має хоч один `planned`, `trigger`, `step` чи `calls` (інакше прогалина `empty`); у самому файлі немає помилок специфікації K001–K005 (кожна — прогалина `diagnostic` з кодом і позицією; рядок, який парсер відкинув, не перевіряється, тож без цього файл здавався б готовим); кожен `planned` у цьому файлі реалізовано (K202, і не K201); кожен `step` кожного потоку цього файла і кожне ID у `calls` мають static `ok`; немає `fail` правил цієї зміни (у будь-якій специфікації, включно з baseline; ADR 0005 §2 — нових порушень немає). `fail` правила — цієї зміни, якщо `check --changed --since <база>` (база фічі — нижче) лишає його у звіті (зачеплено змінений файл, модуль в області правила чи змінену специфікацію), якщо він стоїть у самому файлі фічі або якщо кінець його ребра — ID, який називає файл фічі, чи лежить під ним, або ID експорту, про який каже K104 (`<модуль>.<ім'я>` з рядка `exports`), коли фіча його називає чи планує; сам модуль правила кінцем не є — інакше кожна фіча, що робить крок у модуль зі старим порушенням, володіла б ним. Решта — успадковані: не прогалини, а підказки `rule` і записи `info.rules` (`{id, file, line, col, verdict, reason}`), готовність вони не блокують; на brownfield-репозиторії старе порушення не тримає жодну фічу. Без git (`info.base` — `unavailable`) нове від успадкованого не відрізнити: кожен `fail` правила — прогалина, а `info.rules` — `null`. Тести й trace у відповідь входять окремим полем `info` і готовність не блокують.

**Стадія.** Відповідь називає, як далеко зайшов файл від ідеї до специфікації, яку може реалізувати агент. `stage` — перша умова, що виконується: `done` (прогалин немає); `idea` (у файлі немає секції `# flow`); `behavior` (є потік без `trigger` або без жодного `step`, `calls`, `when` чи `invariant`); `structure` (прогалини самої специфікації: `diagnostic`, а також `question`, `deny`, підказки `layer` і `signature` з тікетів c4-zoom/04–05); `ready` (лишилась тільки реалізація: `planned`, `static`, `rule`, `spec`). Кожна прогалина має поле `stage` — стадію, на якій її закривають. Підказки (`hints`) — `{kind, id, file, line, col, reason, stage}` з `kind` `trigger` чи `steps` на рядку заголовка потоку або `layer` чи `signature` на рядку `planned` — кажуть, чого ще бракує специфікації; `rule` стадії `ready` стоїть на місці успадкованого `fail` правила з причиною `inherited (no file changed since <база>, no id of this feature): …`, де `<база>` — `HEAD`, ref з `--since` як його задано або `merge-base <коміт> with <гілка>` (скорочений id коміту, як його дає `git rev-parse --short`, і основна гілка: `merge-base 1a2b3c4 with origin/main`). Підказки готовність не блокують: фіча з одного `planned module` без тригера стає `done`, щойно модуль з'являється в коді.

Крім того, план не має слабшати відносно базового коміту. **База фічі** — `--since <ref>` (у MCP — `since`), а без нього — merge-base `HEAD` з основною гілкою: на гілці фічі зміна — це й її власні коміти, тож порушення, яке фіча внесла й уже закомітила, лишається прогалиною `rule`, а не успадкованою підказкою (до 2026-10-06 типовою базою був `HEAD`, [ADR 0016](adr/0016-agent-loop-after-review.md), поправка). Основна гілка — та, на яку вказує `refs/remotes/origin/HEAD`, інакше локальна `main`, `master`, інакше `origin/main`, `origin/master`. Коли основної гілки немає, merge-base не знайдено (ще немає коміту, непов'язані історії) або він дорівнює `HEAD` (робота на самій основній гілці), база — `HEAD`, як раніше. Тож на локальній `main` з незапушеними комітами, коли є `origin/HEAD`, база — merge-base з `origin/main`: незапушені коміти теж зміна. keylang читає файл фічі на базовому коміті через git (`src/git-changes.ts`). `planned`, якого вже немає у файлі і який код не реалізує (K202 не було б), — прогалина `spec`. `trigger` чи `step`, якого вже немає під тим самим потоком і тими самими батьками (змінено ID або прибрано), — теж прогалина `spec`. Так само відкрите питання `- ? …`, якого вже немає: на питання відповідають комітом, а не видаленням. З merge-base файл порівнюється і з базою, і з `HEAD`, а знахідки об'єднуються: файл, якого на базі немає (нова фіча на гілці), однаково не можна послабити до коміту, а одне видалення, яке знаходять обидва порівняння, — одна прогалина бази. Позиція такої прогалини — рядок у версії, з якою порівнювали, а `reason` називає її так само, як підказка `inherited` (`at HEAD`, `at merge-base 1a2b3c4 with origin/main`). `planned`, прибраний після K202, нові кроки й інший порядок сусідніх кроків прогалин не дають. Так `done` не отримати, переписавши план під уже наявний код. Змінений план людина приймає комітом, і тоді він стає новою базою (на гілці — після злиття в основну). `info.base` — `{ref, state, source, main?}`: `ref` — коміт, як його читає git (ref з `--since` як його задано, повний id merge-base або `HEAD`); `source` — як обрано базу: `since`, `merge-base` чи `HEAD`; `main` — основна гілка, з якою шукали merge-base (`origin/main`, `main`…), її немає, коли основної гілки не знайдено. `state`: `compared` — файл є на базовому коміті; `absent` — його там немає (нова фіча або ще немає коміту), і порівнювати з базою нічого (з merge-base файл на `HEAD` усе одно порівнюється); `unavailable` з `reason` — git недоступний або це не репозиторій, тож план не порівнювався, а кожен `fail` правила блокує. З тією самою базою keylang читає й змінені файли (`git diff` і невідстежені, як `check --changed --since <база>`): до першого коміту змінено все, тож кожен `fail` правила — цієї зміни. Явний `--since`, який не читається (невідомий ref, немає git), — код 2.

`keylang feature <slug> [--since <ref>] [--format json]` друкує цей результат: у stdout прогалини (`file:line:col: kind id: reason`), потім підказки з префіксом `hint: ` (успадкований `fail` правила — `hint: <файл>:<рядок>:<колонка>: rule <id>: inherited …`), у stderr — підсумок `done` або `<n> gap(s) · stage <stage>`. Код 0 — готово, 1 — є прогалини, 2 — файла немає, `--since` не читається або виклик неправильний. Файл лише з прозою і файл з помилками специфікації тепер дають 1, а не 0. Прогалина — `{kind, id, file, line, col, reason, stage}`, де `kind` — `empty`, `diagnostic`, `question`, `deny`, `planned`, `static`, `rule` або `spec`, у стабільному порядку. Кожен рядок `- ? <текст>` у файлі фічі — прогалина `question` стадії `structure` ([format.md](format.md) Р16). Прогалина `deny` — прогноз до реалізації: ребро, яке з'явиться, коли один із його кінців ще `planned`, а правило його заборонить. Викликач — батьківський `trigger` чи `step` (для `step` і `calls` верхнього рівня — перший тригер), ціль — `step` чи ціль `calls`; оцінка та сама, що в `check` (`denyingRule`, ручні правила над baseline, ADR 0013). `reason` називає правило з файлом і рядком і каже, що робити: для заборони з baseline людина додає `- allow <шар> <шар>` у `keylang/rules.md` (агент лише пропонує це через `apply_diff`), для ручної заборони план потребує іншого шляху. Коли обидва кінці вже є в коді, прогнозу немає: ребро судить `check` (прогалина `rule`, коли `fail` — цієї зміни). Підказки стадії `structure`: `layer` — ID `planned` починається не з шару `keylang.json` і не з `external`, тож код його ніколи не реалізує; `signature` — `planned fn` без сигнатури. Вони готовність не блокують. Рядок `step` з невідомим ID дає лише прогалину `diagnostic` K001, без другої прогалини `static` на тому самому рядку. JSON — `{done, stage, gaps, hints, info}`, `info` — `{tests, trace, rules, base}`. `--format json` пише лише JSON у stdout. Той самий об'єкт повертає MCP `feature_status` і дія TUI «Feature readiness» (спільна операція `feature` у `src/operations.ts`); рядок стану TUI рахує стадію тим самим `featureReportOf` з тією самою типовою базою (merge-base з основною гілкою, інакше `HEAD`) і тими самими змінами відносно неї. `feature` пише лише локальний кеш фактів (як `check`).

`keylang/rules.baseline.md` генерують `init` і `keylang baseline`. Перший рядок — маркер `keylang:generated`, далі `# rules`. Для кожного шару з `keylang.json` (і для `unassigned`, якщо в ньому є модуль) пишеться `deny <шар> <шари, на які зараз немає ребра>`, серед цілей завжди є `external` і `unassigned`, якщо залежності немає. Шар, що вже імпортує пакети, отримує `deny <шар> external` і точковий `allow <шар> external.<pkg>` на кожен такий пакет. Стандартна бібліотека Python пакетом не є: `allow` для `typing` чи `asyncio` не пишеться, а новий імпорт stdlib не дає K102. `check` читає файл як правила. Одразу після генерації baseline не додає `fail`: нове ребро між шарами або новий пакет — K102 з рядком цього файла; уже дозволений пакет — ні. Baseline — нижчий шар правил ([ADR 0013](adr/0013-baseline-lower-rule-layer.md)): ручне правило в `rules.md` з тими самими областями заміщає рядок baseline, тож людина заздалегідь дозволяє нове ребро рядком `- allow article mail` (через `apply_diff`). Тоді після реалізації `check` і `hook stop` не дають K102, а `baseline --check` дає 1: граф змінився, і `keylang baseline` приймає його. `baseline` ідемпотентний; файл, що відрізняється лише CRLF (checkout на Windows), вважається актуальним і не переписується. `baseline --check` нічого не пише: код 1, якщо файл не збігається з графом, і в повідомленні є `keylang baseline`. Файл `rules.baseline.md` без маркера `keylang:generated` — ручний: `baseline` його не перезаписує, а `baseline` і `--check` дають код 1 з рядком `<шлях>: manual file without keylang:generated marker` (раніше `baseline` його переписував). Запис іде через загальні правила `src/safe-write.ts`: ціль через посилання за межі репозиторію, зміна цілі, `keylang.json` чи джерел між обчисленням і записом — відмова з кодом 1, нічого не записано; помилка I/O — код 2. Без підтримуваних джерел — код 2 і `baseline: no supported source files; run \`keylang init\``, а не порожні правила.

<a id="proposals"></a>
**Пропозиції без TUI.** `keylang proposals` перелічує `.keylang/proposals/` за абеткою: на рядок — ціль і `+N -M` (рядки `+` і `-`, які надрукує `show`), `(new file)` для цілі, якої ще немає, або `cannot be accepted: <причина>`; підсумок — у stderr; нічого не пише, код 0. Ціль — шлях від кореня, як у переліку; шлях сховища `.keylang/proposals/<ціль>` теж приймається. `proposals show <ціль>` друкує рядковий diff пропозиції проти цілі на диску (як `spec-to-code --print`). `proposals accept <ціль>` — для людини там, де TUI немає (Claude Code у web, SSH без TTY, CI): повний текст пропозиції стає ціллю, як MERGE, у якому прийнято всі шматки. Перевірки ті самі, що в MERGE: правила цілі нижче; пропозиція — звичайний файл сховища, не посилання; ціль, яку не можна писати (`chmod a-w`), — відмова. Запис іде за протоколом `src/safe-write.ts`: атомарно, з правами й CRLF старого файла, у межах каталогу специфікацій (для коду — репозиторію) і лише поки ціль та сама, що прочитана. Потім пропозиція видаляється, якщо досі має прийнятий текст; новіша лишається, а stderr про це каже. Пропозиція, що збігається з ціллю, лише видаляється. `proposals reject <ціль>` видаляє пропозицію, ціль не змінюється; відкинути можна й пропозицію, яку правила не пропускають. Для специфікації `accept` і `reject` рахують рядки моделі в `.keylang/stats.json`, як MERGE. Коди: 0 — зроблено; 1 — для цілі немає пропозиції або `accept` (чи `show`) відмовлено, нічого не записано; 2 — неправильний виклик, зламаний `keylang.json` чи помилка I/O. Агент `proposals accept` не запускає ніколи: він пропонує (`apply_diff`, `draft`, `spec-to-code`), людина приймає.

**Правила цілі пропозиції** одні для кожного входу — `--into` у CLI, сканування TUI, MCP `apply_diff`, `keylang proposals`, — тож причина та сама, звідки б шлях не прийшов (`src/proposals.ts`). Спершу протокол запису: шлях простий і відносний (без `..`, `.`, порожніх сегментів, `\`, `C:` чи `/` на початку), інакше `not a plain relative path`. Специфікація — `.md` під каталогом специфікацій, поза теками під ним, яких `check` не читає (приховані, `node_modules`, `target`), і не те, що keylang генерує: `map/` (`a generated map file: …`), `map-explained/` (`the explained map is generated: …`), `explain/` разом з `explain/brief/` (`saved explanations: only \`keylang explain\` writes them`) і файл з маркером `keylang:generated` (причина називає генератор; для baseline — радить пропонувати зміну в `rules.md`). Каталог специфікацій, що сам є посиланням за межі репозиторію, дає `the spec directory leads out of the repository through a link`; ціль через посилання за межі каталогу — `leads out of <dir>/ through a link`. Код — файл мови, яку keylang читає, у межах репозиторію з урахуванням посилань (зокрема на ще не створену ціль), поза прихованими теками, `node_modules` і `target`, без маркера `keylang wire` чи іншого `keylang:generated`.

`init` і `keylang agents [--agents=LIST] [--check]` ставлять файли харнесів. Без `--agents` харнес визначається за каталогами `.claude/`, `.codex/`, `.cursor/` і файлом `opencode.json` або `opencode.jsonc`. `--agents` — це `claude`, `codex`, `opencode`, `cursor` через кому, або `none`. Невідоме ім'я — код 2 і перелік допустимих. Без виявленого харнеса і без `--agents` з'являється лише керований блок `AGENTS.md`, а `init` (не `--check`) пише в stderr один рядок-підказку: MCP, skill, deny і хук Stop ставить `keylang agents --agents=claude,codex,cursor,opencode` з тими харнесами, якими користуються. `--agents=none` не пише файлів харнеса поза каталогом специфікацій (baseline усе одно пишеться: це специфікація, не адаптер) і прибирає записи keylang, які там уже є: керований блок, сервер `keylang` у MCP-конфігах, копії skill, deny-правила й хук Stop у Claude, `[mcp_servers.keylang]` у Codex. Файл без жодного запису keylang (`{}`, `{"mcpServers":{}}`, `config.toml` з самих коментарів, чужі налаштування з іншим форматуванням) лишається байт у байт і не є кроком; файл видаляється лише тоді, коли, крім записів keylang, у ньому нічого не було (тобто keylang його й створив), інакше він переписується без них. Блок, skill і deny нижче називають каталог специфікацій `<dir>` — поле `dir` з `keylang.json`, типово `keylang`. Тому `agents` читає `keylang.json` (лише це поле; файла немає — `keylang`): зіпсований файл — код 2 з його назвою, нічого не записано. Після зміни `dir` `agents --check` називає застарілими блок, копії skill і `.claude/settings.json`, а `agents` переписує їх; змінений `dir` між планом і записом — відмова з кодом 1. Блок стоїть між `<!-- keylang:begin -->` і `<!-- keylang:end -->`, не довший за 4 КіБ, описує цикл фічі, запасний CLI і те, що `.codex/` діє лише в trusted-проєкті. Агент без skill бачить лише цей блок, тож у ньому є граматика: валідний приклад файла фічі до 10 рядків (`# flow`, `- planned fn <id> (…) → T`, `- trigger`, вкладений `- step`, `- ? <питання>`), що крок — виклик від батька, звідки брати ID (`<dir>/map/*.md` або MCP `search`, копіювати, не скорочувати), що перейменований чи переміщений файл змінює ID і `… map` оновлює карту, і що `- ? <питання>` — відкрите питання до людини. Запасний CLI — та сама закріплена команда, що в MCP і хуку: `npx -y keylang@<версія> feature <slug> --format json`, `… check`, `… spec-to-code <id> --print`, `… baseline`, бо в чужому репозиторії глобального `keylang` немає, а `npx keylang` без версії в пісочниці без мережі падає (`EAI_AGAIN`) або висне. Текст поза маркерами не змінюється, CRLF зберігається. Для Claude відсутній `CLAUDE.md` створюється з `@AGENTS.md`; наявний файл без цього рядка отримує його в керованому блоці.

`init` (і з `--agents=none`: це гігієна репозиторію, а не адаптер) стежить, щоб кореневий `.gitignore` містив `.keylang/`: індекс, кеш фактів, пропозиції, звіти тестів і trace — локальний кеш, а не специфікація, і `git add -A` не має їх комітити. Рядок `.keylang`, `.keylang/`, `/.keylang` чи `/.keylang/` (пробіли в кінці git ігнорує) уже рахується; коментар, `!.keylang/`, `sub/.keylang/` чи `.keylang/*` — ні. Без запису `init` дописує в кінець після порожнього рядка коментар `# keylang: local cache …` і `.keylang/`, а файла немає — створює його з цих двох рядків. Решта файла лишається байт у байт; нові рядки мають CRLF, якщо ним закінчується кожен рядок файла. stdout — `.gitignore: .keylang/ added`; коли запис уже є, рядка немає. Запис іде після `keylang.json` і до карти, за загальними правилами `src/safe-write.ts` і з тим самим планом: `.gitignore` через посилання за межі репозиторію (тоді його й не читають), тека чи файл, змінений між читанням і записом, — `.gitignore: .keylang/ not added (<причина>)` у stdout і код 1, інші стадії все одно виконуються; помилка I/O — код 2. `init --check` нічого не пише: без запису — `.gitignore: .keylang/ is not listed; run \`keylang init\`` і код 1, нечитабельний `.gitignore` — код 2. `keylang agents` `.gitignore` не чіпає.

Вибрані харнеси отримують сервер MCP `keylang` з командою `npx -y keylang@<версія> mcp`, де версія — з `package.json` keylang, що виконав команду: `.mcp.json` і `.cursor/mcp.json` у `mcpServers.keylang`, `.codex/config.toml` у `[mcp_servers.keylang]`, `opencode.json` у `mcp.keylang` з `type: "local"`. Ключ `keylang` замінюється цілком; інші сервери й поля лишаються. Виняток — Codex: у `[mcp_servers.keylang]` keylang ставить `command`, `args` і `default_tools_approval_mode = "approve"`, а інші ключі таблиці (наприклад `startup_timeout_sec` чи `tools.<name>.approval_mode`) лишає. У `.codex/config.toml` keylang замінює, прибирає чи дописує лише рядки таблиці `[mcp_servers.keylang]` (із її підтаблицями), тож коментарі й форматування решти файла лишаються; файл при цьому розбирається цілком — невалідний TOML лишається помилкою. Запис keylang, записаний інакше (inline-таблиця, dotted-ключі), або файл, у якому таблицю не можна дописати (`mcp_servers` як inline-таблиця), серіалізується заново цілком, і тоді коментарі губляться. Без цього ключа `codex exec` (approval policy `never`) відхиляє кожен виклик MCP keylang: «MCP tool call requires approval, but approval policy is never». Інструменти keylang лише читають (і оновлюють локальний кеш фактів), а `apply_diff` пише тільки пропозицію в `.keylang/proposals/`, тож їх схвалено наперед. Передати ключ через `codex -c mcp_servers.keylang.…` не можна (Codex відповідає «invalid transport»), тому він лише в проєктному `.codex/config.toml`; `agents --check` вважає файл без нього застарілим. Той самий запуск пише `.agents/skills/keylang-feature/SKILL.md` і байт-у-байт копію `.claude/skills/keylang-feature/SKILL.md` (не symlink) з frontmatter `name` і `description`. Ресурс skill у пакеті називає CLI як `npx -y keylang@<version> …`, а каталог специфікацій — `<dir>/`; у копію підставляються версія з `package.json` і `dir`, тож `agents --check` бачить застарілу версію чи інший `dir` і в керованому блоці, і в skill. Для Claude у `.claude/settings.json` додаються `permissions.deny` на `Edit`/`Write` для `<dir>/rules.md` і `<dir>/rules.baseline.md`, Bash-правила `Bash(* proposals accept *)` і `Bash(* proposals reject *)` (рішення про пропозицію приймає людина; `*` у правилі Claude збігає будь-який текст, тож вони ловлять і `npx -y keylang@<версія> …`, і голий `keylang …`) і хук `hooks.Stop`. Такі самі записи keylang для типового `keylang/` прибираються, коли `dir` інший; інші записи deny, зокрема свої записи людини, лишаються. Для Codex, Cursor і opencode такого deny на рівні проєкту немає: у Codex він лише в beta-профілях `[permissions.*.filesystem]`, які не можна поєднувати з `sandbox_mode`; у Cursor — лише в CLI-конфізі `<project>/.cursor/cli.json`; `permission.edit` в `opencode.json` keylang не чіпає. Захист цих трьох — інструкція в `AGENTS.md` і skill. Codex отримує `.codex/hooks.json`. Cursor імпортує хуки Claude. opencode хука Stop не отримує: API плагінів V1 і V2 несумісні. Наявні дозволи й хуки зберігаються. Зіпсований маркер (begin без end) або невалідний JSON/TOML — код 2 з назвою файла, і нічого не пишеться. `agents --check`, `init --check` і `baseline --check` нічого не пишуть: код 1, якщо керований блок, версія в команді MCP, копія skill або baseline застарілі чи відсутні (для `init --check` — і коли `.gitignore` не містить `.keylang/`); код 0, якщо вони поточні. `agents` — принтер над спільною операцією `agents` (`src/operations.ts`, адаптери — `src/harness.ts`): спершу будується повний план усіх файлів вибору, далі перед записом кожен файл харнеса перечитується — змінений ззовні файл або інший набір виявлених харнесів для auto дають відмову з кодом 1 і нічого не записують (рядки причин у stdout, `keylang: nothing was written…` у stderr); ціль через посилання за межі репозиторію — теж відмова до першого запису (`<шлях>: leads out of the repository through a link`), і для видалення так само: `.cursor`, `.claude`, `.codex` чи `.agents`, що є посиланням за межі репозиторію (зокрема закоміченим у чужому репозиторії, який робить `clone`), keylang не спорожнює. Файли пишуться по одному атомарно (CRLF старого файла зберігається), видалення прибирає сам файл; помилка I/O посеред запису — код 2, у stdout лишаються рядки вже записаних файлів, у stderr — `keylang: <шлях>: <помилка>` і `keylang: <шлях>: not written` для решти. `init` перевіряє той самий план до запису `keylang.json`.

`check --changed [--since <ref>]` (типово робоче дерево відносно `HEAD`, плюс невідстежені файли; власний стан keylang у `.keylang/` — індекс, кеш фактів, пропозиції — змінами не вважається) робить повний аналіз і лишає у звіті лише те, що зачіпає змінені файли: правила, чия область містить змінений модуль (`allow`/`deny` — джерело, `layers` — його шари, `entry` — точки старту, `exports` — модуль правила, хоч K104 і стоїть на рядку `rules.md`, а не в коді; `no-cycles` під модулем M — M, його підмодулі й усе, що з них досяжне `import` / `re-export` без `typeOnly`, як `area` у [semantics.md](semantics.md), тож цикл через M, який замкнула зміна файла поза M, лишається у звіті; глобальний `no-cycles` — кожен модуль); потоки, у яких крок веде в змінений файл; змінені специфікації цілком. Видалений файл теж змінений: ID і static кроків, чий код був у ньому, лишаються у звіті, хоча вузла вже немає. Коди виходу ті самі, що в `check`. До першого коміту `HEAD` немає, тож зміненими вважаються всі файли: відстежені порівнюються з порожнім деревом, невідстежені додаються як завжди. Це стосується й `hook stop`. Коли git має `core.ignorecase=true` (типово на macOS і Windows), шляхи змін беруться в тому регістрі, в якому вони лежать на диску: файл, перейменований лише регістром звичайним `mv` (`view.ts` → `View.ts`), git і далі показує як `view.ts`, а модуль у знімку — `View.ts`; без цього жодна правка такого файла не потрапляла б у `--changed`, `hook stop` і `feature`, доки хтось не зробить `git mv`. Без git `check --changed` дає код 2, а `hook stop` — `systemMessage`, що хід не перевірено (нижче). git запускається зі stdin на нульовому пристрої, не з каналом: у пісочниці Codex (`workspace-write`, seccomp) закрити канал stdin не можна, і раніше `spawnSync` давав `EPERM`, а git, що читав stdin, чекав без кінця. Якщо пісочниця все ж забороняє запуск git (`EPERM` чи `EACCES`), повідомлення каже запустити команду поза пісочницею або повний `keylang check` без git. Звичайний `check` без `--changed` git не читає.

`keylang hook stop` читає JSON події зі stdin, виконує цю змінену перевірку і пише лише локальний кеш фактів `.keylang/cache/facts.json`, тож наступний хід розбирає лише змінені джерела. Нові `fail` дають `{"decision":"block","reason":…}`: у `reason` є файл і рядок кожної діагностики. Та сама подія з `stop_hook_active: true` не блокує. Без нових `fail` — `{}`. Повтор того самого вводу дає те саме рішення. Хук у `.claude/settings.json` і `.codex/hooks.json` викликає `npx -y keylang@<версія> hook stop`. Після старту хук завжди пише в stdout рівно один JSON-об'єкт і завершується кодом 0: код 2 хука Stop харнес читає як блокувальну помилку, на яку агент не може відповісти. Хід, який перевірити не вдалося (stdin — не JSON-об'єкт події, `stop_hook_active` не булеве, git немає чи пісочниця його не запускає, `keylang.json` зіпсований, аналіз упав), дає в stdout `{"systemMessage":"keylang: this turn was not checked: <причина>"}` і той самий рядок у stderr; причина з кількох рядків стає одним. Claude Code і Codex показують `systemMessage` людині як попередження й агента не блокують; stderr хука з кодом 0 Claude Code пише лише в debug-лог, тож без цього поля людина збою не бачила б (до 2026-10-06 так і було: `{}` і рядок лише в stderr, [ADR 0016](adr/0016-agent-loop-after-review.md), поправка). Код 2 лишається лише для неправильного виклику: `keylang hook` без підкоманди чи з невідомою, зайвий аргумент після `stop` чи `install`; stdin тоді не читається.

`keylang hook install` пише git-хук `pre-commit`, що виконує `npx -y keylang@<версія> check --changed`: знахідка, яка зачіпає змінений файл, зупиняє коміт (код 1 чи 2), `git commit --no-verify` хук пропускає. Тека хуків — відповідь `git rev-parse --git-path hooks`, тож `core.hooksPath` і linked worktrees враховано; поза робочим деревом git — код 2. Файл належить keylang цілком і має маркер `keylang:pre-commit`; повторний запуск переписує його на місці (нова версія, права на виконання), той самий текст лишає без запису. Чужий `pre-commit` без маркера не перезаписується: код 2 і рядок, який варто додати в нього самому. `--check` нічого не пише: 0 — хук стоїть і актуальний, 1 — його немає, він застарів, не виконуваний або чужий.

`keylang new flow <name>` створює `<dir>/flows/<name>.md` з одним заголовком `# flow <name>` — той самий мінімальний текст, що дає «New specification» у TUI. `keylang new module <name> --layer <layer>` створює файл фічі `<dir>/features/<name>.md`, де модуль без коду записано наміром: `# flow <name>` і `- planned module <layer>.<name>`. Між ними — абзац прози: файл фічі описує, що збудувати, `keylang feature <name>` каже, чого ще бракує, а рядки `- trigger` і `- step` описують потік. Це лише пояснення, граматика та сама: `check` і `feature` дають на заготовці той самий результат, що й без абзацу. Шар має бути в `layers` з `keylang.json`, інакше код 2 з переліком шарів; без файла `keylang.json` — `no keylang.json here; add "layers" to keylang.json (or run \`keylang init\` once there is code)`, а з файлом без `layers` — `no layers in keylang.json` (теж код 2, нічого не записано). Ім'я — один сегмент ID. Наявний файл не перезаписується (код 2); шлях проходить ті самі перевірки, що нова специфікація в TUI. Обидві заготовки проходять `check` і `fmt --check` без діагностик. Імена потоків — один простір імен (format.md, Р3), тож `new flow x` і `new module x` разом дають K002 на другому `# flow x`; ім'я потоку в заготовці модуля можна перейменувати, `planned module` від нього не залежить.

`keylang completions bash|zsh|fish` друкує скрипт автодоповнення: `eval "$(keylang completions bash)"`, `source <(keylang completions zsh)` (або файл `_keylang` у `$fpath`), `keylang completions fish | source`. Команди й підкоманди скрипт бере з `--help`, прапорці — з таблиці розбору аргументів, тож нова команда доповнюється без окремого списку. Невідома оболонка чи її відсутність — код 2.

<a id="explained-map"></a>
### Карта з поясненнями (`explain.map`)

`"explain": { "map": true }` у `keylang.json` вмикає другу згенеровану карту, `<dir>/map-explained/` (ADR 0004). Типово опцію вимкнено. Значення не типу boolean дає код 2 з назвою поля `explain.map`. Файл `<layer>.md` має те саме дерево, порядок, посилання на код, сигнатури, залежності й `calls`, що й канонічна карта. Під рядком вузла додано рядок опису ([grammar.md](grammar.md) §3) з якорем і поясненням, а посилання на вузли стали лінками (див. «Навігація»). `README.md` — зміст. Він починається розділом про сам репозиторій (рівень «система» C4): заголовок `## <name>` з `name` кореневого маніфесту (без нього — `## Repository`) і перші речення кореневого README з позначкою `_(README.md)_`, інакше `description` маніфесту з позначкою його файла ([snapshot.md](snapshot.md) §11, поле `system`). Без жодного з них слова дає brief моделі з позначкою `_(llm · …)_`, а без нього стоїть `—` і підказка `keylang explain --missing --llm`. Далі — шари з поясненням шару й лічильниками за походженням (код, LLM, LLM stale, без пояснення). Пояснення шару — README його власної теки чи коментар індекс-модуля в ній ([snapshot.md](snapshot.md) §11), інакше brief моделі. Зовнішні пакети в лічильники не входять.

Пояснення вузла береться в такому порядку: спершу `doc` зі знімка, тобто коментар документації ([snapshot.md](snapshot.md) §11), потім збережений brief від моделі, інакше рядка опису немає. Рядок опису починається з `<br>`, щоб переглядач Markdown показав пояснення окремим рядком. Текст із коментаря йде без позначки: це слова автора коду, а посилання на код уже стоїть у вузлі. Текст моделі закінчується позначкою `_(llm · <модель> · <дата>)_`, застарілий — `_(llm · <модель> · <дата> · stale)_`. Текст стиснуто в один рядок. `<` поза кодом у зворотних лапках стає `&lt;`, а `-->` — `--&gt;`. Тож HTML у тексті (`Promise<void>`, випадковий `<details>`, `<!--`) нічого не ховає й коментаря не відкриває, а в коді лишається як написано. Початок, що відкрив би блок Markdown (`-`, `*`, `+`, `#`, `>`, `1.`, огорожу коду), екрановано `\`. Тож файл лишається валідним keylang: `parse` дає нуль діагностик, `fmt --check` проходить.

**Навігація.** Кожен вузол має якір `<a id="<якір>"></a>` на початку свого рядка опису. Вузол без пояснення має рядок опису лише з якорем. Якір — це ID, у якому кожен символ, крім ASCII-літери, цифри, `.`, `_` і `-`, записано як `~<hex>~` (його кодова точка): `app.util.$save` → `app.util.~24~save`, `app.util.café` → `app.util.caf~e9~`. GitHub зберігає такий `id` як написано, а `~` в ID не буває, тож два ID ніколи не мають одного якоря. `calls` і цілі залежностей записано лінками `[id](<шар>.md#<якір>)` ([grammar.md](grammar.md) §4 «Посилання як лінк») на якір вузла у файлі його шару. Зовнішні пакети мають якорі в `external.md`. ID у зворотних лапках у тексті пояснення, якщо він є у знімку, стає лінком на свій якір; невідоме ID (вигадане моделлю) лишається кодом. Файл шару починається рядком `[README](README.md) · modules: …` з лінками на всі модулі шару в порядку карти. `README.md` після таблиці шарів має покажчик: усі модулі й класи репозиторію (без зовнішніх пакетів) за іменем без урахування регістру (порядок кодових одиниць, тож від ICU він не залежить), по абзацу на першу літеру, з ID батька в дужках, щоб шукати через `Ctrl+F`. Посилання на код рахуються від `<dir>/map-explained/`, тож відкривають ті самі рядки, що й з канонічної карти.

Маркер `keylang:generated` той самий, що в карти, і правила ті самі. Ручний файл на місці цілі — конфлікт, і `map` нічого не пише. `map --check` перевіряє обидві карти й нічого не пише. З вимкненою опцією `map` видаляє згенеровані файли `map-explained/` (ручні лишаються), а `map --check` вважає їх застарілими. `keylang map` ніколи не звертається до моделі.

Карта з поясненнями й збережені пояснення (`<dir>/explain/`) — не специфікації. `check` їх не оцінює, тож ID не дублюються (K002), а результат `check` з опцією й без неї однаковий. Названі в `check` явно файл чи тека з них пропускаються з приміткою в stderr. `fmt` і `parse` пропускають збережені пояснення (файли із заголовком `keylang:explain`): це текст моделі, а не keylang, і форматування змінило б збережену відповідь; `parse` називає кожен такий файл приміткою в stderr.

<a id="model"></a>
## Модель: API або агент-CLI

Модель, яку питають `explain --llm`, `explain --missing|--stale --llm`, `draft` і `code-to-spec` (`--mode llm|hybrid`), ghost-текст і `Ctrl+Space` у TUI, — одне значення `agent`:

```text
"anthropic:<model>"            офіційний SDK, ключ ANTHROPIC_API_KEY / ~/.config/keylang/anthropic.key
"openrouter:<model>"           chat completions із SSE, ключ OPENROUTER_API_KEY / …/openrouter.key
"cli:<name>[:<model>]"         встановлений агент-CLI, без API-ключа (підписка CLI)
  <name>  = claude | codex | opencode | cursor     пресети
          | [a-z][a-z0-9-]*                        власний CLI з agents.json
  <model> будь-якого провайдера — без пробілів, `<`, `>` і `--`, не починається з `-`
          (модель стоїть у заголовку `<!-- keylang:explain agent=… -->` і після `--model` агент-CLI)
          напр. anthropic:claude-sonnet-5, openrouter:openai/gpt-4o:free, cli:claude:opus,
          cli:codex:gpt-5.5, cli:opencode:anthropic/claude-sonnet-5, cli:cursor:gpt-5
```

**Пріоритет:** змінна `KEYLANG_AGENT` > `"use"` у `~/.config/keylang/agents.json` > `agent` у `keylang.json`. Порожня змінна не діє. Невалідне значення будь-якого джерела — код 2 з назвою змінної або файла й поля. `doctor` показує значення, його джерело (`(from KEYLANG_AGENT)`, `(from agents.json)`; без позначки — `keylang.json`), для CLI — бінарник і версію, і окремий рядок `agent CLIs: claude 2.1.289 · codex 0.155.1 · opencode 2.0.20 · cursor 2026.09.28-64d2043` (`—` — не знайдено). `doctor` викликає лише `--version`, ніколи вхід чи статус: чи виконано вхід у CLI, видно на першому запиті.

**`~/.config/keylang/agents.json`** — файл користувача, не репозиторію:

```json
{
  "use": "cli:claude",
  "clis": {
    "grok": { "command": ["grok", "--permission-mode", "plan", "--tools", "", "--output-format", "plain", "--model={model}", "--prompt-file", "{prompt_file}"] },
    "cursor": { "bin": "/opt/cursor/cursor-agent" }
  }
}
```

- `command` — непорожній масив рядків; `command[0]` — бінарник (ім'я з PATH або шлях). Плейсхолдери: `{prompt_file}` — тимчасовий файл (0600, поза репозиторієм) із system-текстом і промтом; без нього той самий текст іде в stdin. Елемент із `{model}` відкидається, коли модель не названо. Відповідь — stdout без пробілів по краях, код виходу 0.
- Ім'я пресета приймає лише `bin` — інший шлях до того самого CLI (колізії на PATH).
- Невідоме поле, невідомий плейсхолдер, не масив, невалідний JSON — код 2 з назвою файла й поля (`clis.grok.command[1]: unknown placeholder {prompt}`).

**Пресети.** Кожен запускається як «лише відповідь»: без хуків, MCP та інструкцій проєкту там, де CLI це дозволяє (інакше Stop-hook keylang з `keylang agents` перехопив би вкладений хід), з вимкненими інструментами запису, `cwd = PWD = корінь репозиторію`, у середовищі `NO_COLOR=1` і `KEYLANG_NESTED=1`. Під `KEYLANG_NESTED` агент `cli:*` недоступний (`missing`): агент, якого запустив keylang, не запускає наступного. System-текст доповнюється реченням «Answer with text only. Do not run tools or commands and do not edit files.»

`agent` на PATH може бути Grok CLI: тоді `cli:cursor` — `missing` з текстом «`agent` on PATH … is `grok …`, not the Cursor CLI» і порадою поставити `cursor-agent` чи задати `"cursor": {"bin": …}`.

**Процес, таймаут, скасування.** CLI запускається масивом аргументів (без shell) в окремій групі процесів. Відповідь `{"type":"result"}`, скасування (новий ghost-запит, `Esc`, Cancel операції, закриття TUI) і таймаут `KEYLANG_LLM_TIMEOUT_MS` (для ghost — 60 с) вбивають усю групу: SIGTERM, через 2 с SIGKILL. Вихід keylang вбиває всі живі групи; SIGINT/SIGTERM/SIGHUP без власного обробника — теж. Тимчасові файли видаляються після запиту; в репозиторії нічого не пишеться.

**Модель у підписі.** Агент без моделі (`cli:claude`) підписує відповідь моделлю, яку назвав сам CLI: Claude Code кладе в рядок `{"type":"result"}` поле `modelUsage`, і keylang бере модель із найбільшим `outputTokens`. Тож заголовок пояснення — `agent=cli:claude:<модель>`, а позначка в карті з поясненнями — `_(llm · claude:<модель> · <дата>)_`. Модель із пробілом, `<`, `>` чи `--` відкидається. Агент із моделлю в конфігу (`cli:claude:opus`) підписується як задано. Інші CLI модель не повідомляють, тож їхні відповіді підписано лише іменем агента. Підпис не входить у baseline: brief-и з підписом `cli:claude` лишаються свіжими.

**Помилки.** Бінарника немає на PATH — як відсутній ключ: `explain <id> --llm` друкує офлайн-зведення з кодом 0, `explain --missing|--stale --llm` — код 2, `hybrid` падає до `algo` з приміткою, `--mode llm` — код 2, ghost мовчить. Ненульовий код виходу (`cli:codex: exited with code 3: <кінець stderr>`), результат-помилка, порожня відповідь (`cli:claude answered without text`), таймаут — код 2, нічого не записано.

**Типові значення з CLI.** `ghost.delay` — 1500 мс замість 400 (кожен запит — окремий процес CLI); явне значення в `keylang.json` діє як завжди. `explain --missing|--stale --llm` без `--jobs` — 2 запити одночасно замість 4.

**Безпека.**
- `agent: "cli:…"` у `keylang.json` діє так само, як API-провайдер: відкрити TUI зі склонованим репозиторієм, де `ghost` доступний, означає запустити ваш CLI і витрачати квоту підписки. `doctor` показує джерело; `KEYLANG_AGENT` чи agents.json перекривають значення репозиторію. Власні команди задаються лише в agents.json, ніколи в `keylang.json`.
- Власний CLI keylang не обмежує: що він робить, вирішує його команда.
- Вкладений агент бачить репозиторій (`cwd`) і може прочитати його секрети й інструкції (`AGENTS.md`, правила Cursor), якщо CLI їх не вимикає; `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL` з середовища передаються далі й можуть перемкнути Claude Code з підписки на API-ключ.
- opencode усе одно вантажить плагіни й MCP з глобального конфігу користувача і зберігає сесію на кожен запит.
- Призупинений TUI (`Ctrl+Z`, SIGTSTP) лишає запущені CLI працювати до відповіді чи таймауту.

Відповідь CLI перевіряється так само, як відповідь API: ghost — розбором рядка, draft — звіркою зі знімком, пояснення — перевіркою ID. Пишуть лише keylang і лише пропозиціями, MERGE чи `--apply` (ADR [0011](adr/0012-agent-cli-provider.md)).
