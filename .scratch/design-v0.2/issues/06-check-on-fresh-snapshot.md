# 06: `check` працює на актуальному знімку, правила — на ребрах знімка

**Етап:** M1.1 · **Джерело:** design §4.1, §7 «Глибокий модуль аналізу», review RV02, RV14

**What to build:** `keylang check` перед перевіркою звіряє manifest знімка з поточними джерелами (вміст файлів, додані/видалені файли, конфігурація, версії) і за розбіжності перебудовує аналіз у пам'яті, не записуючи ні карту, ні специфікації, ні `.keylang/index.json`. Правила K101–K105 обчислюються на ребрах знімка (вид, span у коді), а не на графі, відновленому з Markdown; кожна діагностика правила вказує на позицію в коді як доказ. `map --check` окремо перевіряє закомічену карту й нічого не записує. I/O-збій під час отримання знімка — код 2, а не «0 помилок».

Рішення для людини (пропозиція): для директорій без коду й конфігу (examples/shop, слайд) `check` виконує лише резолвінг ID (K001/K002/K003–K006), а правила звітує як `unverified` з причиною «no snapshot». Якщо користувач хоче зберегти K101–K105 на самому Markdown, це фіксується як окремий режим із явним попередженням.

- [x] `docs/semantics.md` §7 більше не стверджує, що правила перевіряються лише по IR карти

## Answer

`check` будує знімок у пам'яті (`src/analyze.ts`), замінює згенеровані `map/*.md` свіжою картою, знаходить корінь угору від cwd і приймає будь-яке написання шляху. Рішення за пропозицією: без коду правила `unverified` «no snapshot», резолвінг ID лишається. `keylang.json` валідується з назвою файла й поля, код 2.
