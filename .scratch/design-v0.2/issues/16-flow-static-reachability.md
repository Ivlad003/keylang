# 16: Статична перевірка flow: кожен `step` досяжний від батьківського контексту

**Етап:** M2 · **Джерело:** design §3.4, §4.2 доказ `static`, review RV15

**What to build:** Потоки компілюються з текстового IR у `SpecIR`: `trigger`, вкладені `step`, `reads`/`emits`, `when`/`then`/`invariant`/`test`. `check` перевіряє для кожного `step` можливу досяжність у статичному графі викликів від батьківського кроку (для верхнього рівня — від `trigger`). Сусідні `step` не потребують шляху між собою. Посилання на alias зводиться до callable-цілі, інакше `unverified`. Результат для кожного кроку: `ok` (шлях знайдено в повністю покритій області), `unverified` (шляху немає, але є unresolved-ребра або opaque-модулі на маршруті), K001 (ціль відсутня в complete-модулі). `reads`/`emits`/`invariant`/`when` без доказу — `unverified`, без вигаданого підтвердження.

**Blocked by:** 07 (вердикти), 08 (повнота модуля)

**Status:** resolved

- [x] фікстура з дизайну §3.4 (`checkout`: `buy` → `create`, `save`; `validate(); save();` у тілі `buy`): усі кроки `ok`, шлях `validate → save` не вимагається
- [x] видалення `save` з коду й перегенерація → K001 на кроці
- [x] крок, до якого веде лише виклик через колбек → `unverified` із причиною та позицією unresolved-ребра
- [x] `check --format json` містить для кожного кроку критерій, область і verdict
- [x] `docs/format.md` описує семантику `step` (вкладеність vs послідовність) і вердикти для flow

## Answer

`src/flows.ts`: крок перевіряється від батька (для верхнього рівня — від `trigger`, поруч чи над ним). Шлях resolved-викликів — `ok`; інакше `unverified` з позицією першого нерозв'язаного/неоднозначного виклику на маршруті або «no call path» (відсутність шляху — не `fail`, design §4.2); K001 без другого `static`-рядка. Не-функція (модуль, alias) — «not a callable». Семантика й таблиця вердиктів — `semantics.md` §7 «Flows: докази кроку». Тести: `tests/flows.test.ts` «static: …».
