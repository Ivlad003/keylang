# 13: Сусідній крок у піддереві попереднього сусіда не підтверджує порядок

**Джерело:** research-pl §5 Р-5; знахідка 3; рішення Q15 (spec). Відхилення коду від впорядкованого включення, знайдене пробами.

**What to build:** За впорядкованим включенням образ наступного сусіда не може лежати в піддереві образу попереднього. `orderOutcome` (src/trace-evidence.ts:426-440) перевіряє лише причинний порядок. На CHECKOUT із завершеним запуском це дає два хибні вердикти:
- синхронний `save` усередині `create` (`c` create 3–6, `d` save під `c` 4–5) дає `` trace unverified … `infrastructure.store.save` starts before `domain.order.create` ends (parallel) `` і код 0 (S1). Це вкладення, а не паралельність. Так само поводяться другий із двох однакових сусідів усередині першого (S4c) і потік без тригера (S9);
- async-продовження `create` дає `trace ok` (S2): `d` save під `c`, 5–6, почався після завершення `create`, `links: ["c"]`. Проте `buy` сам `save` не викликав.

Типовий код: `buy() { create(() => save()) }` чи `create() { setTimeout(save) }`. Поведінка S2 узгоджена з format.md:309, де порядок підтверджують «`links` на попереднього». Тож це зміна семантики, а не лише баг.

Після зміни span, чий ланцюжок `parentSpanId` проходить через образ попереднього сусіда, порядок не підтверджує:
- у завершеному запуску вердикт — `` fail … nested in `<prev>`, not after it ``, де `<prev>` — символ образу попереднього сусіда;
- у неповному запуску `fail` стає `unverified` наявним механізмом (:263-266);
- якщо є інший span кроку в правильному порядку, перемагає він за правилом максимального часткового включення.

Перекриття без відношення предок — нащадок лишається `unverified … (parallel)`. `links` на попереднього підтверджують порядок лише для span поза його піддеревом. Версія формату (35) для цієї зміни не потрібна: виправлення входить до заморожування v1, а несумісність записано в spec.

Тікет прибирає застереження про вкладеного сусіда з підрозділу «Семантика» (10). У dogfood-трасах .keylang/trace/check.jsonl і tui.jsonl вкладених сусідів немає. Тож вердикти `@flow check` і `@flow tui` не змінюються (перевірено на поточних файлах). На модель порядку з цього тікета спирається `never <b> before <a>` (47).

**Blocked by:** 10 (семантика flows)

**Status:** resolved

**Контракт:** змінюється семантика вердикту trace, несумісно. Async-сусід у піддереві попереднього дає `fail` замість `ok`, синхронне вкладення — `fail` замість `unverified`. Код виходу `check` на таких запусках змінюється з 0 на 1. З'являється нове повідомлення `nested in …, not after it`. Форма JSON, адаптери й схема trace не змінюються. Зміну треба записати в «Несумісних змінах» spec.
