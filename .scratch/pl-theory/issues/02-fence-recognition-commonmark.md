# 02: Огорожа коду за правилами CommonMark (Р15): жоден рядок специфікації не зникає мовчки

**Джерело:** research-pl §5 Р-2; знахідка 5; рішення Q3 (spec)

**What to build:** Зараз будь-який рядок, що після відступу починається з `` ``` `` чи `~~~`, відкриває огорожу, а закриває її лише рядок, що після `trim()` точно дорівнює маркеру (src/parser.ts:260). Тому рядок прози на кшталт `` ```x``` — інлайн-код ``, закривна огорожа, довша за відкривну, чи рядок огорожі з відступом ≥ 4 поза списком перетворюють решту файла на код. Правила й потоки після них мовчки не перевіряються: `check` дає `0 fail, 0 unverified, 0 ok` і код 0, хоча GitHub показує їх як список. Це хибний зелений результат, тож тікет не чекає на тест розбіжності 01.

Мінімальне відтворення: `keylang/rules.md` нижче, `check` → `0 fail, 0 unverified, 0 ok`, код 0.

~~~~markdown
# rules

```x``` inline

- deny a b
~~~~

Парсер розпізнає огорожу за CommonMark, а format.md записує це як рішення **Р15**:
- закривна огорожа має той самий символ, довжину не меншу за відкривну, а після неї — лише пробіли;
- відкривна огорожа з бектиків, чий info-рядок містить бектик, — не огорожа: рядок класифікується далі як звичайний текст (проза або опис). В info огорожі `~~~` бектики дозволені;
- рядок огорожі з відступом ≥ 4 без відкритого списку — проза (у CommonMark це відступний блок коду).

Р9 зберігається: коли список відкритий, огорожа з будь-яким відступом закриває список і стає блоком коду секції. Незакрита огорожа, як і в CommonMark, триває до кінця файла; попередження для неї не додається, бо новий код діагностики — окрема зміна контракту. fmt і далі лишає блок дослівно. Виконуваний приклад для Р15 додає тікет 34.
