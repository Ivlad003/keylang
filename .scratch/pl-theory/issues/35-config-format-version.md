# 35: Поле `format` у `keylang.json`: версія мови, розділ «Версії формату» і ADR 0007

**Джерело:** research-pl §5 Р-10; знахідка 7; рішення Q17 (spec)

**What to build:** `keylang.json` приймає ціле поле `"format"`: це версія мови, за якою keylang читає специфікації репозиторію. Зараз такого поля немає. Білий список (src/config.ts:147) дає на нього `` unknown field `format` `` і код 2, тож старий keylang гучно відхилить новий конфіг. Цей тікет вводить механізм і формат 1. Першу поведінку, що залежить від версії, додає 37.

Значення поля:
- поля немає — формат 1, як відсутній `edition` у Cargo. Так оновлення пакета не змінює мовчки значення старих конфігів. Пропозиція дослідження «відсутнє = поточна версія» суперечила власній політиці editions;
- `keylang.json` немає зовсім (examples/, MCP `validate_spec` у теці без конфігу, вгаданий конфіг `loadConfig`) — поточний формат;
- ціле число, більше за найновішу відому версію, — код 2 з назвою файла й поля та порадою: `` keylang.json: `format` 2 is newer than this keylang reads (1); upgrade keylang ``;
- рядок, `null`, нуль, від'ємне чи дробове число — код 2 у стилі наявних помилок конфігу (src/config.ts:135-137): `` keylang.json: `format` must be a positive integer, got "1" ``.

Відмовляє кожна команда, що читає конфіг. `fmt` і `parse` зараз конфіг не читають (src/cli.ts:1055, :1226). Тепер вони перевіряють поле `format` у `keylang.json` найближчого кореня (`findRoot`, src/analyze.ts:97), бо граматика й канонічна форма наступних версій можуть бути іншими. Перевірка легка: без вгадування конфігу й без валідації решти полів. Файл, що не є JSON-об'єктом, дає код 2, бо версію тоді не визначити. `keylang lsp` не завершується: помилку конфігу він показує клієнту, як зараз (tests/lsp.test.ts:217).

`Config` отримує поле `format`, а `configToJson` (src/config.ts:234-244) пише його першим ключем. `init` на свіжому репо записує поточну версію, а наявний `keylang.json` лишає байт у байт (src/cli.ts:815-816). `draft map` друкує версію наявного конфігу, а без нього — поточну. `keylang.json` самого репозиторію отримує `"format": 1`.

`format` не входить у `snapshotId`: маніфест хешує лише `dir`, `languages`, `module`, `layers`, `exclude` і `guessed` (src/snapshot.ts:173-180). Речення format.md §11 «зміна файла або `keylang.json` змінює його» (format.md:408) суперечить коду. Треба виправити: `snapshotId` змінюють лише перелічені поля конфігурації.

Розділ «Версії формату» у мовній частині format.md (межа за Q22):
- формат 1 — мова цього документа (v0.2). До заморожування v1 (design-v0.2/28; після 43 — design-v0.2/40) він ще змінний;
- як читається `keylang.json` без поля і тека без `keylang.json`;
- політика: несумісна зміна значення наявних текстів можлива лише з новою версією. Формат 1 підтримується до наступної мажорної версії пакета, тобто прибрати його можна лише мажорним релізом. Невідома версія дає код 2;
- `fmt` мовчки не мігрує: не змінює `format` і не переписує тексти під нову версію. Мігрує лише явна дія автора — правка тексту; команди міграції поки немає (48, wontfix);
- одне речення про збіг назви поля з `check --format`.

Також:
- ADR 0007 пояснює три вибори: editions замість мовчазних змін; поле в конфігу, а не в кожному `.md`; відсутнє поле означає 1, а не поточну версію;
- термін «Format version (версія формату)» у CONTEXT.md;
- згадка поля в курсі 02-install-and-check (en і uk).

Поза тікетом:
- протягування версії в `assess` і правило, що від неї залежить, — робота 37;
- показ версії в `check --format json`.

38 править той самий білий список (src/config.ts:147), але конфлікт між ними лише злиттєвий.

**Blocked by:** None (can start immediately)

**Status:** resolved

**Контракт:** конфіг і коди виходу:
- нове поле `format` у `keylang.json`; `init` і `draft map` його пишуть;
- версія, новіша за відому, або невалідне значення дає код 2;
- `fmt` і `parse` уперше читають `keylang.json` (лише `format`) і можуть завершитися з кодом 2.

Наявні конфіги без поля сумісні: для них діє формат 1, `snapshotId` не змінюється. Нове рішення записано в ADR 0007.

- [ ] Без поля і з `"format": 1` `check --format json` і `map` дають однаковий вивід. Після додавання `"format": 1` у `keylang.json` репозиторію `map --check` дає 0: `snapshotId` не змінився.
- [ ] З `"format": 2` код 2 дають `check`, `map`, `fmt --check` і `parse --json`. У stderr є `keylang.json`, `` `format` ``, `2` і `upgrade`, а `map` нічого не пише. Це нові кроки тесту tests/cli.test.ts:1407.
- [x] `"format": "1"`, `0`, `-1`, `1.5` і `null` дають код 2 з `` `format` must be a positive integer, got … ``. Якщо `format` валідний, а в `layers` помилка, `fmt --check` поводиться як раніше.
- [ ] `init` на свіжому репо пише `"format": 1` першим ключем. Повторний `init` друкує `already exists, kept`, а файл лишається байт у байт. `draft map` друкує конфіг із `format`.
- [ ] LSP з `"format": 2` показує клієнту помилку конфігу й не завершується. Це один крок наявного тесту tests/lsp.test.ts:217.
- [x] Документація: у format.md є розділ «Версії формату» з політикою, зокрема з тим, що `fmt` мовчки не мігрує, а речення §11 про `snapshotId` виправлено. ADR 0007, термін у CONTEXT.md і курс 02 (en і uk) додано, посилання перевірено.
- [ ] `npm run typecheck`, `npm test`; `node bin/keylang.js map` (diff переглянуто, разом із картою з поясненнями: `explain.map` увімкнено), `node bin/keylang.js map --check` = 0, `node bin/keylang.js check` на репозиторії — 0 fail.
