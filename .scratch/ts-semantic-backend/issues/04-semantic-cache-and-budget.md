# 04: Кеш результатів backend і бюджет часу

**Status:** ready-for-agent

**Type:** code

**Blocked by:** 02 <!-- 02 — прохід backend, чиї результати кешуються -->

**Verify:** `node --test tests/ts-semantic-cache.test.ts` · `npm run typecheck` · `npm test` · `node bin/keylang.js map --check` · `node bin/keylang.js check --strict`

**Джерело:** spec §4.4, §3, П1, П3; [ADR 0020](../../../docs/adr/0020-typescript-semantic-backend.md) п. 4–6 і відкриті питання 4–5; ADR 0016 п. 4 (кеш фактів)

**What to build:** На keylang Program будується ~1,5 с, а теплий `check` зараз триває ~1,0 с. Тож без кешу backend не вкладається в бюджет.

- **Окремий кеш.** Результати backend-а зберігає власний кеш у `.keylang/cache/`. Ключ: версія `typescript`, хеш опцій, хеші файлів знімка й входи поза manifest. Що саме брати з останніх — lock-файл чи файли, які прочитала попередня Program, — вирішує відкрите питання 5; відповідь тікет записує в Notes.
- **Запис** best-effort, як у кеша фактів. Режими `--check` його не пишуть, зіпсований чи чужий кеш ігнорується.
- **Інкрементальність.** Коли змінилися файли, Program будується знову, а запити до checker ідуть лише для дірок у змінених файлах і тих, що від них залежать. Для `declare global` і ambient-модулів запити йдуть для всіх.
- **LSP, TUI й MCP** тримають Program між поколіннями аналізу (`oldProgram`).
- **Бюджет:** теплий `check` на keylang без змін — ≤ +10 % (~1,1 с), після зміни одного файла TS — ≤ 3 с. Холодний запуск вимірюється.
