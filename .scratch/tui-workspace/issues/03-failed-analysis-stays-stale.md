# 03: Зберігати outdated і причину після невдалого F5

**What to build:** після збою переаналізу користувач бачить, що попередній вердикт застарілий, навіть після навігації.
**Blocked by:** None (can start immediately).
**Status:** resolved
**Parent:** [Специфікація](../spec.md), A06, A30.

## З чого почати

Знайти `App.reanalyze`, `adoptResult`, `reanalyzeSoon`, поля `updating`, `outdated`, `error`, renderer нижнього рядка. Прочитати тести superseded analysis і dimmed marks.

## Кроки

1. Спочатку відтворити: analyzer один раз успішний, другий виклик відхиляє Promise; початкова сесія не dirty.
2. На початку повторного аналізу старий звіт не вважати актуальним. На помилці зняти updating, зберегти старі дані, встановити outdated і стійку причину.
3. Відокремити постійний стан помилки аналізу від transient message, яку очищає клавіша.
4. Причина показується до успішного аналізу нового покоління; старе покоління не може ні скинути, ні перезаписати її.
5. Успішний повтор очищає помилку; якщо буфер змінився під час нього, його звіт однаково outdated.

## Фікстури й очікування

- Успіх → rejection → кілька стрілок: жолоб лишається dimmed, текст причини видимий.
- Помилка → успішний новий F5: причина зникає, актуальні позначки відновлені.
- Два керовані покоління завершити у зворотному порядку: старе не змінює новий стан.
- Помилка першого аналізу: немає порожнього «успішного» знімка, сесія реагує на клавіші.

## Result

Реалізовано A30: невдалий переаналіз лишає старий звіт явно застарілим із постійною причиною.

- **`src/tui/app.ts`** — у rejection-гілці `reanalyze` тепер встановлюється `state.outdated = true` разом із `updating = false`: старий звіт більше ніколи не подається як поточний. Перевірка покоління (`generation !== this.generation`) лишається перед змінами стану, тож пізня помилка старого покоління не затирає і не скидає стан нового (покрито тестом). `state.error` — постійна причина, `state.message` — transient-копія, яку очищає наступна клавіша (існуючий рядок `this.state.message = null` у `handle`). Оновлено коментар заголовка модуля.
- **`src/tui/state.ts`** — задокументовано `error`: постійна причина неактуальності звіту; скидає лише успішний аналіз нового покоління (`adoptResult` уже робив `error = null`).
- **`src/tui/view.ts`** — рядок стану тепер показує `outdated: <причина>` (червоним, 160) за наявності `state.error`; звичайний outdated-текст і updating-фаза не змінені.
- **`tests/tui.test.ts`** — 4 нові тести: (1) успіх → rejection → навігація: жолоб лишається dimmed, причина видима в рядку стану, transient message зникає від клавіші; (2) помилка → успішний F5: причина зникає, позначки відновлені; (3) два керовані покоління у зворотному порядку: пізній fail старого покоління не псує новий результат; (4) помилка першого аналізу: `analysis === null`, немає фіктивних лічильників, сесія відповідає на клавіші. Тести 1, 2, 4 падали на попередній поведінці (тест 3 проходив: скидання поколінь уже було) — зафіксовано до виправлення.
