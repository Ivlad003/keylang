# 21: Вибирати будь-яку пропозицію перед MERGE

**What to build:** список proposals дозволяє відкрити код, тест або специфікацію незалежно від поточного файла й інших невирішених пропозицій.
**Blocked by:** [02 — каталог дій](02-palette-doctor-results.md).
**Status:** resolved
**Parent:** [Специфікація](../spec.md), A14, A31.

## З чого почати

Знайти `MergeSession`, сканування proposals, `proposalProblem`, `codeProposalProblem`, `MergeState`, `diffLines`. Поточний `m` обирає current/first — змінюється лише вибір цілі.

## Кроки

1. Додати дію Proposals зі списком path, kind spec/code, кількістю hunks і причиною непридатності. Стабільне сортування за POSIX-шляхом.
2. Якщо поточний файл має придатну proposal, `m` лишається прямим переходом; інакше відкриває список, а не першу ціль автоматично.
3. Enter на придатній цілі запускає той самий MERGE щодо файла на диску. Непридатна показує причину без записів.
4. Повторно сканувати перед відкриттям і застосуванням; файл, видалений/переписаний після побудови списку, не стає старою неперевіреною пропозицією.
5. Після w/Esc повернутися до попереднього режиму за чинним контрактом, оновити список і counts.

## Перевірки

- Три proposals: перша невирішена, обрати третю → правильний diff; перша лишилася.
- Spec/code/test/new file: тип, hunk-count, target і записи відповідають вибору.
- Dirty spec, generated/поза межами/symlink proposal: причина видима, немає запису.
- Під час MERGE агент переписав proposal: w відмовляє, новий текст не видалено; u зберігає чинну семантику.

## Приймання

- [x] Наявні тести часткового MERGE, Esc і u проходять без послаблення.
- [x] Список не застосовує й не видаляє proposals лише від перегляду.
- [x] Можна перейти до кожної pending-цілі клавіатурою.

**Межі:** формат збереженої proposal й алгоритм diff не змінювати.
**Validation:** `npm run typecheck`, `npm test`.

## Result

Реалізовано список пропозицій і вибір цілі перед MERGE; формат `.keylang/proposals/`, `diffLines` і контракт `w`/`Esc`/`u` не змінювались.

- **`src/tui/merge-session.ts`** — `ProposalEntry { path, kind: spec|code, newFile, hunks, problem }` і `entries()`: кожен файл сховища (сортування `compareText` за POSIX-шляхом) з кількістю шматків відносно файла на диску; причина непридатності — `proposalProblem`/`codeProposalProblem`, незбережені правки буфера специфікації, нечитабельна пропозиція, а також символічне посилання всередині `.keylang/proposals/` (раніше мовчки пропускалось; тепер у списку з причиною, ніколи не читається). Побудова списку нічого не пише. `open(wanted)` для недоступної цілі тепер дає конкретне повідомлення (`proposal ignored: <path> (<reason>)` / `no proposal for <path> … any more`) замість загального. `leave()` (w/Esc) повторно сканує сховище, тож `≈ N proposal(s)` відповідає диску.
- **`src/tui/app.ts`** — `mergeOrPick()` для `m` і дії `merge`: придатна пропозиція поточного файла → прямий MERGE; інакше, якщо є хоч одна придатна → список; інакше чинне повідомлення про проігноровані. `openProposals()` / `refreshProposalPrompt()` / `submitProposal()`: Prompt `kind: "proposal"`, фільтр за підрядком шляху, `↑↓`, note з причиною або `Enter merges into <path> on disk`. Enter спершу знову сканує: видалена — `<path>: the proposal is gone`, список оновлено; переписана — відкривається з поточним текстом; непридатна — список лишається відкритим із причиною, без записів.
- **`src/tui/actions.ts`** — дія `proposals` («Proposals», aliases proposals/pending/targets/pick proposal); недоступна в MERGE (`MERGE_REASON`) і на стартовому екрані.
- **`src/tui/state.ts`**, **`src/tui/view.ts`** — `Prompt.kind "proposal"`, мітка `proposal: `, заголовок `N proposal(s)`, note біля запиту; довідка `m merge or list`.
- **`docs/tools.md`** — абзац «Список пропозицій», рядок клавіш `m`.
- **Карта** — `keylang/map/tui.md`, `keylang/map-explained/{tui,README}.md` перегенеровано штатним генератором; diff WIP-файлів `extract.md` байтово той самий до й після.
- **Тести** (`tests/tui.test.ts`): 3 нові — (1) spec new file / spec / code / test: рядки й типи, hunks, перегляд і Esc не змінюють дерево (`treeBytes`), перша ціль відкрита й лишена невирішеною, через палітру обрано третю (код) → правильний diff і запис, перша лишилась; далі тест (r) і rules (a), `u` відкочує останнє злиття й повертає пропозицію; (2) dirty spec, поза `keylang/`, генерована карта, ціль-симлінк назовні, симлінк у сховищі: причина видима до й після Enter, MERGE не відкрито, буфер збережено, дерево байтово незмінне; (3) видалена після побудови списку → gone; переписана → новий diff; переписана агентом під час MERGE → `w` відмовляє, новий текст не видалено, `u` — `no merge to undo`, інша пропозиція не зачеплена, `m` на поточному файлі відкриває новий текст. Три наявні тести (Esc, spec-to-code, draft під час MERGE) отримали додатковий Enter у списку — перевірки не послаблено.

Припущення й залишки:
- Без жодної придатної пропозиції `m` не відкриває список, а лишає чинне повідомлення з причинами (зберігає наявні тести); палітра «Proposals» показує список і в цьому разі.
- Тип лише `spec`/`code`: тест від `spec-to-code` — це `code` (окремої ознаки тесту в сховищі немає).
- Після `w`/`Esc` список не відкривається знову — повернення до режиму за чинним контрактом; список щоразу будується заново.
- Пропозиція з 0 шматків показується як `0 hunk(s)`; Enter на ній — чинна поведінка `open()` (видаляє збіглу пропозицію як явна дія).
- Ручну TTY-перевірку наживо не виконано.
