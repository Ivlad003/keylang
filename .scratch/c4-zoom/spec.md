## 1b. Рев'ю тікетів (2026-10-04)

Факти перевірено за кодом і на тимчасовому репозиторії. Вони змінили тікети так:

- **Збій у `feature`** (відтворено): файл лише з прозою і файл із K004 команда вважала готовими, код 0, хоча `check` на другому дає код 1 → тікет 03.
- **Brief шару моделлю вже є:** `planBriefs` питає шари останньою хвилею, `snapshotBaseline` робить шар застарілим від усього під ним → тікет 01 звужено до brief-у репозиторію й документа шару.
- **Ім'я `system` не зарезервоване,** а збережене пояснення для ID поза знімком `explain --stale` позначає як `gone` → файл `@system.md` з власною базою.
- **`- ? …` сьогодні дає K004** у будь-якому потоці; правило Р2 format.md (вид за заголовком, не за шляхом) виключає «лише у файлі фічі» → тікет 04.
- **Неможливі види прогалин прибрано:** `step` завжди має ID, `emits` — проза, а збіг `planned` з наявним вузлом і є K202 «реалізовано»; зовнішню ціль без `planned` уже ловить K001.
- **`planned module` з невідомим шаром приймається мовчки** (відтворено) → підказка `layer`.
- **`denyingRule` уже оцінює ребро до `planned`** у spec-to-code → прогноз `deny` перевикористовує його.
- **Невідомі ID у відповіді моделі** зберігаються й позначаються, а не відкидаються → тікет 06 цю поведінку не змінює.
- **`F3` — панель навігації** (дерево шар → модуль → член із поясненням вибраного вузла); «Feature readiness» з аліасом `gaps` і екран §2.7 уже є → тікет 11 розширює їх; екран зуму бере дерево з `src/tui/nav.ts`.
- **safe-write не пропускає запис без змін,** а `isGeneratedText` знає лише `<!--` і `//` → тікет 12.
- **`g` у TUI означає «на початок»** → зв'язки на `c`.
- **Власна карта keylang змінюється з кожним код-тікетом:** усі останні коміти її перегенеровують → у Verify код-тікетів додано `map --check` і `check`.
- **«Вид» у глосарії означає kind** → термін ADR — «представлення».
- **Нумерація:** колишній 08 (підпис рядка) влито в 07; кнопки миші — окремий 10 після зв'язків і потоку; решту перенумеровано під Р4 (§7).

## 1. Мета

Два сценарії, обидва за ідеєю зуму C4 (context → container → component → code):

- **A. Читання.** Відкрити чужий репозиторій і за хвилину зрозуміти, що це і для кого; далі спускатися: шар → модуль → функція → виклики → код. На кожному рівні — коротке пояснення простою мовою з видимим походженням.
- **B. Написання.** Описати фічу спершу одним реченням, потім поступово уточнювати до стану, який харнес (Claude Code, Codex, …) може реалізувати без розпитувань. Чим глибше опис, тим більше допомагає вбудований асистент — але без «скріпки», яка перебиває.

## 2. Що вже є і чого бракує (перевірено за кодом 2026-10-04)

| Рівень C4 | Відповідник у keylang | Є зараз | Бракує |
|---|---|---|---|
| Context | репозиторій + вузли `external.*` | зовнішні пакети в карті | **brief репозиторію** з README чи маніфесту |
| Container | шар | рядок шару, brief шару моделлю (`explain --missing --llm`), застарілість від усього під шаром | **детермінованого документа шару** |
| Component | модуль | brief з doc-коментаря або моделі | — |
| Code | `fn` / `type` | сигнатура, `calls`, brief, `explain <id> --llm --brief|--full` | структури `full` |
| Dynamic | `flow` | потоки з трьома доказами, trace | накладання потоку на рівні зуму |

- **TUI:** панель навігації `F3` — дерево шар → модуль → член з поясненням вибраного вузла; панель контексту `F4` — вузол і сусіди; `t`, `s`, hover. Окремого екрана зі входом у вузол немає.
- **Фіча** — `keylang/features/<slug>.md`: потоки з `planned`. `feature <slug>` знає лише «готово / прогалини» і вважає готовим файл без перевірюваних тверджень.
- **Асистент:** ghost-текст, `Ctrl+Space`, `Ctrl+G` text → spec через MERGE, MCP `context`/`validate_spec`/`scaffold`/`feature_status`. Проактивних підказок немає, і дослідження радить так і лишити (Clippy, Horvitz 1999, усі сучасні харнеси — лише на вимогу).

## 3. Висновки дослідження, на які спирається план

1. Люди читають код опортуністично, не лінійно (Brooks; Letovsky; von Mayrhauser & Vans) → вхід з будь-якого рівня, зв'язок за ID, історія «звідки прийшов».
2. Навігацію веде «запах» підпису (information foraging; beacons) → правдивий brief на кожному рядку й дешевий перехід у код; без brief-у — `—`, а не евристичний текст.
3. c4model.com: рівень Code «optional, generated by tooling»; context + container «sufficient for most teams» → два верхні рівні — головна прогалина keylang. Контейнер у C4 — застосунок чи сховище, тож шар моноліту ним не є.
4. Structurizr: одна модель — багато представлень → знімок = модель; карта, карта з поясненнями, екран зуму, експорт C4 — представлення (ADR 0014).
5. Резюмування репозиторіїв з LLM (RepoAgent, CodeWiki, Dhulshette 2025) — знизу вгору з агрегацією по рівнях; галюцинації ≈20–50 % без обмежень → посилання лише на ID знімка, видимий провенанс і `stale`.
6. Недоспецифікованість — головна причина провалу агентів (38 % SWE-bench; Ambig-SWE +74 % після уточнення; ClarifyGPT +10 п.п.) → прогалини авторства шукаються детерміновано, питання моделі — лише на вимогу.
7. Spec-driven інструменти (Spec Kit, Kiro, OpenSpec) зійшлися на сходинках specify → plan → tasks з маркером `[NEEDS CLARIFICATION]`; keylang відрізняється перевіркою кожної сходинки проти знімка.
8. Переривання — лише на межах підзадач (McFarlane; Iqbal & Bailey); персонаж піднімає соціальні очікування (Swartz) → екран із лічильником, рядок стану, без персонажа.
9. Зум — розв'язана задача HCI: мантра Shneiderman, DOI-дерева Furnas/Card → алгоритм рівнів і сусідів у терміналі.

## 4. Контракт

### 4.1 Режим A — читання

- **A1. Brief репозиторію й документ шару** (тікет 01, Р1, Р11). Поле знімка `system` з першого абзацу README або `description` маніфесту; модель лише без них, файл `explain/brief/@system.md`. `doc` вузла шару — з `README.md` теки шару чи doc-коментаря index-модуля.
- **A2. Структурований `full`** (06). П'ять розділів: призначення, кроки, гілки й крайні випадки, виклики (з `holes`), потоки й правила. Невідомі ID позначаються, як зараз.
- **A3. Екран «Зум»** (07, Р5, Р6). Чистий модуль рівнів і сусідів на індексі дерева панелі навігації; рядок `ім'я · brief · позначка · ↔ n`; хлібні крихти; вихід `q` на той самий вузол у перегляді.
- **A4. Зв'язки** (08, Р8). `c`: групи `in`/`out`/`external`, зведені до рівня, `◌` для нерозв'язаного; `Enter` — в інший кінець; `x`…`x` — explain-edge у `F6`.
- **A5. Шлях потоку** (09, Р8). `f`: номери кроків у порядку запису, позначки жолоба, рядок послідовності шарів; `F` — наступний потік.
- **A6. Кнопки миші** (10, Р7). Кнопки в заголовку дублюють клавіші; без подвійного кліку.
- **A7. Експорт C4** (12, Р10). PlantUML і Mermaid; шари — межі, модулі — компоненти; файл із маркером `keylang:generated`.
- **A8. Якість пояснень.** Детермінована частина вже є (`unknown ids`); рубрика й вибірка людиною — у `bench/`, поза тікетами.

### 4.2 Режим B — фіча від ідеї до спеки

**B1. Стадії** (тікет 03, Р3). `done`, коли прогалин немає; інакше перша умова згори:

| Стадія | Коли | Що далі робить автор |
|---|---|---|
| idea | у файлі немає секції `# flow` | пише `# flow <name>` з `trigger` і поведінкою |
| behavior | є потік без `trigger` або без жодного `step`, `calls`, `when`, `invariant` | додає точку входу й кроки |
| structure | є помилка специфікації, відкрите питання, прогноз `deny`, `planned` з невідомим шаром чи `planned fn` без сигнатури | закриває прогалини авторства |
| ready | лишились тільки прогалини реалізації | віддає файл харнесу |
| done | прогалин немає | — |

**B2. Відкрите питання** (04, Р2). `- ? <текст>` — листок у потоці; `check` його не звітує; `feature` рахує прогалиною; зникле без коміту питання — послаблений план.

**B3. Прогалини й підказки.** Інваріант: `done` ⇔ `gaps` порожній.

| Вид | Блокує `done` | Стадія | Тікет |
|---|---|---|---|
| `empty` — немає жодного `planned`, `trigger`, `step`, `calls` | так | idea | 03 |
| `trigger`, `steps` (підказки) | ні | behavior | 03 |
| `diagnostic` — K001–K005 у файлі фічі | так | structure | 03 |
| `question` — рядок `- ?` | так | structure | 04 |
| `deny` — ребро з `planned`-кінцем, яке після реалізації заборонить правило | так | structure | 05 |
| `layer` (підказка) — ID `planned` не починається з шару чи `external` | ні | structure | 05 |
| `signature` (підказка) — `planned fn` без сигнатури | ні | structure | 05 |
| `planned`, `static`, `rule`, `spec` (чинні; `spec` тепер включає зникле питання) | так | ready | — |

**B4. Екран готовності** (11). Розширює наявний «Feature readiness»: драбина стадій, прогалини за стадіями, позначка `?` у жолобі, рядок стану, питання моделі лише на вимогу й лише через MERGE.

### 4.3 Принципи (ADR 0014 «Одна модель — багато представлень», тікет 02)

Знімок — модель; карта, карта з поясненнями, екран зуму, експорт C4, панель контексту — представлення. Будь-яке представлення обчислюється зі знімка й `explain/brief/` детерміновано; модель запитується лише явними командами (`--llm`) і завжди з походженням.

## 5. Поза обсягом

- Проактивні спливаючі підказки й персонаж.
- Spec-as-source (код генерується зі спеки): код пише харнес, keylang звіряє (ADR 0005).
- Нові види вузлів чи зміна семантики `flow`/`rules`, крім додавального `?`; EARS-шаблони поза `when`/`then` — після заморожування v1 (ADR 0009).
- Канвас/просторовий інтерфейс (Code Bubbles) — не лягає на термінал.
- Евристичний brief шару, зведений з модулів (Р11).
- Кластеризація шарів (Bunch) — лише як чернетка `keylang.json` в `init`, окрема фіча.
