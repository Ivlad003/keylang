# Зум за C4: читання репозиторію зверху вниз і фіча від ідеї до спеки

**Джерело:** запит користувача 2026-10-04; [research-c4-zoom-literature.md](../../docs/research-c4-zoom-literature.md) (теорія) і [research-c4-zoom-tools.md](../../docs/research-c4-zoom-tools.md) (готові рішення); design §5.4, §7.1–7.3, §7.6; ADR 0004 (карта з поясненнями), ADR 0005 (харнеси); спеки `explained-map` і `harness-integration`. Терміни — `CONTEXT.md`.

**Статус:** рішення людини прийнято 2026-10-04 (§1a); тікети — у `issues/` зі статусом `needs-triage` до перегляду людиною.

## 1a. Рішення користувача (2026-10-04)

| # | Рішення |
|---|---|
| Р1 | `system` і шари — лише вузли представлення (карта з поясненнями, TUI). Формат мови, SpecIR і правила не змінюються. Перехід до ID мови можливий пізніше без ламання файлів |
| Р2 | Невизначеність у файлі фічі — рядок списку `- ? <питання>`; `validate_spec` і `feature` рахують його як прогалину сходинки |
| Р3 | Сходинка фічі (`idea → behavior → structure → ready → done`) лише обчислюється; у файл не пишеться |
| Р4 | Порядок кроків 1 → 3 → 2 → 4; експорт C4 лишається в обсязі (крок 4) |
| Р5 | Зум у TUI — додаток до наявного дерева: `Enter` на шарі/модулі — вхід у його рівень (на `fn` — у код, як зараз), `Esc`/`Backspace` — вгору, хлібні крихти; `+`/`−` — глибина сусідів по графу всередині рівня |
| Р6 | Усередині рівня видно членів вузла та його сусідів по графу (callers/callees, типово глибина 1); решта згорнута з лічильником |

Номер ADR для принципу «одна модель — багато видів» — **0014** (0013 зайнято).

## 1. Мета

Два сценарії, обидва за ідеєю зуму C4 (context → container → component → code):

- **A. Читання.** Відкрити чужий репозиторій і за хвилину зрозуміти, що це і для кого; далі спускатися: шар → модуль → функція → виклики → код. На кожному рівні — коротке пояснення простою мовою з видимим походженням.
- **B. Написання.** Описати фічу спершу одним реченням, потім поступово уточнювати до стану, який харнес (Claude Code, Codex, …) може реалізувати без розпитувань. Чим глибше опис, тим більше допомагає вбудований асистент — але без «скріпки», яка перебиває.

## 2. Що вже є і чого бракує (перевірено за кодом 2026-10-04)

| Рівень C4 | Відповідник у keylang | Є зараз | Бракує |
|---|---|---|---|
| Context | `keylang.json` + вузли `external.*` | список шарів у `keylang.json`, зовнішні пакети в карті | **кореневий brief «що це за система і для кого»**; README карти з поясненнями має порожню колонку Explanation для шарів |
| Container | шар (`layer`) | рядок шару в карті, таблиця покриття поясненнями | **brief шару**, порядок і призначення шарів простою мовою |
| Component | модуль | brief з doc-коментаря або моделі (`explain --missing --llm`) | агрегований brief з членів, коли doc-коментаря немає |
| Code | `fn` / `type` / `event` | сигнатура, `calls`, brief, `explain <id> --llm` (`short`/`full`) | семантичний зум в одному місці (brief → short → full → код) без перескоків між файлами |
| Dynamic | `flow` | потоки з трьома доказами, trace | — |

- **TUI** показує канонічну карту і карту з поясненнями (`t`), пошук `s`, пояснення у `F3`, hover. Дерево розгортається повністю, зуму «вхід у вузол = його внутрішній рівень» немає.
- **Фіча** — `keylang/features/<slug>.md` одразу з `planned` і потоками; етапу «ідея простою мовою» немає, `feature <slug>` знає лише «готово / прогалини».
- **Асистент:** ghost-текст (один рядок після паузи), `Ctrl+Space`, `Ctrl+G` text → spec через MERGE, MCP `context`/`validate_spec`/`scaffold`/`feature_status`. Проактивних підказок немає, і дослідження радить так і лишити (Clippy, Horvitz 1999, усі сучасні харнеси — лише на вимогу).

## 3. Висновки дослідження, на які спирається план

1. Люди читають код опортуністично, не лінійно (Brooks; Letovsky; von Mayrhauser & Vans) → вхід з будь-якого рівня, зв'язок за ID, історія «звідки прийшов».
2. Навігацію веде «запах» підпису (information foraging; beacons) → правдивий brief на кожному рядку дерева і дешевий перехід у код.
3. c4model.com: рівень Code «optional, generated by tooling»; context + container «sufficient for most teams» → два верхні рівні — головна прогалина keylang.
4. Structurizr: одна модель — багато видів → знімок = модель; карта, карта з поясненнями, flows, експорт C4 — види. Зафіксувати як принцип (ADR).
5. Резюмування репозиторіїв з LLM (RepoAgent, CodeWiki, Dhulshette 2025) — знизу вгору з агрегацією по рівнях; галюцинації ≈20–50 % без обмежень → brief верхнього рівня будується з brief-ів нижнього, посилання лише на ID знімка, видимий провенанс і `stale`.
6. Недоспецифікованість — головна причина провалу агентів (38 % SWE-bench; Ambig-SWE +74 % після уточнення; ClarifyGPT +10 п.п.) → асистент B спершу шукає «дірки» детерміновано, LLM-питання — лише де детерміновано не видно.
7. Spec-driven інструменти (Spec Kit, Kiro, OpenSpec) зійшлися на трьох сходинках specify → plan → tasks з маркером `[NEEDS CLARIFICATION]` і станами proposal → applied → archived; keylang відрізняється перевіркою кожної сходинки проти знімка.
8. Переривання — лише на межах підзадач (McFarlane; Iqbal & Bailey); персонаж піднімає соціальні очікування (Swartz) → панель з лічильником, індикатор, без персонажа.
9. Зум — розв'язана задача HCI: мантра Shneiderman, DOI-дерева Furnas/Card → алгоритм розгортання дерева в терміналі.

## 4. Контракт (ескіз)

### 4.1 Режим A — читання

**A1. Корінь `system` і brief шару.** Карта з поясненнями отримує верхній рівень:

```
# map
<brief системи: що це, для кого, точки входу · походження: README · package.json · flows>
- base   <brief шару>
  - module …
```

- Джерело brief-у системи: детерміновано — перший абзац `README.md`, `description` з `package.json`/`Cargo.toml`/`pyproject.toml`, список тригерів потоків; модель — лише `explain --missing --llm`, із записом `explain/brief/system.md` і `explain/brief/<layer>.md` (той самий формат, що для вузлів).
- Brief шару без моделі: агрегація з brief-ів модулів (перше речення найзв'язнішого модуля за PageRank/ступенем + кількість модулів). Позначка походження `(aggregated)`.
- Р1: `system` і шар — вузли представлення, не ID мови.

**A2. Семантичний зум вузла.** Одна команда й одна панель: `brief` → `short` → `full` → код. `explain <id> --level brief|short|full` уже є частково (`short`/`full`); додати `brief` і структуру `full` як NL outline: призначення, кроки, гілки, крайні випадки, виклики з ◌ для нерозв'язаних. Кожний рівень — з рядком `джерело · модель · дата · stale`.

**A3. Дерево DOI у TUI.** Замість повного дерева — розгортання за ступенем інтересу: фокус і його сусіди по графу (callers/callees, глибина N, типово 1) розкриті, решта згорнута з лічильником `(+12)`. `Enter`/`→` на вузлі — вхід у його внутрішній рівень з тим самим фільтром («клік = scoped view», LikeC4); `←` — назад з історією «звідки прийшов». Хлібні крихти `system › tui › app › App.render`.

**A4. Scent на рядку.** Підпис вузла в дереві: `ім'я · brief (обрізаний) · ✓/✗/◌ · ↔ n`. Рядки без brief-у показують `—`, не вигадують текст.

**A5. Експорт C4.** `keylang export c4 --format plantuml|mermaid [--level container|component]` — похідний артефакт із карти (PlantUML первинний, Mermaid C4 експериментальний). Детермінований, без моделі.

**A6. Перевірка якості пояснень.** Детерміновано: кожний brief ≥1 посилання на ID знімка, 0 посилань на неіснуючі ID (вже K-код у ADR 0004 — звірити). Рубрика + вибірка людиною — у `bench/`, не в CI.

### 4.2 Режим B — фіча від ідеї до спеки

**B1. Чотири сходинки одного файла** `keylang/features/<slug>.md`, нової граматики немає:

| Сходинка | Що пише людина | Що перевіряє keylang | Що пропонує асистент (лише на вимогу) |
|---|---|---|---|
| 1. Ідея | заголовок + абзац простою мовою | файл є, розбирається | **питання** про шари, точку входу, зовнішні системи |
| 2. Поведінка | `flow` з `when`/`then`, кроки можуть бути прозою | кроки без ID — прогалини, не помилки | `when/then` як пропозиція (MERGE), EARS-сніпети в автодоповненні |
| 3. Структура | `planned module|fn|event` із шаром і сигнатурою | `validate_spec`: сигнатура, шар, конфлікт з `deny`, збіг з наявним ID | сигнатури й шар з автодоповнення; підбір існуючих вузлів для кроків |
| 4. Готовність | кроки з ID, критерій готовності | `feature_status`: K201/K202, static `ok`, правила | `scaffold` → заготовки й тести через MERGE |

Рівень допомоги росте з глибиною: на сходинці 1 — лише питання; більше ніж рядок тексту — завжди через MERGE.

**B2. Маркер невизначеності.** Рядок `? <питання>` (або `needs: <текст>`) у файлі фічі; `validate_spec` і `feature <slug>` рахують його як прогалину сходинки. Це і є «скріпка, яка не перебиває»: питання лежать у файлі й панелі з лічильником, людина відповідає, коли хоче.
Р2: синтаксис — `- ? <питання>`; рядок у format.md (файл фічі) і узгодження з тікетом заморожування design-v0.2/40.

**B3. Детекція «дірок»** (детерміновано, без моделі): `planned` без сигнатури або шару; крок потоку без ID; `emits` без емітера; крок, що порушив би `deny`/baseline; ім'я, що збігається з наявним ID; зовнішня система без `planned module external.<pkg>`. Вивід — `feature <slug> --gaps` і MCP `feature_status.gaps[]`, згруповано за сходинками.

**B4. Стан фічі.** `feature <slug>` повертає сходинку (`idea|behavior|structure|ready|done`), а не лише «готово/прогалини». Р3: стан лише обчислюється; `done` → файл лишається як специфікація (як зараз).

**B5. Асистент.** Один режим «спитай зараз» (`Ctrl+Space`/команда палітри «Що бракує фічі?») замість проактивних вікон; панель `F3` показує для файла фічі: сходинка, список дірок, накопичені питання моделі з лічильником. Індикатор присутності й того, що саме піде в модель (панель контексту вже є). Персонажа немає.

### 4.3 Принципи (ADR 0014 «Одна модель — багато видів»)

Знімок — модель; карта, карта з поясненнями, DOI-дерево, flows, експорт C4, панель контексту — види. Будь-який вид обчислюється зі знімка і `explain/brief/` детерміновано; модель запитується лише явними командами (`--llm`) і завжди з походженням.

## 5. Поза обсягом

- Проактивні спливаючі підказки й персонаж.
- Spec-as-source (код генерується зі спеки): код пише харнес, keylang звіряє (ADR 0005).
- Нові види вузлів чи зміна семантики `flow`/`rules`; EARS-шаблони поза `when`/`then` — після заморожування v1 (ADR 0009).
- Канвас/просторовий інтерфейс (Code Bubbles) — не лягає на термінал.
- Кластеризація шарів (Bunch) — лише як чернетка `keylang.json` в `init`, окрема фіча.
