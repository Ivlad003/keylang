# 20: `spec-to-code <id>` (algo): заготовка для `planned` і сценарій `refund`

**Етап:** M7 · **Джерело:** design §5.5, §9 M7; батьківський 37

**What to build:** Для `planned`-вузла створюється заготовка коду в дозволеному шарі з очікуваною сигнатурою як diff-пропозиція (неоднозначний шлях — вимога уточнити). Кандидат аналізується як overlay-знімок: `allow`/`deny` і потрібні докази перевіряються до запису. На K001 пропонується виправити посилання або оголосити намір. Сценарій `refund`: planned → spec-to-code → прийнятий diff → `map` → окремі докази.

**Status:** resolved

## Answer

`src/spec-to-code.ts` + `keylang spec-to-code <id> [--into] [--apply]`. Результат — diff у stdout і пропозиції `.keylang/proposals/<файл>` (код і тест), які TUI зливає по шматках (`MERGE … · code`, запис на диск, `u`); `--print` нічого не пише, `--apply` пише напряму. (До 2026-09-28 був лише `--apply`; MERGE коду додано за рішенням користувача.) Кандидат перевіряється overlay-знімком до запису (для цього `generateMap` бере й нові файли overlay). Тест сценарію `refund`: planned → `ID unverified planned`; dry-run показує `ID ok` зі заготовкою; `--apply` + `map` → `ID ok`, K202, `tests`/`trace` unverified. K001 не генерує код; `deny` на ребрі потоку блокує. Доповнення 2026-09-28: для кожного `test <файл> "<назва>"` потоку, чийого файла ще немає (TS/JS), — новий `node:test`-файл, що падає до написання; тест сценарію запускає його з репортером keylang і бачить `tests fail`.
